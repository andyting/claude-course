Task Statement 2.3 — Distribute tools appropriately across agents and configure tool choice

Knowledge of:

  • The principle that giving an agent access to too many tools (e.g., 18 instead of 4-5) degrades tool selection reliability by increasing decision complexity
  • Why agents with tools outside their specialization tend to misuse them (e.g., a synthesis agent attempting web searches)
  • Scoped tool access: giving agents only the tools needed for their role, with limited cross-role tools for specific high-frequency needs
  • tool_choice configuration options: "auto", "any", and forced tool selection ({"type": "tool", "name": "..."})

Skills in:

  • Restricting each subagent's tool set to those relevant to its role, preventing cross-specialization misuse
  • Replacing generic tools with constrained alternatives (e.g., replacing fetch_url with load_document that validates document URLs)
  • Providing scoped cross-role tools for high-frequency needs (e.g., a verify_fact tool for the synthesis agent) while routing complex cases through the coordinator
  • Using tool_choice forced selection to ensure a specific tool is called first (e.g., forcing extract_metadata before enrichment tools), then processing subsequent steps in follow-up turns
  • Setting tool_choice: "any" to guarantee the model calls a tool rather than returning conversational text
本題情境 · SCENARIO 3
Scenario 3 — Multi-Agent Research System

延續多代理研究系統:把工具依角色分配給各 subagent(搜尋 agent 只給搜尋、分析 agent 只給讀取),並用 tool_choice 控制何時必須呼叫特定工具。本 Task 教的就是這套工具分配與 tool choice。

一句話抓住主軸:工具不是給愈多愈好。 給太多,模型挑工具就會變得不可靠;給了它本行以外的工具,它就會亂用。原則是「每個 agent 只拿它角色該用的工具」,再用 tool_choice 控制「要不要、用哪個」。

Knowledge of · 知識點

知識 1  工具太多，tool selection（工具選擇）可靠度會下降

遇到這個問題時用到你的研究系統 coordinator 掌管 18 個工具，監控顯示工具選擇錯誤率高達 30%，你需要理解工具數量與選擇可靠度之間的關係，才能決定如何重新分配工具。

核心原則：給一個 agent 18 個工具，遠不如給它精準的 4～5 個。工具一多，每次要選的「決策複雜度」就暴增，模型更容易選錯。少而精的工具集，選擇才可靠。

# ❌ 一個 agent 塞 18 個工具 → 決策複雜度爆炸,常選錯
overloaded_agent = {"allowedTools": [
    "search", "fetch", "summarize", "translate", "write_file",
    "send_email", "query_db", "chart", "...再 10 個...",
]}

# ✅ 聚焦 4～5 個與角色相關的工具 → 選擇可靠
search_agent = {"allowedTools": ["web_search", "load_document"]}
考點重點:4～5 個 > 18 個;工具愈多,選擇可靠度愈低。

知識 2  拿到本行以外的工具，agent 會誤用（cross-specialization misuse）

遇到這個問題時用到你的 synthesis agent 負責整合各來源的研究結果，但日誌顯示它頻繁呼叫 web_search 工具自行蒐集新資料，導致重複搜尋且與 search agent 的結果不一致，你需要理解為何給 agent 超出其角色的工具會造成誤用。

當 agent 手上有不屬於它專長的工具時,它傾向去亂用。官方例子:一個負責「綜合(synthesis)」的 agent,如果給了它網路搜尋工具,它就會跑去搜尋——但那不是它該做的事。把工具限制在角色範圍內,就能避免這種跨專長的誤用。

# ❌ synthesis agent 被給了 web_search → 它會跑去搜尋(誤用)
synthesis_agent = {"allowedTools": ["web_search", "summarize"]}

# ✅ synthesis 只該整合既有資料,不該自己去搜尋
synthesis_agent = {"allowedTools": ["summarize"]}  # 不給搜尋工具
重點:本行外的工具 → 誤用;工具要對齊 agent 的專長。

知識 3  scoped access（範圍限制）：只給角色需要的，外加少量高頻跨角色工具

遇到這個問題時用到你需要設計一個多代理研究系統的工具分配策略，既要避免各 subagent 越權操作，又要讓 synthesis agent 能處理高頻的查證需求而不必每次都繞回 coordinator，你需要了解 scoped access 的設計原則。

實務上的平衡點：每個 agent 只拿它角色需要的工具（scoped access，範圍限制），但允許少量例外——那些「高頻、跨角色」的需求，可以給一兩個跨角色工具。重點是「少量、針對特定高頻需求」，不是大開後門。

agents = {
    "search":    {"allowedTools": ["web_search", "load_document"]},
    "analysis":  {"allowedTools": ["extract_data_points", "read_file"]},
    "synthesis": {"allowedTools": [
        "summarize",
        "verify_fact",   # ← 少量跨角色工具,給高頻的「查證」需求
    ]},
}
重點:scoped = 角色該用的工具 + 少量高頻跨角色工具。

知識 4  tool choice configuration（工具選擇設定）三種模式：auto / any / 強制指定

遇到這個問題時用到你的 data enrichment pipeline 需要確保 metadata 提取永遠是第一步，但 agent 有時跳過它直接進行 enrichment，導致後續步驟缺少必要的上下文，你需要了解如何用 tool_choice 強制控制工具呼叫順序。

除了「給哪些工具」,還能控制「怎麼用工具」。tool_choice 有三種:

"auto":模型自己決定要不要用工具(預設)。
"any":強制模型一定要呼叫某個工具(不准只回文字)。
強制指定 {"type":"tool","name":"..."}:指定非用哪一個工具不可。

tool_choice_auto   = {"type": "auto"}      # 模型自行決定用不用
tool_choice_any    = {"type": "any"}       # 一定要用某個工具
tool_choice_forced = {"type": "tool",
                      "name": "extract_metadata"}  # 指定非用這個不可
重點:auto(自行) / any(必用工具) / forced(指定工具),三選一。

Skills in · 技能點

技能 1  把每個 subagent 的工具集限制在它的角色內（role-scoped tool set）

遇到這個問題時用到你需要為多代理研究系統的四個角色（搜尋、分析、整合、報告）各自設定 allowedTools 清單，確保每個 subagent 只能使用其角色範圍內的工具，從架構層面防止跨專長誤用。

知識 1～2 的實作:逐一替每個 subagent 設定 allowedTools,只放角色相關工具,從源頭杜絕跨專長誤用。

def scoped_tools(role):
    table = {
        "search":    ["web_search", "load_document"],
        "analysis":  ["extract_data_points", "read_file"],
        "synthesis": ["summarize"],
        "report":    ["write_file"],
    }
    return table[role]   # 每個角色只拿自己那一份

技能 2  用 constrained tool（受限工具）替換「通用工具」

遇到這個問題時用到你的 search agent 配備了 fetch_url 工具，結果它開始抓取不相關的外部 API 端點和內部系統頁面，你需要設計一個只接受合法文件 URL 的受限替代工具來收窄操作邊界。

通用工具(如 fetch_url 能抓任何網址)權限太寬、容易被誤用。改成受限版本:例如 load_document,只接受並驗證「文件 URL」。功能收斂、邊界清楚,模型不會拿去做不該做的事。

# ❌ 通用:fetch_url 能抓任何網址,範圍太寬
fetch_url = {"description": "抓取任意 URL 的內容"}

# ✅ 受限:load_document 只接受並驗證文件 URL
load_document = {
    "name": "load_document",
    "description": "載入文件型 URL(PDF/HTML 文件);會先驗證是否為合法文件連結。",
}
重點:通用工具 → 受限工具,功能收斂、邊界明確。

技能 3  高頻跨角色需求給 scoped 工具，複雜情況才 routing（路由）回 coordinator

遇到這個問題時用到你的 synthesis agent 每次需要查證事實都要繞回 coordinator 再轉發給 search agent，造成不必要的延遲和多餘的通訊開銷，你需要為這個高頻需求設計一個直接可用的 scoped 工具，同時保留複雜案例的 routing 路徑。

對應知識 3。像 synthesis agent 常需要「查證事實」,就給它一個專用的 verify_fact 工具處理這個高頻需求;但若遇到複雜狀況,仍要回頭透過 coordinator 協調,而不是讓 synthesis agent 自己越權處理。

synthesis_agent = {
    "allowedTools": ["summarize", "verify_fact"],  # verify_fact:高頻查證,直接給
}

# 但複雜案例(需多來源交叉、需重新搜尋)→ 回報 coordinator 處理
if case.is_complex:
    return escalate_to_coordinator(case)   # 不自己越權,交給協調者
重點:高頻需求給專用工具;複雜案例路由回 coordinator。

技能 4  用 forced 強制先呼叫某工具；用 "any" 保證一定呼叫工具

遇到這個問題時用到你的 agent 有時在沒有呼叫任何工具的情況下就直接回覆閒聊文字，或跳過必要的 metadata 提取步驟，你需要用 tool_choice 設定來強制執行正確的操作順序並保證工具一定被呼叫。

兩個實用設定。forced 強制指定：確保某工具第一個被呼叫（例如先 extract_metadata 再做後續 enrichment），後續步驟在接下來的回合處理。"any"：當你不要模型只回閒聊文字、一定要它呼叫某個工具時使用。

# ✅ 強制先抽 metadata,再進入 enrichment;後續步驟下一回合再處理
first_turn = {
    "tools": [extract_metadata, enrich_a, enrich_b],
    "tool_choice": {"type": "tool", "name": "extract_metadata"},  # 非它不可,且最先
}

# ✅ 保證模型呼叫工具,而不是回一句閒聊文字
must_use_tool = {"tool_choice": {"type": "any"}}
重點:forced = 指定先用哪個工具;"any" = 保證一定用工具(不回純文字)。

整個 Task 2.3 的記憶骨架

工具少而精(4～5 個 > 18 個);給了本行外工具,agent 就誤用。原則是 scoped access——每個 agent 只拿角色該用的工具,外加少量高頻跨角色工具(如 synthesis 的 verify_fact),複雜案例走 coordinator。通用工具換成受限工具(fetch_url → load_document)。用 tool_choice 控制:auto 自行、any 保證用工具、forced 指定先用哪個。

考試情境題

以下三題模擬正式考試格式，每題一個生產情境，四個選項。先嘗試作答，再展開解析。

Q 1 Scenario 3 · Multi-Agent Research System

A multi-agent research system has a single coordinator agent equipped with 18 tools covering web search, document loading, data extraction, summarization, fact verification, report writing, database queries, translation, and more. Engineers observe that tool selection errors have increased significantly compared to an earlier version with 5 tools per agent. What is the most likely root cause?

  1. The model's tool descriptions are too long, causing the model to ignore some of them.
  2. Too many tools in a single agent increases decision complexity, degrading the reliability of tool selection.
  3. The coordinator is calling tools in the wrong order, and forced tool_choice should be used.
  4. The tools have overlapping names that confuse the model into selecting the wrong one.
展開解析

Correct Answer: B

工具太多是工具選擇可靠度下降的根本原因。每次呼叫時，模型需要從 18 個工具中判斷應該用哪一個，決策複雜度遠高於只有 4～5 個工具的情況。官方建議每個 agent 只給它角色所需的少量工具，以維持選擇的可靠性。

A 錯在哪：描述長度本身不是問題，問題是工具數量導致的決策複雜度；且題目說的是「tool selection errors」，不是「description comprehension errors」。C 錯在哪：forced tool_choice 是用來保證特定工具被優先呼叫，不是解決工具太多導致的選擇錯誤問題。D 錯在哪：工具命名重疊確實會造成 misrouting，但題目描述的是多種功能不同的工具，問題的核心是數量而非命名相似。

Q 2 Scenario 3 · Multi-Agent Research System

A synthesis agent in a multi-agent research system is given web_search, summarize, and verify_fact tools. In production, the agent frequently uses web_search to gather new information instead of synthesizing the documents already collected by the search agent. Which change best addresses this issue?

  1. Update the synthesis agent's system prompt to explicitly instruct it not to call web_search.
  2. Remove web_search from the synthesis agent's allowed tools, keeping only summarize and verify_fact.
  3. Replace web_search with a constrained load_document tool that only accepts document URLs.
  4. Set tool_choice: "any" to ensure the synthesis agent always calls a tool instead of returning text.
展開解析

Correct Answer: B

Synthesis agent 的職責是整合已有資料，而非搜尋新資料。根據 scoped access 原則，應從 allowedTools 中完全移除 web_search，讓 synthesis agent 只保留其角色需要的 summarize 和 verify_fact。工具不在清單裡，agent 就無法誤用它。

A 錯在哪：用 system prompt 指令禁止使用某工具是 keyword-sensitive 做法，且「不要做 X」的負向指令比直接移除工具更不可靠，agent 在某些情況下仍可能選用。C 錯在哪：把 web_search 換成 load_document 雖然更受限，但 synthesis agent 根本不需要任何 URL 抓取工具，這個替換沒有解決角色邊界的根本問題。D 錯在哪：tool_choice: "any" 是用來保證模型一定呼叫工具（而非回純文字），和解決「呼叫了不該呼叫的工具」這個問題無關。

Q 3 Scenario 3 · Multi-Agent Research System

An architect is building a data enrichment pipeline where the agent must always call extract_metadata as the very first tool before any enrichment tools. In testing, the agent sometimes skips extract_metadata and calls enrichment tools directly. Which tool_choice configuration most effectively enforces the required sequence?

  1. Set tool_choice: "any" to force the model to call a tool instead of returning conversational text.
  2. Set tool_choice: "auto" and add a note in the system prompt instructing the model to always start with extract_metadata.
  3. Set tool_choice: {"type": "tool", "name": "extract_metadata"} to force the first call to be extract_metadata, then process subsequent steps in follow-up turns.
  4. Remove all enrichment tools from the first API call and add them back only after extract_metadata has been called.
展開解析

Correct Answer: C

Forced tool_choice 設定 {"type": "tool", "name": "extract_metadata"} 可以強制模型在這一輪一定先呼叫指定的工具，無論上下文如何都不例外。後續的 enrichment 步驟在 extract_metadata 完成後的下一回合處理，這是官方建議的順序控制做法。

A 錯在哪：tool_choice: "any" 只保證模型一定會呼叫某個工具（不回純文字），但不指定是哪個工具，模型仍可能選擇任何一個 enrichment 工具而非 extract_metadata。B 錯在哪：tool_choice: "auto" 加 system prompt 指令是 keyword-sensitive 且不可靠的做法，不能保證 extract_metadata 一定是第一個被呼叫的工具。D 錯在哪：動態調整工具清單在技術上可行，但架構複雜且維護成本高；直接用 forced tool_choice 是更簡潔、更標準的解法。
