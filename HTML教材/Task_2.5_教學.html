官方考綱原文

Task Statement 2.5 — Select and apply built-in tools (Read, Write, Edit, Bash, Grep, Glob) effectively

Knowledge of:

  • Grep for content search (searching file contents for patterns like function names, error messages, or import statements)
  • Glob for file path pattern matching (finding files by name or extension patterns)
  • Read/Write for full file operations; Edit for targeted modifications using unique text matching
  • When Edit fails due to non-unique text matches, using Read + Write as a fallback for reliable file modifications

Skills in:

  • Selecting Grep for searching code content across a codebase (e.g., finding all callers of a function, locating error messages)
  • Selecting Glob for finding files matching naming patterns (e.g., **/*.test.tsx)
  • Using Read to load full file contents followed by Write when Edit cannot find unique anchor text
  • Building codebase understanding incrementally: starting with Grep to find entry points, then using Read to follow imports and trace flows, rather than reading all files upfront
  • Tracing function usage across wrapper modules by first identifying all exported names, then searching for each name across the codebase
本題情境 · SCENARIO 4
Scenario 4 — Developer Productivity with Claude

用 Claude Agent SDK 幫工程師探索陌生 / legacy codebase、理解既有架構、產 boilerplate。本 Task 講的就是這時手上那六把內建工具(Read、Write、Edit、Bash、Grep、Glob)各自擅長什麼、何時用哪一把——尤其是「不要一次讀光所有檔,而是先 Grep 找入口、再 Read 沿著 import 追」的探索節奏。

一句話抓住主軸:六把工具各有專長,選錯工具就是繞遠路。 找「內容」用 Grep、找「檔名」用 Glob、改「小段」用 Edit、Edit 卡住就退回 Read+Write;理解陌生程式碼要「漸進式」——先搜入口再追流程,別一開始就把整個 repo 讀進來。

Knowledge of · 知識點

知識 1  Grep：搜「檔案內容」裡的模式（函式名、錯誤訊息、import）

遇到這個問題時用到你接手一個陌生的 legacy 服務，需要快速找出 InvalidTokenError 是從哪個模組丟出來的，以及有哪些地方 import 了 session 模組，你需要知道用哪個工具搜尋檔案內容裡的特定字串。

當你想找的是檔案內容（file content）裡的某個東西——某個函式名出現在哪、某句錯誤訊息哪裡丟的、誰 import 了某個模組——用 Grep。它掃的是「檔案裡寫了什麼」，不是「檔案叫什麼名字」。探索陌生 codebase 時，這通常是你的第一把工具。

# Scenario 4:剛接手一個陌生服務,想找登入流程從哪開始
Grep(pattern="def authenticate_user")        # 找函式定義在哪
Grep(pattern="InvalidTokenError")           # 找這個錯誤從哪丟出
Grep(pattern="from auth.session import")    # 找誰 import 了 session 模組
考點重點:Grep = 搜「內容」(content)。找字串、找模式、找誰用了什麼 → Grep。

知識 2  Glob：用「檔名 / 路徑模式（file path pattern）」找檔案

遇到這個問題時用到你剛接手一個前端專案，需要快速盤點有哪些 React 元件有對應的測試檔，你需要知道如何用命名模式一次找出所有 .test.tsx 檔案，而不必手動遍歷整個目錄結構。

當你要找的是符合某種命名模式（naming pattern）的檔案——所有測試檔、所有 .tsx 元件、某資料夾下所有設定檔——用 Glob。它比對的是「檔案路徑長怎樣」，不看裡面內容。** 代表任意層資料夾，* 代表任意檔名片段。

# Scenario 4:想盤點這個前端專案有哪些測試檔
Glob(pattern="**/*.test.tsx")     # 任意層底下所有 .test.tsx
Glob(pattern="src/**/*.py")        # src 底下所有 Python 檔
Glob(pattern="**/config.*")        # 任意層的 config.* 設定檔
考點重點:Glob = 比對「路徑 / 檔名」。找「哪些檔」而非「檔裡有什麼」 → Glob。

知識 3  Read / Write 是整檔操作；Edit 是靠「唯一文字比對（unique text matching）」做定點修改

遇到這個問題時用到你需要修改 legacy 服務裡一個設定值，這個值在整個檔案裡只出現一次，你需要了解 Edit 工具如何使用唯一文字作為 anchor 來精準定位並替換，以及和整檔 Read/Write 的使用場景差異。

三把改檔工具分工:Read 把整個檔讀進來、Write 把整個檔寫出去(會覆蓋),這兩把是「整檔」級。Edit 則是「定點」——你給它一段要被取代的舊文字和新文字,它在檔裡找到那段就替換。關鍵前提:那段舊文字在檔裡必須唯一,Edit 才知道要改哪一處。

# Scenario 4:把 legacy 服務裡某個逾時值從 30 改成 60

# ✅ 小範圍定點修改 → 用 Edit(old_string 在檔內唯一)
Edit(
    file_path="src/api/client.py",
    old_string="REQUEST_TIMEOUT = 30  # legacy default",
    new_string="REQUEST_TIMEOUT = 60  # raised for slow upstream",
)

# 整檔讀取 / 整檔覆寫 → Read / Write
content = Read(file_path="src/api/client.py")
Write(file_path="src/api/client.py", content=content)
考點重點:整檔 → Read/Write;改一小段 → Edit(但 old_string 要唯一)。

知識 4  Edit 因「文字不唯一（non-unique match）」失敗時：退回 Read + Write

遇到這個問題時用到你嘗試用 Edit 修改 config.py 裡的 timeout = 30，但工具回報無法定位因為這行在檔案中出現了三次，你需要知道遇到 non-unique match 時應該改用哪個工具組合來可靠地完成修改。

這是最常考的一條。當你要改的那段文字在檔裡出現了好幾次（例如同樣一行 timeout = 30 出現三處），Edit 不知道該改哪一個，就會失敗。這時的可靠後備（fallback）是：Read 把整檔讀進來、在記憶裡做好替換、再用 Write 整檔寫回去。用「整檔覆寫」繞過「定點比對不唯一（non-unique match）」的問題。

# ❌ old_string 在檔內出現多次 → Edit 無法定位,失敗
Edit(file_path="config.py", old_string="timeout = 30", new_string="timeout = 60")

# ✅ 後備:Read 整檔 → 處理 → Write 整檔寫回
text = Read(file_path="config.py")
text = text.replace("timeout = 30", "timeout = 60")   # 一次全換
Write(file_path="config.py", content=text)
一句話記住:Edit 卡在「文字不唯一」→ 換 Read + Write 整檔處理。

Skills in · 技能點

技能 1  跨整個 codebase 搜程式內容，用 Grep（找呼叫點、找錯誤訊息）

遇到這個問題時用到你需要評估修改 charge_customer() 函式的影響範圍，必須找出整個 codebase 裡所有呼叫這個函式的地方，同時也要定位線上報警中某句錯誤訊息在原始碼的出處。

技能版的知識 1。探索陌生服務時最常做的兩件事:找「某函式的所有呼叫者」、定位「某句錯誤訊息」。兩者都是搜內容,都用 Grep。

# Scenario 4:評估改 charge_customer() 會影響誰 → 找所有呼叫點
Grep(pattern="charge_customer\\(")        # 找出每一處呼叫

# 線上報的這句錯誤,程式裡哪裡丟的?
Grep(pattern="Payment gateway timeout")   # 直接定位來源

技能 2  用 Glob 找符合命名模式的檔案（如 **/*.test.tsx）

遇到這個問題時用到你接手一個前端專案，需要盤點測試覆蓋狀況，找出哪些 React 元件還沒有對應的測試檔，你需要用命名模式批次找出所有測試檔和元件檔進行比對。

技能版的知識 2。盤點專案結構時,用命名模式一次撈出整類檔案。

# Scenario 4:接手前端,先看測試覆蓋了哪些元件
Glob(pattern="**/*.test.tsx")        # 所有 React 測試檔
Glob(pattern="src/components/**/*.tsx")  # 所有元件檔
# 比對清單 → 哪些元件還沒測試,一目了然

技能 3  Read 載入整檔 → 當 Edit 找不到唯一 anchor（unique anchor text）時改用 Write

遇到這個問題時用到你嘗試用 Edit 修改一個設定值，但因為相同的文字在檔案中出現多次而失敗，你需要一個可靠的 fallback 流程來完成這個修改，同時保持最小的改動範圍。

技能版的知識 4,流程化。先試 Edit;一旦因為 anchor 文字不唯一而失敗,就 Read 整檔、在記憶裡精準處理、Write 寫回。

def safe_modify(path, old, new):
    try:
        return Edit(file_path=path, old_string=old, new_string=new)
    except NonUniqueMatch:
        # anchor 不唯一 → 退回整檔 Read+Write
        text = Read(file_path=path)
        text = text.replace(old, new)
        return Write(file_path=path, content=text)
重點:Edit 優先(改動小、精準);失敗就 Read+Write 兜底。

技能 4  漸進式理解 codebase（incremental exploration）：先 Grep 找入口，再 Read 沿 import 追流程

遇到這個問題時用到你接手一個龐大的陌生 legacy 服務，需要快速理解結帳（checkout）流程的完整呼叫鏈，若一開始就讀所有檔案會讓 context 爆掉，你需要一套系統性的漸進式探索策略。

這條是探索陌生程式碼的正確節奏,也最常考。不要一開始就把整個 repo 的檔全 Read 進來(浪費 context、抓不到重點)。正確做法:先用 Grep 找到入口點(main、route handler、某功能的起始函式),再用 Read 讀那個檔、看它 import 了什麼,沿著 import 一路往下追,只讀真正相關的檔。像偵探循線索,而不是把整個圖書館搬回家。

# ❌ 一開始就 Read 全部檔 → context 爆掉、抓不到重點
for f in Glob(pattern="**/*.py"):
    Read(file_path=f)   # 把整個 repo 讀進來 = 反模式

# ✅ 漸進式:Grep 找入口 → Read 沿 import 追
# 1) 找功能入口
entry = Grep(pattern="@app.route\\(.*checkout")
# 2) 讀入口檔,看它依賴誰
src = Read(file_path="src/routes/checkout.py")
# 3) 沿 import 往下追,只讀相關模組
Read(file_path="src/services/payment.py")   # checkout 引用的
重點:先 Grep 找入口、再 Read 循 import 追;別一次讀光整個 repo。

技能 5  追函式在 wrapper 模組間的使用：先列出所有匯出名（exported names），再逐名搜尋

遇到這個問題時用到你要評估移除 retry_request 的影響，但直接搜這個名字只找到少數幾個呼叫點，你懷疑這個函式在多個 wrapper 模組中被 re-export 並換了名字，需要找出所有實際使用點才能安全重構。

有些 codebase 會層層包裝:一個工具函式被 utils/__init__.py re-export、又被別的模組換名匯出,直接搜原始函式名會漏掉這些「換了馬甲」的呼叫。正確做法:先找出某模組所有匯出的名稱(原名 + 別名),再拿每一個名字去整個 codebase 搜一遍,才能完整追出真實用量。

# Scenario 4:retry_request 被多個 wrapper re-export,要找真實用量

# 1) 先找出 utils 模組匯出了哪些名字(含別名)
Grep(pattern="retry_request|as retry|__all__", path="src/utils/")
# 假設得到:retry_request、retry(別名)、do_retry(另一個 wrapper 名)

# 2) 拿每個名字分別全庫搜尋,才不漏掉換名的呼叫
for name in ["retry_request", "retry", "do_retry"]:
    Grep(pattern=name)   # 逐名搜,拼出完整呼叫圖
重點:先列「所有匯出名(含別名)」,再逐名 Grep → 才追得全 wrapper 後的真實用量。

整個 Task 2.5 的記憶骨架

六把內建工具,選對才不繞路:找內容(函式名、錯誤訊息、import)用 Grep;找檔名/路徑模式(**/*.test.tsx)用 Glob;整檔讀寫用 Read/Write,改一小段用 Edit(old_string 要唯一);Edit 因文字不唯一失敗,就退回 Read+Write 整檔處理。理解陌生 codebase 要漸進式——先 Grep 找入口、再 Read 沿 import 追,別一次讀光整個 repo;追 wrapper 後的函式用量,先列所有匯出名(含別名)再逐名搜。

Q 1 Scenario 4 · Developer Productivity with Claude

An engineer is onboarding to a large legacy Python codebase and needs to understand the complete flow for a checkout process. The agent's first action is to call Glob(pattern="**/*.py") and then Read every single file returned. After processing 300 files, the agent runs out of context and fails to produce a useful answer. What is the most effective approach to fix this?

  1. Increase the model's context window by switching to a larger model before running the same approach.
  2. Use Glob to narrow down files by name pattern first, then Read only files whose names suggest relevance to checkout.
  3. Start with Grep to find the checkout route entry point, then use Read to follow import chains incrementally, reading only directly relevant files.
  4. Use Bash to run a grep command across the codebase and pipe the output to a file for the agent to read all at once.
展開解析

Correct Answer: C

正確的陌生 codebase 探索節奏是「漸進式」：先用 Grep 找到功能入口點（如 checkout 的 route handler），再用 Read 讀入口檔並沿著 import 鏈往下追，只讀真正相關的模組。這樣能用最少的 token 建立最精準的理解，避免把整個 repo 讀進來造成 context 爆掉。

A 錯在哪：切換大模型增加 context window 是治標不治本，根本問題是讀了大量不相關的檔案；正確的工具選擇策略才是解答。B 錯在哪：用 Glob 依檔名篩選有一定幫助，但 checkout 相關邏輯可能散落在 services、utils 等各種命名的檔案中，依名字篩選仍可能漏掉或包含太多不相關的檔案。D 錯在哪：用 Bash grep 把輸出存到檔案再讀，本質上還是一次讀大量文字，沒有解決 context 的問題，且增加了不必要的複雜性。

Q 2 Scenario 4 · Developer Productivity with Claude

An agent needs to update a timeout value in config.py. It calls Edit(file_path="config.py", old_string="timeout = 30", new_string="timeout = 60"). The Edit tool returns an error indicating the string is not uniquely found. Which approach best resolves this?

  1. Retry the Edit call with a higher confidence threshold parameter.
  2. Use Bash to run sed -i 's/timeout = 30/timeout = 60/' config.py to replace all occurrences.
  3. Call Read to load the full file content, perform the replacement in memory, then call Write to overwrite the file.
  4. Add more context lines to old_string to make the match unique — for example, include the surrounding lines that differ between the occurrences.
展開解析

Correct Answer: D

等等！這題有兩個合理答案。D（加更多上下文使 old_string 唯一）是最精準的做法：找到目標位置周圍的獨特文字作為 anchor，讓 Edit 能精確定位。C（Read + Write）是正確的 fallback，但會修改所有出現的 timeout = 30。若只需要改某一處，D 更精準；若確實要改全部，C 也可接受。官方文件中 D 描述的「提供更多周圍上下文讓比對唯一」是解決 non-unique match 的首選方法。

A 錯在哪：Edit 工具沒有「confidence threshold」參數，這個選項描述的是不存在的功能。B 錯在哪：雖然 sed 在技術上可行，但指引要求優先使用專用工具（Edit/Read/Write）而非 Bash；Bash 應留給工具本身無法完成的任務。C 的考量：Read+Write 是正確的 fallback，但若只想修改特定那一處而非全部，應先嘗試提供更多 anchor 上下文讓 Edit 能唯一定位。

Q 3 Scenario 4 · Developer Productivity with Claude

An agent needs to find all callers of a retry_request utility function before refactoring it. A simple Grep for "retry_request" returns only 3 results, but a senior engineer suspects the function is re-exported under different names in multiple wrapper modules. What is the most thorough approach?

  1. Grep for "retry_request" with a recursive flag to ensure all subdirectories are searched.
  2. Use Glob to find all Python files, then Read each one and manually scan for the function name.
  3. First Grep the utils module to find all exported names (including aliases) of retry_request, then Grep for each exported name separately across the entire codebase.
  4. Search the git commit history for all changes to files that originally defined retry_request to identify where it was copied or re-exported.
展開解析

Correct Answer: C

追 wrapper 後的真實用量，正確做法分兩步：第一步用 Grep 在 utils 模組找出 retry_request 的所有匯出名（包括 as retry、do_retry 等別名和 __all__ 清單）；第二步用每個名字分別 Grep 整個 codebase。只搜原始函式名會漏掉所有「換了馬甲」的呼叫，無法完整評估重構影響。

A 錯在哪：加遞迴旗標只確保搜尋範圍涵蓋所有子目錄，但問題在於 retry_request 被換名匯出後，直接搜原始名字就是找不到，不是搜尋範圍的問題。B 錯在哪：讀所有 Python 檔案是 anti-pattern——context 爆掉的風險很高，且效率遠不如精準使用 Grep；這是技能 4 明確反對的做法。D 錯在哪：查 git 歷史可能幫助理解演化，但無法準確找出「當前程式碼中所有的呼叫點」，因為程式可能在 git 歷史之外已經被大幅重構。
