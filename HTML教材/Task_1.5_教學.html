官方考綱原文

Task Statement 1.5 — Apply Agent SDK hooks for tool call interception and data normalization

Knowledge of:

  • Hook patterns (e.g., PostToolUse) that intercept tool results for transformation before the model processes them
  • Hook patterns that intercept outgoing tool calls to enforce compliance rules (e.g., blocking refunds above a threshold)
  • The distinction between using hooks for deterministic guarantees versus relying on prompt instructions for probabilistic compliance

Skills in:

  • Implementing PostToolUse hooks to normalize heterogeneous data formats (Unix timestamps, ISO 8601, numeric status codes) from different MCP tools before the agent processes them
  • Implementing tool call interception hooks that block policy-violating actions (e.g., refunds exceeding $500) and redirect to alternative workflows (e.g., human escalation)
  • Choosing hooks over prompt-based enforcement when business rules require guaranteed compliance
本題情境 · SCENARIO 1
Scenario 1 — Customer Support Resolution Agent

延續客服解決 agent:用 hook 攔截 process_refund 之類的高風險工具呼叫,在送出前強制檢查 compliance(如尚未驗證客戶就擋下)。本 Task 的攔截與正規化,就是這道確定性防線。

一句話抓住主軸:Hook 是「掛」在工具呼叫前後的攔截器,讓你用程式碼(而非靠 prompt 拜託模型)強制做兩件事——把回傳資料洗乾淨、把違規動作擋下來。 核心對比始終是:hook = 確定性保證(deterministic);prompt = 機率性遵守(probabilistic)。

Knowledge of · 知識點

知識 1  PostToolUse:在模型「看到」工具結果前先轉換它

工具(例如某個 MCP API)回傳結果後,結果不會直接送進模型。PostToolUse hook 卡在中間,先攔下這份結果,讓你做轉換、清洗、補欄位,再把處理過的版本交給模型。模型看到的是你整理好的乾淨資料。

想像成郵件分檢:包裹(工具結果)送到你手上前,先經過一個分檢站(hook),貼好標籤、整理格式,你才收到。

# PostToolUse:工具回傳後、模型處理前,先攔截轉換
def post_tool_use_hook(tool_name, raw_result):
    # raw_result 是工具原始輸出,模型還沒看到
    cleaned = transform(raw_result)   # 在這裡轉換
    return cleaned                  # 模型只會看到 cleaned
考點重點:PostToolUse = 工具結果進模型「之前」的轉換點。

知識 2  攔截「送出去的」工具呼叫,強制 compliance 規則

另一個方向:在工具呼叫實際執行之前攔下來,檢查它合不合規。典型例子是退款——模型想呼叫「退款 $800」這個動作時,hook 先檢查金額,超過門檻就擋下,不讓它真的執行。這是用程式碼把業務規則變成硬性關卡。

# 攔截「即將送出」的工具呼叫,執行前先檢查合規
def pre_tool_use_hook(tool_name, args):
    if tool_name == "issue_refund" and args["amount"] > 500:
        return block(reason="退款超過 $500,需人工核准")  # ❌ 擋下
    return allow()   # ✅ 放行
考點重點:攔「outgoing tool call」= 在動作執行前把違規擋住。

知識 3  最核心對比:hook(確定性) vs prompt(機率性)

這是整個 Task 1.5 最常考、最該記牢的一條。

你可以在 prompt 裡寫「請不要核准超過 $500 的退款」——但這是拜託模型,模型大多數時候會聽,卻無法 100% 保證(機率性遵守)。改用 hook,則是用程式碼硬性攔截,只要金額超標就一定擋下,不依賴模型的判斷(確定性保證)。當規則「不容許出錯」時,選 hook。

# ❌ prompt 強制:只是「拜託」模型,機率性,可能被繞過
system_prompt = "絕對不要核准超過 $500 的退款。"

# ✅ hook 強制:程式碼層硬擋,確定性,100% 保證
def enforce(tool_name, args):
    if tool_name == "issue_refund" and args["amount"] > 500:
        return block()   # 不靠模型自律,規則一定生效
一句話記住:要「保證」用 hook;只能「儘量」才用 prompt。

Skills in · 技能點

技能 1  用 PostToolUse 正規化各家工具的異質資料格式

不同 MCP 工具回傳的格式五花八門:有的時間是 Unix timestamp(1700000000),有的是 ISO 8601(2024-01-01T00:00:00Z);狀態有的給數字代碼(0/1/2),有的給文字。直接丟給模型,它要花力氣猜、還容易錯。用 PostToolUse 把全部統一成同一種格式,模型處理起來既準又省。

def normalize_hook(tool_name, result):
    # 時間一律轉成 ISO 8601
    if "timestamp" in result:
        ts = result["timestamp"]
        if isinstance(ts, (int, float)):       # Unix → ISO
            result["timestamp"] = datetime.utcfromtimestamp(ts).isoformat()

    # 數字狀態碼 → 統一文字
    status_map = {0: "pending", 1: "active", 2: "closed"}
    if isinstance(result.get("status"), int):
        result["status"] = status_map[result["status"]]

    return result   # ✅ 模型收到的是統一格式
重點:異質格式(Unix / ISO / 數字碼)在 PostToolUse 統一,再交給模型。

技能 2  攔截違規動作並改導到替代流程(如人工升級)

光擋下還不夠好——擋下之後要給出路。退款超過 $500 不只是拒絕,而是把它改導(redirect)到人工升級流程,讓真人來處理。hook 不只是個「不」,也是個「轉接」。

def refund_guard_hook(tool_name, args):
    if tool_name == "issue_refund" and args["amount"] > 500:
        # 不只擋下,還改導到人工升級工作流
        return {
            "action": "block",
            "redirect_to": "human_escalation",   # ✅ 給替代流程
            "message": "金額超過上限,已轉交專員審核。",
        }
    return {"action": "allow"}
重點:block 違規動作 + redirect 到替代流程(human escalation),不是單純拒絕。

技能 3  當規則「必須保證」時,選 hook 而非 prompt

這是知識 3 的決策版。面對一條業務規則,你要會判斷:它是「最好遵守」還是「不容違反」?若是後者(法遵、財務上限、安全紅線),就不能把它交給 prompt 碰運氣,必須用 hook 在程式碼層保證。判斷準則:出錯的代價是否無法承受。

# 決策準則:這條規則「違反的代價」能不能承受?

# 不容違反(財務上限、法遵、安全) → 用 hook 確定性保證
if rule.is_critical():          # ✅ guaranteed
    enforce_with_hook(rule)

# 偏好 / 風格 / 軟性建議 → prompt 就夠了
else:                            # 機率性遵守可接受
    add_to_prompt(rule)
重點:關鍵/不可違反的規則 → hook;軟性偏好 → prompt。判準=出錯代價。

整個 Task 1.5 的記憶骨架

Hook 是掛在工具呼叫前後的攔截器:PostToolUse 在結果進模型前做正規化(Unix/ISO/數字碼統一);攔截 outgoing 呼叫可在動作執行前擋下違規(退款 > $500)並改導到人工升級。最核心的一條對比:hook = 確定性保證,prompt = 機率性遵守——規則不容違反就用 hook,軟性偏好才交給 prompt。
