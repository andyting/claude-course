Task Statement 1.5 — Apply Agent SDK hooks for tool call interception and data normalization

Knowledge of:

  • Hook patterns (e.g., PostToolUse) that intercept tool results for transformation before the model processes them
  • Hook patterns that intercept outgoing tool calls to enforce compliance rules (e.g., blocking refunds above a threshold)
  • The distinction between using hooks for deterministic guarantees versus relying on prompt instructions for probabilistic compliance

Skills in:

  • Implementing PostToolUse hooks to normalize heterogeneous data formats (Unix timestamps, ISO 8601, numeric status codes) from different MCP tools before the agent processes them
  • Implementing tool call interception hooks that block policy-violating actions (e.g., refunds exceeding $500) and redirect to alternative workflows (e.g., human escalation)
  • Choosing hooks over prompt-based enforcement when business rules require guaranteed compliance
本題情境 · SCENARIO 1
Scenario 1 — Customer Support Resolution Agent

延續客服解決 agent:用 hook 攔截 process_refund 之類的高風險工具呼叫,在送出前強制檢查 compliance(如尚未驗證客戶就擋下)。本 Task 的攔截與正規化,就是這道確定性防線。

一句話抓住主軸:Hook（鉤子）是「掛」在工具呼叫前後的攔截器（interceptor），讓你用程式碼(而非靠 prompt 拜託模型)強制做兩件事——把回傳資料洗乾淨（正規化）、把違規動作擋下來。 核心對比始終是:hook = 確定性保證(deterministic);prompt = 機率性遵守(probabilistic)。

Knowledge of · 知識點

知識 1  PostToolUse:在模型「看到」工具結果前先轉換它

遇到這個問題時用到整合了三個不同廠商的 MCP 工具後，模型對時間欄位的理解出現混亂，有的是 Unix timestamp、有的是 ISO 格式，模型花了大量 token 猜測格式，偶爾還解讀錯誤。

工具(例如某個 MCP API)回傳結果後,結果不會直接送進模型。PostToolUse hook 卡在中間,先攔下這份結果,讓你做轉換、清洗、補欄位,再把處理過的版本交給模型。模型看到的是你整理好的乾淨資料。

想像成郵件分檢:包裹(工具結果)送到你手上前,先經過一個分檢站(hook),貼好標籤、整理格式,你才收到。

# PostToolUse:工具回傳後、模型處理前,先攔截轉換
def post_tool_use_hook(tool_name, raw_result):
    # raw_result 是工具原始輸出,模型還沒看到
    cleaned = transform(raw_result)   # 在這裡轉換
    return cleaned                  # 模型只會看到 cleaned
考點重點:PostToolUse = 工具結果進模型「之前」的轉換點。

知識 2  攔截「送出去的」工具呼叫,強制 compliance 規則

遇到這個問題時用到客服代理被發現嘗試核准了一筆 $800 的退款，超過了公司設定的 $500 上限，但模型仍然呼叫了退款工具，因為沒有在執行前進行攔截檢查。

另一個方向:在工具呼叫實際執行之前攔下來,檢查它合不合規。典型例子是退款——模型想呼叫「退款 $800」這個動作時,hook 先檢查金額,超過門檻就擋下,不讓它真的執行。這是用程式碼把業務規則變成硬性關卡。

# 攔截「即將送出」的工具呼叫,執行前先檢查合規
def pre_tool_use_hook(tool_name, args):
    if tool_name == "issue_refund" and args["amount"] > 500:
        return block(reason="退款超過 $500,需人工核准")  # ❌ 擋下
    return allow()   # ✅ 放行
考點重點:攔「outgoing tool call」= 在動作執行前把違規擋住。

知識 3  最核心對比:hook（確定性 / deterministic）vs prompt（機率性 / probabilistic）

遇到這個問題時用到安全審查要求所有超過金額上限的退款請求「零例外」必須被攔截，你需要評估現有的 prompt 指令是否足夠，還是必須改用 hook 來達到確定性保證。

這是整個 Task 1.5 最常考、最該記牢的一條。

你可以在 prompt 裡寫「請不要核准超過 $500 的退款」——但這是拜託模型,模型大多數時候會聽,卻無法 100% 保證（機率性遵守，probabilistic compliance）。改用 hook,則是用程式碼硬性攔截,只要金額超標就一定擋下,不依賴模型的判斷（確定性保證，deterministic guarantee）。當規則「不容許出錯」時,選 hook。

# ❌ prompt 強制:只是「拜託」模型,機率性,可能被繞過
system_prompt = "絕對不要核准超過 $500 的退款。"

# ✅ hook 強制:程式碼層硬擋,確定性,100% 保證
def enforce(tool_name, args):
    if tool_name == "issue_refund" and args["amount"] > 500:
        return block()   # 不靠模型自律,規則一定生效
一句話記住:要「保證」用 hook;只能「儘量」才用 prompt。

Skills in · 技能點

技能 1  用 PostToolUse 正規化（normalize）各家工具的異質資料格式

遇到這個問題時用到你整合了多個 MCP 工具，它們各自回傳不同格式的時間戳和狀態碼，需要在資料進入模型前統一格式，以避免模型誤判或花費過多 token 處理格式差異。

不同 MCP 工具回傳的格式五花八門:有的時間是 Unix timestamp(1700000000),有的是 ISO 8601(2024-01-01T00:00:00Z);狀態有的給數字代碼(0/1/2),有的給文字。直接丟給模型,它要花力氣猜、還容易錯。用 PostToolUse 把全部統一成同一種格式,模型處理起來既準又省。

def normalize_hook(tool_name, result):
    # 時間一律轉成 ISO 8601
    if "timestamp" in result:
        ts = result["timestamp"]
        if isinstance(ts, (int, float)):       # Unix → ISO
            result["timestamp"] = datetime.utcfromtimestamp(ts).isoformat()

    # 數字狀態碼 → 統一文字
    status_map = {0: "pending", 1: "active", 2: "closed"}
    if isinstance(result.get("status"), int):
        result["status"] = status_map[result["status"]]

    return result   # ✅ 模型收到的是統一格式
重點:異質格式(Unix / ISO / 數字碼)在 PostToolUse 統一,再交給模型。

技能 2  攔截違規動作並改導（redirect）到替代流程（如人工升級）

遇到這個問題時用到退款請求超過 $500 上限時，系統不應只是拒絕，而是要把案件自動轉給人工審核流程；你需要設計一個 hook，讓它在攔截違規動作的同時也觸發正確的升級路徑。

光擋下還不夠好——擋下之後要給出路。退款超過 $500 不只是拒絕,而是把它改導(redirect)到人工升級流程,讓真人來處理。hook 不只是個「不」,也是個「轉接」。

def refund_guard_hook(tool_name, args):
    if tool_name == "issue_refund" and args["amount"] > 500:
        # 不只擋下,還改導到人工升級工作流
        return {
            "action": "block",
            "redirect_to": "human_escalation",   # ✅ 給替代流程
            "message": "金額超過上限,已轉交專員審核。",
        }
    return {"action": "allow"}
重點:block 違規動作 + redirect 到替代流程(human escalation),不是單純拒絕。

技能 3  當規則「必須保證」時,選 hook（鉤子）而非 prompt

遇到這個問題時用到你在設計一條業務規則的執行方式，需要判斷這條規則應該寫進 system prompt 還是實作成 hook，判準是「違反的代價是否無法承受」。

這是知識 3 的決策版。面對一條業務規則,你要會判斷:它是「最好遵守」還是「不容違反」?若是後者(法遵、財務上限、安全紅線),就不能把它交給 prompt 碰運氣,必須用 hook 在程式碼層保證。判斷準則:出錯的代價是否無法承受。

# 決策準則:這條規則「違反的代價」能不能承受?

# 不容違反(財務上限、法遵、安全) → 用 hook 確定性保證
if rule.is_critical():          # ✅ guaranteed
    enforce_with_hook(rule)

# 偏好 / 風格 / 軟性建議 → prompt 就夠了
else:                            # 機率性遵守可接受
    add_to_prompt(rule)
重點:關鍵/不可違反的規則 → hook;軟性偏好 → prompt。判準=出錯代價。

整個 Task 1.5 的記憶骨架

Hook 是掛在工具呼叫前後的攔截器:PostToolUse 在結果進模型前做正規化(Unix/ISO/數字碼統一);攔截 outgoing 呼叫可在動作執行前擋下違規(退款 > $500)並改導到人工升級。最核心的一條對比:hook = 確定性保證,prompt = 機率性遵守——規則不容違反就用 hook,軟性偏好才交給 prompt。

考試情境題

以下三題模擬正式考試格式，每題一個生產情境，四個選項。先嘗試作答，再展開解析。

Q 1 Scenario 1 · Customer Support Resolution Agent

A customer support agent integrates three MCP tools from different vendors. After deployment, engineers notice that the model frequently misinterprets timestamps — one tool returns Unix epoch integers, another returns ISO 8601 strings, and a third returns locale-formatted dates. The model spends extra tokens converting formats and occasionally makes errors. What is the most effective approach to fix this?

  1. Update the system prompt to instruct the model to normalize all timestamps to ISO 8601 format before processing them.
  2. Implement a PostToolUse hook that intercepts each tool result and normalizes all timestamp formats to ISO 8601 before the model processes them.
  3. Replace the three MCP tools with a single unified tool that returns a consistent format.
  4. Add retry logic so the model can re-invoke tools when it detects an unexpected timestamp format.
展開解析

Correct Answer: B

PostToolUse hook 的設計目的正是在工具回傳結果後、模型處理前，對資料進行轉換和正規化。用 hook 統一所有時間戳格式，模型收到的永遠是乾淨一致的 ISO 8601，完全消除格式混亂的問題，不依賴模型的自行判斷。

A 錯在哪：要求模型「自己去轉換」是機率性做法，轉換本身會消耗 token、且無法保證正確；hook 是在資料進入模型前就已轉換好，才是確定性解法。C 錯在哪：換工具是不切實際的重大架構改動，且未來整合更多工具時同樣問題會重現；hook 是更通用的解決方案。D 錯在哪：重試不解決格式問題——模型每次讀到同一個 Unix timestamp，無論重試幾次格式都不會自動變成 ISO 8601。

Q 2 Scenario 1 · Customer Support Resolution Agent

A compliance team requires that no automated refund above $500 should ever be approved without human review. The current implementation adds this rule to the agent's system prompt. A weekly audit finds that approximately 0.4% of refunds above $500 are still being approved automatically. What is the most effective change to achieve guaranteed compliance?

  1. Rewrite the system prompt instruction using stronger language such as "you must NEVER approve refunds over $500 under any circumstances."
  2. Implement a pre-tool-use hook that intercepts all issue_refund calls, blocks those where the amount exceeds $500, and redirects them to the human escalation workflow.
  3. Add a separate validation agent that reviews each refund decision before it is executed.
  4. Log all refund amounts and trigger an alert when the $500 threshold is exceeded so a human can intervene.
展開解析

Correct Answer: B

0.4% 的違規率正是「prompt = 機率性遵守」的體現。對於「零例外」的合規要求，必須從 prompt 換成程式碼層的 hook。Pre-tool-use hook 在工具執行前攔截請求，金額超標時 100% 擋下並轉到人工升級流程，達到確定性保證，而不依賴模型每次都遵守指示。

A 錯在哪：強化 prompt 措辭只是程度上的改進，無法從根本上消除 LLM 的機率性本質；模型仍然有非零機率跳過指示，0.4% 可能降低但不會歸零。C 錯在哪：加入驗證代理增加了系統複雜度和延遲，且驗證代理本身也是 LLM，同樣存在機率性失誤；hook 是更輕量且確定性更高的解法。D 錯在哪：事後告警屬於偵測性控制，無法防止違規發生；題目要求的是預防性的「保證合規」，而非事後通知。

Q 3 Scenario 1 · Customer Support Resolution Agent

An engineering team is reviewing two business rules for a customer support agent: (1) "Response tone should be professional and empathetic" and (2) "Identity verification must be completed before any financial transaction is processed." They are deciding whether to implement each rule as a hook or as a prompt instruction. Which approach is correct?

  1. Implement both as hooks to ensure consistent enforcement across all interactions.
  2. Implement both as prompt instructions since the model is generally reliable at following instructions.
  3. Implement rule 1 as a prompt instruction (tone is a soft preference) and rule 2 as a programmatic hook (financial compliance is non-negotiable).
  4. Implement rule 1 as a hook (to prevent brand risk) and rule 2 as a prompt instruction (since the model understands financial workflows).
展開解析

Correct Answer: C

判準是「這條規則違反的代價是否無法承受」。語氣和語調屬於「偏好」，偶爾偏差可以接受，用 prompt 提示就夠了。身分驗證是金融合規的硬性要求，任何一次失敗都可能導致財務損失或法律責任，屬於「絕不能錯」的類別，必須用 hook 在程式層強制保證。

A 錯在哪：把語氣規則也實作成 hook 是過度工程，增加不必要的複雜度；軟性偏好用 prompt 就足夠，hook 應留給真正不容違反的規則。B 錯在哪：把財務合規規則交給 prompt 是本 Task 的反模式，LLM 的機率性本質確保了無論 prompt 多麼明確，仍有非零失敗率，在財務場景下完全不可接受。D 錯在哪：顛倒了兩條規則的優先級——語氣用 hook 是大材小用，財務合規用 prompt 是以輕敵重，兩者都選錯了工具。
