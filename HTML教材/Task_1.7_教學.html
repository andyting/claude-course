官方考綱原文

Task Statement 1.7 — Manage session state, resumption, and forking

Knowledge of:

  • Named session resumption using --resume <session-name> to continue a specific prior conversation
  • fork_session for creating independent branches from a shared analysis baseline to explore divergent approaches
  • The importance of informing the agent about changes to previously analyzed files when resuming sessions after code modifications
  • Why starting a new session with a structured summary is more reliable than resuming with stale tool results

Skills in:

  • Using --resume with session names to continue named investigation sessions across work sessions
  • Using fork_session to create parallel exploration branches (e.g., comparing two testing strategies or refactoring approaches from a shared codebase analysis)
  • Choosing between session resumption (when prior context is mostly valid) and starting fresh with injected summaries (when prior tool results are stale)
  • Informing a resumed session about specific file changes for targeted re-analysis rather than requiring full re-exploration
本題情境 · SCENARIO 2
Scenario 2 — Code Generation with Claude Code

你在用 Claude Code 加速開發。本 Task 的 session resumption 與 fork,讓你能跨工作階段續用同一脈絡,或從共同基線分岔出多條重構方案分別嘗試。

一句話抓住主軸:session 可以「續(resume)」、可以「分岔(fork)」;但續用前要先問——舊的 context 還新鮮嗎? 新鮮就 resume,過期(stale)就帶著一份結構化摘要重開新局。這個取捨是整個 Task 1.7 的核心。

Knowledge of · 知識點

知識 1  具名 session resumption:用 --resume <session-name> 續特定對話

你可以給 session 取名字,之後用 --resume <session-name> 精準接回那一個之前的對話,而不是大海撈針。重點在「具名(named)」——靠名字鎖定要續哪一段歷史。

# 具名 resume:用 session 名字接回特定那段對話
$ claude --resume auth-refactor-investigation

# 對比:沒名字就只能從一堆 session 裡慢慢找
考點重點:--resume <session-name> = 用名字續特定的舊對話。

知識 2  fork_session:從共享基線分岔出獨立分支

fork_session 把一個已建立的分析基線複製分岔,各分支獨立往下走、互不干擾。用途是「從同一起點探索不同方向」(divergent approaches)——例如同一份程式碼分析基線,一條試方案 A、一條試方案 B。(與 Task 1.3 的 fork-based session 呼應。)

# 已有共享分析基線
baseline = session.analyze("codebase")

# fork 出兩條獨立分支,各探索不同方向
branch_a = fork_session(baseline, name="strategy_A")
branch_b = fork_session(baseline, name="strategy_B")
# 共用基線、各走各的,互不影響
考點重點:fork_session = 共享基線 + 獨立分支,探索 divergent approaches。

知識 3  resume 改過的程式碼後,要主動告知 agent「哪些檔變了」

常見陷阱:你上次分析完後改了程式碼,隔天 resume 舊 session——但 agent 腦中記得的還是舊版的檔案內容。如果不告訴它「這些檔已經變了」,它會拿過期認知繼續做,結論就錯。resume 後務必主動通報變更。

# resume 後,主動告知期間改了哪些檔(否則 agent 用舊版認知)
$ claude --resume auth-refactor-investigation

> "注意:自上次以來 auth.py 與 session.py 已修改,
  請以最新版本重新檢視這兩個檔。"   # ✅ 主動通報變更
考點重點:改過碼再 resume → 一定要告知 agent 哪些檔變了。

知識 4  為什麼「帶摘要重開」比「續用過期結果」更可靠

這是 Task 1.7 最深的一條觀念。當舊 session 裡的工具結果已經過期(stale)——例如那些檔案、那些查詢結果都變了——硬 resume 反而危險:agent 會被一堆過時資料污染。更可靠的做法是開一個新 session,只注入一份乾淨的結構化摘要,把「目前真正有效的結論」帶過去,而不是拖著一整袋過期的 tool results。

# ❌ 硬 resume:把一整袋過期 tool results 也帶進來,污染判斷
$ claude --resume old-session-with-stale-results

# ✅ 重開新局 + 注入結構化摘要:只帶「現在仍有效」的結論
$ claude   # 全新 session
> "背景摘要:已確認登入流程瓶頸在 token 驗證;
  目前有效結論為 A、B、C。請從此基礎繼續。"
考點重點:結果過期時,帶「結構化摘要」重開 > 拖著 stale results 硬 resume。

Skills in · 技能點

技能 1  用 --resume + session 名稱跨工作階段續調查

知識 1 的實作。一個長期調查可能跨好幾天、好幾次坐下來做。給它一個固定名字,每次用 --resume <name> 接回同一條調查線,context 自然延續,不必每次重講背景。

# 跨多次工作階段,續同一條具名調查
$ claude --resume perf-bottleneck-hunt   # 週一
# ...隔天...
$ claude --resume perf-bottleneck-hunt   # 週二,接回同一條線
重點:具名 + --resume = 跨日續同一條調查,不重講背景。

技能 2  用 fork_session 開平行探索分支

知識 2 的實作。從一份共享的 codebase 分析基線,fork 出多條平行分支,各自試不同策略——例如「比較兩種測試策略」或「兩種重構方法」。最後把各分支結果擺在一起比較,而起點完全一致,比較才公平。

# 從同一基線分岔,平行比較兩種重構方法
baseline = analyze_codebase()

refactor_a = fork_session(baseline, name="refactor_strategy_pattern")
refactor_b = fork_session(baseline, name="refactor_factory_pattern")

# 起點一致 → 兩種方法的比較才公平
compare(refactor_a.run(), refactor_b.run())
重點:fork_session 從共享基線開平行分支,公平比較不同策略。

技能 3  判斷:resume 還是「重開 + 注入摘要」?

這是整個 Task 1.7 最該練熟的決策。判準很單純:舊 context 大致還有效 → resume;舊 tool results 已過期(stale)→ 重開新 session 並注入摘要。不要因為「續用比較省事」就忽略資料已經過期的事實。

def choose_continuation(prior):
    if prior.context_mostly_valid():    # 舊 context 大致還準
        return resume(prior.name)        # ✅ 直接 resume
    else:                              # tool results 已 stale
        summary = build_structured_summary(prior)
        return start_fresh(inject=summary)  # ✅ 重開 + 注入摘要
重點:context 大致有效 → resume;結果 stale → 重開新局 + 注入摘要。

技能 4  告知「具體哪些檔變了」做針對性重分析,而非整包重跑

知識 3 的精緻版。resume 後若有檔案改動,不要叫 agent 把整個 codebase 從頭再 explore 一遍(浪費)。而是明確點名哪幾個檔變了,讓它只針對那幾個做targeted re-analysis。範圍縮小,又快又準。

# ❌ 籠統:叫 agent 整個 codebase 重新 explore 一遍(浪費)
> "有些東西改了,請重新分析整個專案。"

# ✅ 精準:點名變更檔,只做針對性重分析
> "僅 payment.py 與 invoice.py 已修改,
  請只重新檢視這兩個檔及其直接相依,其餘維持原分析。"
重點:點名變更檔做 targeted re-analysis > 要求整包重新探索。

整個 Task 1.7 的記憶骨架

Session 可具名 resume(--resume <name> 續特定對話)、可 fork_session(從共享基線開獨立分支比較不同方向)。改過碼再 resume,務必告知哪些檔變了並做針對性重分析。最核心的取捨:舊 context 大致有效就 resume;tool results 過期(stale)時,帶結構化摘要重開新 session 比硬續更可靠。
