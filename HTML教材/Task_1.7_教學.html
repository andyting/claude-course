Task Statement 1.7 — Manage session state, resumption, and forking

Knowledge of:

  • Named session resumption using --resume <session-name> to continue a specific prior conversation
  • fork_session for creating independent branches from a shared analysis baseline to explore divergent approaches
  • The importance of informing the agent about changes to previously analyzed files when resuming sessions after code modifications
  • Why starting a new session with a structured summary is more reliable than resuming with stale tool results

Skills in:

  • Using --resume with session names to continue named investigation sessions across work sessions
  • Using fork_session to create parallel exploration branches (e.g., comparing two testing strategies or refactoring approaches from a shared codebase analysis)
  • Choosing between session resumption (when prior context is mostly valid) and starting fresh with injected summaries (when prior tool results are stale)
  • Informing a resumed session about specific file changes for targeted re-analysis rather than requiring full re-exploration
本題情境 · SCENARIO 2
Scenario 2 — Code Generation with Claude Code

你在用 Claude Code 加速開發。本 Task 的 session resumption 與 fork,讓你能跨工作階段續用同一脈絡,或從共同基線分岔出多條重構方案分別嘗試。

一句話抓住主軸:session 可以「續（resume，恢復）」、可以「分岔（fork）」;但續用前要先問——舊的 context（對話歷史）還新鮮嗎? 新鮮就 resume,過期(stale，陳舊)就帶著一份結構化摘要重開新局。這個取捨是整個 Task 1.7 的核心。

Knowledge of · 知識點

知識 1  具名 session resumption（續接）:用 --resume <session-name> 續特定對話

遇到這個問題時用到你進行了一個跨越三天的架構調查，每次重新開始都要重新向 Claude Code 解釋背景脈絡，浪費大量時間；你需要一個機制讓每次工作都能接回上次中斷的地方。

你可以給 session 取名字,之後用 --resume <session-name> 精準接回那一個之前的對話,而不是大海撈針。重點在「具名(named)」——靠名字鎖定要續哪一段歷史。

# 具名 resume:用 session 名字接回特定那段對話
$ claude --resume auth-refactor-investigation

# 對比:沒名字就只能從一堆 session 裡慢慢找
考點重點:--resume <session-name> = 用名字續特定的舊對話。

知識 2  fork_session:從共享基線 fork（分岔）出獨立分支

遇到這個問題時用到你已完成一份完整的 codebase 分析，現在想比較「策略模式重構」和「工廠模式重構」兩個方案，但不想為了每個方案重新跑一遍相同的基線分析。

fork_session 把一個已建立的分析基線複製分岔,各分支獨立往下走、互不干擾。用途是「從同一起點探索不同方向」（divergent approaches，分歧探索）——例如同一份程式碼分析基線,一條試方案 A、一條試方案 B。(與 Task 1.3 的 fork-based session 呼應。)

# 已有共享分析基線
baseline = session.analyze("codebase")

# fork 出兩條獨立分支,各探索不同方向
branch_a = fork_session(baseline, name="strategy_A")
branch_b = fork_session(baseline, name="strategy_B")
# 共用基線、各走各的,互不影響
考點重點:fork_session = 共享基線 + 獨立分支,探索 divergent approaches。

知識 3  resume 改過的程式碼後,要主動告知 agent「哪些檔變了」

遇到這個問題時用到你昨天用 Claude Code 分析了 auth 模組，今天修改了 auth.py 後 resume 同一個 session，但 Claude Code 基於過時的認知給出了錯誤的建議，沒有反映最新的程式碼狀態。

常見陷阱:你上次分析完後改了程式碼,隔天 resume 舊 session——但 agent 腦中記得的還是舊版的檔案內容。如果不告訴它「這些檔已經變了」,它會拿過期認知繼續做,結論就錯。resume 後務必主動通報變更。

# resume 後,主動告知期間改了哪些檔(否則 agent 用舊版認知)
$ claude --resume auth-refactor-investigation

> "注意:自上次以來 auth.py 與 session.py 已修改,
  請以最新版本重新檢視這兩個檔。"   # ✅ 主動通報變更
考點重點:改過碼再 resume → 一定要告知 agent 哪些檔變了。

知識 4  為什麼「帶摘要重開」比「續用過期（stale）結果」更可靠

遇到這個問題時用到一個調查 session 已有兩週歷史，其中引用的檔案路徑、函式名稱和架構決策大多已改變，你面臨抉擇：繼續用這個 session 還是帶著結論重開新的。

這是 Task 1.7 最深的一條觀念。當舊 session 裡的工具結果已經過期（stale，陳舊）——例如那些檔案、那些查詢結果都變了——硬 resume 反而危險:agent 會被一堆過時資料污染。更可靠的做法是開一個新 session,只注入一份乾淨的結構化摘要（structured summary）,把「目前真正有效的結論」帶過去,而不是拖著一整袋過期的 tool results。

# ❌ 硬 resume:把一整袋過期 tool results 也帶進來,污染判斷
$ claude --resume old-session-with-stale-results

# ✅ 重開新局 + 注入結構化摘要:只帶「現在仍有效」的結論
$ claude   # 全新 session
> "背景摘要:已確認登入流程瓶頸在 token 驗證;
  目前有效結論為 A、B、C。請從此基礎繼續。"
考點重點:結果過期時,帶「結構化摘要」重開 > 拖著 stale results 硬 resume。

Skills in · 技能點

技能 1  用 --resume + session 名稱跨工作階段續調查

遇到這個問題時用到你正在進行一個需要多天才能完成的效能瓶頸調查，希望每次坐下來工作時都能直接從上次分析中斷的地方繼續，而不必重新描述背景。

知識 1 的實作。一個長期調查可能跨好幾天、好幾次坐下來做。給它一個固定名字,每次用 --resume <name> 接回同一條調查線,context 自然延續,不必每次重講背景。

# 跨多次工作階段,續同一條具名調查
$ claude --resume perf-bottleneck-hunt   # 週一
# ...隔天...
$ claude --resume perf-bottleneck-hunt   # 週二,接回同一條線
重點:具名 + --resume = 跨日續同一條調查,不重講背景。

技能 2  用 fork_session 開平行探索分支（parallel exploration branches）

遇到這個問題時用到完成 codebase 基線分析後，你想同時評估「測試策略 A：以整合測試為主」和「測試策略 B：以單元測試為主」，需要從同一個起點分別往兩個方向探索並最後比較結果。

知識 2 的實作。從一份共享的 codebase 分析基線,fork 出多條平行分支,各自試不同策略——例如「比較兩種測試策略」或「兩種重構方法」。最後把各分支結果擺在一起比較,而起點完全一致,比較才公平。

# 從同一基線分岔,平行比較兩種重構方法
baseline = analyze_codebase()

refactor_a = fork_session(baseline, name="refactor_strategy_pattern")
refactor_b = fork_session(baseline, name="refactor_factory_pattern")

# 起點一致 → 兩種方法的比較才公平
compare(refactor_a.run(), refactor_b.run())
重點:fork_session 從共享基線開平行分支,公平比較不同策略。

技能 3  判斷:resume 還是「重開 + 注入摘要（structured summary）」?

遇到這個問題時用到你需要決定是否繼續使用一個三週前的調查 session，判準是舊 session 中的 tool results（工具查詢結果）是否仍然反映現在的程式碼狀態。

這是整個 Task 1.7 最該練熟的決策。判準很單純:舊 context 大致還有效 → resume;舊 tool results 已過期(stale)→ 重開新 session 並注入摘要。不要因為「續用比較省事」就忽略資料已經過期的事實。

def choose_continuation(prior):
    if prior.context_mostly_valid():    # 舊 context 大致還準
        return resume(prior.name)        # ✅ 直接 resume
    else:                              # tool results 已 stale
        summary = build_structured_summary(prior)
        return start_fresh(inject=summary)  # ✅ 重開 + 注入摘要
重點:context 大致有效 → resume;結果 stale → 重開新局 + 注入摘要。

技能 4  告知「具體哪些檔變了」做針對性重分析（targeted re-analysis）,而非整包重跑

遇到這個問題時用到Resume 一個 session 後，你修改了兩個檔案，但不確定應該請 agent 重新分析整個專案，還是只針對那兩個變更的檔案及其直接相依進行重分析。

知識 3 的精緻版。resume 後若有檔案改動,不要叫 agent 把整個 codebase 從頭再 explore 一遍(浪費)。而是明確點名哪幾個檔變了,讓它只針對那幾個做targeted re-analysis。範圍縮小,又快又準。

# ❌ 籠統:叫 agent 整個 codebase 重新 explore 一遍(浪費)
> "有些東西改了,請重新分析整個專案。"

# ✅ 精準:點名變更檔,只做針對性重分析
> "僅 payment.py 與 invoice.py 已修改,
  請只重新檢視這兩個檔及其直接相依,其餘維持原分析。"
重點:點名變更檔做 targeted re-analysis > 要求整包重新探索。

整個 Task 1.7 的記憶骨架

Session 可具名 resume(--resume <name> 續特定對話)、可 fork_session(從共享基線開獨立分支比較不同方向)。改過碼再 resume,務必告知哪些檔變了並做針對性重分析。最核心的取捨:舊 context 大致有效就 resume;tool results 過期(stale)時,帶結構化摘要重開新 session 比硬續更可靠。

考試情境題

以下三題模擬正式考試格式，每題一個生產情境，四個選項。先嘗試作答，再展開解析。

Q 1 Scenario 2 · Code Generation with Claude Code

An engineer runs claude --resume auth-investigation to continue a two-week-old session analyzing the authentication module. The session resumes successfully, but Claude Code's suggestions are based on function signatures and file structures that were refactored five days ago. The engineer receives incorrect recommendations. What is the most likely root cause?

  1. The --resume flag loaded the wrong session because the session name was ambiguous.
  2. The resumed session contains stale tool results from two weeks ago; Claude Code is reasoning from outdated file analysis rather than the current codebase state.
  3. The session's context window was truncated after two weeks, causing Claude Code to lose track of the original investigation goals.
  4. Claude Code does not support resuming sessions that are older than one week.
展開解析

Correct Answer: B

Session resumption 最常見的陷阱是：session 裡的 tool results（讀取的檔案內容、查詢的結果）在 session 建立後就被「凍結」了。如果那之後程式碼被重構，agent resume 後仍然看到的是舊版的函式簽名和檔案結構，所有基於這些過時資料的建議都會偏離現實。正確的處理是：要麼 resume 後立即告知 agent 哪些檔案已更改，要麼在資料大幅過期時改用「帶摘要重開新 session」。

A 錯在哪：具名 session 用明確的名字鎖定特定 session，沒有歧義問題；題目也說「resumes successfully」，表示 session 被正確找到了。C 錯在哪：context window 截斷可能發生，但症狀是建議偏離目標，而非完全失憶；題目描述的問題是建議基於「過時的程式碼狀態」，這是 stale results 的典型症狀。D 錯在哪：Claude Code 的 session resumption 沒有時間限制；只要 session 存在且名稱正確，無論多久都能 resume。

Q 2 Scenario 2 · Code Generation with Claude Code

After completing a thorough analysis of a shared codebase, a team wants to evaluate two refactoring strategies: Strategy A uses the Strategy design pattern, and Strategy B uses the Factory pattern. They want both explorations to start from the same analysis baseline, and the results to be fairly comparable. What is the most effective approach?

  1. Run the full codebase analysis twice — once for each strategy — to ensure each exploration has a clean, independent starting point.
  2. Use fork_session to create two independent branches from the shared analysis baseline, then explore each strategy in its own branch.
  3. Run Strategy A first, complete it fully, then resume the original session and run Strategy B from that point.
  4. Create two separate named sessions and independently reproduce the baseline analysis in each before starting the strategy-specific work.
展開解析

Correct Answer: B

fork_session 的設計目的正是「從同一基線出發、探索不同方向」。它複製目前 session 的狀態作為兩個獨立分支的起點，各分支往後的操作互不影響。兩種策略從完全相同的分析基線出發，比較結果才具有公平性；而且不需要重複跑一遍耗時的基線分析。

A 錯在哪：重複跑兩次完整的基線分析浪費大量時間和資源，且兩次分析結果可能因為執行細節不同而略有差異，影響比較公平性；fork_session 正是為了解決「不必重複基線」這個問題。C 錯在哪：先跑完 A 再 resume 原始 session 跑 B，這種方法讓兩次探索在時序上有先後，resume 後的 session 已包含 A 的影響（即使你 resume 到原始點，A 的工作歷程可能影響後續判斷）；fork 才能真正獨立。D 錯在哪：分別在兩個 session 中重新做一遍基線分析等同於選項 A 的問題——浪費資源且無法保證基線完全一致。

Q 3 Scenario 2 · Code Generation with Claude Code

An engineer resumes a session named payment-refactor that was used three days ago. Since then, payment.py and invoice.py have been significantly modified, but the other 20 files in the codebase are unchanged. The engineer needs Claude Code to re-analyze the changes. What is the most effective approach?

  1. Start a completely new session and re-explain the full project context from scratch to avoid any stale information.
  2. Ask Claude Code to re-analyze the entire project from the beginning to ensure all information is fresh.
  3. After resuming, explicitly tell Claude Code that payment.py and invoice.py have been modified and ask it to re-analyze only those two files and their direct dependencies.
  4. Run --resume payment-refactor without any additional instructions, as Claude Code will automatically detect and re-read changed files.
展開解析

Correct Answer: C

當只有少數幾個檔案發生變更時，最有效率的做法是 targeted re-analysis（針對性重分析）：resume session 後明確告知 agent 哪些具體檔案已變更，請它只針對那幾個檔案及其直接相依重新分析，其餘 20 個未變更的檔案維持原有分析結果。這樣既保留了舊 session 中仍然有效的大量分析，又確保變更部分被重新評估。

A 錯在哪：只有兩個檔案變更，舊 session 中其他 20 個檔案的分析仍然有效；完全重開新 session 放棄了大量仍然有用的 context，浪費不必要的工作。B 錯在哪：要求重新分析整個專案同樣浪費——這是「整包重跑」的反模式；針對性重分析比整包重跑更快、更準。D 錯在哪：Claude Code 在 resume 時不會自動偵測檔案變更並重新讀取；agent 的認知仍停留在上次 session 讀取的狀態，必須由工程師主動告知哪些檔案已更改。
