Task Statement 1.2 — Orchestrate multi-agent systems with coordinator-subagent patterns

Knowledge of:

  • Hub-and-spoke architecture where a coordinator agent manages all inter-subagent communication, error handling, and information routing
  • How subagents operate with isolated context—they do not inherit the coordinator's conversation history automatically
  • The role of the coordinator in task decomposition, delegation, result aggregation, and deciding which subagents to invoke based on query complexity
  • Risks of overly narrow task decomposition by the coordinator, leading to incomplete coverage of broad research topics

Skills in:

  • Designing coordinator agents that analyze query requirements and dynamically select which subagents to invoke rather than always routing through the full pipeline
  • Partitioning research scope across subagents to minimize duplication (e.g., assigning distinct subtopics or source types to each agent)
  • Implementing iterative refinement loops where the coordinator evaluates synthesis output for gaps, re-delegates to search and analysis subagents with targeted queries, and re-invokes synthesis until coverage is sufficient
  • Routing all subagent communication through the coordinator for observability, consistent error handling, and controlled information flow
本題情境 · SCENARIO 3
Scenario 3 — Multi-Agent Research System

你在用 Claude Agent SDK 打造多代理研究系統:coordinator 把任務拆給 web 搜尋、文件分析、綜合、產報告等 subagent。本 Task 的 coordinator-subagent 編排正是這個系統的骨架。

一句話抓住主軸:一個 coordinator(協調者)當中樞,所有 subagent 都掛在它身上像輪輻——subagent 之間不直接對話,一切溝通、錯誤處理、資訊路由都要經過 coordinator。 這個 Task 的考點,圍繞「中樞怎麼拆任務、怎麼選人、怎麼匯整、怎麼補洞」。

Knowledge of · 知識點

知識 1  Hub-and-spoke:coordinator（協調者）掌管所有跨 subagent（子代理）的溝通、錯誤處理與路由

遇到這個問題時用到多代理系統上線後難以追蹤資料流向，某個 subagent 回傳錯誤卻不知道是哪個環節出問題，因為各代理彼此直接傳訊、沒有統一的觀察點。

架構長得像腳踏車輪:中間的軸心(hub)是 coordinator,周圍的輪輻(spoke)是各個 subagent。重點是 subagent 彼此不直接講話——A 要把結果給 B,不是 A 傳給 B,而是 A → coordinator → B。所有的溝通、錯誤處理、資訊路由,全部集中在 coordinator 這個軸心。

好處:單一進出點 → 容易觀察(observability)、錯誤統一處理、資訊流可控。壞處若違反:讓 subagent 互相直連,系統會變成一團亂線,沒人說得清資料怎麼流的。

# ✅ Hub-and-spoke:所有溝通經過 coordinator
class Coordinator:
    def handle(self, query):
        search = self.call_subagent("search", query)     # A 的結果回到中樞
        analysis = self.call_subagent("analysis", search)  # 中樞再轉給 B
        return self.call_subagent("synthesis", analysis)

    def call_subagent(self, name, payload):
        try:
            return Task(agent=name, prompt=payload).result
        except Exception as e:
            return self.handle_error(name, e)   # 錯誤也統一在中樞處理

# ❌ 反例:讓 subagent 之間直連 → 無法觀察、錯誤散落各處
考點重點:中樞輻條 = 一切經過 coordinator;subagent 不互相直連。

知識 2  subagent 的 context 是隔離的——不會自動繼承 coordinator 的對話歷史

遇到這個問題時用到你呼叫分析 subagent 時只傳了「請分析剛才搜尋到的資料」，結果 subagent 回傳空洞的答案，因為它根本看不到 coordinator 之前的搜尋結果。

這是最常考、也最容易踩雷的一條。subagent 被叫出來時,看不到 coordinator 之前的對話。它沒有自動繼承任何歷史,也不會跟其他 subagent 共享記憶。你想讓它知道什麼,就得明白寫進它的 prompt 裡。

把它想成你找一位外部顧問:他完全不知道你公司內部之前討論過什麼,你得把背景整理好交給他。(此點與 Task 1.3「context 必須在 prompt 裡明白給」直接呼應。)

# ❌ 以為 subagent 看得到 coordinator 的對話
Task(agent="analysis", prompt="分析剛才搜尋到的資料")
# 「剛才搜尋到的」對 subagent 是空白——它沒有那段歷史

# ✅ 把背景明白塞進 prompt
Task(
    agent="analysis",
    prompt=f"""分析以下搜尋結果並萃取重點:

{search_results}
"""
)
一句話記住:subagent 的 context 是隔離的——背景要手動餵,不會自動繼承。

知識 3  coordinator 的職責:task decomposition（拆任務）、派工、匯整結果、決定要叫哪些 subagent

遇到這個問題時用到簡單的查詢也走完整條 pipeline（搜尋→分析→綜合），浪費大量 token 與時間，系統回應速度遠低於預期。

coordinator 不只是傳話的,它有四項核心職責:task decomposition（任務分解，把大問題拆成子任務）、delegation(把子任務派給合適的 subagent)、result aggregation(把各方結果匯整成完整答案)、以及依查詢複雜度決定要叫哪些 subagent——簡單的問題不必動用整條 pipeline,複雜的才全員出動。

class Coordinator:
    def run(self, query):
        subtasks = self.decompose(query)        # 1. 拆任務
        results = []
        for st in subtasks:
            agent = self.pick_agent(st)         # 2. 依需要派給合適 subagent
            results.append(Task(agent=agent, prompt=st).result)
        return self.aggregate(results)         # 3. 匯整成完整答案

    def pick_agent(self, subtask):
        # 4. 依複雜度決定:簡單問題不必叫全部 subagent
        return "search" if subtask.is_factual else "analysis"
重點:coordinator = 拆任務 + 派工 + 匯整 + 依複雜度選人。

知識 4  風險:任務拆得太細太窄,反而漏掉廣泛主題的涵蓋面

遇到這個問題時用到研究報告產出後客戶反映重大面向（如政策、基礎建設）完全沒有涵蓋，但每個 subagent 各自的子題都查得很細，問題出在任務拆解時切得太窄。

拆任務不是拆越細越好。如果 coordinator 把一個廣泛的研究題目拆得太窄,每個 subagent 只盯著一個小角落,結果就是「每個點都查了,但整體主題沒查全」——出現涵蓋面缺口(incomplete coverage)。

例如研究「2025 電動車趨勢」,若只拆成「查特斯拉股價」「查比亞迪銷量」兩個極窄子題,就會漏掉電池技術、政策補貼、充電基建等同樣重要的面向。

# ❌ 拆太窄:只盯兩個點 → 廣泛主題涵蓋不全
subtasks = ["查特斯拉股價", "查比亞迪銷量"]
# 漏了:電池技術、政策、充電基建、市場規模...

# ✅ 涵蓋主要面向,廣度與深度兼顧
subtasks = [
    "電動車市場規模與成長率",
    "電池技術趨勢",
    "各國政策與補貼",
    "充電基礎建設",
    "主要廠商競爭態勢",
]
重點:拆太窄 → 涵蓋面缺口。廣泛主題要確保子題涵蓋主要面向。

Skills in · 技能點

技能 1  coordinator 動態選人,而非每次都跑完整 pipeline

遇到這個問題時用到使用者詢問一個簡單的事實問題，系統卻觸發了完整的搜尋→分析→綜合 pipeline，導致延遲數秒才回覆，嚴重影響使用體驗。

這是知識 3 的實作版。好的 coordinator 會先分析這個 query 需要什麼,再動態挑出該叫的 subagent——而不是不管什麼問題都把整條 pipeline(搜尋→分析→綜合)全跑一遍。簡單的事實查詢可能只需要 search;複雜的研究才動用全員。這省時、省 token,也降低出錯面。

def select_subagents(query):
    needs = analyze_requirements(query)   # 先看這題需要什麼
    agents = []
    if needs.requires_search:
        agents.append("search")
    if needs.requires_deep_analysis:    # 簡單問題就不必加分析
        agents.append("analysis")
    if needs.requires_synthesis:
        agents.append("synthesis")
    return agents
# ❌ 反模式:不分情況一律跑 search→analysis→synthesis 全程

技能 2  切分研究範圍,讓 subagent 不重工

遇到這個問題時用到多個搜尋 subagent 各自回傳了大量重複的資料，最終報告中有三分之一內容高度雷同，浪費了 token 預算，也增加了後續整合的難度。

把研究範圍切給不同 subagent 時,要分清楚各自負責的子題或來源類型,避免兩個 subagent 查到同一批東西(重工浪費)。常見做法:依「子主題」切(A 查電池、B 查政策),或依「來源類型」切(A 查學術論文、B 查新聞、C 查官方數據)。

# ✅ 依子主題切分,各管一塊,不重疊
assignments = {
    "agent_1": "電池技術趨勢",
    "agent_2": "各國政策補貼",
    "agent_3": "充電基礎建設",
}

# ✅ 或依來源類型切分,避免大家都去翻同一批資料
by_source = {
    "agent_1": "學術論文",
    "agent_2": "產業新聞",
    "agent_3": "官方統計數據",
}
# ❌ 反模式:三個 agent 都去搜同樣的關鍵字 → 結果高度重複
重點:明確切分子題或來源 → 最小化重工。

技能 3  iteration（迭代精修）:coordinator 評估綜合結果、找缺口、再派工、再綜合

遇到這個問題時用到研究系統跑完一輪後產出的報告明顯遺漏了幾個重要子題，但因為沒有評估機制，系統直接把這份不完整的報告交給使用者，客戶滿意度很低。

不是「跑一次就交差」。好的 coordinator 會看 synthesis 的產出有沒有缺口,有的話用更精準的 query 重新派給 search / analysis subagent,補完後再叫 synthesis 重做——直到涵蓋面夠了才收。這是一個 refinement loop（迭代精修迴圈）。

def refine_until_complete(query, max_rounds=3):
    findings = gather(query)
    for _ in range(max_rounds):
        draft = Task(agent="synthesis", prompt=build(findings)).result
        gaps = self.evaluate_gaps(draft)       # coordinator 找缺口
        if not gaps:
            return draft                       # ✅ 涵蓋足夠 → 收
        # 針對缺口用更精準的 query 重新派工
        findings += Task(agent="search", prompt=targeted(gaps)).result
    return draft
重點:評估缺口 → 針對性重派 → 重綜合,迴圈到足夠為止。

技能 4  所有 subagent 溝通都路由經過 coordinator

遇到這個問題時用到生產環境中某個 subagent 靜默失敗，整個系統沒有任何錯誤日誌，因為那個 subagent 是直接被另一個 subagent 呼叫的，繞過了 coordinator 的統一錯誤處理。

這是知識 1 的實作紀律。把每一次對 subagent 的呼叫與回收都集中在 coordinator（協調者），好處有三:統一觀察(observability,能看到完整資料流)、一致的錯誤處理(在一處 try/except)、可控的資訊流（pipeline，管線）(誰拿到什麼由中樞決定)。絕不讓 subagent 私下互傳。

class Coordinator:
    def dispatch(self, agent, payload):
        self.log(f"→ {agent}")          # 觀察:每次呼叫都留痕
        try:
            result = Task(agent=agent, prompt=payload).result
            self.log(f"← {agent} ok")
            return result
        except Exception as e:
            self.log(f"← {agent} error: {e}")   # 一致錯誤處理
            return self.fallback(agent, e)
# 所有資料流都過這個方法 → 可觀察、可控、錯誤集中
重點:一切經中樞 → 可觀察、錯誤一致、資訊流可控。

整個 Task 1.2 的記憶骨架

架構是 hub-and-spoke:coordinator 當軸心,subagent 是輪輻,彼此不直連,一切溝通/錯誤/路由都經中樞。subagent 的 context 是隔離的,背景要手動餵。coordinator 負責拆任務、派工、匯整、依複雜度選人,並動態選人而非每次跑完整 pipeline。拆任務別太窄(會漏涵蓋面),要切分範圍避免重工,並用迭代精修補缺口,直到夠了才收。

考試情境題

以下三題模擬正式考試格式，每題一個生產情境，四個選項。先嘗試作答，再展開解析。

Q 1 Scenario 3 · Multi-Agent Research System

A multi-agent research system is deployed in production. Logs show that when a search subagent encounters an error, the failure is never logged at the coordinator level, and subsequent subagents receive no signal that data is missing — they silently produce incomplete synthesis. Which architectural issue is most likely the root cause?

  1. The coordinator's system prompt does not explicitly instruct it to check for errors before proceeding.
  2. Subagents are communicating directly with each other instead of routing all results through the coordinator, bypassing centralized error handling.
  3. The synthesis subagent lacks access to the coordinator's conversation history and therefore cannot detect gaps.
  4. The search subagent's allowedTools list does not include an error-reporting tool.
展開解析

Correct Answer: B

Hub-and-spoke 架構的核心原則是：所有 subagent 之間的溝通必須路由經過 coordinator，由 coordinator 統一處理錯誤、記錄日誌、控制資訊流。如果 subagent 繞過 coordinator 直接互傳，錯誤就無法在中樞被截獲，後續 subagent 也不會知道資料缺失。

A 錯在哪：prompt 提示屬於「建議」層級，無法保證錯誤一定被處理；根本問題是架構設計，不是 prompt 措辭。C 錯在哪：synthesis subagent 的 context 隔離是已知設計，它不應該依賴 coordinator 的對話歷史來偵測缺口——正確做法是 coordinator 在傳遞資料時就標記狀態。D 錯在哪：錯誤報告不是靠 subagent 自己呼叫工具，而是透過 coordinator 統一的 try/except 和日誌機制來處理。

Q 2 Scenario 3 · Multi-Agent Research System

A research coordinator receives a broad query: "Analyze the global EV market in 2025." It decomposes the task into two subtasks: "Find Tesla stock price" and "Find BYD sales numbers." After synthesis, the client rejects the report, saying it completely omits battery technology trends, government subsidies, and charging infrastructure. What is the most likely root cause of this coverage failure?

  1. The synthesis subagent did not have access to web search tools and could not fill in the missing topics independently.
  2. The coordinator's iterative refinement loop ran only once instead of the required three rounds.
  3. The coordinator decomposed the broad topic into overly narrow subtasks, causing incomplete coverage of major aspects.
  4. The subagents were invoked sequentially rather than in parallel, reducing the breadth of research.
展開解析

Correct Answer: C

拆任務的目的是讓每個 subagent 負責一塊清楚定義的範圍，但這個範圍必須足以涵蓋主題的主要面向。只拆成「特斯拉股價」和「比亞迪銷量」是極度窄化的子題，完全無法代表「全球電動車市場」這個廣泛研究議題，自然遺漏了電池技術、政策補貼、充電基建等同等重要的面向。

A 錯在哪：synthesis subagent 的職責是整合已有資料，而非主動補充研究；根本問題在於前端的任務拆解太窄。B 錯在哪：迭代精修迴圈能補充缺口，但前提是要有評估機制去「發現」缺口；此處問題在於拆解階段就已漏掉主要面向，而非精修次數不足。D 錯在哪：並行 vs. 序列影響的是速度，不影響涵蓋廣度；即使並行執行兩個極窄的子題，結果仍然不完整。

Q 3 Scenario 3 · Multi-Agent Research System

A coordinator invokes an analysis subagent with the prompt: "Please analyze the search results found earlier and extract key insights." The subagent returns a generic response that does not address the actual research topic. What is the most effective change to fix this?

  1. Add a line to the coordinator's system prompt reminding it to always pass context to subagents.
  2. Grant the analysis subagent access to the coordinator's conversation history via a shared memory tool.
  3. Include the complete search results directly in the analysis subagent's prompt so it has explicit context to work from.
  4. Switch from a hub-and-spoke architecture to a peer-to-peer architecture so the analysis subagent can directly query the search subagent.
展開解析

Correct Answer: C

Subagent 的 context 是完全隔離的：它看不到 coordinator 的對話歷史，也看不到其他 subagent 找到的資料。「剛才搜尋到的結果」對這個 subagent 來說是一片空白。正確做法是把搜尋結果的完整內容直接寫進這次呼叫的 prompt 裡，讓 subagent 從明確給定的資料開始工作。

A 錯在哪：修改 coordinator 的 system prompt 是「提示式」改法，屬於建議層級；根本問題是這次呼叫的 prompt 裡沒有資料，需要在程式層修正傳遞邏輯。B 錯在哪：subagent 在設計上刻意隔離 context，讓它透過工具取用 coordinator 的對話歷史會打破隔離原則，且帶入大量不相關的歷史訊息，效果反而更差。D 錯在哪：peer-to-peer 架構違反 hub-and-spoke 原則，會導致資料流不可觀察、錯誤散落各處，是典型的反模式。
