官方考綱原文

Task Statement 1.2 — Orchestrate multi-agent systems with coordinator-subagent patterns

Knowledge of:

  • Hub-and-spoke architecture where a coordinator agent manages all inter-subagent communication, error handling, and information routing
  • How subagents operate with isolated context—they do not inherit the coordinator's conversation history automatically
  • The role of the coordinator in task decomposition, delegation, result aggregation, and deciding which subagents to invoke based on query complexity
  • Risks of overly narrow task decomposition by the coordinator, leading to incomplete coverage of broad research topics

Skills in:

  • Designing coordinator agents that analyze query requirements and dynamically select which subagents to invoke rather than always routing through the full pipeline
  • Partitioning research scope across subagents to minimize duplication (e.g., assigning distinct subtopics or source types to each agent)
  • Implementing iterative refinement loops where the coordinator evaluates synthesis output for gaps, re-delegates to search and analysis subagents with targeted queries, and re-invokes synthesis until coverage is sufficient
  • Routing all subagent communication through the coordinator for observability, consistent error handling, and controlled information flow
本題情境 · SCENARIO 3
Scenario 3 — Multi-Agent Research System

你在用 Claude Agent SDK 打造多代理研究系統:coordinator 把任務拆給 web 搜尋、文件分析、綜合、產報告等 subagent。本 Task 的 coordinator-subagent 編排正是這個系統的骨架。

一句話抓住主軸:一個 coordinator(協調者)當中樞,所有 subagent 都掛在它身上像輪輻——subagent 之間不直接對話,一切溝通、錯誤處理、資訊路由都要經過 coordinator。 這個 Task 的考點,圍繞「中樞怎麼拆任務、怎麼選人、怎麼匯整、怎麼補洞」。

Knowledge of · 知識點

知識 1  Hub-and-spoke:coordinator 掌管所有跨 subagent 的溝通、錯誤處理與路由

架構長得像腳踏車輪:中間的軸心(hub)是 coordinator,周圍的輪輻(spoke)是各個 subagent。重點是 subagent 彼此不直接講話——A 要把結果給 B,不是 A 傳給 B,而是 A → coordinator → B。所有的溝通、錯誤處理、資訊路由,全部集中在 coordinator 這個軸心。

好處:單一進出點 → 容易觀察(observability)、錯誤統一處理、資訊流可控。壞處若違反:讓 subagent 互相直連,系統會變成一團亂線,沒人說得清資料怎麼流的。

# ✅ Hub-and-spoke:所有溝通經過 coordinator
class Coordinator:
    def handle(self, query):
        search = self.call_subagent("search", query)     # A 的結果回到中樞
        analysis = self.call_subagent("analysis", search)  # 中樞再轉給 B
        return self.call_subagent("synthesis", analysis)

    def call_subagent(self, name, payload):
        try:
            return Task(agent=name, prompt=payload).result
        except Exception as e:
            return self.handle_error(name, e)   # 錯誤也統一在中樞處理

# ❌ 反例:讓 subagent 之間直連 → 無法觀察、錯誤散落各處
考點重點:中樞輻條 = 一切經過 coordinator;subagent 不互相直連。

知識 2  subagent 的 context 是隔離的——不會自動繼承 coordinator 的對話歷史

這是最常考、也最容易踩雷的一條。subagent 被叫出來時,看不到 coordinator 之前的對話。它沒有自動繼承任何歷史,也不會跟其他 subagent 共享記憶。你想讓它知道什麼,就得明白寫進它的 prompt 裡。

把它想成你找一位外部顧問:他完全不知道你公司內部之前討論過什麼,你得把背景整理好交給他。(此點與 Task 1.3「context 必須在 prompt 裡明白給」直接呼應。)

# ❌ 以為 subagent 看得到 coordinator 的對話
Task(agent="analysis", prompt="分析剛才搜尋到的資料")
# 「剛才搜尋到的」對 subagent 是空白——它沒有那段歷史

# ✅ 把背景明白塞進 prompt
Task(
    agent="analysis",
    prompt=f"""分析以下搜尋結果並萃取重點:

{search_results}
"""
)
一句話記住:subagent 的 context 是隔離的——背景要手動餵,不會自動繼承。

知識 3  coordinator 的職責:拆任務、派工、匯整結果、決定要叫哪些 subagent

coordinator 不只是傳話的,它有四項核心職責:task decomposition(把大問題拆成子任務)、delegation(把子任務派給合適的 subagent)、result aggregation(把各方結果匯整成完整答案)、以及依查詢複雜度決定要叫哪些 subagent——簡單的問題不必動用整條 pipeline,複雜的才全員出動。

class Coordinator:
    def run(self, query):
        subtasks = self.decompose(query)        # 1. 拆任務
        results = []
        for st in subtasks:
            agent = self.pick_agent(st)         # 2. 依需要派給合適 subagent
            results.append(Task(agent=agent, prompt=st).result)
        return self.aggregate(results)         # 3. 匯整成完整答案

    def pick_agent(self, subtask):
        # 4. 依複雜度決定:簡單問題不必叫全部 subagent
        return "search" if subtask.is_factual else "analysis"
重點:coordinator = 拆任務 + 派工 + 匯整 + 依複雜度選人。

知識 4  風險:任務拆得太細太窄,反而漏掉廣泛主題的涵蓋面

拆任務不是拆越細越好。如果 coordinator 把一個廣泛的研究題目拆得太窄,每個 subagent 只盯著一個小角落,結果就是「每個點都查了,但整體主題沒查全」——出現涵蓋面缺口(incomplete coverage)。

例如研究「2025 電動車趨勢」,若只拆成「查特斯拉股價」「查比亞迪銷量」兩個極窄子題,就會漏掉電池技術、政策補貼、充電基建等同樣重要的面向。

# ❌ 拆太窄:只盯兩個點 → 廣泛主題涵蓋不全
subtasks = ["查特斯拉股價", "查比亞迪銷量"]
# 漏了:電池技術、政策、充電基建、市場規模...

# ✅ 涵蓋主要面向,廣度與深度兼顧
subtasks = [
    "電動車市場規模與成長率",
    "電池技術趨勢",
    "各國政策與補貼",
    "充電基礎建設",
    "主要廠商競爭態勢",
]
重點:拆太窄 → 涵蓋面缺口。廣泛主題要確保子題涵蓋主要面向。

Skills in · 技能點

技能 1  coordinator 動態選人,而非每次都跑完整 pipeline

這是知識 3 的實作版。好的 coordinator 會先分析這個 query 需要什麼,再動態挑出該叫的 subagent——而不是不管什麼問題都把整條 pipeline(搜尋→分析→綜合)全跑一遍。簡單的事實查詢可能只需要 search;複雜的研究才動用全員。這省時、省 token,也降低出錯面。

def select_subagents(query):
    needs = analyze_requirements(query)   # 先看這題需要什麼
    agents = []
    if needs.requires_search:
        agents.append("search")
    if needs.requires_deep_analysis:    # 簡單問題就不必加分析
        agents.append("analysis")
    if needs.requires_synthesis:
        agents.append("synthesis")
    return agents
# ❌ 反模式:不分情況一律跑 search→analysis→synthesis 全程

技能 2  切分研究範圍,讓 subagent 不重工

把研究範圍切給不同 subagent 時,要分清楚各自負責的子題或來源類型,避免兩個 subagent 查到同一批東西(重工浪費)。常見做法:依「子主題」切(A 查電池、B 查政策),或依「來源類型」切(A 查學術論文、B 查新聞、C 查官方數據)。

# ✅ 依子主題切分,各管一塊,不重疊
assignments = {
    "agent_1": "電池技術趨勢",
    "agent_2": "各國政策補貼",
    "agent_3": "充電基礎建設",
}

# ✅ 或依來源類型切分,避免大家都去翻同一批資料
by_source = {
    "agent_1": "學術論文",
    "agent_2": "產業新聞",
    "agent_3": "官方統計數據",
}
# ❌ 反模式:三個 agent 都去搜同樣的關鍵字 → 結果高度重複
重點:明確切分子題或來源 → 最小化重工。

技能 3  迭代精修:coordinator 評估綜合結果、找缺口、再派工、再綜合

不是「跑一次就交差」。好的 coordinator 會看 synthesis 的產出有沒有缺口,有的話用更精準的 query 重新派給 search / analysis subagent,補完後再叫 synthesis 重做——直到涵蓋面夠了才收。這是一個 refinement loop(精修迴圈)。

def refine_until_complete(query, max_rounds=3):
    findings = gather(query)
    for _ in range(max_rounds):
        draft = Task(agent="synthesis", prompt=build(findings)).result
        gaps = self.evaluate_gaps(draft)       # coordinator 找缺口
        if not gaps:
            return draft                       # ✅ 涵蓋足夠 → 收
        # 針對缺口用更精準的 query 重新派工
        findings += Task(agent="search", prompt=targeted(gaps)).result
    return draft
重點:評估缺口 → 針對性重派 → 重綜合,迴圈到足夠為止。

技能 4  所有 subagent 溝通都路由經過 coordinator

這是知識 1 的實作紀律。把每一次對 subagent 的呼叫與回收都集中在 coordinator,好處有三:統一觀察(observability,能看到完整資料流)、一致的錯誤處理(在一處 try/except)、可控的資訊流(誰拿到什麼由中樞決定)。絕不讓 subagent 私下互傳。

class Coordinator:
    def dispatch(self, agent, payload):
        self.log(f"→ {agent}")          # 觀察:每次呼叫都留痕
        try:
            result = Task(agent=agent, prompt=payload).result
            self.log(f"← {agent} ok")
            return result
        except Exception as e:
            self.log(f"← {agent} error: {e}")   # 一致錯誤處理
            return self.fallback(agent, e)
# 所有資料流都過這個方法 → 可觀察、可控、錯誤集中
重點:一切經中樞 → 可觀察、錯誤一致、資訊流可控。

整個 Task 1.2 的記憶骨架

架構是 hub-and-spoke:coordinator 當軸心,subagent 是輪輻,彼此不直連,一切溝通/錯誤/路由都經中樞。subagent 的 context 是隔離的,背景要手動餵。coordinator 負責拆任務、派工、匯整、依複雜度選人,並動態選人而非每次跑完整 pipeline。拆任務別太窄(會漏涵蓋面),要切分範圍避免重工,並用迭代精修補缺口,直到夠了才收。
