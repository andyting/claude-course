Task Statement 4.2 — Apply few-shot prompting to improve output consistency and quality

Knowledge of:

  • Few-shot examples as the most effective technique for achieving consistently formatted, actionable output when detailed instructions alone produce inconsistent results
  • The role of few-shot examples in demonstrating ambiguous-case handling (e.g., tool selection for ambiguous requests, branch-level test coverage gaps)
  • How few-shot examples enable the model to generalize judgment to novel patterns rather than matching only pre-specified cases
  • The effectiveness of few-shot examples for reducing hallucination in extraction tasks (e.g., handling informal measurements, varied document structures)

Skills in:

  • Creating 2-4 targeted few-shot examples for ambiguous scenarios that show reasoning for why one action was chosen over plausible alternatives
  • Including few-shot examples that demonstrate specific desired output format (location, issue, severity, suggested fix) to achieve consistency
  • Providing few-shot examples distinguishing acceptable code patterns from genuine issues to reduce false positives while enabling generalization
  • Using few-shot examples to demonstrate correct handling of varied document structures (inline citations vs bibliographies, methodology sections vs embedded details)
  • Adding few-shot examples showing correct extraction from documents with varied formats to address empty/null extraction of required fields
本題情境 · SCENARIO 6
Scenario 6 — Structured Data Extraction

用 Claude 從非結構化文件(發票、研究論文)抽資訊並以 JSON schema 驗證。當「詳細指令」還是抽得時好時壞、必填欄位變空值、非正式量詞被亂猜時,few-shot 範例就是把品質拉穩的最強手段。本 Task 的程式碼也會帶到 Scenario 5(CI code review)的降 false positive 用法。

一句話抓住主軸:當你把規則寫到天花亂墜、模型還是輸出得時好時壞時,別再加指令——「示範」幾個例子給它看,效果遠勝再多文字描述。 這就是 few-shot 的核心。

Knowledge of · 知識點

知識 1  當「詳細指令」失靈時,few-shot（少樣本）是拉穩格式的最強手段

遇到這個問題時用到你已寫了詳細的輸出格式說明（四欄、欄位名稱、型別），但不同批次的發票進來後輸出格式仍然忽多忽少、欄位順序不穩定，需要找一個更有效的方法穩住格式。

你可以把輸出規則寫成一大段文字:「請輸出 location、issue、severity、suggested_fix 四欄,severity 用 high/medium/low……」。但實務上,光靠文字指令,模型常常今天這樣排、明天那樣排。給它看 2~4 個「長這樣」的實際範例,一致性立刻拉起來——few-shot（少樣本）示範比描述有效。

在 Scenario 6 的抽取任務裡,這特別明顯:你描述了 invoice 該抽哪些欄位,但不同格式的發票一進來,輸出就歪掉;放幾個 input→output 範例,模型就「抓到感覺」了。這是解決 structured output（結構化輸出）不穩定的最有效手段。

考點重點:detailed instructions 還是不一致 → 改用 few-shot examples,這是最有效的技巧。

知識 2  few-shot 專治「模糊案例」的處理示範

遇到這個問題時用到你的抽取系統收到一份文件，它既有發票編號又有「Paid」戳記，模型在 extract_invoice 和 extract_receipt 之間搖擺不定，需要示範這種邊界情況該怎麼判斷。

規則最難寫清楚的,就是模糊地帶:這個請求到底該用哪個工具?這段測試到底算不算覆蓋到某個 branch?與其用文字硬解釋,不如示範一個模糊案例怎麼判,並把「為什麼選 A 不選 B」的理由寫進範例裡。模型學的不是答案,是判斷的尺度。

重點:ambiguous-case(工具選擇、branch 覆蓋缺口)用範例示範,比寫規則有效。

知識 3  few-shot 讓模型「類推」到沒見過的新樣式,而非只配對已列舉的案例

遇到這個問題時用到上線後客戶提交了一種新版型的發票，和你在 few-shot 裡示範的三種版型都不一樣，你需要確認模型能正確泛化而非回傳預設錯誤值。

這條最容易被誤解。few-shot 不是「把所有情況都列出來當查表」——那永遠列不完。好的範例是讓模型學會背後的判斷邏輯,再類推(generalize)到你沒寫過的新樣式。所以範例要挑「能代表一類判斷」的,而不是堆一堆雷同案例。

重點:few-shot 目標是 generalize judgment,不是 match pre-specified cases。

知識 4  few-shot 能降低抽取任務的幻覺(hallucination)

遇到這個問題時用到處理台灣客戶的發票時，「壹打」「半箱」這類非正式量詞讓模型自行猜測為 12 或 0.5，導致 quantity 欄位數值不可靠，你需要修正這個幻覺問題。

在 Scenario 6 抽取場景,模型最愛幻覺的地方是:遇到非正式量詞(「一打」「半箱」)、或文件結構長得不一樣時,就自己編一個值。放幾個「這種非正式寫法應該抽成什麼」的範例,模型就不會亂猜,hallucination（幻覺）明顯下降。

重點:varied document structures / informal measurements 的範例 → 降低 extraction 幻覺。

Skills in · 技能點

技能 1  為模糊案例寫 2~4 個範例,並寫出「為何選這個而非另一個」的理由

遇到這個問題時用到你要設計 few-shot 範例幫助模型在「發票 vs 收據 vs 論文」之間正確分類，需要確定範例數量、格式以及是否需要附上推理說明。

數量抓 2~4 個就好(太多反而稀釋、增加 token)。關鍵是每個範例要附上推理:不只給答案,還要說明在幾個看似合理的選項中,為什麼挑了這個。下面用 Scenario 6 的「一張看不出類型的文件,該用哪個抽取工具」示範。

# Scenario 6:文件類型不明,示範如何選對 extract_* 工具
few_shot_examples = """
範例 1
輸入文件:「Invoice #A-200 ... Total Due: $1,240」
判斷:含 Invoice 編號與 Total Due → 屬發票。
選用工具:extract_invoice(而非 extract_receipt,因為有正式發票編號與付款條件)
理由:receipt 通常無編號與付款條件;這裡兩者都有,故為 invoice。

範例 2
輸入文件:「Abstract ... Methods ... References [1] Smith 2024」
判斷:含 Abstract/Methods/References → 屬研究論文。
選用工具:extract_paper_metadata(而非 extract_invoice)
理由:無金額與編號,卻有章節與引用結構,明顯是論文。
"""

prompt = few_shot_examples + f"\n\n現在請判斷並抽取以下文件:\n{document}"
重點:2~4 個範例 + 附「為何選 A 不選 B」的 reasoning。

技能 2  用範例示範「指定輸出格式」(location / issue / severity / suggested_fix)

遇到這個問題時用到CI code review 回傳的格式每次都不一樣，有時缺 location、有時 severity 用不同字眼，下游自動開票系統因為 parse 失敗而告警，你需要強制輸出固定的四欄結構。

要輸出一致的結構,最穩的做法是直接示範一筆完整格式。這在 Scenario 5(CI code review)很典型:你要 PR 回饋固定包含「位置、問題、嚴重度、建議修法」四欄,就給它看一個範例長怎樣。

# Scenario 5:示範 PR review 回饋的固定輸出格式
format_example = """
範例輸入(diff 片段):
+ password = request.get("pwd")
+ db.query("SELECT * FROM users WHERE pwd = " + password)

範例輸出(嚴格四欄):
{
  "location": "auth.py:42",
  "issue": "SQL 字串拼接導致 SQL injection",
  "severity": "high",
  "suggested_fix": "改用參數化查詢 db.query(sql, [password])"
}
"""

review_prompt = format_example + f"\n請依相同四欄格式 review 以下 diff:\n{diff}"
重點:示範一筆「目標格式」的完整範例 → 輸出欄位一致。

技能 3  用範例區分「可接受的 code pattern」與「真正的問題」,降 false positive

遇到這個問題時用到CI reviewer 把團隊既有的 for i in range(len(items)) 慣用風格當作 bug 回報，工程師每天都要 dismiss 這類誤報，你需要讓模型學會區分「可接受的本地慣例」和「真正的問題」。

承接 Task 4.1。CI review 最惱人的是把正常寫法誤報成問題(false positive),磨掉開發者信任。解法:給一組對照範例——這種寫法是 OK 的(別報)、那種才是真 bug(要報)。讓模型學會分界,同時還能類推到沒見過的相似寫法。

# Scenario 5:對照範例,教模型分辨「可接受」vs「真問題」
contrast_examples = """
✅ 可接受(不要報):
  for i in range(len(items)):  # 專案慣用風格,非錯誤
  → 不回報。屬團隊既有 local pattern。

❌ 真問題(要報):
  result = data["key"]  # 未檢查 key 是否存在,KeyError 風險
  → 回報。severity: medium,建議用 data.get("key")。
"""

prompt = contrast_examples + f"\n依上述分界 review:\n{diff}"
重點:acceptable pattern vs genuine issue 的對照範例 → 降 false positive 又能 generalize。

技能 4  用範例示範「不同文件結構」的正確處理

遇到這個問題時用到同樣是研究論文，有的把參考文獻放在末尾、有的用 inline citation，模型在處理 inline 格式時 citations 欄位經常抽空，需要補範例讓模型認識這兩種結構。

回到 Scenario 6。同樣是「引用來源」,有的文件用 inline citation(內文括號),有的集中放 bibliography;有的把 methodology 獨立成章,有的散在內文。給模型看不同結構各該怎麼抽的範例,它才不會只認得一種版型。

# Scenario 6:示範不同文件結構下,citations 怎麼抽
structure_examples = """
結構 A(inline 引用):
  「...如 (Smith, 2024) 指出...」
  → citations: [{"author": "Smith", "year": 2024}]

結構 B(末尾參考書目):
  「References\n[1] Lee, J. (2023). ...」
  → citations: [{"author": "Lee", "year": 2023}]

結構 C(methodology 嵌在內文,非獨立章節):
  → 仍要抽出 methodology 欄位,從內文段落擷取。
"""

extract_prompt = structure_examples + f"\n抽取以下文件:\n{document}"
重點:inline vs bibliography、獨立 vs 嵌入章節,各給範例,模型才能跨結構正確抽。

技能 5  用範例修正「必填欄位被抽成空值/null」

遇到這個問題時用到某種版型的台灣發票沒有「Total」字樣、改用「應付」，你的 total_amount 必填欄位在這種版型下一律抽成 null，下游系統因此拒絕這批資料入庫。

常見故障:某種版型的文件一進來,本來該有值的必填欄位卻一律抽成 null。多半是模型沒在那種版型裡認出該欄位。對症下藥:針對那種版型補一個範例,示範該欄位其實藏在哪、該抽成什麼。

# Scenario 6:某版型 total 一直抽成 null → 補範例修正
fix_null_example = """
這種版型沒有「Total」字樣,但底部「應付:NT$3,500」就是總額。
輸入:「... 應付:NT$3,500」
正確輸出:{"total_amount": 3500, "currency": "TWD"}
(不要因為沒看到 'Total' 字樣就輸出 null)
"""

prompt = fix_null_example + f"\n抽取(total_amount 為必填):\n{document}"
重點:對「會抽成 null」的那種格式,專門補範例 → 補回必填欄位。

整個 Task 4.2 的記憶骨架

當詳細指令仍輸出不一致,改用 few-shot:示範勝過描述。寫 2~4 個範例,模糊案例要附「為何選 A 不選 B」的理由;示範目標格式(location/issue/severity/fix)、用對照範例分辨可接受 vs 真問題以降 false positive;在 Scenario 6 抽取裡,對不同文件結構、會抽成 null 的版型各補範例。核心精神:讓模型學會判斷並類推到新樣式,而非死背已列舉的案例。

考試情境題

以下三題模擬正式考試格式，每題一個生產情境，四個選項。先嘗試作答，再展開解析。

Q 1 Scenario 6 · Structured Data Extraction

You have written detailed instructions for extracting four fields from invoices: "Output a JSON object with keys: location, issue, severity, and suggested_fix. Use only 'high', 'medium', or 'low' for severity." Despite these instructions, the model produces inconsistent field ordering and sometimes omits the suggested_fix key. What is the most effective next step?

  1. Add "You must always include all four fields" to emphasize the requirement more strongly.
  2. Switch to a JSON schema enforced via tool use to guarantee field presence.
  3. Add 2–4 few-shot examples showing a complete input→output pair with all four fields correctly populated.
  4. Reduce the number of required output fields to simplify the model's task.
展開解析

Correct Answer: C

C 正確：題目的情境是「詳細指令失靈、輸出不一致」——這正是 few-shot 的典型適用場景。給模型看 2~4 個完整的 input→output 範例，讓它「看到」目標格式是什麼樣子，一致性會顯著提升，效果遠勝再加一行文字強調。

A 錯在哪：繼續加文字強調是在同一條路上疊加更多文字指令，但題目已說明「文字指令失靈」，加更多同類型指令不會改變問題根源。B 錯在哪：tool use + JSON schema 是另一個有效方向（Task 4.3），但題目問的是「most effective next step」，在已有詳細指令的情境下，few-shot 是直接針對「格式不穩定」的最小修改。D 錯在哪：減少欄位是用縮減需求來迴避問題，不解決格式不一致的根本原因。

Q 2 Scenario 6 · Structured Data Extraction

Your extraction pipeline receives documents that could be invoices, receipts, or research papers. The model must choose the correct extraction tool (extract_invoice, extract_receipt, or extract_paper_metadata), but it frequently selects the wrong tool for documents that have characteristics of more than one type. Which approach best addresses this ambiguity?

  1. Add a pre-classification step that uses keyword matching to detect document type before extraction.
  2. Provide 2–4 few-shot examples of ambiguous documents, each showing the chosen tool and the explicit reasoning for why the other tools were not selected.
  3. Create a single unified extraction tool that handles all three document types with optional fields.
  4. Increase the number of few-shot examples to 10 or more to cover all possible document variants.
展開解析

Correct Answer: B

B 正確：模糊案例（ambiguous cases）是 few-shot 最擅長處理的情境。關鍵是每個範例不只給答案，還要說明「為什麼選 A 不選 B」的推理——模型學的是判斷的尺度，而不只是查表。2~4 個範例是最有效的數量，能讓模型 generalize 到沒見過的新樣式。

A 錯在哪：keyword matching 是脆弱的 rule-based 方法，遇到新格式或混合類型文件就失效，而且無法處理真正模糊的邊界案例。C 錯在哪：合併成一個工具會失去 schema 的類型約束優勢，讓每筆抽取的結構變得不確定，反而更難驗證輸出品質。D 錯在哪：堆 10+ 個範例不代表更好——太多範例會稀釋焦點、增加 token、還可能讓模型模式匹配而非真正理解判斷邏輯；官方建議 2~4 個精選範例。

Q 3 Scenario 6 · Structured Data Extraction

Your invoice extraction pipeline works well for standard formats. However, for a specific Taiwanese supplier's invoices that use "應付" instead of "Total", the total_amount required field is consistently extracted as null, causing downstream database rejections. What is the most targeted fix?

  1. Mark total_amount as optional (nullable) so the pipeline can accept null values for this supplier.
  2. Add a format normalization rule in the prompt: "If you see '應付', treat it as the total amount."
  3. Add a few-shot example specifically for this format, showing that "應付: NT$3,500" should extract to total_amount: 3500.
  4. Pre-process all documents to replace "應付" with "Total" before sending to the extraction pipeline.
展開解析

Correct Answer: C

C 正確：針對「特定版型造成必填欄位抽成 null」的問題，最直接有效的修法是補一個針對那種版型的 few-shot 範例，示範該欄位其實藏在哪個文字之下、該抽成什麼值。這是 Task 4.2 技能 5 的核心模式。

A 錯在哪：把必填欄位改成 nullable 是「接受錯誤」而非「修正錯誤」，讓有問題的資料進入下游系統，會造成更嚴重的資料品質問題。B 錯在哪：加文字規則是指令方式，對這個特定的「文字對應問題」理論上可以，但實務上文字指令的穩定性不如 few-shot 範例；且題目情境已暗示指令方式不夠穩定。D 錯在哪：在資料進入管線前替換文字是 workaround，如果供應商格式繼續變化就需要不斷維護替換規則，而 few-shot 的泛化能力可以處理更多變體。
