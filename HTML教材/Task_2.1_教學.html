官方考綱原文

Task Statement 2.1 — Design effective tool interfaces with clear descriptions and boundaries

Knowledge of:

  • Tool descriptions as the primary mechanism LLMs use for tool selection; minimal descriptions lead to unreliable selection among similar tools
  • The importance of including input formats, example queries, edge cases, and boundary explanations in tool descriptions
  • How ambiguous or overlapping tool descriptions cause misrouting (e.g., analyze_content vs analyze_document with near-identical descriptions)
  • The impact of system prompt wording on tool selection: keyword-sensitive instructions can create unintended tool associations

Skills in:

  • Writing tool descriptions that clearly differentiate each tool's purpose, expected inputs, outputs, and when to use it versus similar alternatives
  • Renaming tools and updating descriptions to eliminate functional overlap (e.g., renaming analyze_content to extract_web_results with a web-specific description)
  • Splitting generic tools into purpose-specific tools with defined input/output contracts (e.g., splitting a generic analyze_document into extract_data_points, summarize_content, and verify_claim_against_source)
  • Reviewing system prompts for keyword-sensitive instructions that might override well-written tool descriptions
本題情境 · SCENARIO 1
Scenario 1 — Customer Support Resolution Agent

延續客服解決 agent:get_customer / lookup_order / process_refund 等工具的描述與邊界要清楚,agent 才不會在退貨或帳務情境裡選錯工具。本 Task 教的就是這份工具介面設計。

一句話抓住主軸:對 LLM 來說,工具的「描述」就是它唯一能讀懂的說明書。 描述寫得模糊、彼此重疊,模型就會選錯工具(misrouting)。這個 Task 教你把工具介面設計得讓模型「一看就知道該用哪個」。

Knowledge of · 知識點

知識 1  tool description（工具描述）是 LLM 選工具的「主要依據」

遇到這個問題時用到你的 agent 在幾個功能相似的工具之間反覆選錯，導致客戶資料被送進退款流程、訂單查詢卻呼叫了帳戶工具，你需要從根本理解 LLM 靠什麼決定呼叫哪個工具。

模型在決定要呼叫哪個工具時,主要不是看工具名稱、也不是看程式碼,而是讀工具的 description（工具描述）。description 就是模型眼中的「使用說明」。如果你只寫一句草率的描述,模型在多個相似工具之間就會選得不可靠——時對時錯。

把它想成超市貨架:標籤寫得清楚,客人一眼挑對;標籤含糊,客人就拿錯。

# ❌ 描述太少 → 模型在相似工具間選不準
get_data = {
    "name": "get_data",
    "description": "取得資料",   # 取什麼資料?從哪來?何時用?全沒講
}

# ✅ 描述完整 → 模型清楚知道用途與時機
lookup_order = {
    "name": "lookup_order",
    "description": "用訂單編號查詢單一筆訂單的狀態與明細。"
                   "輸入:order_id(字串,如 'A1023')。"
                   "查客戶資料請改用 get_customer。",
}
考點重點:description 是選工具的主要機制;描述太少 = 選擇不可靠。

知識 2  好描述要含：input format（輸入格式）、example queries（範例查詢）、boundary（邊界）與 edge cases（例外）

遇到這個問題時用到你的工具描述只寫了一句「查詢訂單」，上線後發現模型在某些特殊格式的訂單編號或「查不到結果」時行為異常，你需要知道一份完整工具描述應該包含哪些元素。

一個夠用的工具描述不是只寫「這工具做什麼」,還要把模型需要的判斷資訊都補齊:

輸入格式(input format):參數長怎樣、型別是什麼。
範例查詢(example queries):什麼樣的請求該用它。
邊界說明(boundary):什麼情況不該用它、它跟哪個工具的分工。
例外情況(edge cases):查無結果、輸入異常時會回什麼。

search_products = {
    "name": "search_products",
    "description": (
        "依關鍵字搜尋商品目錄,回傳符合的商品清單。\n"
        "輸入格式:query(字串關鍵字)、limit(整數,預設 10)。\n"
        "範例查詢:『無線耳機』、『紅色 T 恤 M 號』。\n"
        "邊界:本工具只搜『商品』;要查訂單請用 lookup_order。\n"
        "例外:查無商品時回傳空陣列 []，不是錯誤。"
    ),
}
重點:輸入格式 + 範例 + 邊界 + 例外,四件齊全,模型才不會猜。

知識 3  描述重疊會造成 misrouting（派錯工具）

遇到這個問題時用到你的系統裡有 analyze_content 和 analyze_document 兩個工具，測試時發現 agent 隨機選擇兩者之一，造成網頁內容分析與 PDF 文件分析的結果互換，你需要理解為何描述重疊是 misrouting 的根本原因。

最經典的 anti-pattern（反模式）:兩個工具描述幾乎一模一樣。例如 analyze_content 和 analyze_document 都寫「分析內容」——模型根本分不出差別,只好亂猜,把該給 A 的請求送去 B。這就是 misrouting。

# ❌ 兩個工具描述近乎相同 → 模型無法區分,派錯
analyze_content  = {"description": "分析內容並萃取資訊"}
analyze_document = {"description": "分析文件並萃取資訊"}
# 「內容」vs「文件」差在哪?模型看不出來 → misrouting

# ✅ 讓兩者用途明確分離
extract_web_results   = {"description": "萃取網路搜尋結果(輸入:search hits 清單)"}
extract_pdf_datapoints = {"description": "從 PDF 文件萃取結構化數據(輸入:檔案路徑)"}
重點:描述重疊 = misrouting 的元兇;每個工具的描述要彼此「可區分」。

知識 4  system prompt 的措辭也會影響 tool selection（工具選擇）

遇到這個問題時用到你把工具描述寫得很清楚，但 agent 在某些情況下仍固執地選同一個工具，翻查後發現 system prompt 裡有「優先分析文件」這樣的措辭，你需要了解 keyword-sensitive（對關鍵字敏感）指令如何干擾工具選擇。

就算工具描述寫得很好,system prompt 裡某些關鍵字仍可能「蓋過」它,造成意外的工具聯想。例如 system prompt 寫「優先分析文件」,模型可能一看到「文件」兩字就硬選名字含 document 的工具,即使該情境其實該用別的。這叫 keyword-sensitive（對關鍵字敏感）。

# ❌ system prompt 的關鍵字製造了不該有的工具聯想
system_prompt = "你是文件分析助理,務必先『分析文件』。"
# 模型可能一律去找名字含 document/文件 的工具,忽略更合適者

# ✅ 措辭中性,讓工具描述自己決定,不綁特定關鍵字
system_prompt = "你是研究助理。依使用者需求,挑選最合適的工具完成任務。"
重點:system prompt 的關鍵字可能覆蓋掉好工具描述,措辭要審慎。

Skills in · 技能點

技能 1  寫出能清楚區分用途、輸入輸出與「何時用」的 tool description（工具描述）

遇到這個問題時用到你被要求為客服 agent 的三個工具（get_customer、lookup_order、process_refund）撰寫描述，你需要一套實作框架來確保每個描述都能讓模型在退款與帳務情境中正確選擇。

把知識 1～2 落實:每個工具的描述都要回答四個問題——做什麼、吃什麼輸入、吐什麼輸出、何時該用它而非相似工具。最後一點(versus 相似工具)最關鍵,因為那正是模型最容易混淆的地方。

get_customer = {
    "name": "get_customer",
    "description": (
        "用 customer_id 取得單一客戶的基本資料與帳戶狀態。\n"
        "輸入:customer_id(字串)。輸出:姓名、email、會員等級、帳戶狀態。\n"
        "何時用:需要客戶『身分/帳戶』資訊時。\n"
        "何時別用:要查該客戶的訂單請用 lookup_order;要退款請用 process_refund。"
    ),
}

技能 2  改名 + 改描述，消除功能重疊

遇到這個問題時用到code review 時發現系統中有兩個名稱相近且描述幾乎相同的工具，你需要重構它們的命名與描述來徹底消除 overlap，使模型的工具選擇變得可預期。

遇到重疊工具,最直接的修法是重新命名並改寫描述,讓名字本身就帶出差異。官方範例:把含糊的 analyze_content 改名為 extract_web_results,描述也改成「網路專用」,一眼就和其他分析工具區隔開。

# 修改前:名字含糊,和其他 analyze_* 撞車
analyze_content = {"description": "分析內容"}

# 修改後:改名 + 網路專屬描述 → 不再重疊
extract_web_results = {
    "name": "extract_web_results",
    "description": "從網路搜尋回傳的結果清單中萃取重點與來源網址。"
                   "輸入:search_hits(清單)。專供『網路搜尋結果』使用。",
}
重點:改名 + 改描述 = 消除 overlap 的第一招。

技能 3  把「通用大工具」拆成「目的明確的 purpose-specific 小工具」

遇到這個問題時用到你的 analyze_document 工具被 agent 在萃取數據、摘要和查證三種場景中隨機呼叫，造成輸出格式不一致，你需要將它拆解成有明確 input/output contract（輸入/輸出契約）的子工具。

一個 analyze_document 想包山包海(萃取數據、摘要、查證),反而讓模型不知何時用。官方做法:拆成三個各有明確輸入/輸出契約的小工具——extract_data_points(取數據)、summarize_content(摘要)、verify_claim_against_source(對原文查證)。各司其職,選擇就明確。

# ❌ 一個通用工具,什麼都做 → 模型不知何時用
analyze_document = {"description": "分析文件(萃取/摘要/查證都行)"}

# ✅ 拆成三個目的單一、契約明確的小工具
extract_data_points = {
    "description": "從文件萃取結構化數據點。輸入:doc。輸出:鍵值清單。"}
summarize_content = {
    "description": "把文件濃縮成重點摘要。輸入:doc。輸出:摘要文字。"}
verify_claim_against_source = {
    "description": "檢核某主張是否能在原文找到佐證。輸入:claim, doc。輸出:布林 + 引文。"}
重點:通用工具拆成 purpose-specific 小工具,每個有明確 input/output 契約。

技能 4  審查 system prompt，揪出 keyword-sensitive（對關鍵字敏感）的指令

遇到這個問題時用到工具描述重構完成、單元測試全過，但上線後特定流程仍發生 misrouting，你懷疑問題出在 system prompt，需要一套審查清單找出會蓋過工具描述的措辭。

對應知識 4 的實作:設計完工具後,回頭檢查 system prompt,看有沒有「對關鍵字敏感」的指令會把模型硬導向某工具。把這類措辭改成中性、以任務為準,讓寫得好的工具描述真正發揮作用。

# 審查清單:system prompt 是否藏有 keyword-sensitive 指令?
checks = [
    "是否出現會綁定特定工具名的關鍵字(如『文件』硬指向 document 工具)?",
    "是否用『務必先用 X』之類措辭,蓋過工具描述的判斷?",
    "指令是否描述『任務目標』而非『指定某工具』?",
]
# 結論:措辭描述目標、保持中性 → 交給工具描述決定該用哪個
重點:好工具描述會被壞 system prompt 蓋掉;審查 prompt 是收尾必做。

整個 Task 2.1 的記憶骨架

對 LLM 來說,工具描述就是說明書:寫得太少或彼此重疊就會 misrouting。好描述要含輸入格式、範例、邊界、例外,並講清「何時用它 vs 相似工具」。修法三招:改名改描述消重疊、把通用工具拆成目的明確的小工具、回頭審查 system prompt 避免關鍵字蓋過好描述。

考試情境題

以下三題模擬正式考試格式，每題一個生產情境，四個選項。先嘗試作答，再展開解析。

Q 1 Scenario 1 · Customer Support Resolution Agent

A customer support agent has two tools: get_customer (described as "retrieves customer information") and lookup_order (described as "retrieves order information"). In production, when a user says "I need help with my recent purchase," the agent calls get_customer instead of lookup_order about 40% of the time. Logs confirm the tool descriptions are the only difference between the two tool configs. What is the most likely root cause?

  1. The model's context window is too small to process both tool descriptions simultaneously.
  2. The two tool descriptions are too similar and lack boundary explanations, so the model cannot reliably distinguish between them.
  3. The system prompt is not instructing the model to prefer lookup_order for purchase-related queries.
  4. The get_customer tool is listed first in the tools array, causing the model to select it by position bias.
展開解析

Correct Answer: B

兩個工具的描述都只寫了籠統的「retrieves X information」，完全沒有說明各自的輸入格式、使用時機或與對方的邊界。模型看不出差異，只能在兩者之間隨機猜測，導致約 40% 的情況選錯。

A 錯在哪：兩個工具的描述都很短，context window 完全足夠，問題不在長度。C 錯在哪：system prompt 確實可影響工具選擇，但題目明確說「tool descriptions are the only difference」，且加入 keyword instruction 並非解決描述不清的根本辦法。D 錯在哪：LLM 工具選擇不是依陣列順序，而是依描述內容語義匹配，沒有「位置偏好」機制。

Q 2 Scenario 1 · Customer Support Resolution Agent

An architect is redesigning a generic analyze_document tool that currently handles data extraction, summarization, and claim verification all in one. In testing, the agent frequently calls it for the wrong sub-task and produces misformatted outputs. Which change best addresses this issue?

  1. Add a mode parameter to analyze_document with values "extract", "summarize", and "verify" so the agent can specify intent.
  2. Improve the single tool's description to list all three capabilities with detailed examples of each use case.
  3. Split analyze_document into three purpose-specific tools — extract_data_points, summarize_content, and verify_claim_against_source — each with a clear input/output contract.
  4. Add a routing layer in the system prompt that maps user intent keywords to the correct tool mode.
展開解析

Correct Answer: C

通用大工具（generic tool）包山包海是根本問題。把它拆成三個 purpose-specific 小工具，每個都有明確的 input/output contract，模型就能根據任務需求精確選擇，輸出格式也自然對應。這正是官方範例中的推薦做法。

A 錯在哪：加 mode 參數只是把問題從「選哪個工具」變成「填什麼 mode」，模型仍然需要判斷正確的 mode，沒有解決根本的歧義問題。B 錯在哪：在一個工具裡把三種用途都列出來，反而讓描述更長、更難閱讀，模型的決策複雜度不降反升。D 錯在哪：system prompt routing 是 keyword-sensitive 的 anti-pattern，容易被用戶措辭影響，且維護成本高，不如在工具介面層解決問題。

Q 3 Scenario 1 · Customer Support Resolution Agent

After an architect refactors all tool descriptions to be specific and non-overlapping, a new issue emerges: whenever the system prompt contains the phrase "always analyze the customer's document first," the agent calls analyze_document even for queries that only require looking up an order status. Tool descriptions are correct. What is the most effective approach to fix this?

  1. Remove analyze_document from the tool list for order-status queries and add it back only for document-related queries.
  2. Rewrite the system prompt to use neutral, task-goal-oriented language instead of keyword instructions that reference specific tool names or actions.
  3. Add a negative example to analyze_document's description that explicitly says "do not use for order status lookups."
  4. Increase the temperature setting so the model is less likely to rigidly follow the system prompt instruction.
展開解析

Correct Answer: B

System prompt 裡的「always analyze the customer's document first」是 keyword-sensitive 指令——模型一看到「document」或「analyze」就被觸發，蓋過了工具描述的判斷。正確解法是把 system prompt 改成中性的任務目標描述（如「根據使用者需求選擇最合適的工具」），讓工具描述自己發揮作用。

A 錯在哪：動態調整工具清單在技術上可行但架構複雜，且 root cause 是 system prompt 措辭，不是工具清單問題。C 錯在哪：在工具描述加排除說明是好習慣，但當 system prompt 強制導向某工具時，工具描述的 negative example 難以抵抗，治標不治本。D 錯在哪：調高 temperature 增加隨機性，會讓整體工具選擇更不穩定，是完全錯誤的方向。
