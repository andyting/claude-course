Task Statement 4.5 — Design efficient batch processing strategies

Knowledge of:

  • The Message Batches API: 50% cost savings, up to 24-hour processing window, no guaranteed latency SLA
  • Batch processing is appropriate for non-blocking, latency-tolerant workloads (overnight reports, weekly audits, nightly test generation) and inappropriate for blocking workflows (pre-merge checks)
  • The batch API does not support multi-turn tool calling within a single request (cannot execute tools mid-request and return results)
  • custom_id fields for correlating batch request/response pairs

Skills in:

  • Matching API approach to workflow latency requirements: synchronous API for blocking pre-merge checks, batch API for overnight/weekly analysis
  • Calculating batch submission frequency based on SLA constraints (e.g., 4-hour windows to guarantee 30-hour SLA with 24-hour batch processing)
  • Handling batch failures: resubmitting only failed documents (identified by custom_id) with appropriate modifications (e.g., chunking documents that exceeded context limits)
  • Using prompt refinement on a sample set before batch-processing large volumes to maximize first-pass success rates and reduce iterative resubmission costs
本題情境 · SCENARIO 5
Scenario 5 — Claude Code for Continuous Integration

把 Claude Code 接進 CI/CD。本 Task 教你判斷哪種工作該走「同步 API」、哪種該走「批次 API」:擋在 merge 前的 pre-merge check 必須同步、立刻回;而 nightly 測試產生、weekly audit 這類「能等」的工作就走 Message Batches API 省一半成本。範例都用 CI 場景的 nightly test generation / weekly audit / pre-merge review。

一句話抓住主軸:「能不能等」決定走哪條 API——擋路的(pre-merge)要同步、即時;不擋路的(overnight / weekly)走批次,省 50% 成本、容忍最長 24 小時的處理窗口。

Knowledge of · 知識點

知識 1  Message Batches API:省 50% 成本、最長 24 小時窗口、不保證延遲 SLA

批次 API 的三個核心數字務必記牢:成本省 50%、處理窗口最長 24 小時、沒有延遲保證(no latency SLA)。你把一大堆請求一次丟進去,Anthropic 在 24 小時內某個時間點處理完——可能 20 分鐘,也可能 23 小時,不保證。換來的是半價。

考點重點:50% cost savings、up to 24-hour window、no guaranteed latency SLA,三件一組。

知識 2  批次適合「不擋路、能等」的工作,不適合「擋路」的工作

判斷的關鍵是這份工作會不會擋住別人。在 CI 場景:nightly 報表、weekly 程式碼稽核、夜間自動產測試——這些是non-blocking、latency-tolerant,完美適合批次。反過來,pre-merge check(開發者按下 merge、要等結果才能合併)是 blocking,不能等批次跑一整天,必須走同步 API。

重點:overnight reports / weekly audits / nightly test generation → 批次;pre-merge checks → 同步。

知識 3  批次 API 不支援「單一請求內」的多輪 tool calling

很常被忽略的限制。批次是「丟進去、跑完拿回來」的單程任務,無法在請求進行中執行工具、拿到結果、再繼續。所以需要 agent 來回呼叫工具的工作流(例如客服 agent 邊查訂單邊回應)不能用批次。批次只適合「一次輸入 → 一次輸出」的單程抽取/分析。

重點:batch 不支援 mid-request 的多輪 tool calling;要邊跑邊用工具請走同步。

知識 4  custom_id:對應批次請求與回應的「身分證」

批次回來是一大包、順序不保證,你要靠每筆請求自帶的 custom_id 把回應對回原始請求。所以送出前一定要給每筆一個唯一的 custom_id(例如 "pr-1042-fileA"),回來才知道哪筆對應哪個檔。它也是後面「只重送失敗那幾筆」的關鍵。

重點:custom_id = 請求/回應配對的唯一鍵,也是失敗重送時定位的依據。

Skills in · 技能點

技能 1  按延遲需求選 API:pre-merge 走同步、夜間/每週分析走批次

把「會不會擋路」變成程式決策。CI pipeline 裡:pre-merge review 必須立刻回結果,走同步 messages.create;nightly test generation 整晚都能跑,走 messages.batches.create 省一半。

import anthropic
client = anthropic.Anthropic()

# Scenario 5:依「會不會擋 merge」決定走哪條 API
def run_ci_job(job_type, prompt):
    if job_type == "pre_merge_review":
        # ✅ 擋路、要立刻回 → 同步 API
        return client.messages.create(
            model="claude-sonnet-4-6",
            max_tokens=2048,
            messages=[{"role": "user", "content": prompt}],
        )
    else:  # nightly_test_gen / weekly_audit
        # ✅ 不擋路、能等 → 批次 API,省 50%
        return "queued_to_batch"
重點:blocking → synchronous;latency-tolerant → batch。判準是「會不會擋住開發者」。

技能 2  依 SLA 反推批次「提交頻率」

常考的計算題型。批次處理最長 24 小時,若你對下游承諾 30 小時 SLA,那就有 30 − 24 = 6 小時的緩衝;為了保險,改用 4 小時提交一次,等於最壞情況 4(等湊批)+ 24(處理)= 28 小時 < 30,SLA 守得住。核心公式:提交間隔 + 24h 處理 ≤ 承諾 SLA。

# Scenario 5:weekly audit 對下游承諾 30 小時 SLA
# 批次最長處理 = 24h,需保留湊批等待的緩衝
BATCH_MAX_HOURS = 24
TARGET_SLA_HOURS = 30

# 提交間隔上限 = SLA − 批次處理上限
max_submit_interval = TARGET_SLA_HOURS - BATCH_MAX_HOURS  # = 6h

# 取 4h(留安全邊際):最壞 4 + 24 = 28h < 30h ✅
submit_interval_hours = 4
assert submit_interval_hours + BATCH_MAX_HOURS <= TARGET_SLA_HOURS
重點:提交間隔 + 24h(批次處理上限)≤ 承諾 SLA;4h 窗口可守 30h SLA。

技能 3  處理批次失敗:用 custom_id 只重送「失敗那幾筆」並修正

批次裡有少數請求失敗(例如某個檔超過 context 上限),不要整批重跑。用 custom_id 找出失敗的那幾筆,只針對它們做修正(例如把過大的文件切塊 chunking),再重送這一小批。省成本、也省時間。

# Scenario 5:nightly test gen 批次回來,挑出失敗的只重送
results = client.messages.batches.results(batch_id)

retry = []
for r in results:
    if r.result.type == "errored":
        # 用 custom_id 定位原始文件
        doc = source_docs[r.custom_id]
        if r.result.error.type == "context_length":
            # ✅ 超長 → 切塊後重送,而非整批重跑
            retry += chunk_document(doc, r.custom_id)
        else:
            retry.append(build_request(doc, r.custom_id))

if retry:
    client.messages.batches.create(requests=retry)  # 只重送失敗的
重點:失敗只重送、靠 custom_id 定位;超 context 的就 chunking 後再送。

技能 4  大量批次前,先在「樣本集」上精修 prompt,拉高首次成功率

成本優化的關鍵心法。批次量很大時,若 prompt 沒調好,失敗率高 → 一直重送 → 成本反而暴增。正確流程:先抽一小撮樣本同步試跑、精修 prompt,把 first-pass 成功率拉到夠高,再把調好的 prompt 套到整個大批次。先小後大,降低反覆重送的代價。

# Scenario 5:weekly audit 跑全量前,先在樣本上精修 prompt
sample = all_repos[:20]   # 抽 20 個 repo 當樣本

# 1) 同步試跑樣本,量測 first-pass 成功率
success = evaluate(sample, prompt_v1)
if success < 0.95:
    prompt_v1 = refine_prompt(prompt_v1)   # 調到夠穩再放大

# 2) 用調好的 prompt 才送全量批次,降低重送成本
requests = [build_request(r, prompt_v1) for r in all_repos]
client.messages.batches.create(requests=requests)
重點:先樣本精修 prompt → 拉高 first-pass 成功率 → 再跑全量,省下反覆重送成本。

整個 Task 4.5 的記憶骨架

批次的取捨是「用延遲換成本」:Message Batches API 省 50%、窗口最長 24h、不保證延遲。判準是「會不會擋路」——pre-merge 擋路走同步;overnight / weekly / nightly 不擋路走批次。批次不支援單請求內多輪 tool calling。每筆帶 custom_id 做配對,失敗就只重送那幾筆(超長則 chunking)。算提交頻率:提交間隔 + 24h ≤ SLA(4h 守 30h)。跑大量前先在樣本上精修 prompt,拉高首次成功率、省重送錢。
