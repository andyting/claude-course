Task Statement 1.3 — Configure subagent invocation, context passing, and spawning

Knowledge of:

  • The Task tool as the mechanism for spawning subagents, and the requirement that allowedTools must include "Task" for a coordinator to invoke subagents
  • That subagent context must be explicitly provided in the prompt—subagents do not automatically inherit parent context or share memory between invocations
  • The AgentDefinition configuration including descriptions, system prompts, and tool restrictions for each subagent type
  • Fork-based session management for exploring divergent approaches from a shared analysis baseline

Skills in:

  • Including complete findings from prior agents directly in the subagent's prompt (e.g., passing web search results and document analysis outputs to the synthesis subagent)
  • Using structured data formats to separate content from metadata (source URLs, document names, page numbers) when passing context between agents to preserve attribution
  • Spawning parallel subagents by emitting multiple Task tool calls in a single coordinator response rather than across separate turns
  • Designing coordinator prompts that specify research goals and quality criteria rather than step-by-step procedural instructions, to enable subagent adaptability
本題情境 · SCENARIO 3
Scenario 3 — Multi-Agent Research System

延續多代理研究系統:coordinator 用 Task 工具 spawn 出 web 搜尋、文件分析、綜合等 subagent,並把前一個 agent 的完整 findings 寫進下一個的 prompt。本 Task 的 subagent 呼叫、context 傳遞與 spawning,就是這個系統的運作機制。

一句話抓住主軸:Coordinator（coordinator，協調者）要叫出 subagent（子代理）幫忙時,有幾件事系統不會幫你自動做——你必須親手做。 這個 Task 的所有考點,都繞著「哪些事不會自動發生」轉。

Knowledge of · 知識點

知識 1  Task 工具是 spawn（衍生）subagent（子代理）的機制,且 allowedTools 必須含 "Task"

遇到這個問題時用到你的 coordinator agent 在程式碼中呼叫了 Task 工具，但執行時卻報錯說無法呼叫 subagent，排查後發現 coordinator 的設定中根本沒有授予 Task 工具的使用權限。

subagent 不是用特別的 API 生出來的,而是 coordinator 呼叫一個叫 Task 的工具把它叫出來。關鍵卡關點:如果你沒有在 coordinator 的 allowedTools 裡放 "Task",coordinator 就沒有權限呼叫 subagent——它連叫人幫忙的能力都沒有。

這跟現實很像:你想找助理,但公司沒給你「召喚助理」這個權限,你再聰明也叫不動人。

# coordinator 的設定
coordinator_config = {
    "system_prompt": "你是研究協調者,負責拆解問題並派發給子代理。",
    # ↓ 沒有 "Task",coordinator 就無法 spawn 任何 subagent
    "allowedTools": ["Task", "Read", "WebSearch"],
}

# 反例:少了 "Task" → 想呼叫 subagent 時會失敗
broken_config = {
    "system_prompt": "...",
    "allowedTools": ["Read", "WebSearch"],   # ❌ 無法 spawn subagent
}
考點重點:spawn 的機制 = Task 工具;前提 = allowedTools 要有 "Task"。

知識 2  subagent 的 context 必須在 prompt 裡明白給

遇到這個問題時用到綜合 subagent 被呼叫後回傳了毫無針對性的通用摘要，因為 prompt 只寫了「請根據前面的搜尋結果做總結」，而 subagent 根本看不到「前面的結果」是什麼。

這是整個 Task 1.3 最重要、最常考的一條。

subagent 被叫出來時,腦袋是空的。它看不到 coordinator 之前的對話、看不到別的 subagent 找到的資料、兩次呼叫之間也不會記得彼此。你想讓它知道什麼,就得寫進它的 prompt 裡。

# ❌ 錯誤:以為 subagent 會自己知道前面查到的東西
def spawn_synthesis_agent_wrong():
    return Task(
        agent="synthesis",
        prompt="請根據前面的搜尋結果做總結。"  # 「前面的」是什麼?它根本看不到
    )

# ✅ 正確:把需要的資料整包塞進 prompt
def spawn_synthesis_agent_right(search_results, doc_analysis):
    prompt = f"""請綜合以下資料寫出總結。

[網路搜尋結果]
{search_results}

[文件分析結果]
{doc_analysis}
"""
    return Task(agent="synthesis", prompt=prompt)
一句話記住:subagent 是「失憶的」,context 要用手餵。

知識 3  AgentDefinition:每種 subagent 的 description、system prompt、工具限制

遇到這個問題時用到搜尋 subagent 被發現嘗試呼叫了寫檔工具，導致資料被意外覆蓋；事後檢查發現所有 subagent 都共用同一份 AgentDefinition，沒有按職責限制各自的工具存取權。

每一種 subagent 你都先「定義」好它是誰、能做什麼。三個欄位:

description:這個 agent 做什麼的(coordinator 靠它判斷該不該派任務給它)。
system prompt:它的角色與行為規範。
工具限制:它只准用哪些工具(最小權限原則——搜尋 agent 不該有寫檔權限)。

agent_definitions = {
    "search": {
        "description": "負責網路搜尋,蒐集外部資料來源",
        "system_prompt": "你是搜尋專員,只負責找資料,不做判斷。",
        "allowedTools": ["WebSearch"],          # 只給搜尋,不給寫檔
    },
    "analysis": {
        "description": "分析文件內容,萃取重點與引用出處",
        "system_prompt": "你是分析師,負責閱讀並萃取關鍵資訊。",
        "allowedTools": ["Read", "Grep"],
    },
    "synthesis": {
        "description": "綜合各方資料,產出最終結論",
        "system_prompt": "你是綜合撰寫者,整合資料寫成完整答案。",
        "allowedTools": [],                     # 不需要工具,純推理
    },
}
重點:不同 subagent 用不同 AgentDefinition,並按需要限制工具。

知識 4  Fork-based session:從同一基線 fork（分岔）,探索不同方向

遇到這個問題時用到你想比較兩種程式碼重構方案的優劣，但每次要切換方案就得重新分析整份程式碼基線，浪費大量時間；你需要一種機制從同一份分析出發、獨立往兩個方向走。

有時你想「從同一個起點,試兩三條不同的路」。Fork 就是把目前的 session 狀態複製分岔,各自獨立往下走,互不干擾。共用前面的基線,但後面各走各的。

例如:程式碼已經分析到一半(基線),你想分別試「重構方案 A」「重構方案 B」——fork 出兩條,各自探索,最後比較。

# 已建立共同基線(例如已完成程式碼分析)
baseline = session.analyze("review_codebase")

# 從同一基線分岔成兩條獨立 session
branch_a = baseline.fork(name="approach_A")   # 探索方案 A
branch_b = baseline.fork(name="approach_B")   # 探索方案 B

branch_a.run("用策略模式重構")
branch_b.run("用工廠模式重構")
# 兩條互不影響,最後比較結果
重點:fork = 共用基線、獨立分岔,用來比較不同方向。(與 Task 1.7 的 fork_session 呼應。)

Skills in · 技能點

技能 1  把前面 agent 的完整 findings 直接寫進 subagent 的 prompt

遇到這個問題時用到綜合 subagent 產出的報告只引用了部分搜尋結果，遺漏了文件分析的重要發現，因為呼叫時只傳入了搜尋結果而沒有把文件分析輸出一起塞進 prompt。

這是知識 2 的實作版。把搜尋結果、文件分析結果整包交給 synthesis subagent。注意是「完整」findings,不是摘要——你截斷了,它就少看到那些資訊。

def run_pipeline(query):
    search_out = Task(agent="search", prompt=f"搜尋:{query}").result
    doc_out    = Task(agent="analysis", prompt=f"分析相關文件:{query}").result

    # 把兩邊的完整產出都塞進 synthesis 的 prompt
    synthesis_prompt = f"""根據以下資料,回答:{query}

=== 搜尋結果 ===
{search_out}

=== 文件分析 ===
{doc_out}
"""
    return Task(agent="synthesis", prompt=synthesis_prompt).result

技能 2  用結構化格式分開「內容」與「metadata」,保住出處

遇到這個問題時用到最終報告中的引用標註錯誤，synthesis subagent 把來自不同來源的數據混在一起標了錯誤的 URL，因為傳入時所有資料都是純文字，出處和內容沒有分離。

傳 context（對話歷史）時,別把來源網址、文件名、頁碼跟內文混成一坨純文字。用結構化格式(像 dict / JSON),內容歸內容、出處歸出處（attribution，可追溯出處）。這樣 synthesis agent 才能在最後正確標註「這句話出自哪裡」。

# ❌ 內容和出處混成一團,synthesis 無法可靠標來源
bad = "AI 市場成長很快(來源:某報告 第12頁 https://...)"

# ✅ 結構化:content 與 metadata 分離
finding = {
    "content": "AI 市場 2025 年成長 35%。",
    "metadata": {
        "source_url": "https://example.com/report",
        "document_name": "2025 AI 市場報告",
        "page": 12,
    },
}

# 傳給下一個 agent 時,出處完整保留,可被正確引用
findings = [finding, ...]
synthesis_prompt = f"資料如下(含出處):\n{json.dumps(findings, ensure_ascii=False, indent=2)}"
重點:content 與 metadata 分開 → 保住 attribution(可追溯出處)。

技能 3  平行 spawn:在「同一個 coordinator response」裡發出多個 Task

遇到這個問題時用到研究系統需要並行搜尋五個子題，但實作後發現執行時間是單一搜尋的五倍，排查後發現 coordinator 是一輪一輪地發 Task，每次等回來才發下一個，退化成了序列執行。

這條的細節很重要,常考。要平行跑多個 subagent,做法是在同一次 coordinator 的回應裡,一口氣發出多個 Task 工具呼叫——而不是分成好幾輪(turn),一輪叫一個。同一回應發多個 = 平行;分好幾輪 = 變成序列(慢)。

# ✅ 平行:同一個 response 裡同時發出多個 Task → 並行執行
def coordinator_response_parallel(subtopics):
    return [
        Task(agent="search", prompt=f"研究子題:{t}")
        for t in subtopics
    ]   # 多個 Task 一次回傳 → 同時跑

# ❌ 序列:一輪只發一個,等它回來再發下一個 → 慢
def coordinator_sequential(subtopics):
    results = []
    for t in subtopics:
        results.append(Task(agent="search", prompt=f"研究:{t}").result)  # 等待
    return results
重點:平行 = 一個 response 內發多個 Task;分多輪 = 退化成序列。

技能 4  coordinator prompt 給「目標與品質標準」,而非「逐步指令」

遇到這個問題時用到搜尋 subagent 在面對非預期的搜尋結果時完全卡住，因為 prompt 的逐步指令規定了「取前 5 筆、抓第一段」，但這次結果格式不同，它不知道怎麼應對。

最後一條是設計哲學。寫給 subagent 的 coordinator prompt,應該說「我要達成什麼、好的標準長怎樣」,而不是手把手規定「第一步做 X、第二步做 Y」。給目標,subagent 才能依現場狀況自己調整(adaptability);給死步驟,它就只會照本宣科,遇到意外就卡住。

# ❌ 逐步指令:綁死流程,subagent 無法應變
procedural = """
1. 搜尋關鍵字「電動車」
2. 取前 5 筆
3. 每筆抓第一段
4. 串起來回傳
"""

# ✅ 目標 + 品質標準:讓 subagent 自行決定怎麼達成
goal_based = """
研究目標:電動車市場 2025 的主要趨勢。
品質標準:
- 至少涵蓋 3 個獨立來源
- 需含市場規模與成長率數據
- 標明每項數據的出處
做法由你判斷,以達成上述標準為準。
"""
重點:給目標與標準(可適應)> 給逐步指令(僵化)。

整個 Task 1.3 的記憶骨架

Coordinator 用 Task 工具(allowedTools 要有 "Task")叫出 subagent;subagent 是失憶的,所有 context 都要手動寫進 prompt(完整 findings、結構化保住出處);要平行就在同一 response 發多個 Task;prompt 給目標而非死步驟;需要比較不同方向時用 fork 從共同基線分岔。

考試情境題

以下三題模擬正式考試格式，每題一個生產情境，四個選項。先嘗試作答，再展開解析。

Q 1 Scenario 3 · Multi-Agent Research System

A coordinator agent is configured with allowedTools: ["Read", "WebSearch"]. When it attempts to invoke a synthesis subagent using the Task tool, the invocation fails at runtime. What is the most likely root cause?

  1. The synthesis subagent's AgentDefinition does not include a description field, so the coordinator cannot determine when to invoke it.
  2. The coordinator's allowedTools list does not include "Task", so it lacks permission to spawn subagents.
  3. The synthesis subagent's prompt does not contain the required context from prior agents, causing a validation error.
  4. The coordinator is attempting to invoke the subagent from a separate turn rather than a single response, which is not supported.
展開解析

Correct Answer: B

在 Claude Agent SDK 中，coordinator 呼叫 subagent 的唯一機制是 Task 工具。如果 coordinator 的 allowedTools 設定中沒有包含 "Task"，它就沒有「召喚 subagent」的權限，任何 Task 工具呼叫都會在執行時失敗。這是最直接、最典型的設定錯誤。

A 錯在哪：AgentDefinition 的 description 欄位協助 coordinator 判斷何時派任務，缺少它可能影響路由邏輯，但不會導致呼叫機制本身在 runtime 失敗。C 錯在哪：prompt 缺少 context 會讓 subagent 回傳不佳的結果，但不會造成呼叫本身失敗——subagent 還是會被執行，只是輸出品質差。D 錯在哪：要實現平行執行才需要在同一 response 發多個 Task；從不同 turn 發 Task 只是變成序列而非平行，並不會導致失敗。

Q 2 Scenario 3 · Multi-Agent Research System

A research pipeline spawns three search subagents for different subtopics and measures total latency. Despite running on high-capacity infrastructure, the pipeline takes three times longer than a single subagent call. Code review shows the coordinator issues each Task call only after receiving the previous subagent's result. What is the most effective change to reduce latency?

  1. Increase the timeout setting for each subagent call to allow more processing time per task.
  2. Reduce the amount of context passed to each subagent to decrease token processing overhead.
  3. Emit all three Task tool calls within a single coordinator response so they execute in parallel rather than sequentially.
  4. Merge the three subtopics into a single comprehensive prompt sent to one subagent to eliminate coordination overhead.
展開解析

Correct Answer: C

要讓多個 subagent 並行執行，做法是在 coordinator 的「同一次回應」中一口氣發出多個 Task 工具呼叫。系統會同時執行它們，總延遲接近單一呼叫的時間。目前的問題是 coordinator 每輪只發一個 Task 並等待回傳，這讓三個本可並行的任務退化成序列，總延遲變成三倍。

A 錯在哪：增加 timeout 不解決序列執行的根本問題，只是讓每個步驟允許更長時間，總延遲不會縮短反而可能更長。B 錯在哪：減少 context 是 token 最佳化的考量，與序列 vs. 並行的架構問題無關，無法改善延遲三倍的根本原因。D 錯在哪：把三個子題塞給一個 subagent 會導致 attention dilution（注意力稀釋），且放棄了專業分工的好處；問題是並行化架構，不應該用合併任務來解決。

Q 3 Scenario 3 · Multi-Agent Research System

A synthesis subagent produces a report with incorrect citations — source URLs are attributed to the wrong data points. Reviewing the coordinator code shows that search results were passed to the synthesis subagent as a single plain-text string with sources mixed inline. What change best addresses this attribution failure?

  1. Instruct the synthesis subagent via system prompt to be more careful about matching citations to content.
  2. Pass context using a structured format (e.g., a list of dicts) that separates content from metadata such as source URL, document name, and page number.
  3. Limit the synthesis subagent's tools so it cannot access external URLs and must rely only on provided text.
  4. Run the synthesis subagent twice and compare outputs to detect inconsistent citations.
展開解析

Correct Answer: B

當內容和出處混成純文字時，synthesis subagent 需要靠語義推斷來判斷哪段文字對應哪個來源，這種機率性的比對極易出錯。改用結構化格式（如 dict / JSON list），讓每一筆資料的 content 和 metadata（source_url、document_name、page）明確對應，subagent 可以精確保留並標註出處，attribution 問題從根本上被解決。

A 錯在哪：在 system prompt 叮嚀 subagent「要小心」是機率性做法，無法保證它正確識別混在純文字中的出處歸屬；根本問題在資料傳遞格式，不在 subagent 的謹慎程度。C 錯在哪：限制工具存取與引用標註的準確性毫無關係；subagent 引用的是傳入的資料，不是它主動去抓取的外部資源。D 錯在哪：跑兩次只能發現不一致，無法修復根本的格式問題；如果格式有歧義，兩次跑出來可能各自有不同的錯誤引用。
