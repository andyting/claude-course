官方考綱原文

Task Statement 4.1 — Design prompts with explicit criteria to improve precision and reduce false positives

Knowledge of:

  • The importance of explicit criteria over vague instructions (e.g., "flag comments only when claimed behavior contradicts actual code behavior" vs "check that comments are accurate")
  • How general instructions like "be conservative" or "only report high-confidence findings" fail to improve precision compared to specific categorical criteria
  • The impact of false positive rates on developer trust: high false positive categories undermine confidence in accurate categories

Skills in:

  • Writing specific review criteria that define which issues to report (bugs, security) versus skip (minor style, local patterns) rather than relying on confidence-based filtering
  • Temporarily disabling high false-positive categories to restore developer trust while improving prompts for those categories
  • Defining explicit severity criteria with concrete code examples for each severity level to achieve consistent classification
本題情境 · SCENARIO 5
Scenario 5 — Claude Code for Continuous Integration

把 Claude Code 接進 CI 做自動 code review。重點不是「找更多問題」,而是設計能給可行動回饋、降低 false positive 的 prompt——因為一旦 reviewer 常誤報,工程師就不再信任它的留言。本 Task 教你怎麼用明確標準取代模糊指令,把誤報壓下來。

一句話抓住主軸:提升精準、降誤報靠的是「明確的分類標準」,不是「叫它保守一點」。把「報什麼、跳過什麼」用具體準則寫死;誤報高的類別先暫時關掉以挽回信任;每個 severity 都配具體 code 範例,讓分級一致。

Knowledge of · 知識點

知識 1  explicit criteria（明確標準）> 模糊指令

遇到這個問題時用到你的 CI reviewer 每次 PR 都噴出大量「可能不準確」的 comment，工程師抱怨訊噪比太低、開始無視所有留言，你需要讓模型只在真正矛盾時才標記。

提升精準度的根本:把指令具體化、可判定。官方對照超經典——「只在註解宣稱的行為與實際程式行為相矛盾時才標記」遠勝於「檢查註解是否準確」。前者給了一條清楚的判定線(矛盾才報),後者全憑模型自由心證,什麼都可能被當成「不準確」。這正是 explicit criteria（明確標準）的威力。

# ❌ 模糊:全憑自由心證 → 誤報一堆
claude -p "review 這份 diff,檢查註解是否準確。"

# ✅ 明確:給可判定的標準 → 只報真矛盾
claude -p "review 這份 diff。只有當『註解宣稱的行為』
與『程式實際行為』相矛盾時才標記該註解;
單純不夠詳細、風格問題,不要報。"
考點重點:「矛盾才標記」這類可判定標準 > 「檢查是否準確」這類模糊指令。

知識 2  「保守一點」「只報高信心」這類通則無效

遇到這個問題時用到你已在 prompt 加了「be conservative, only report high-confidence findings」，但 false positive 率幾乎沒降，team lead 要求你找出真正有效的調整方向。

很多人想靠調語氣降 false positive（假陽性）:「be conservative」「only report high-confidence findings」。考點明說:這些通則無法真正提升精準度,因為它們沒告訴模型「具體哪一類該報、哪一類不報」——模型還是用自己的標準判斷,只是嘴上更謹慎。真正有效的是具體的分類準則(categorical criteria)。

# ❌ 信心式過濾:沒有可操作的界線
claude -p "review 時保守一點,只回報高信心的問題。"
# → 模型仍自由心證,誤報照樣發生

# ✅ 改用具體分類準則
claude -p "只回報:① 會造成錯誤行為的 bug
② 安全漏洞(注入、認證繞過)。
不報:命名偏好、可讀性建議、本地慣例。"
重點:"be conservative" / "high-confidence" 是信心式過濾,無效;要用具體 categorical criteria。

知識 3  false positive 會侵蝕信任,還會拖累準確的類別

遇到這個問題時用到metrics 顯示 security findings 的 dismiss 率突然從 10% 跳到 60%，但 security 類別的 prompt 根本沒動過，你需要解釋為什麼信任崩塌以及如何止血。

關鍵後果:某一類誤報太高,工程師會連帶不信任其他準確的類別。一旦 reviewer 留言常常是雜訊,大家就學會「直接無視」——這時連它真的抓到的嚴重 bug 也被一起跳過。所以降誤報不只是品質問題,更是維持整套自動 review 可信度的問題。

考點重點:高 false positive 的類別會拉低開發者對「準確類別」的整體信任,導致真問題也被忽略。

Skills in · 技能點

技能 1  寫明確 review 準則:界定「報什麼 / 跳過什麼」

遇到這個問題時用到你要從頭設計 CI code review 的 prompt，需要決定要把哪些問題類別列入「必報」、哪些列入「略過」，讓模型有清楚的判定邊界而非靠自由心證。

知識 1、2 的落點。與其靠信心過濾,不如直接列要報(bug、安全)與要跳過(小風格、本地慣例)的清單。在 Scenario 5 的 CI review,這份準則就是 prompt 的核心。

# ✅ CI review prompt:明列 report vs skip
git diff origin/main...HEAD | claude -p "
你是 CI 的 code reviewer。
【要回報】
  - bug:會導致錯誤輸出 / 例外 / 資料損毀
  - security:注入、認證/授權繞過、機密外洩
【要跳過】
  - 次要風格(命名、排版、import 順序)
  - 不影響行為的本地慣例
依此準則 review 下方 diff。"
重點:用「report(bug/security)vs skip(minor style/local pattern)」的具體清單,取代信心式過濾。

技能 2  暫時關掉高誤報類別,先把信任救回來

遇到這個問題時用到「可讀性建議」類別誤報爆炸，工程師開始把整個 bot 的留言全部 dismiss，連真正的 security bug 都被無視，你需要立即行動但又不能一夜之間修好所有 prompt。

當某一類(例如「可讀性建議」)誤報失控、工程師開始無視整個 bot 時,務實做法:先把那一類關掉,讓 reviewer 只留下精準的類別、恢復信任;同時在背景慢慢改善那一類的 prompt,改好再開回來。先止血,再修因。

# ✅ 暫時停用高誤報類別,挽回信任
git diff origin/main...HEAD | claude -p "
本輪 review 暫時【停用】可讀性/風格類建議
(該類誤報過高、正在重寫準則)。
只回報 bug 與 security,兩類都附可行動的修法。"
# → 留言乾淨、可信;待風格準則改好再重新啟用
重點:高 false-positive 類別先暫時 disable 救信任,同時離線改 prompt,改好再上。

技能 3  為每個 severity（嚴重程度）配具體 code 範例,讓分級一致

遇到這個問題時用到同一個 SQL injection 問題這次被分到 critical、下次被分到 high，下游 ticket 系統因此漏掉優先處理，你需要讓 severity 分級在所有 PR 上保持一致。

要讓「critical / high / medium / low」每次分級都一致,光給形容詞不夠,要為每一級附具體的 code 範例。模型有了錨點,分類才穩定,不會同一種問題這次 high 下次 low。

# ✅ 每個 severity 配具體範例 → 分級一致
git diff origin/main...HEAD | claude -p "
依下列 severity 定義分類 findings:
  critical 例:SQL 字串拼接造成注入 → execute(f'... {user}')
  high     例:未檢查的 None 解參照 → user.id 但 user 可能為 None
  medium   例:吞掉例外只 log,未向上拋
  low      例:magic number 未具名常數
" --json-schema review_schema.json
重點:每個 severity 都給具體 code 範例當錨點 → classification 一致、可重現。

整個 Task 4.1 的記憶骨架

在 Scenario 5 設計 CI code review 的 prompt,核心是用明確標準提升精準、降低 false positive:① 明確標準 > 模糊指令——「註解與實際行為矛盾才標記」勝過「檢查註解是否準確」;② 「保守一點 / 只報高信心」這類信心式通則無效,要改用具體 categorical criteria;③ 記住高誤報會侵蝕信任,還拖累準確類別。三個技能:寫明列 report(bug/security)vs skip(minor style) 的準則;誤報失控時先暫時關掉該類別救信任、再離線改 prompt;為每個 severity 配具體 code 範例讓分級一致。

考試情境題

以下三題模擬正式考試格式，每題一個生產情境，四個選項。先嘗試作答，再展開解析。

Q 1 Scenario 5 · Claude Code for Continuous Integration

Your CI pipeline uses Claude to review every PR. The reviewer currently uses the instruction: "Check that all comments are accurate." Developers report that 70% of flagged comments are false positives — Claude flags comments that are slightly imprecise but not actually wrong. Which prompt change is most likely to reduce false positives?

  1. Add "be conservative and only flag issues you are highly confident about" to the existing instruction.
  2. Replace the instruction with "flag a comment only when the behavior it describes directly contradicts the actual code behavior."
  3. Lower the model temperature to make outputs more deterministic.
  4. Add "only report high-severity issues" to filter out minor comment problems.
展開解析

Correct Answer: B

B 正確：「只在宣稱行為與實際行為相矛盾時才標記」給了一條清楚的可判定邊界（矛盾才報），模型不需要自由心證「什麼叫準確」，false positive 率會顯著下降。這正是 explicit criteria（明確標準）的核心原則。

A 錯在哪：「be conservative / high-confidence」是信心式通則（confidence-based filtering），沒有告訴模型哪一類問題該報、哪一類不該報，模型還是用自己的尺度判斷，誤報率不會真正改善。C 錯在哪：temperature 控制輸出隨機性，與 false positive 的分類邊界無關，改 temperature 解決不了「哪種問題該報」的定義問題。D 錯在哪：「只報高嚴重度」改變的是 severity 過濾，不是 comment accuracy 的判定邏輯，仍然沒有定義「什麼算矛盾」。

Q 2 Scenario 5 · Claude Code for Continuous Integration

Your CI reviewer reports bugs, security issues, and readability suggestions. Developers have started dismissing all bot comments after the readability category produced numerous false positives for weeks. Security findings are now also being ignored. You need to restore trust quickly. What is the most effective immediate action?

  1. Rewrite the readability prompt criteria with more specific rules and redeploy immediately.
  2. Temporarily disable the readability category from the prompt while keeping bug and security reporting active, then refine the readability criteria offline.
  3. Reduce the total number of findings per PR to no more than three, regardless of category.
  4. Switch to a more capable model that has lower intrinsic false positive rates.
展開解析

Correct Answer: B

B 正確：先暫時停用高誤報的可讀性類別（disable high false-positive category），讓 reviewer 只留下精準的 bug/security 類別，立刻讓留言恢復可信度；同時在背景離線改善可讀性 prompt，改好再重新啟用。這是「先止血、再修因」的務實做法。

A 錯在哪：立刻重寫並重部署代表這段時間誤報還在繼續傷害信任，且「立刻重寫」不代表新版本就一定準確，沒有先隔離高誤報類別的緩衝步驟。C 錯在哪：限制每次最多三條 finding 是數量過濾，不解決根本問題——那三條裡仍可能都是 readability 誤報，信任問題依然存在。D 錯在哪：換模型不是針對性解法；問題出在 prompt 對「可讀性」的定義模糊，換更強的模型也只是用更自信的方式誤報同樣類型的問題。

Q 3 Scenario 5 · Claude Code for Continuous Integration

Your CI reviewer classifies findings as critical, high, medium, or low. Engineers report that the same SQL injection pattern is sometimes rated "critical" and sometimes "high" across different PRs, causing inconsistent ticket priority in the downstream issue tracker. What change best addresses this inconsistency?

  1. Ask the model to explain its severity reasoning in each finding so engineers can manually re-classify.
  2. Collapse critical and high into a single "blocking" category to eliminate ambiguity between the two levels.
  3. Add concrete code examples for each severity level to the prompt — e.g., "critical: SQL string concatenation causing injection → execute(f'...{user}')".
  4. Run the reviewer twice and take the higher severity rating when the two runs disagree.
展開解析

Correct Answer: C

C 正確：為每個 severity（嚴重程度）附上具體的 code 範例當「錨點（anchor）」，模型在分類時有了明確的參照對象，就不會在邊界案例上左右搖擺。範例示範比文字描述更能穩定分類行為，確保相同類型的問題每次都落在同一個 severity 級別。

A 錯在哪：要求模型解釋理由只是讓不一致變得可見，沒有解決分類不一致的根本原因；還把重新分類的負擔轉給工程師，增加人工成本。B 錯在哪：合併 critical/high 是用「縮減分類數」迴避問題，不是解決分類不一致；而且會讓下游系統失去優先級區分能力。D 錯在哪：取兩次中較高的 severity 是一種噪音放大策略，會讓 severity 整體往高偏移，不能讓分級穩定，也沒有對齊「哪種問題該算 critical」的定義。
