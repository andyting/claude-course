Task Statement 3.6 — Integrate Claude Code into CI/CD pipelines

Knowledge of:

  • The -p (or --print) flag for running Claude Code in non-interactive mode in automated pipelines
  • --output-format json and --json-schema CLI flags for enforcing structured output in CI contexts
  • CLAUDE.md as the mechanism for providing project context (testing standards, fixture conventions, review criteria) to CI-invoked Claude Code
  • Session context isolation: why the same Claude session that generated code is less effective at reviewing its own changes compared to an independent review instance

Skills in:

  • Running Claude Code in CI with the -p flag to prevent interactive input hangs
  • Using --output-format json with --json-schema to produce machine-parseable structured findings for automated posting as inline PR comments
  • Including prior review findings in context when re-running reviews after new commits, instructing Claude to report only new or still-unaddressed issues to avoid duplicate comments
  • Providing existing test files in context so test generation avoids suggesting duplicate scenarios already covered by the test suite
  • Documenting testing standards, valuable test criteria, and available fixtures in CLAUDE.md to improve test generation quality and reduce low-value test output
本題情境 · SCENARIO 5
Scenario 5 — Claude Code for Continuous Integration

把 Claude Code 接進 CI/CD:每次 PR 自動跑 code review、產測試、給回饋。在無人值守的 pipeline 裡,必須用 -p 跑非互動模式、用 --json-schema 把結果變成機器可解析的 JSON 直接貼成 inline PR comment,並用 CLAUDE.md 餵專案規範。本 Task 全程貼這個情境。

一句話抓住主軸:CI 裡的 Claude Code 必須「非互動、輸出結構化、有專案脈絡、且 review 要獨立」。四件事:-p 防卡住、--json-schema 出機器可讀結果、CLAUDE.md 餵脈絡、review 用獨立 instance 而非寫程式的同一個 session。

Knowledge of · 知識點

知識 1  -p / --print:在自動化 pipeline（管線）裡跑非互動模式（non-interactive mode）

遇到這個問題時用到你把 Claude Code 加進 GitHub Actions workflow，但 CI job 每次都在等待使用者輸入而超時卡死，整條 pipeline 跑不完，你需要知道哪個 flag 能讓它在無人值守環境中正常執行。

互動模式的 Claude Code 會等你輸入;但 CI 沒有人坐在前面。-p(或 --print)讓它跑非互動模式:讀 prompt、做完事、印出結果就結束,不會停下來等輸入而把整條 pipeline 卡死(hang)。這是把 Claude Code 接進 CI 的第一個前提。

# ❌ CI 裡用互動模式 → 等不到輸入,job 卡死逾時
# claude        # 進入互動 REPL,在 CI 永遠 hang

# ✅ 用 -p 跑非互動,做完即結束
claude -p "review 本次 PR 的 diff,找出 bug 與安全問題。"
# 適合放進 GitHub Actions / GitLab CI 的 step
考點重點:-p / --print = 非互動模式,防止 CI job 等輸入而 hang。

知識 2  --output-format json + --json-schema:在 CI pipeline（管線）強制結構化輸出

遇到這個問題時用到你的 CI review job 每次輸出的發現（findings）格式不一致，有時是條列，有時是段落，導致自動貼 PR inline comment 的腳本無法 parse，你需要強制輸出可被程式讀取的固定結構。

CI 需要把 Claude 的發現程式化處理(例如貼成 PR comment),所以輸出不能是自由散文。--output-format json 讓它輸出 JSON;--json-schema 再用一個 schema 把欄位、型別、嚴重度等級鎖死,確保每次都長一樣、可被腳本 parse。

重點:--output-format json 出 JSON;--json-schema 把結構鎖死 → 機器可解析。

知識 3  CLAUDE.md file（CLAUDE.md 檔）:把專案脈絡餵給 CI 觸發的 Claude Code

遇到這個問題時用到CI 自動產生的測試完全不符合團隊的規範——建議了大量沒有意義的 getter/setter 測試，卻沒有覆蓋任何 edge case，你需要一個機制把測試標準和可用 fixture 告訴 CI 裡的 Claude。

CI 裡的 Claude 沒有你腦中的專案常識。CLAUDE.md 就是把這些脈絡寫下來的機制:測試標準(testing standards)、fixture 慣例、review 準則(review criteria)。CI 觸發 Claude Code 時會讀到它,產測試、做 review 才會貼合團隊規範,而不是亂槍打鳥。

重點:用 CLAUDE.md 寫下 testing standards / fixture 慣例 / review criteria,餵給 CI 的 Claude。

知識 4  session context 隔離:寫程式的 session 不適合 review 自己的改動（anti-pattern 反模式）

遇到這個問題時用到你發現 CI 的 code review 幾乎從不找出問題，尤其是由同一個 Claude Code session 寫完程式碼後立刻做 review 時，你需要了解為什麼這種做法有根本性的偏見問題以及如何修正。

關鍵觀念:同一個產生程式碼的 Claude session,review 自己的改動時會比較弱。因為它已經帶著「當初為何這樣寫」的偏見,容易為自己的決定辯護、看不到盲點。正解是用獨立的 review instance——乾淨脈絡、沒有立場,才能客觀挑錯。這就像人也不該 review 自己剛寫完的 code。

# ❌ 同一 session 寫完又自評 → 帶偏見,漏看盲點
# claude -p "寫這個功能" ... 接著同一 session "順便 review"

# ✅ review 用獨立 instance,乾淨脈絡客觀挑錯
claude -p "你是獨立 reviewer,沒寫過這段 code。
review 以下 diff,只看正確性與安全。" < pr.diff
考點重點:review 用獨立 instance,別讓寫程式的同一 session 評自己的改動。

Skills in · 技能點

技能 1  在 CI pipeline（管線）用 -p 非互動模式（non-interactive mode）跑,避免互動輸入把 job 卡死

遇到這個問題時用到你在 GitLab CI 的 pipeline 步驟中加入 Claude Code review，但每次 job 都在 "Waiting for input..." 狀態超時，你需要找到讓 Claude Code 在無人看管的 CI 環境下自動執行並退出的方法。

知識 1 的落點。把 review/測試產生包進一個 CI step,一律加 -p。

# .github/workflows/review.yml(片段)
# - name: Claude PR review
#   run: |
# ✅ -p 非互動,從 stdin 餵 diff,不會 hang
git diff origin/main...HEAD | \
  claude -p "review 這份 diff,找 bug 與安全問題。"

技能 2  用 JSON + schema 產機器可讀發現,自動貼成 inline PR comment（pipeline 管線整合）

遇到這個問題時用到你想讓 CI 的 code review 結果直接以 inline comment 形式貼在 PR 的對應行上，而不是一整段文字，你需要讓 Claude Code 的輸出能被腳本 parse 並逐筆對應到檔案行號。

知識 2 的實作核心。定一個 schema(每筆 finding 有 file、line、severity、message),用 --json-schema 強制輸出,再讓腳本逐筆貼成 inline comment。

# review_schema.json:鎖死每筆 finding 的結構
{
  "findings": [{
    "file": "str", "line": "int",
    "severity": "critical|high|medium|low",
    "message": "str"
  }]
}

# ✅ 強制結構化輸出 → 腳本逐筆貼 inline PR comment
git diff origin/main...HEAD | claude -p \
  "review 此 diff,回報 findings。" \
  --output-format json --json-schema review_schema.json \
  | post_inline_comments.py
重點:--output-format json + --json-schema → 穩定 JSON → 腳本自動貼 inline comment。

技能 3  重跑 review 時帶入先前 findings,只回報「新的或仍未處理」的問題（anti-pattern 反模式：重複留言）

遇到這個問題時用到工程師推了一個新 commit，CI 的 review job 重跑後把上一輪已經修好的問題又重新貼了一遍，整個 PR 充滿重複的 inline comment，你需要讓 review 只報告真正新的問題。

知識 4 衍生的實戰痛點:新 commit 進來重跑 review,若不帶上一輪結果,會把已經貼過的問題重複貼一次,洗版又煩人。做法:把上輪 findings 放進 context,並明確指示「只回報新出現或仍未處理的」。

# ✅ 帶上輪 findings,避免重複留言
git diff origin/main...HEAD | claude -p \
  "這是新 commit 後的 diff。下面是上一輪 review 的
findings(JSON)。只回報『新出現』或『仍未修正』的問題,
已解決的不要再提,也不要重貼舊留言。" \
  --json-schema review_schema.json \
  --append-context prev_findings.json
重點:重跑 review 帶入 prior findings,指示只報 new / still-unaddressed,避免 duplicate comment。

技能 4  產測試時帶入既有測試檔（allowlist 允許清單 context）,避免建議重複的測試情境

遇到這個問題時用到CI 的自動測試生成每次都建議大量已經存在的測試情境，工程師得手動刪掉重複的，浪費時間，你需要讓 Claude 知道哪些情境已經被覆蓋了。

讓 Claude 在 CI 產測試時,先把現有測試檔放進 context。否則它會建議一堆已經被覆蓋過的情境,徒增 noise。帶進去後,它能補的是真正缺的 case。

# ✅ 帶既有測試 → 只補沒覆蓋到的情境
claude -p "為 cart.py 新增測試。
下方是現有 test_cart.py,別重複已覆蓋的情境,
只補尚未測到的 edge case。" \
  --append-context tests/test_cart.py

技能 5  在 CLAUDE.md file（CLAUDE.md 檔）寫測試標準、有價值的測試準則與可用 fixture

遇到這個問題時用到CI 自動產測試的品質每次都讓 reviewer 不滿意——太多無意義的測試、從不用團隊已有的 mock_payment fixture——你需要把團隊的測試哲學和可用工具寫進 Claude 每次都會讀到的設定檔裡。

知識 3 的落點。把測試標準、什麼算「有價值的測試」、有哪些 fixture 可用寫進 CLAUDE.md,CI 產測試時品質更高、low-value 的測試更少。

# CLAUDE.md(測試章節範例)
## Testing standards
# - 用 pytest;每個 public function 至少一個 happy path + 一個 edge
# - 有價值的測試:覆蓋邊界與錯誤路徑,不為 getter/setter 寫測試
# - 可用 fixtures:db_session、sample_order、mock_payment
# → CI 觸發的 Claude Code 讀到後,產出貼合規範、少廢測試
重點:testing standards + valuable test criteria + fixtures 寫進 CLAUDE.md → 測試品質升、低價值輸出降。

整個 Task 3.6 的記憶骨架

在 Scenario 5 把 Claude Code 接進 CI/CD,記四件事:① 用 -p / --print 跑非互動模式,別讓 job 等輸入而 hang;② 用 --output-format json + --json-schema 產機器可解析的 findings,腳本自動貼成 inline PR comment;③ 用 CLAUDE.md 寫下 testing standards / fixture 慣例 / review criteria,把專案脈絡餵給 CI 的 Claude;④ review 要獨立 instance,因為寫程式的同一 session 評自己的改動會帶偏見。兩個實戰細節:重跑 review 帶 prior findings 只報 new/unaddressed 避免重複留言;產測試帶既有測試檔避免重複情境。

考試情境題

以下三題模擬正式考試格式，每題一個生產情境，四個選項。先嘗試作答，再展開解析。

Q 1 Scenario 5 · Claude Code for Continuous Integration

A team integrates Claude Code into their GitHub Actions CI pipeline to automate PR code reviews. The pipeline step runs claude "review the diff for bugs and security issues" without any flags. Every CI job times out after 10 minutes at the "Waiting for user input" stage. What is the root cause and the correct fix?

  1. Claude Code requires a CLAUDE.md file to operate in CI environments; add a CLAUDE.md with review criteria to the repository to enable non-interactive mode.
  2. Claude Code defaults to interactive mode and waits for user input; add the -p (or --print) flag to run in non-interactive mode so the job completes without waiting for input.
  3. The GitHub Actions runner lacks sufficient permissions; grant the workflow write access to the repository to allow Claude Code to run.
  4. Claude Code cannot run in CI without --output-format json; add this flag to produce machine-readable output and prevent the hang.
展開解析

Correct Answer: B

-p（--print）是讓 Claude Code 在無人值守的 CI 環境中運行的第一個必要條件：它告訴 Claude Code 採用非互動模式（non-interactive mode），讀完 prompt、執行完任務、印出結果後即自動退出，不等待任何輸入。

A 錯在哪：CLAUDE.md 提供的是專案脈絡（testing standards、review criteria），可以提升輸出品質，但不是解決「等輸入卡死」問題的機制。C 錯在哪：CI 卡在等輸入是 Claude Code 自身的互動模式問題，不是 runner 的權限問題。D 錯在哪：--output-format json 控制的是輸出格式，對於防止 hang 沒有任何作用，沒有 -p 的情況下加 JSON 格式旗標仍會等輸入。

Q 2 Scenario 5 · Claude Code for Continuous Integration

A team's CI pipeline runs Claude Code to review PRs and post findings as inline comments. After a developer pushes a second commit to address three of five reported issues, the CI re-runs the review and posts the same five issues again — including the three that were already fixed. Engineers are frustrated by duplicate comments cluttering the PR. What change to the CI invocation best addresses this?

  1. Use a separate independent Claude instance for each review run to ensure there is no shared session context that could carry over stale findings.
  2. Include the previous review's findings in context and instruct Claude to report only new or still-unaddressed issues, avoiding duplicate comments.
  3. Switch from --output-format json to plain text output so the review script can detect and filter duplicate lines before posting.
  4. Delete all existing inline comments before each CI review run so there are no duplicates from previous passes.
展開解析

Correct Answer: B

正確做法是在重跑 review 時把上一輪的 findings 放進 context，並明確指示「只回報新出現或仍未修正的問題，已解決的不要再提」。這樣 Claude 有了對照基準，能判斷哪些問題真的解決了，只輸出增量的發現。

A 錯在哪：用獨立 instance 是正確的 review 實踐（避免寫程式的 session 評自己），但這不是解決重複留言的方法，獨立 instance 沒有上輪 findings 仍會重複回報所有問題。C 錯在哪：切換到純文字格式更難 parse，不能解決邏輯層面的「重複回報已修問題」問題，還破壞了結構化輸出的優勢。D 錯在哪：刪除舊留言後重貼所有問題，對已解決的 issue 又新貼一次通知，讓工程師要二次確認哪些是真的新問題，反而更煩。

Q 3 Scenario 5 · Claude Code for Continuous Integration

A team uses Claude Code in CI to automatically generate tests for new code in pull requests. Engineers report that 60% of the suggested tests duplicate scenarios already covered in the existing test suite, and the remaining tests are mostly for getters and setters rather than meaningful edge cases. The project has a CLAUDE.md but it only contains code style rules. What two changes would most effectively improve test generation quality?

  1. Add --output-format json to the test generation command so the output is structured, and switch to plan mode so Claude designs the test strategy before writing tests.
  2. Include the existing test files in context so Claude avoids duplicating covered scenarios, and add testing standards, valuable test criteria, and available fixtures to CLAUDE.md to guide quality.
  3. Use a separate independent review instance after test generation to evaluate whether the suggested tests are valuable before posting them to the PR.
  4. Move the test generation step to after code review is complete, so Claude has more context about what the correct implementation looks like before writing tests.
展開解析

Correct Answer: B

這題需要同時解決兩個問題：①「重複情境」→ 把現有測試檔放進 context，讓 Claude 知道哪些已被覆蓋；②「低價值測試」→ 在 CLAUDE.md 寫下「什麼算有價值的測試（邊界與錯誤路徑）、有哪些 fixture 可用」，CI 觸發的 Claude 讀到後才能產出貼合規範的測試。兩項改動各解一個問題，組合起來正好對症。

A 錯在哪：--output-format json 改變輸出格式，對測試品質沒有影響；plan mode 適合架構決策任務，不是提升測試品質的工具。C 錯在哪：加一個 review 步驟可以過濾低品質測試，但這是事後篩選而非從源頭提升品質，而且 review 本身也需要脈絡才能判斷測試是否有價值。D 錯在哪：調整步驟順序無法解決「重複情境」或「低價值測試」的根本問題，因為即使在 code review 之後，Claude 仍不知道現有測試覆蓋了什麼。
