官方考綱原文

Task Statement 3.5 — Apply iterative refinement techniques for progressive improvement

Knowledge of:

  • Concrete input/output examples as the most effective way to communicate expected transformations when prose descriptions are interpreted inconsistently
  • Test-driven iteration: writing test suites first, then iterating by sharing test failures to guide progressive improvement
  • The interview pattern: having Claude ask questions to surface considerations the developer may not have anticipated before implementing
  • When to provide all issues in a single message (interacting problems) versus fixing them sequentially (independent problems)

Skills in:

  • Providing 2-3 concrete input/output examples to clarify transformation requirements when natural language descriptions produce inconsistent results
  • Writing test suites covering expected behavior, edge cases, and performance requirements before implementation, then iterating by sharing test failures
  • Using the interview pattern to surface design considerations (e.g., cache invalidation strategies, failure modes) before implementing solutions in unfamiliar domains
  • Providing specific test cases with example input and expected output to fix edge case handling (e.g., null values in migration scripts)
  • Addressing multiple interacting issues in a single detailed message when fixes interact, versus sequential iteration for independent issues
本題情境 · SCENARIO 2
Scenario 2 — Code Generation with Claude Code

團隊用 Claude Code 寫程式、重構、除錯、寫文件。當你下的指令太模糊、產出不穩定時,你不會一次次重貼長篇 prose,而是用幾個迭代技巧:給具體 input/output 範例、先寫測試再餵失敗、讓 Claude 先訪談你。本 Task 教這幾招逐步逼近正確結果。

一句話抓住主軸:不要靠「再講清楚一點」的散文,要靠範例、測試、與提問來逼近正確。四個技巧:具體 I/O 範例、test-driven 迭代、interview pattern、以及「互相牽動的問題一次講、獨立的問題分次修」。

Knowledge of · 知識點

知識 1  具體 input/output 範例,是溝通「期望轉換」最有效的方式

當你用散文(prose)描述「我要把這個轉成那個」,Claude 常會各次解讀不一致——因為自然語言本身有歧義。最有效的解法不是把描述寫得更長,而是直接給 2~3 組具體的 input → output 範例,讓期望的轉換「演」給它看。

Scenario 2 的例子:你要 Claude 寫一個把雜亂日期字串正規化的函式,光說「正規化日期」會做出五花八門的結果。給範例就一目了然。

# ❌ 散文描述:解讀不一致
# claude -p "寫一個函式把日期字串正規化成標準格式"
# → "標準格式" 到底是哪種?每次產出可能都不一樣

# ✅ 給具體 input/output 範例
claude -p "寫 normalize_date(s),依下列範例對應:
  '2026/6/9'   -> '2026-06-09'
  'Jun 9 2026' -> '2026-06-09'
  '9-6-2026'   -> '2026-06-09'
"
考點重點:prose 解讀不一致時,改用具體 input/output 範例溝通期望轉換。

知識 2  test-driven 迭代:先寫測試,再用「失敗」引導逐步改善

另一個強力技巧:先把測試套件寫出來(描述期望行為),讓 Claude 實作;若沒過,就把測試失敗的訊息餵回去當下一輪的引導。失敗訊息是極精準的回饋——它告訴 Claude 「哪個 case 錯、錯成什麼」,比你再用散文解釋有效得多。一輪輪 share failures,產出逐步收斂。

重點:test suite 先行 → 跑失敗 → 把 failure 餵回 → 收斂。失敗訊息是最精準的迭代回饋。

知識 3  interview pattern:讓 Claude 先發問,挖出你沒想到的考量

進入陌生領域時,你常常不知道自己漏了什麼。interview pattern 是:在開始實作前,先請 Claude 對你提問,把你沒預期到的設計考量(例如 cache 失效策略、各種 failure mode)逼出來。先問清楚再寫,勝過寫完才發現缺角。

# ✅ interview pattern:先問再做
claude -p "在動手實作這個快取層之前,先問我 5~8 個問題,
釐清:cache 失效策略、過期時間、併發寫入、
失敗時要 fail-open 還是 fail-closed。
等我回答完,再開始寫。"
# → Claude 反問 → 你補齊考量 → 才實作,少踩坑
重點:陌生領域先讓 Claude 提問(cache 失效、failure mode...),把隱藏考量攤開再實作。

知識 4  何時「一次講完」vs「分次修」:看問題彼此是否牽動

修多個問題時要分流:若幾個問題互相牽動(改 A 會影響 B 的修法),要在同一則詳細訊息裡一次講完,讓 Claude 通盤考量、一起解;若幾個問題彼此獨立,則逐一分次修,每次聚焦一個、回饋更乾淨。誤把牽動的問題拆開修,常會出現「修了 A 又弄壞 B」的來回。

考點重點:interacting(互相牽動)→ 一則訊息一起講;independent(獨立)→ 分次依序修。

Skills in · 技能點

技能 1  產出不穩時,給 2~3 組具體 input/output 範例

知識 1 的落點。當自然語言描述產生不一致結果,別再加形容詞,直接補範例。2~3 組通常就足以把轉換規則釘死。

# 任務:把使用者輸入的金額字串轉成分(cents)整數
# ✅ 用 2~3 組範例釘死規則
claude -p "實作 to_cents(s),依範例:
  '$12.50' -> 1250
  '12'     -> 1200
  '0.99'   -> 99
這些範例就是規格,不一致時以範例為準。"

技能 2  先寫涵蓋行為/邊界/效能的測試,再餵失敗迭代

知識 2 的實作。測試要涵蓋三類:預期行為、邊界 case、效能要求。先寫好讓 Claude 實作,跑出失敗就把 failure 貼回。

# 步驟一:先寫測試(行為 + 邊界 + 效能)
def test_parse():
    assert parse("a,b,c") == ["a","b","c"]   # 行為
    assert parse("") == []                  # 邊界:空字串
    assert parse("a,,c") == ["a","","c"]  # 邊界:空欄

# 步驟二:跑失敗 → 把 failure 餵回 Claude
claude -p "test_parse 的第 3 個 assert 失敗,
got ['a','c'],expected ['a','','c']。修正 parse 保留空欄。"
重點:測試先行,涵蓋行為/邊界/效能;迭代靠 share failures,不靠重講。

技能 3  用 interview pattern 在陌生領域先攤開設計考量

知識 3 的落點。官方點名範例:cache invalidation 策略、各種 failure mode——這類「你不問就不會浮現」的決策,讓 Claude 先訪談你。

# ✅ 陌生領域:先 interview,再實作
claude -p "我要做訊息重試佇列,但這領域我不熟。
動手前,先針對 cache 失效、重試上限、
冪等性、訊息順序保證 這幾點問我問題,
逐一釐清後再寫程式。"

技能 4  用具體測試案例修邊界(如 migration script 的 null 值)

知識 1 與 2 的合體用法:修 edge case 時,給具體的 input 與 expected output。官方範例就是 migration script 遇到 null 值的處理。

# edge case:migration script 遇到欄位為 null
# ✅ 給具體 input/expected 修邊界
claude -p "migrate() 在 email 欄為 null 時崩潰。
修正:input  {id:7, email:null}
      expect {id:7, email:'', migrated:true}
其他非 null 行為不變,並補一個 null 的測試。"

技能 5  判斷:互相牽動的問題一則訊息講完,獨立的問題分次修

知識 4 的實戰。下面兩種錯誤示範與正解,直接對照。

# ❌ 牽動的問題卻拆開修:改了重試又破壞了去重
# 訊息1:加重試  訊息2:加去重 → 兩者衝突,來回返工

# ✅ interacting:一則訊息一起講,讓它通盤設計
claude -p "重試與去重會互相影響:重試不可重複送已處理訊息。
請在同一套設計裡一起解決:重試上限、去重鍵、
兩者如何協調。"

# ✅ independent:彼此無關 → 分次各修各的
# 例:修 typo + 加 log 等級設定 → 分兩次,回饋更乾淨
重點:會互相影響 → 同一則詳細訊息一起解;互不相干 → 分次依序修。

整個 Task 3.5 的記憶骨架

在 Scenario 2 改善 Claude Code 產出,不靠「再講清楚的散文」,而靠四招逐步精煉:① 產出不一致時給 2~3 組具體 input/output 範例,讓轉換規則被範例釘死;② test-driven 迭代——先寫涵蓋行為/邊界/效能的測試,再把 test failure 餵回引導收斂;③ 陌生領域先用 interview pattern 讓 Claude 提問,攤開 cache 失效、failure mode 等隱藏考量;④ 修多個問題看牽動關係:互相牽動 → 一則訊息一起講,獨立 → 分次依序修。修 edge case(如 migration 的 null)同樣用具體 input/expected 來釘。
