Task Statement 3.5 — Apply iterative refinement techniques for progressive improvement

Knowledge of:

  • Concrete input/output examples as the most effective way to communicate expected transformations when prose descriptions are interpreted inconsistently
  • Test-driven iteration: writing test suites first, then iterating by sharing test failures to guide progressive improvement
  • The interview pattern: having Claude ask questions to surface considerations the developer may not have anticipated before implementing
  • When to provide all issues in a single message (interacting problems) versus fixing them sequentially (independent problems)

Skills in:

  • Providing 2-3 concrete input/output examples to clarify transformation requirements when natural language descriptions produce inconsistent results
  • Writing test suites covering expected behavior, edge cases, and performance requirements before implementation, then iterating by sharing test failures
  • Using the interview pattern to surface design considerations (e.g., cache invalidation strategies, failure modes) before implementing solutions in unfamiliar domains
  • Providing specific test cases with example input and expected output to fix edge case handling (e.g., null values in migration scripts)
  • Addressing multiple interacting issues in a single detailed message when fixes interact, versus sequential iteration for independent issues
本題情境 · SCENARIO 2
Scenario 2 — Code Generation with Claude Code

團隊用 Claude Code 寫程式、重構、除錯、寫文件。當你下的指令太模糊、產出不穩定時,你不會一次次重貼長篇 prose,而是用幾個迭代技巧:給具體 input/output 範例、先寫測試再餵失敗、讓 Claude 先訪談你。本 Task 教這幾招逐步逼近正確結果。

一句話抓住主軸:不要靠「再講清楚一點」的散文（prose），要靠範例、測試、與提問來逼近正確。四個技巧:具體 I/O 範例（few-shot 少樣本）、test-driven（測試驅動）迭代、interview pattern（訪談模式）、以及「互相牽動的問題一次講、獨立的問題分次修」（iterative refinement 迭代精煉）。

Knowledge of · 知識點

知識 1  具體 input/output 範例,是溝通「期望轉換」最有效的方式

遇到這個問題時用到你請 Claude 寫一個「把各種格式日期字串正規化」的函式，但每次產出的目標格式都不一樣——有時輸出 MM/DD/YYYY，有時輸出 YYYY-MM-DD，你需要一個更精確的方式來釘死期望的轉換規則。

當你用散文（prose）描述「我要把這個轉成那個」,Claude 常會各次解讀不一致——因為自然語言本身有歧義。最有效的解法不是把描述寫得更長,而是直接給 2~3 組具體的 input → output 範例,讓期望的轉換「演」給它看。

Scenario 2 的例子:你要 Claude 寫一個把雜亂日期字串正規化的函式,光說「正規化日期」會做出五花八門的結果。給範例就一目了然。

# ❌ 散文描述:解讀不一致
# claude -p "寫一個函式把日期字串正規化成標準格式"
# → "標準格式" 到底是哪種?每次產出可能都不一樣

# ✅ 給具體 input/output 範例
claude -p "寫 normalize_date(s),依下列範例對應:
  '2026/6/9'   -> '2026-06-09'
  'Jun 9 2026' -> '2026-06-09'
  '9-6-2026'   -> '2026-06-09'
"
考點重點:prose 解讀不一致時,改用具體 input/output 範例溝通期望轉換。

知識 2  test-driven（測試驅動）迭代:先寫測試,再用「失敗」引導逐步改善

遇到這個問題時用到你的 CSV parser 實作已經是第三次重寫，每次 Claude 的版本都能通過你描述的 case 但遺漏邊界情況，你需要一個方法讓每次迭代都有明確的通過/失敗依據而不是靠文字描述。

另一個強力技巧:先把測試套件寫出來(描述期望行為),讓 Claude 實作;若沒過,就把測試失敗的訊息餵回去當下一輪的引導。失敗訊息是極精準的回饋——它告訴 Claude 「哪個 case 錯、錯成什麼」,比你再用散文解釋有效得多。一輪輪 share failures,產出逐步收斂。

重點:test suite 先行 → 跑失敗 → 把 failure 餵回 → 收斂。失敗訊息是最精準的迭代回饋。

知識 3  interview pattern（訪談模式）:讓 Claude 先發問,挖出你沒想到的考量

遇到這個問題時用到你要實作一個分散式快取層但對這個領域不熟，擔心 Claude 直接下手時會遺漏 cache invalidation 策略或 fail-open/fail-closed 等關鍵設計決策，你需要讓 Claude 先問清楚再寫。

進入陌生領域時,你常常不知道自己漏了什麼。interview pattern 是:在開始實作前,先請 Claude 對你提問,把你沒預期到的設計考量(例如 cache 失效策略、各種 failure mode)逼出來。先問清楚再寫,勝過寫完才發現缺角。

# ✅ interview pattern:先問再做
claude -p "在動手實作這個快取層之前,先問我 5~8 個問題,
釐清:cache 失效策略、過期時間、併發寫入、
失敗時要 fail-open 還是 fail-closed。
等我回答完,再開始寫。"
# → Claude 反問 → 你補齊考量 → 才實作,少踩坑
重點:陌生領域先讓 Claude 提問(cache 失效、failure mode...),把隱藏考量攤開再實作。

知識 4  何時「一次講完」vs「分次修」:看問題彼此是否牽動

遇到這個問題時用到你發現系統同時有重試邏輯 bug 和訊息去重邏輯 bug，你不確定是否該分兩次修：你需要判斷這兩個問題是否互相牽動，因為分開修可能讓修重試的那次把去重搞壞。

修多個問題時要分流:若幾個問題互相牽動(改 A 會影響 B 的修法),要在同一則詳細訊息裡一次講完,讓 Claude 通盤考量、一起解;若幾個問題彼此獨立,則逐一分次修,每次聚焦一個、回饋更乾淨。誤把牽動的問題拆開修,常會出現「修了 A 又弄壞 B」的來回。

考點重點:interacting(互相牽動)→ 一則訊息一起講;independent(獨立)→ 分次依序修。

Skills in · 技能點

技能 1  產出不穩時,給 2~3 組具體 input/output 範例（few-shot 少樣本）

遇到這個問題時用到Claude 寫的貨幣轉換函式有時把 "$12.50" 轉成 12.50（浮點數）有時轉成 1250（整數分），每次重試結果都不穩定，你需要用具體的 I/O 範例把期望行為釘死。

知識 1 的落點。當自然語言描述產生不一致結果,別再加形容詞,直接補範例。2~3 組通常就足以把轉換規則釘死。

# 任務:把使用者輸入的金額字串轉成分(cents)整數
# ✅ 用 2~3 組範例釘死規則
claude -p "實作 to_cents(s),依範例:
  '$12.50' -> 1250
  '12'     -> 1200
  '0.99'   -> 99
這些範例就是規格,不一致時以範例為準。"

技能 2  先寫涵蓋行為/邊界/效能的測試（test-driven 測試驅動）,再餵失敗迭代

遇到這個問題時用到你讓 Claude 實作一個 CSV parser，但需要確保它能正確處理空字串、空欄位、以及大檔效能，你需要先把這三類期望都用測試描述清楚，再讓 Claude 實作並靠失敗訊息迭代。

知識 2 的實作。測試要涵蓋三類:預期行為、邊界 case、效能要求。先寫好讓 Claude 實作,跑出失敗就把 failure 貼回。

# 步驟一:先寫測試(行為 + 邊界 + 效能)
def test_parse():
    assert parse("a,b,c") == ["a","b","c"]   # 行為
    assert parse("") == []                  # 邊界:空字串
    assert parse("a,,c") == ["a","","c"]  # 邊界:空欄

# 步驟二:跑失敗 → 把 failure 餵回 Claude
claude -p "test_parse 的第 3 個 assert 失敗,
got ['a','c'],expected ['a','','c']。修正 parse 保留空欄。"
重點:測試先行,涵蓋行為/邊界/效能;迭代靠 share failures,不靠重講。

技能 3  用 interview pattern（訪談模式）在陌生領域先攤開設計考量

遇到這個問題時用到你要建一個訊息重試佇列（message retry queue）但不熟悉這個領域，擔心遺漏冪等性、順序保證、重試上限等設計要點，你需要讓 Claude 先對你提問而不是直接開始寫程式。

知識 3 的落點。官方點名範例:cache invalidation 策略、各種 failure mode——這類「你不問就不會浮現」的決策,讓 Claude 先訪談你。

# ✅ 陌生領域:先 interview,再實作
claude -p "我要做訊息重試佇列,但這領域我不熟。
動手前,先針對 cache 失效、重試上限、
冪等性、訊息順序保證 這幾點問我問題,
逐一釐清後再寫程式。"

技能 4  用具體測試案例修邊界（iterative refinement 迭代精煉）—如 migration script 的 null 值

遇到這個問題時用到你的資料庫 migration script 在 email 欄位為 null 的記錄上崩潰，你需要告訴 Claude 確切的輸入資料和期望的輸出結果，讓它精確修正而不影響其他正常的 non-null 記錄。

知識 1 與 2 的合體用法:修 edge case 時,給具體的 input 與 expected output。官方範例就是 migration script 遇到 null 值的處理。

# edge case:migration script 遇到欄位為 null
# ✅ 給具體 input/expected 修邊界
claude -p "migrate() 在 email 欄為 null 時崩潰。
修正:input  {id:7, email:null}
      expect {id:7, email:'', migrated:true}
其他非 null 行為不變,並補一個 null 的測試。"

技能 5  判斷:互相牽動的問題一則訊息講完（iterative refinement 迭代精煉）,獨立的問題分次修

遇到這個問題時用到你的 message queue 同時有重試 bug 和去重 bug，上次分兩次修的結果是修了重試卻弄壞了去重，你需要判斷這次要不要把兩個問題放在同一個訊息裡一起解決。

知識 4 的實戰。下面兩種錯誤示範與正解,直接對照。

# ❌ 牽動的問題卻拆開修:改了重試又破壞了去重
# 訊息1:加重試  訊息2:加去重 → 兩者衝突,來回返工

# ✅ interacting:一則訊息一起講,讓它通盤設計
claude -p "重試與去重會互相影響:重試不可重複送已處理訊息。
請在同一套設計裡一起解決:重試上限、去重鍵、
兩者如何協調。"

# ✅ independent:彼此無關 → 分次各修各的
# 例:修 typo + 加 log 等級設定 → 分兩次,回饋更乾淨
重點:會互相影響 → 同一則詳細訊息一起解;互不相干 → 分次依序修。

整個 Task 3.5 的記憶骨架

在 Scenario 2 改善 Claude Code 產出,不靠「再講清楚的散文」,而靠四招逐步精煉:① 產出不一致時給 2~3 組具體 input/output 範例,讓轉換規則被範例釘死;② test-driven 迭代——先寫涵蓋行為/邊界/效能的測試,再把 test failure 餵回引導收斂;③ 陌生領域先用 interview pattern 讓 Claude 提問,攤開 cache 失效、failure mode 等隱藏考量;④ 修多個問題看牽動關係:互相牽動 → 一則訊息一起講,獨立 → 分次依序修。修 edge case(如 migration 的 null)同樣用具體 input/expected 來釘。

考試情境題

以下三題模擬正式考試格式，每題一個生產情境，四個選項。先嘗試作答，再展開解析。

Q 1 Scenario 2 · Code Generation with Claude Code

A developer asks Claude Code to write a normalize_date(s) function. The prompt says: "Convert date strings to a standard format." Claude produces code that sometimes returns YYYY-MM-DD, sometimes MM/DD/YYYY, and sometimes a Unix timestamp, depending on the session. The developer rewrites the prompt three times with more adjectives but the inconsistency persists. What is the most effective change to fix this?

  1. Switch to plan mode first, so Claude produces a design document specifying the output format before writing any code.
  2. Add 2–3 concrete input/output examples to the prompt (e.g., 'Jun 9 2026' → '2026-06-09') to unambiguously specify the expected transformation.
  3. Use the interview pattern and ask Claude to clarify which date format it prefers before implementing the function.
  4. Write the function signature with type hints and a docstring specifying "ISO 8601 format" to constrain Claude's output.
展開解析

Correct Answer: B

當散文（prose）描述產生不一致解讀時，根本原因是自然語言本身有歧義。具體的 input/output 範例直接示範期望的轉換，不留任何詮釋空間，2-3 組通常就足以釘死規則，是教材明確指出最有效的做法。

A 錯在哪：plan mode 適合有架構決策或多檔修改的複雜任務，一個格式轉換函式不需要規劃階段，而且規劃文件本身也可能對「標準格式」有歧義解讀。C 錯在哪：interview pattern 是讓 Claude 向你提問以攤開設計考量，在這個場景中問「你偏好哪種格式」是反向的——你才是有答案的人，應該直接給 Claude 範例而不是讓它發問。D 錯在哪：「ISO 8601」是較好的描述，但比起具體範例仍然有歧義（ISO 8601 有多種有效表示方式），是比 B 弱的解法。

Q 2 Scenario 2 · Code Generation with Claude Code

A team is building a distributed message retry queue and asks Claude Code to implement it. The engineer is unfamiliar with this domain and worries about missing critical design decisions. After Claude produces an initial implementation, the team discovers it fails to handle idempotency and has no maximum retry limit. Which technique, applied BEFORE the initial implementation, would have most effectively surfaced these missing considerations?

  1. Write a test suite covering expected behavior and edge cases, then share test failures to guide Claude's implementation iteratively.
  2. Use the interview pattern: ask Claude to pose 5–8 questions about retry limits, idempotency, message ordering, and failure modes before writing any code.
  3. Provide 2–3 concrete input/output examples of the retry queue's expected behavior to constrain Claude's implementation choices.
  4. Address retry logic and idempotency in a single detailed message after the initial implementation to fix both issues simultaneously.
展開解析

Correct Answer: B

interview pattern（訪談模式）正是為「陌生領域、擔心遺漏隱藏考量」的情境設計的：先讓 Claude 問你問題，把冪等性、重試上限、訊息順序、failure mode 這類「你不問就不會浮現」的決策攤開，等你回答完再實作，大幅減少事後補救。

A 錯在哪：test-driven 迭代是很好的技巧，但「先寫測試」需要你已知道該測什麼——在你不熟悉這個領域的前提下，你可能不知道冪等性測試是必要的，因此無法在一開始就寫出完整的測試套件。C 錯在哪：I/O 範例適合解決「轉換格式解讀不一致」的問題，但 message queue 的核心挑戰是設計決策而非輸入輸出格式，用範例無法迫使你思考 retry 上限等問題。D 錯在哪：事後在一則訊息修兩個互相牽動的問題，雖然比分次修好，但這是亡羊補牢，遠不如在實作前用 interview pattern 把問題預防掉。

Q 3 Scenario 2 · Code Generation with Claude Code

An engineer is debugging a message queue system and identifies two issues: (1) the retry counter increments even when the message was already successfully processed (a deduplication bug), and (2) there is a typo in a log message. The engineer asks Claude to fix both issues. In the first attempt, Claude fixes the retry counter but the deduplication logic breaks. What is the root cause, and what approach should be used instead?

  1. The root cause is insufficient context; the engineer should use plan mode to let Claude analyze both issues before attempting any fix.
  2. The root cause is that the retry and deduplication logic interact; both interacting issues should be described together in a single detailed message so Claude can address them holistically.
  3. The root cause is that the issues are independent; they should be fixed sequentially, one per message, to get cleaner feedback on each.
  4. The root cause is ambiguous prose descriptions; the engineer should provide input/output examples for both bugs to clarify the expected behavior.
展開解析

Correct Answer: B

重試計數器與去重邏輯彼此牽動（interacting problems）——修重試邏輯時必然影響去重邏輯的運作。對於互相牽動的問題，應該在同一則詳細訊息裡一起說明，讓 Claude 能通盤設計、一次解決兩者間的協調問題，而不是分次各修各的導致來回返工。

C 錯在哪：「分次修、各修各的」適合彼此獨立的問題，但重試與去重互相牽動，拆開修正是造成這次失敗的直接原因，不是解法。A 錯在哪：plan mode 適合有架構決策或大規模多檔修改的任務，修兩個有關聯的 bug 不需要規劃階段，正確的工具是在一則訊息裡說清楚兩者的牽動關係。D 錯在哪：I/O 範例適合解決「輸出格式不一致」的問題，而這個情境的核心問題是兩個邏輯互相影響，需要通盤設計而非格式說明。
