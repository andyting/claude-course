官方考綱原文

Task Statement 5.3 — Implement error propagation strategies across multi-agent systems

Knowledge of:

  • Structured error context (failure type, attempted query, partial results, alternative approaches) as enabling intelligent coordinator recovery decisions
  • The distinction between access failures (timeouts needing retry decisions) and valid empty results (successful queries with no matches)
  • Why generic error statuses ("search unavailable") hide valuable context from the coordinator
  • Why silently suppressing errors (returning empty results as success) or terminating entire workflows on single failures are both anti-patterns

Skills in:

  • Returning structured error context including failure type, what was attempted, partial results, and potential alternatives to enable coordinator recovery
  • Distinguishing access failures from valid empty results in error reporting so the coordinator can make appropriate decisions
  • Having subagents implement local recovery for transient failures and only propagate errors they cannot resolve, including what was attempted and partial results
  • Structuring synthesis output with coverage annotations indicating which findings are well-supported versus which topic areas have gaps due to unavailable sources
本題情境 · SCENARIO 3
Scenario 3 — Multi-Agent Research System（多代理研究系統）

多代理研究系統裡,coordinator 把任務派給 web 搜尋、文件分析、綜合等 subagent。當其中一個 subagent 的搜尋逾時、或某個來源查無資料時,錯誤要怎麼回報才能讓 coordinator 做出聰明的恢復決策?本 Task 教的就是「結構化錯誤傳播」——而不是把一個失敗變成整個研究流程崩潰。

一句話抓住主軸:subagent 出錯時,別回一句「搜尋不可用」就沒了。要回結構化錯誤(失敗類型、試過什麼、部分結果、替代方案),coordinator 才能聰明地重試、改道或標注缺口——而不是默默吞錯,也不是一個失敗就讓整個研究流程崩潰。

Knowledge of · 知識點

知識 1  結構化錯誤 context 讓 coordinator 能做聰明的恢復決策

當 web 搜尋 subagent 失敗,它回給 coordinator 的不該只是「失敗」二字。理想的結構化錯誤 context 含四項:失敗類型、試過的查詢、已拿到的部分結果、可能的替代方案。有了這些,coordinator 才能判斷該重試、換來源、還是先用部分結果。

# ✅ web 搜尋 subagent 回結構化錯誤,而非一句「失敗」
search_error = {
    "status": "error",
    "failure_type": "timeout",
    "attempted_query": "2026 固態電池 量產進度",
    "partial_results": ["找到 2 筆初步來源,尚未抓全文"],
    "alternatives": ["改用文件分析 subagent 查內部報告"],
}
# coordinator 可據此:重試、改派 analysis subagent、或先用 partial
考點重點:結構化錯誤 = 失敗類型 + 試過什麼 + 部分結果 + 替代方案 → 讓 coordinator 能恢復。

知識 2  區分「存取失敗」與「合法的空結果」

兩種情況長得像、意義完全不同:存取失敗(逾時、連線斷)是「沒查成功」,coordinator 可能要重試;合法空結果(查詢成功但真的沒有相符)是「查成功、結果就是空」,重試也沒用。把這兩者混為一談,coordinator 就會做錯決定(該重試的不重試、不該重試的狂重試)。

# ❌ 兩種都回 []，coordinator 分不出該不該重試
return []

# ✅ 明確區分
def search_subagent(query):
    try:
        hits = web_search(query)
        # 查成功但沒結果 = 合法空結果,不需重試
        return {"status": "ok", "results": hits}   # hits 可能為 []
    except Timeout:
        # 存取失敗 = 沒查成功,coordinator 可決定是否重試
        return {"status": "error", "failure_type": "timeout"}
重點:存取失敗(可重試)≠ 合法空結果(查成功就是空)。回報時要分清楚。

知識 3  籠統的錯誤狀態會把寶貴 context 藏起來

回一句 "search unavailable" 看似簡潔,實則把所有有用資訊都藏起來了——是逾時還是限流?試過哪個查詢?有沒有拿到一半?coordinator 什麼都不知道,只能放棄或盲目重試。籠統狀態 = 把恢復所需的線索全砍掉。

# ❌ 籠統狀態,藏掉所有 context
return {"status": "search unavailable"}
# coordinator 不知道:為什麼?試過什麼?能不能換條路?

# ✅ 揭露細節,coordinator 才有材料做決策
return {
    "status": "error",
    "failure_type": "rate_limited",
    "attempted_query": "固態電池 專利 2025",
    "retry_after_sec": 30,
}
重點:「search unavailable」這類籠統狀態藏掉 context;要揭露失敗細節。

知識 4  兩個反模式:默默吞錯 與 單一失敗就終止整個流程

兩個極端都錯。默默吞錯:把錯誤當空結果回成「成功」——coordinator 以為這塊查過了沒東西,最終報告就缺了一塊還不自知。單一失敗終止全流程:一個 subagent 逾時就讓整個研究崩潰——其他 subagent 明明成功了,成果全丟。正解在兩者之間:回報錯誤、但讓流程帶著缺口繼續。

# ❌ 反模式 A:默默吞錯,把失敗偽裝成「查到空」
except Exception:
    return {"status": "ok", "results": []}   # 缺口被藏起來

# ❌ 反模式 B:一個 subagent 失敗就 raise,炸掉整個研究
except Exception as e:
    raise e   # 其他成功的 subagent 成果全被犧牲

# ✅ 正解:回報錯誤,讓 coordinator 帶著缺口繼續
except Exception as e:
    return {"status": "error", "failure_type": type(e).__name__}
重點:不默默吞錯(會藏缺口)、不單點失敗炸全流程(會丟成果)。回報並繼續。

Skills in · 技能點

技能 1  回傳含失敗類型/嘗試/部分結果/替代方案的結構化錯誤

知識 1 的實作。把 subagent 的錯誤回傳統一成一個結構,四項齊全,coordinator 接到就能恢復。下面是文件分析 subagent 的範例。

def analysis_subagent(doc_id):
    try:
        return {"status": "ok", "findings": analyze(doc_id)}
    except PartialReadError as e:
        return {
            "status": "error",
            "failure_type": "partial_read",
            "attempted": f"分析文件 {doc_id}",
            "partial_results": e.parsed_sections,      # 已解析的段落
            "alternatives": ["改用 web 搜尋補齊缺漏章節"],
        }
重點:錯誤回傳四件套:failure_type / attempted / partial_results / alternatives。

技能 2  在錯誤回報中區分存取失敗與合法空結果

知識 2 的實作。讓回報明確標出是哪一種,coordinator 才能對「逾時」決定重試、對「查無相符」直接接受。

def coordinator_handle(resp):
    if resp["status"] == "ok" and not resp["results"]:
        # 合法空結果:這個來源就是沒有,接受並標注
        mark_gap("此來源查無相符")
    elif resp["status"] == "error" and resp["failure_type"] == "timeout":
        # 存取失敗:可重試
        retry_with_backoff(resp["attempted_query"])
重點:回報要讓 coordinator 一眼分清:空結果→接受標注,存取失敗→考慮重試。

技能 3  subagent 先本地恢復暫時性失敗,只把解決不了的往上拋

暫時性失敗(短暫逾時、限流)應該由 subagent 自己先試著恢復(重試幾次、退避),別一遇到就丟給 coordinator。只有本地真的救不回來時,才往上傳——而且要附上「試過什麼」與「部分結果」,coordinator 才能接手。

def search_with_local_recovery(query, max_retry=3):
    partial = []
    for attempt in range(max_retry):
        try:
            return {"status": "ok", "results": web_search(query)}
        except Timeout:
            sleep(2 ** attempt)            # 本地退避重試
    # 本地救不回 → 才往上拋,附 attempted + partial
    return {"status": "error", "failure_type": "timeout",
            "attempted": query, "partial_results": partial}
重點:暫時性失敗 subagent 先本地恢復;救不回才上拋,並帶 attempted + partial。

技能 4  綜合輸出加「coverage 註記」,標明哪些有充分支持、哪些有缺口

當部分來源失敗、研究帶著缺口完成,synthesis subagent 的報告不能假裝完整。要加上 coverage 註記:哪些結論有充分來源支持、哪些主題因來源不可用而有缺口。讓最終讀者知道報告的可信邊界在哪。

report = {
    "findings": [...],
    "coverage": {
        "well_supported": ["市場規模(3 個獨立來源)"],
        "gaps": [
            {"topic": "專利分布",
             "reason": "專利資料庫搜尋逾時,未取得"},  # 誠實標缺口
        ],
    },
}
重點:synthesis 報告加 coverage 註記:well-supported vs. gaps,誠實標明缺口來源。

整個 Task 5.3 的記憶骨架

多代理研究裡,subagent 出錯要回結構化錯誤(失敗類型/試過什麼/部分結果/替代方案),讓 coordinator 能聰明恢復;要分清存取失敗(可重試)與合法空結果(查成功就是空)。籠統狀態(「search unavailable」)會藏掉 context。兩大反模式:默默吞錯(藏缺口)與單點失敗炸全流程(丟成果)都要避免。暫時性失敗 subagent 先本地恢復、救不回才上拋;最後 synthesis 報告加 coverage 註記,誠實標明哪些有支持、哪些有缺口。
