Task Statement 4.6 — Design multi-instance and multi-pass review architectures

Knowledge of:

  • Self-review limitations: a model retains reasoning context from generation, making it less likely to question its own decisions in the same session
  • Independent review instances (without prior reasoning context) are more effective at catching subtle issues than self-review instructions or extended thinking
  • Multi-pass review: splitting large reviews into per-file local analysis passes plus cross-file integration passes to avoid attention dilution and contradictory findings

Skills in:

  • Using a second independent Claude instance to review generated code without the generator's reasoning context
  • Splitting large multi-file reviews into focused per-file passes for local issues plus separate integration passes for cross-file data flow analysis
  • Running verification passes where the model self-reports confidence alongside each finding to enable calibrated review routing
本題情境 · SCENARIO 5
Scenario 5 — Claude Code for Continuous Integration

把 Claude Code 接進 CI/CD 做自動 code review。本 Task 教你:別讓「產 code 的那個實例」自己審自己——要用第二個獨立實例(不帶生成時的推理脈絡)來審,才抓得到細微 bug;大型多檔審查要拆成「逐檔 local pass + 跨檔 integration pass」;再讓審查實例對每個 finding 自報信心以便分流。範例都用 PR review / generator vs reviewer 實例的 CI 場景。

一句話抓住主軸:「自己審自己」會放水——因為生成時的推理脈絡讓它捨不得質疑自己的決定。換上一個沒看過推理過程的獨立實例來審,才抓得到細微問題。

Knowledge of · 知識點

知識 1  self-review（自我審查）的天生限制:同一 session 不容易質疑自己

遇到這個問題時用到你讓 Claude 先產生 code、再要求它「再檢查一下自己的程式是否有 bug」，但上線後仍然發現了原本應該被抓到的邏輯錯誤，你需要解釋這個架構的根本缺陷。

核心觀念。當同一個模型實例在同一個 session 裡先寫了 code、再被要求審查,它還留著生成時的推理脈絡——它已經「說服過自己」這段邏輯是對的,於是較不會去質疑自己的決定。這就是 self-review（自我審查）效果有限的根本原因。

考點重點:self-review 會保留 generation 的 reasoning context → 不易質疑自己。

知識 2  獨立實例 > self-review 指令或 extended thinking

遇到這個問題時用到你的 team lead 建議「開 extended thinking 讓模型多想一下應該就能自己發現問題」，你需要說明為什麼這個方法效果仍不如獨立實例，以及三種方法的效果排序。

關鍵比較。要抓細微問題(subtle issues),「換一個沒有先前推理脈絡的獨立實例」來審,比「叫同一實例 self-review（自我審查）」或「開 extended thinking 多想一下」更有效。因為獨立實例是用全新視角讀這段 code,不會被生成時的思路牽著走。效果排序：獨立 review 實例 > self-review 指令 > extended thinking。

重點:抓細微 bug 的效果:獨立 review 實例 > self-review 指令 > extended thinking。

知識 3  multi-pass review（多輪審查）:逐檔 local pass + 跨檔 integration pass

遇到這個問題時用到一個 PR 改了 15 個檔案，你把全部 diff 塞進同一個 review 請求，回傳的結果有幾個互相矛盾的 comment（在 A 檔說可以、在 B 檔說不可以），你需要重新設計審查架構。

大型 multi-pass review（多輪審查）不能「一次把全部檔案塞進去一起看」——注意力會被稀釋(attention dilution),還可能給出互相矛盾的結論。正確拆法:先做逐檔的 local pass(每個檔各自看區域性問題),再做跨檔的 integration pass(專看檔案之間的資料流、介面、相依)。分工避免分心與矛盾。

重點:大審查拆成 per-file local pass + cross-file integration pass,避免 attention dilution 與矛盾結論。

Skills in · 技能點

技能 1  用「第二個獨立 Claude 實例」審查生成的 code(不帶 generator 脈絡)

遇到這個問題時用到你的 CI pipeline 目前讓同一個 Claude session 先產 code 再自我 review，你需要把它重構成 generator/reviewer 分離的架構，確保 reviewer 是真正乾淨的第二視角。

核心實作。generator 實例負責產 code;審查時另開一個全新實例,只給它「待審的 code + 審查任務」,不要把 generator 的對話脈絡或推理過程帶過去。這樣 reviewer 是用乾淨視角看,抓得到 generator 自己看不到的問題。

import anthropic
client = anthropic.Anthropic()

# Scenario 5:CI 裡 generator 產 code,reviewer 是「全新實例」
def generate_code(spec):
    return client.messages.create(
        model="claude-sonnet-4-6", max_tokens=2048,
        messages=[{"role": "user", "content": spec}],
    )

def independent_review(code):
    # ✅ 只給 code,不帶 generator 的推理脈絡
    return client.messages.create(
        model="claude-sonnet-4-6", max_tokens=2048,
        messages=[{"role": "user",
                   "content": f"審查這段 PR 程式碼,找出 bug:\n{code}"}],
    )

code = generate_code(spec)
review = independent_review(code.content[0].text)  # 乾淨視角
重點:reviewer 另開新實例,只給 code、不帶 generator 脈絡 = 真正獨立的第二意見。

技能 2  大型多檔審查:拆成逐檔 local pass + 獨立的跨檔 integration pass

遇到這個問題時用到你要對一個改了 auth.py、user.py、api.py 三個檔的 PR 做完整審查，需要設計一個能同時捕捉單檔問題和跨檔資料流問題的流程，而不讓這兩種 pass 互相干擾。

把知識 3 變成流程。對一個改了很多檔的 PR:先逐檔各跑一次審查(專看該檔自身的 local 問題),再另跑一次 integration pass(把各檔的介面/資料流一起看,專抓跨檔問題)。兩種 pass 任務不同、互不干擾。

# Scenario 5:PR 改了多個檔 → 先逐檔、再跨檔
def review_pr(changed_files):
    local_findings = []
    # 1) 逐檔 local pass:每檔只看自身問題
    for path, src in changed_files.items():
        local_findings += review_one_file(path, src)

    # 2) integration pass:專看跨檔資料流 / 介面相依
    integration = review_cross_file(
        prompt="只分析這些檔之間的資料流與介面一致性,"
               "忽略單檔內部問題。",
        files=changed_files,
    )
    return local_findings, integration
重點:local pass 抓單檔問題、integration pass 抓跨檔資料流;分開跑避免分心與矛盾。

技能 3  驗證 pass 讓模型「自報信心」,做校準分流

遇到這個問題時用到你的 CI reviewer 有時報出真的很嚴重的 bug、有時又報出明顯不確定的問題，你希望把高信心的問題自動擋 merge、低信心的問題送人工確認，而不是讓所有 finding 走同一條路。

讓審查可被分流。要求 reviewer 在每個 finding 旁邊附上信心值(高/中/低或 0–1)。然後依信心做校準路由（calibrated routing）:高信心的問題自動標記/擋 merge,低信心的送人工複核,避免高 false positive（假陽性）直接吵到開發者。

# Scenario 5:每個 PR finding 自報信心,依信心分流
review_prompt = """審查這段程式碼。每一個問題都要附上:
- issue: 問題描述
- confidence: 0~1 的信心值
只回 JSON 陣列。"""

resp = client.messages.create(
    model="claude-sonnet-4-6", max_tokens=2048,
    messages=[{"role": "user",
               "content": review_prompt + code}],
)

for f in parse_findings(resp):
    if f["confidence"] >= 0.8:
        block_merge(f)         # ✅ 高信心 → 擋 merge
    else:
        route_to_human(f)      # 低信心 → 人工複核,降 false positive
重點:每個 finding 帶 confidence → 高信心自動處理、低信心送人工,校準路由降誤報。

整個 Task 4.6 的記憶骨架

核心一句:自己審自己會放水,因為生成時的推理脈絡讓模型不願質疑自己。所以要用第二個獨立實例(不帶 generator 脈絡)來審,抓細微 bug 的效果勝過 self-review 指令或 extended thinking。大型審查拆成逐檔 local pass(單檔問題)+ 跨檔 integration pass(資料流/介面),避免注意力稀釋與矛盾結論。最後讓每個 finding 自報 confidence,高信心自動擋 merge、低信心送人工,做校準分流降低 false positive。

Q 1 Scenario 5 · Claude Code for Continuous Integration

Your CI pipeline uses a single Claude instance to both generate code fixes for failing tests and then review those same fixes. After several weeks, your team observes that the reviewer rarely flags issues in the generated code — even when human reviewers later find obvious bugs. The review pass uses the same API session as the generation pass. What is the most likely root cause?

  1. The review prompt is too short and does not give the model enough context to find bugs.
  2. The model retains the generation session's reasoning context, making it unlikely to question its own decisions in the same session.
  3. The model's temperature is set too low, reducing creative bug-finding ability.
  4. The generation and review prompts are too similar, causing the model to produce identical outputs for both.
展開解析

Correct Answer: B

B 正確：這是 self-review（自我審查）的天生限制。同一個 session 裡，模型在生成 code 時已經「說服過自己」這段邏輯是對的，推理脈絡殘留在 context 中，於是在審查時不容易質疑自己做出的決定，細微 bug 就被放過了。

A 錯在哪：prompt 長短影響的是能看到多少資訊，但根本問題是「同一實例不願質疑自己」，加長 review prompt 也解決不了 reasoning context 殘留的問題。C 錯在哪：temperature 影響輸出的多樣性，但 self-review 的失效是結構性問題——即使調高 temperature，模型仍然帶著相同的 generation context，偏見依然存在。D 錯在哪：prompt 相似性影響輸出格式，但不是造成 review 放水的原因；兩個 prompt 可以完全不同，self-review 的偏見仍然存在。

Q 2 Scenario 5 · Claude Code for Continuous Integration

A PR modifies 8 files across your authentication, user management, and API gateway modules. You send all 8 files' diffs in a single review request. The review returns 15 findings, but three of them directly contradict each other: file A is told to use pattern X, while file B is told to avoid pattern X. What architectural change most directly addresses this problem?

  1. Add "ensure consistency across all files" to the review prompt so the model maintains a consistent position.
  2. Split the review into per-file local passes (one request per file) plus a separate integration pass focused on cross-file data flow and interface consistency.
  3. Use a more capable model with a larger context window to process all files simultaneously without losing track of earlier content.
  4. Filter out contradictory findings automatically using a post-processing script before showing results to developers.
展開解析

Correct Answer: B

B 正確：大型多檔審查的矛盾結論來自 attention dilution（注意力稀釋）——模型同時處理太多內容，前面看到的和後面看到的會相互干擾。解法是 multi-pass review（多輪審查）：每個檔單獨跑一次 local pass（只看該檔自身問題），再另跑一次 integration pass 專門分析跨檔的資料流和介面一致性，兩種 pass 任務明確不衝突。

A 錯在哪：在同一個請求裡加文字指令「保持一致」並不能解決注意力稀釋的問題；模型仍然要在同一個 context 裡處理 8 個檔案，矛盾的根本原因沒有改變。C 錯在哪：更大的 context window 只是讓所有內容都能塞進去，但 attention dilution 和矛盾結論不是因為 context 不夠，而是因為任務複雜度超過了模型在單次請求中能保持一致性的能力。D 錯在哪：post-processing 過濾矛盾是在治標不治本，而且自動判斷哪條正確、哪條應該被過濾本身就是一個困難問題；正確做法是從架構上避免矛盾的產生。

Q 3 Scenario 5 · Claude Code for Continuous Integration

Your CI reviewer uses an independent Claude instance (no generator context) and produces findings with a confidence score (0–1). Currently, all findings — regardless of confidence — automatically block the merge and notify the developer. Developers are complaining about too many low-confidence findings that turn out to be false positives. Which change best addresses this while keeping high-confidence issues properly enforced?

  1. Remove the confidence field and use only high/medium/low severity to filter which findings block merges.
  2. Raise the minimum confidence threshold to 0.9 to block merges only on near-certain findings, discarding all others silently.
  3. Route findings with confidence ≥ 0.8 to automatic merge blocking, and route findings with confidence < 0.8 to a human review queue instead of auto-blocking.
  4. Switch back to the generator instance for review — it is faster and produces fewer findings overall.
展開解析

Correct Answer: C

C 正確：這是技能 3 的校準分流（calibrated routing）模式。高信心（≥ 0.8）的 finding 自動擋 merge，確保真正的問題不被漏過；低信心的 finding 送人工複核而非直接阻擋，讓有判斷力的人決定是否真的是問題。這樣既降低了 false positive（假陽性）對開發者的干擾，又不會讓高信心的真問題被忽略。

A 錯在哪：用 severity 取代 confidence 是不同維度的資訊——severity 表示問題有多嚴重，confidence 表示模型有多確定這是問題；兩者都有用，移除 confidence 會失去「不確定性」這個關鍵訊號。B 錯在哪：靜默丟棄低信心 finding 會讓真正的問題（只是模型不夠確定）永遠消失，從來不到達任何人的眼前；送人工複核比靜默丟棄保留了發現真問題的機會。D 錯在哪：切回 generator 實例做 review 正是知識 1 說明的問題根源——generator 帶著自己的 reasoning context，更不可能抓到自己的細微 bug，reducing findings 是因為放水，不是因為真的沒有問題。
