Task Statement 4.6 — Design multi-instance and multi-pass review architectures

Knowledge of:

  • Self-review limitations: a model retains reasoning context from generation, making it less likely to question its own decisions in the same session
  • Independent review instances (without prior reasoning context) are more effective at catching subtle issues than self-review instructions or extended thinking
  • Multi-pass review: splitting large reviews into per-file local analysis passes plus cross-file integration passes to avoid attention dilution and contradictory findings

Skills in:

  • Using a second independent Claude instance to review generated code without the generator's reasoning context
  • Splitting large multi-file reviews into focused per-file passes for local issues plus separate integration passes for cross-file data flow analysis
  • Running verification passes where the model self-reports confidence alongside each finding to enable calibrated review routing
本題情境 · SCENARIO 5
Scenario 5 — Claude Code for Continuous Integration

把 Claude Code 接進 CI/CD 做自動 code review。本 Task 教你:別讓「產 code 的那個實例」自己審自己——要用第二個獨立實例(不帶生成時的推理脈絡)來審,才抓得到細微 bug;大型多檔審查要拆成「逐檔 local pass + 跨檔 integration pass」;再讓審查實例對每個 finding 自報信心以便分流。範例都用 PR review / generator vs reviewer 實例的 CI 場景。

一句話抓住主軸:「自己審自己」會放水——因為生成時的推理脈絡讓它捨不得質疑自己的決定。換上一個沒看過推理過程的獨立實例來審,才抓得到細微問題。

Knowledge of · 知識點

知識 1  自我審查的天生限制:同一 session 不容易質疑自己

核心觀念。當同一個模型實例在同一個 session 裡先寫了 code、再被要求審查,它還留著生成時的推理脈絡——它已經「說服過自己」這段邏輯是對的,於是較不會去質疑自己的決定。這就是為什麼「請你再檢查一下自己的程式」效果有限。

考點重點:self-review 會保留 generation 的 reasoning context → 不易質疑自己。

知識 2  獨立實例 > 自我審查指令或 extended thinking

關鍵比較。要抓細微問題(subtle issues),「換一個沒有先前推理脈絡的獨立實例」來審,比「叫同一實例自我審查」或「開 extended thinking 多想一下」更有效。因為獨立實例是用全新視角讀這段 code,不會被生成時的思路牽著走。

重點:抓細微 bug 的效果:獨立 review 實例 > self-review 指令 > extended thinking。

知識 3  多輪審查:逐檔 local pass + 跨檔 integration pass

大型審查不能「一次把全部檔案塞進去一起看」——注意力會被稀釋(attention dilution),還可能給出互相矛盾的結論。正確拆法:先做逐檔的 local pass(每個檔各自看區域性問題),再做跨檔的 integration pass(專看檔案之間的資料流、介面、相依)。分工避免分心與矛盾。

重點:大審查拆成 per-file local pass + cross-file integration pass,避免 attention dilution 與矛盾結論。

Skills in · 技能點

技能 1  用「第二個獨立 Claude 實例」審查生成的 code(不帶 generator 脈絡)

核心實作。generator 實例負責產 code;審查時另開一個全新實例,只給它「待審的 code + 審查任務」,不要把 generator 的對話脈絡或推理過程帶過去。這樣 reviewer 是用乾淨視角看,抓得到 generator 自己看不到的問題。

import anthropic
client = anthropic.Anthropic()

# Scenario 5:CI 裡 generator 產 code,reviewer 是「全新實例」
def generate_code(spec):
    return client.messages.create(
        model="claude-sonnet-4-6", max_tokens=2048,
        messages=[{"role": "user", "content": spec}],
    )

def independent_review(code):
    # ✅ 只給 code,不帶 generator 的推理脈絡
    return client.messages.create(
        model="claude-sonnet-4-6", max_tokens=2048,
        messages=[{"role": "user",
                   "content": f"審查這段 PR 程式碼,找出 bug:\n{code}"}],
    )

code = generate_code(spec)
review = independent_review(code.content[0].text)  # 乾淨視角
重點:reviewer 另開新實例,只給 code、不帶 generator 脈絡 = 真正獨立的第二意見。

技能 2  大型多檔審查:拆成逐檔 local pass + 獨立的跨檔 integration pass

把知識 3 變成流程。對一個改了很多檔的 PR:先逐檔各跑一次審查(專看該檔自身的 local 問題),再另跑一次 integration pass(把各檔的介面/資料流一起看,專抓跨檔問題)。兩種 pass 任務不同、互不干擾。

# Scenario 5:PR 改了多個檔 → 先逐檔、再跨檔
def review_pr(changed_files):
    local_findings = []
    # 1) 逐檔 local pass:每檔只看自身問題
    for path, src in changed_files.items():
        local_findings += review_one_file(path, src)

    # 2) integration pass:專看跨檔資料流 / 介面相依
    integration = review_cross_file(
        prompt="只分析這些檔之間的資料流與介面一致性,"
               "忽略單檔內部問題。",
        files=changed_files,
    )
    return local_findings, integration
重點:local pass 抓單檔問題、integration pass 抓跨檔資料流;分開跑避免分心與矛盾。

技能 3  驗證 pass 讓模型「自報信心」,做校準分流

讓審查可被分流。要求 reviewer 在每個 finding 旁邊附上信心值(高/中/低或 0–1)。然後依信心校準路由:高信心的問題自動標記/擋 merge,低信心的送人工複核,避免高 false positive 直接吵到開發者。

# Scenario 5:每個 PR finding 自報信心,依信心分流
review_prompt = """審查這段程式碼。每一個問題都要附上:
- issue: 問題描述
- confidence: 0~1 的信心值
只回 JSON 陣列。"""

resp = client.messages.create(
    model="claude-sonnet-4-6", max_tokens=2048,
    messages=[{"role": "user",
               "content": review_prompt + code}],
)

for f in parse_findings(resp):
    if f["confidence"] >= 0.8:
        block_merge(f)         # ✅ 高信心 → 擋 merge
    else:
        route_to_human(f)      # 低信心 → 人工複核,降 false positive
重點:每個 finding 帶 confidence → 高信心自動處理、低信心送人工,校準路由降誤報。

整個 Task 4.6 的記憶骨架

核心一句:自己審自己會放水,因為生成時的推理脈絡讓模型不願質疑自己。所以要用第二個獨立實例(不帶 generator 脈絡)來審,抓細微 bug 的效果勝過 self-review 指令或 extended thinking。大型審查拆成逐檔 local pass(單檔問題)+ 跨檔 integration pass(資料流/介面),避免注意力稀釋與矛盾結論。最後讓每個 finding 自報 confidence,高信心自動擋 merge、低信心送人工,做校準分流降低 false positive。
