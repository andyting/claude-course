Task Statement 1.4 — Implement multi-step workflows with enforcement and handoff patterns

Knowledge of:

  • The difference between programmatic enforcement (hooks, prerequisite gates) and prompt-based guidance for workflow ordering
  • When deterministic compliance is required (e.g., identity verification before financial operations), prompt instructions alone have a non-zero failure rate
  • Structured handoff protocols for mid-process escalation that include customer details, root cause analysis, and recommended actions

Skills in:

  • Implementing programmatic prerequisites that block downstream tool calls until prerequisite steps have completed (e.g., blocking process_refund until get_customer has returned a verified customer ID)
  • Decomposing multi-concern customer requests into distinct items, then investigating each in parallel using shared context before synthesizing a unified resolution
  • Compiling structured handoff summaries (customer ID, root cause, refund amount, recommended action) when escalating to human agents who lack access to the conversation transcript
本題情境 · SCENARIO 1
Scenario 1 — Customer Support Resolution Agent

延續客服解決 agent:退款前必須先 get_customer 驗證身分、再 lookup_order,最後才能 process_refund 或 escalate_to_human。本 Task 的強制與交接模式,就是用來保證這個關鍵順序。

一句話抓住主軸:有些步驟順序「最好遵守」,有些則是「絕不能錯」。前者用 prompt 提示就好;後者(像驗證身分才能動錢)一定要用程式強制,因為光靠 prompt 永遠有失敗機率。 這個 Task 還包含:把多訴求拆開平行處理,以及交接給真人時要附上結構化摘要。

Knowledge of · 知識點

知識 1  程式強制（hook，鉤子）(hooks、prerequisite gate)vs. prompt 提示,兩者差在哪

遇到這個問題時用到系統的 system prompt 寫明「處理退款前必須先驗證身分」，但測試發現偶爾 Claude 會直接跳到退款步驟，你需要了解為什麼 prompt 指令不足以保證順序。

要控制工作流（workflow，工作流程）的步驟順序,有兩條路。prompt-based guidance(提示式):在 system prompt 寫「請先驗證身分再退款」——這是建議,Claude 大多會聽,但有時不會。programmatic enforcement(程式強制):用 hook（鉤子）或 prerequisite gate（先決條件閘門）,在程式層硬性擋住——前一步沒完成,後一步根本叫不動。

差別像「貼告示牌請人先洗手」vs.「沒洗手門就打不開」。告示牌靠自覺,門鎖是物理強制。

# 提示式:寫進 prompt,屬「建議」,有非零失敗機率
SYSTEM_PROMPT = "處理退款前,請務必先呼叫 get_customer 驗證身分。"

# ✅ 程式強制:gate 擋住,前置沒完成就無法執行
def gate_process_refund(state, args):
    if not state.verified_customer_id:
        raise BlockedError("必須先完成 get_customer 身分驗證")
    return process_refund(args)   # 只有驗證過才走得到這行
考點重點:提示式 = 建議(可能失敗);程式強制 = hook/gate 硬擋(保證)。

知識 2  需要「確定性遵守」時,光靠 prompt 有非零失敗機率

遇到這個問題時用到合規審計發現有幾筆退款在客戶身分未驗證的情況下被執行，雖然 prompt 有明確指示，但語言模型的機率性行為導致極低機率的不合規操作仍會發生。

這是本 Task 的核心觀念。有些規則必須 100% 遵守——例如「動錢之前一定要先驗證身分」。這種情況下,prompt 指令是不夠的:語言模型是機率性的,即使你叮嚀得再清楚,它仍有「非零的失敗機率」會跳過或弄錯順序。只要這個失敗機率對你來說不可接受(牽涉金錢、合規、安全),就必須改用程式強制,把確定性從程式層保證,而不是寄望模型每次都乖。

# 決策準則:這條規則「偶爾失敗」可以接受嗎?
def choose_enforcement(rule):
    if rule.must_always_hold:        # 例:驗證身分才能退款
        return "programmatic"        # ✅ 用程式強制,保證確定性
    else:                            # 例:回覆語氣、建議格式
        return "prompt"               # 提示即可,容許偶爾偏差

# ❌ 把「絕不能錯」的規則只寫進 prompt → 非零失敗機率不可接受
一句話記住:「絕不能錯」的規則,prompt 不夠——模型有非零失敗率,要用程式強制。

知識 3  結構化交接協定:升級給真人時要含客戶資料、根因、建議行動

遇到這個問題時用到客服代理把案件移交給真人專員時只附了一句「客戶有退款問題」，真人專員需要重新向客戶詢問所有細節，造成客戶體驗極差，交接效率低落。

當流程進行到一半需要升級（escalation，升級）給真人客服時,不能只丟一句「這個給你處理」。要遵循結構化交接協定（handoff，交接）:把真人接手所需的關鍵資訊整理好——客戶資料(誰)、根因分析(問題出在哪)、建議行動(你建議怎麼做)。因為接手的真人看不到你跟客戶之間的完整對話記錄,你給的摘要就是他的全部資訊。

# ✅ 結構化交接:把真人需要的資訊一次給齊
handoff = {
    "customer": {"id": "C-8842", "name": "王小明", "tier": "VIP"},
    "root_cause": "重複扣款:同筆訂單被結帳系統送出兩次",
    "recommended_action": "退還重複的一筆 $620,並補償運費券",
}
# ❌ 只說「客戶有退款問題,請處理」→ 真人沒上下文,得重問一遍
重點:交接摘要 = 客戶資料 + 根因 + 建議行動(因為真人看不到對話)。

Skills in · 技能點

技能 1  實作 prerequisite gate（先決條件閘門）:前置沒完成就擋住下游工具

遇到這個問題時用到你需要設計一個客服退款流程，要求「必須先呼叫 get_customer 取得已驗證的 customer ID，才允許呼叫 process_refund」，且這個順序必須在程式層強制執行，不能只靠 prompt 指示。

這是知識 1、2 的實作核心。最經典的例子:在 get_customer 回傳「已驗證的 customer ID」之前,擋住 process_refund。做法是維護一個流程狀態,並在下游工具執行前檢查前置條件是否滿足——不滿足就直接 block。

class WorkflowState:
    verified_customer_id = None

state = WorkflowState()

def tool_router(name, args):
    if name == "get_customer":
        result = get_customer(args)
        state.verified_customer_id = result["id"]   # 標記前置完成
        return result

    if name == "process_refund":
        if not state.verified_customer_id:           # ← gate 檢查
            return {"error": "擋下:尚未驗證客戶身分"}  # ❌ 擋住
        return process_refund(args)                    # ✅ 通過才執行

技能 2  把多訴求請求拆成獨立項目,共享 context 平行調查,再統一回覆

遇到這個問題時用到客戶在同一封訊息中同時提到訂單未到、上月被多收費、以及想更改配送地址，代理系統需要有效率地同時處理這三個相互獨立的問題，而非逐一序列回應。

客戶常常一次講好幾件事(「我訂單沒到、上個月被多收錢、還想改地址」)。做法:先把這個多訴求請求拆成各自獨立的項目,每件平行調查(共享同一份客戶 context,不必各自重查),最後再綜合成一個統一的回覆——而不是分三次零碎回應。

def handle_multi_concern(request, shared_ctx):
    # 1. 拆成獨立項目
    concerns = split_concerns(request)   # [缺貨, 重複扣款, 改地址]

    # 2. 共享 context 平行調查每一項
    findings = parallel_map(
        lambda c: investigate(c, context=shared_ctx),
        concerns,
    )

    # 3. 綜合成一個統一回覆
    return synthesize_resolution(findings)   # ✅ 一次給完整答覆
重點:多訴求 → 拆項目 → 共享 context 平行查 → 綜合成單一回覆。

技能 3  升級（escalation）時編出結構化交接摘要（handoff，交接）(客戶 ID、根因、退款金額、建議行動)

遇到這個問題時用到你在實作 escalate_to_human 工具的呼叫邏輯，需要確保傳給真人專員的摘要包含所有必要欄位，讓他能在不查閱對話記錄的情況下直接接手處理。

這是知識 3 的實作版。當需要轉給真人時,把固定欄位填齊:客戶 ID、根因、退款金額、建議行動。接手的真人沒有對話記錄,這份摘要就是他唯一的依據——欄位越完整,他越能無縫接手、不必回頭重問客戶。

def build_handoff(state):
    return {
        "customer_id": state.verified_customer_id,
        "root_cause": state.diagnosis,
        "refund_amount": state.refund_amount,
        "recommended_action": state.recommendation,
    }

# 升級給真人:附上完整結構化摘要
escalate_to_human(summary=build_handoff(state))
# ✅ 真人拿到所有關鍵欄位,不必看對話也能接手
重點:交接摘要欄位齊全(ID / 根因 / 金額 / 建議)= 真人無縫接手。

整個 Task 1.4 的記憶骨架

步驟順序控制有兩條路:prompt 提示(建議、容許偶爾失敗)與程式強制(hook / prerequisite gate、硬擋)。凡是「絕不能錯」的規則(如驗證身分才能動錢),prompt 有非零失敗機率,必須用程式強制保證確定性——例如沒驗證就 block 掉 process_refund。多訴求請求要拆項目、共享 context 平行查、再綜合成單一回覆。升級給真人時附上結構化交接摘要(客戶 ID、根因、金額、建議),因為真人看不到對話記錄。

考試情境題

以下三題模擬正式考試格式，每題一個生產情境，四個選項。先嘗試作答，再展開解析。

Q 1 Scenario 1 · Customer Support Resolution Agent

A customer support agent is deployed with the following system prompt instruction: "Always call get_customer to verify the customer's identity before processing any refund." During a compliance audit, logs reveal that in roughly 1 in 200 interactions the agent called process_refund without a prior get_customer call. What is the most likely root cause?

  1. The system prompt instruction was placed in the wrong section of the prompt and was ignored by the model.
  2. The model's probabilistic nature means prompt-based instructions have a non-zero failure rate; programmatic enforcement via a prerequisite gate is required for deterministic compliance.
  3. The get_customer tool returned errors in those cases, so the agent skipped it to avoid an unhandled exception.
  4. The agent's context window was exceeded in long conversations, causing it to forget the earlier instruction.
展開解析

Correct Answer: B

語言模型是機率性系統，即使 prompt 寫得再清楚，仍有非零的機率偶爾跳過或錯誤排序步驟。對於「驗證身分才能動錢」這類「絕不能錯」的規則，光靠 prompt 指示無法達到 100% 的確定性遵守。正確做法是在程式層實作 prerequisite gate：在 process_refund 執行前檢查 verified_customer_id 是否存在，不存在則直接 block。

A 錯在哪：prompt 位置影響有限，根本問題是 LLM 的機率性本質，即使指令位置完美也無法保證 100% 遵守。C 錯在哪：工具錯誤應被捕獲後回傳給 agent 作為工具結果，agent 應該在知道身分驗證失敗的情況下終止流程而非繼續；但即使如此，確定性保證仍應靠 gate 而非靠 agent 的決策邏輯。D 錯在哪：context window 超限會導致模型回應品質下降，但系統 prompt 中的關鍵指令通常會被保留；問題根源是機率性而非記憶消失。

Q 2 Scenario 1 · Customer Support Resolution Agent

A customer contacts support saying: "My order hasn't arrived, I was double-charged last month, and I want to change my delivery address." The support agent handles each concern one at a time, responding three separate times with gaps between responses. The customer complains about the fragmented experience. What is the most effective approach to resolve all three concerns efficiently?

  1. Escalate immediately to a human agent since the request is too complex for an automated system.
  2. Prioritize the most urgent concern (double charge) and resolve it first, then address the others in subsequent interactions.
  3. Decompose the request into three independent items, investigate each in parallel using shared customer context, then synthesize a single unified resolution response.
  4. Ask the customer to submit separate support tickets for each issue to ensure each is handled by the most specialized team.
展開解析

Correct Answer: C

多訴求請求的正確處理模式是：先把不同訴求拆解成獨立項目，利用共享的客戶 context 平行調查每一項（各項之間不必重新查詢客戶資料），最後將所有調查結果綜合成一個完整、統一的回覆。這個流程兼顧了效率（平行調查）和客戶體驗（一次給出完整答案）。

A 錯在哪：多訴求本身不構成升級的理由；升級的判準是問題超出系統能力範圍或需要人工判斷，而非問題數量多。B 錯在哪：逐一序列處理導致回應時間拉長、客戶體驗碎片化，且每次只回答一項讓客戶覺得問題沒被一次解決。D 錯在哪：要求客戶拆分成多個工單是把複雜性轉嫁給客戶，是典型的反模式，嚴重損害服務體驗。

Q 3 Scenario 1 · Customer Support Resolution Agent

A customer support agent determines that a case requires human intervention. It calls escalate_to_human with only the message: "Customer has a refund issue, please handle." The receiving human agent must then call the customer back and re-ask for all details already discussed. Which change best addresses this handoff failure?

  1. Attach the full conversation transcript to the escalation so the human agent can read through the entire interaction history.
  2. Compile a structured handoff summary containing customer ID, root cause analysis, refund amount, and recommended action before calling escalate_to_human.
  3. Add a system prompt instruction telling the agent to include more detail when escalating.
  4. Store the conversation in a shared database that human agents can query when they receive an escalation.
展開解析

Correct Answer: B

結構化交接摘要的設計原則是：提供真人接手所需的所有關鍵欄位（客戶 ID、根因、退款金額、建議行動），讓真人在不看對話記錄的情況下就能直接接手。這些欄位是最小化但完整的「接手套件」，確保交接效率最高。

A 錯在哪：附上完整對話記錄雖然資訊完整，但要求真人從頭閱讀長篇對話以找出關鍵資訊效率極低；結構化摘要的優點正是把關鍵資訊萃取出來，讓真人無需閱讀原始記錄。C 錯在哪：在 system prompt 叮嚀 agent 是機率性做法，無法保證每次交接都包含所有必要欄位；程式層應該強制執行結構化輸出。D 錯在哪：建立共享資料庫讓真人主動查詢，增加了真人的操作負擔，且依賴真人記得去查——比直接在交接請求中附帶摘要效率低。
