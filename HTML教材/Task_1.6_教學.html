Task Statement 1.6 — Design task decomposition strategies for complex workflows

Knowledge of:

  • When to use fixed sequential pipelines (prompt chaining) versus dynamic adaptive decomposition based on intermediate findings
  • Prompt chaining patterns that break reviews into sequential steps (e.g., analyze each file individually, then run a cross-file integration pass)
  • The value of adaptive investigation plans that generate subtasks based on what is discovered at each step

Skills in:

  • Selecting task decomposition patterns appropriate to the workflow: prompt chaining for predictable multi-aspect reviews, dynamic decomposition for open-ended investigation tasks
  • Splitting large code reviews into per-file local analysis passes plus a separate cross-file integration pass to avoid attention dilution
  • Decomposing open-ended tasks (e.g., "add comprehensive tests to a legacy codebase") by first mapping structure, identifying high-impact areas, then creating a prioritized plan that adapts as dependencies are discovered
本題情境 · SCENARIO 5
Scenario 5 — Claude Code for Continuous Integration

你在把 Claude Code 接進 CI/CD 做自動 code review。本 Task 的任務拆解策略,決定大型 PR 要拆成逐檔 local review 還是跨檔 integration review,以維持注意力不被稀釋。

一句話抓住主軸:把大任務拆小有兩種路——「固定流水線（pipeline）」(prompt chaining，提示串接,步驟事先排好)和「動態適應拆解（dynamic decomposition）」(走一步看一步,依發現生成下一步)。 整個 Task 就在教你「什麼時候用哪一種」。

Knowledge of · 知識點

知識 1  固定流水線（pipeline，管線）(prompt chaining) vs 動態適應拆解

遇到這個問題時用到你在設計一個新任務的執行策略，需要判斷應該預先排好固定步驟，還是讓系統根據執行過程中的發現動態生成下一步，而這個判斷取決於任務的可預測程度。

這是 Task 1.6 的主軸對比。
固定流水線:步驟在開始前就排定,一步接一步固定走,適合可預測的任務(我事先就知道要做哪幾步)。
動態適應拆解:下一步要做什麼,取決於上一步發現了什麼,適合開放式、事前無法把步驟列完的任務。

# 固定流水線:步驟事先排好,照順序跑(可預測任務)
def fixed_pipeline(doc):
    a = step_extract(doc)     # 步驟固定
    b = step_summarize(a)
    c = step_translate(b)
    return c

# 動態適應:下一步依「這一步的發現」決定(開放式任務)
def adaptive(goal):
    findings = investigate(goal)
    next_tasks = plan_from(findings)   # 依發現生成子任務
    return run(next_tasks)
考點重點:可預測 → 固定流水線;開放/未知 → 動態適應拆解。

知識 2  Prompt chaining（提示串接）:把審查拆成「逐步」的序列

遇到這個問題時用到大型 PR 的 code review 一次把所有變更檔塞進同一個 context，模型對每個檔案的分析都很淺，跨檔依賴問題更是完全漏看，你需要一個能保持分析深度的拆解策略。

prompt chaining 的經典用法是把一個複雜審查切成幾個固定步驟,前一步的輸出餵給後一步。官方例子:先逐一分析每個檔案,再跑一個跨檔整合(cross-file integration)pass。先個別、再整體,兩階段串起來。

# Prompt chaining:逐檔分析 → 跨檔整合(兩階段序列)
def review_codebase(files):
    # 階段一:每個檔案各自分析
    per_file = [analyze_one_file(f) for f in files]

    # 階段二:把各檔結果合起來,跑一次跨檔整合
    return cross_file_integration_pass(per_file)
考點重點:典型 chain = 逐檔 local 分析 →(串)→ 跨檔 integration pass。

知識 3  適應式調查計畫的價值:依「每步的發現」長出子任務（dynamic decomposition，動態拆解）

遇到這個問題時用到你接到一個開放式任務（如「找出系統的效能瓶頸」），事前無法列出完整步驟，需要一種在調查過程中根據發現動態生成下一步的機制。

開放式任務的價值在於:你事前不可能列完所有步驟。適應式計畫讓系統在每一步根據實際發現,動態生成接下來該做什麼。發現了相依性、發現了高風險區,計畫就跟著長出對應的新子任務。

# 適應式調查:每步的發現,決定下一批子任務
def adaptive_investigation(goal):
    plan = [initial_step(goal)]
    results = []
    while plan:
        step = plan.pop(0)
        found = execute(step)
        results.append(found)
        # 依「這步發現了什麼」生成新的子任務,加回計畫
        plan += generate_subtasks_from(found)   # ✅ 計畫會長大
    return results
考點重點:適應式計畫 = 子任務由「中途發現」生成,而非一開始就寫死。

Skills in · 技能點

技能 1  為工作流（workflow，工作流程）挑對拆解模式

遇到這個問題時用到你要為不同類型的任務選擇合適的拆解策略——多面向的標準安全審查使用 prompt chaining，而開放式的舊系統漏洞調查則使用動態拆解，兩者不能混用。

這是知識 1 的實作判斷。看到任務先分類:可預測的多面向審查(我知道要查哪幾項)→ 用 prompt chaining（提示串接）;開放式調查(終點不明、得邊查邊定方向)→ 用 動態拆解（dynamic decomposition）。挑錯模式的代價:用固定流水線做開放任務會卡住,用動態拆解做可預測任務則徒增複雜度。

def choose_decomposition(task):
    if task.is_predictable():       # 面向已知、步驟可列
        return "prompt_chaining"      # ✅ 固定流水線
    else:                            # 開放式、終點不明
        return "dynamic_decomposition" # ✅ 動態適應
重點:可預測多面向審查 → chaining;開放式調查 → 動態拆解。

技能 2  大型 code review 拆成「逐檔 local + 跨檔 integration」避免注意力稀釋（attention dilution）

遇到這個問題時用到CI pipeline 中的自動 code review 對包含 15 個變更檔的 PR 分析品質極差，每個檔案的問題都被忽略了，因為模型的注意力被稀釋在太多檔案上。

為什麼要拆?因為一次把所有檔案塞進同一個 context（對話歷史），模型的注意力會被稀釋（attention dilution，注意力稀釋）——看了太多東西,每個都看不細。解法:每個檔案單獨跑一個 local 分析 pass(注意力集中在一個檔),再用一個獨立的 pass 處理跨檔關係。

# ❌ 全部塞一起 → 注意力稀釋,每個檔都看不深
review(all_files_concatenated)

# ✅ 拆開:CI 中對 PR 的每個變更檔各跑一次 local pass
# 每個 pass 用 `claude -p` 非互動執行,避免 CI job 卡在等待輸入
def review_pull_request(changed_files):
    local = [claude_p(f"review {f}") for f in changed_files]  # 一次專心一個檔
    integration = cross_file_pass(local)        # 另一個 pass 看全局
    return local, integration
重點:逐檔 local + 獨立跨檔 integration → 避免 attention dilution。

技能 3  拆開放式任務:先測繪結構 → 找高影響區 → 建可調整的優先計畫（adaptive plan）

遇到這個問題時用到你被要求為一個多年未維護的舊程式庫補充完整的測試覆蓋率，面對幾萬行程式碼無從下手，需要一個系統化的拆解方法讓任務可以落地執行。

官方例子是「為老舊程式庫補上完整測試」。這種沒有現成步驟的任務,正確拆法是三段:(1) 先 map 結構(摸清整體長相)→ (2) 找出高影響區(哪些地方最該先測)→ (3) 排出優先順序的計畫,並隨著發現相依性而調整。重點在最後一句:計畫不是死的,發現新相依性就更新。

# 開放式任務拆解三步:測繪 → 找高影響區 → 可調整計畫
def decompose_legacy_testing(codebase):
    structure   = map_structure(codebase)        # 1. 先摸清結構
    high_impact = find_high_impact_areas(structure) # 2. 找最該先測的
    plan        = prioritize(high_impact)         # 3. 排優先序

    for area in plan:
        deps = discover_dependencies(area)
        plan = adapt_plan(plan, deps)   # ✅ 發現相依性就調整計畫
    return plan
重點:map 結構 → 找高影響區 → 排優先序 → 隨相依性發現持續調整。

整個 Task 1.6 的記憶骨架

任務拆解有兩條路:固定流水線(prompt chaining)給可預測任務(例:逐檔分析 → 跨檔整合),動態適應拆解給開放式任務(子任務由中途發現長出)。挑模式看任務可不可預測。大型 review 要拆成逐檔 local + 獨立跨檔 pass 以免注意力稀釋;開放式任務(如補測試)則先測繪結構 → 找高影響區 → 排優先序,並隨相依性發現持續調整。

Q 1 Scenario 5 · Claude Code for Continuous Integration

A CI pipeline uses Claude Code to review pull requests. For a PR with 18 changed files, the automated review flags only 2 low-severity issues and misses a critical API contract violation that spans multiple files. Engineers manually reviewing the same PR easily spotted the issue. What is the most likely root cause of the automated review's poor performance?

  1. Claude Code lacks access to the external API documentation needed to detect contract violations.
  2. All 18 files were processed in a single context window, causing attention dilution that prevented deep analysis of any individual file or cross-file relationship.
  3. The CI pipeline did not provide Claude Code with the full git diff, so it only saw partial changes.
  4. Claude Code requires interactive mode to detect complex multi-file issues and cannot run effectively in non-interactive CI environments.
展開解析

Correct Answer: B

Attention dilution（注意力稀釋）是把大型 code review 一次全部塞進 context 的核心問題：模型面對大量內容，每個部分的分析深度都被稀釋，跨檔關係更是難以追蹤。正確做法是把 review 拆成兩個階段——先對每個變更檔各自跑獨立的 local pass（注意力集中在一個檔），再跑一個專門的跨檔 integration pass。

A 錯在哪：外部 API 文件存取問題與 attention dilution 無關；即使有外部文件，若注意力被 18 個檔稀釋，也無法做深入分析。C 錯在哪：git diff 完整性是前置條件問題，但題目描述的症狀（淺層分析、漏掉跨檔關係）是典型的 attention dilution 表現，而非資料缺失。D 錯在哪：claude -p（非互動模式）正是專為 CI 設計的執行方式，可以對每個檔案獨立呼叫；非互動模式不是導致品質差的原因。

Q 2 Scenario 5 · Claude Code for Continuous Integration

A team is designing an automated task: "Add comprehensive test coverage to a legacy Python codebase with 50,000 lines of code." They propose two approaches: (A) Define fixed sequential steps upfront: scan all files → generate tests → run tests → report. (B) Start by mapping the codebase structure, identify high-impact areas, then generate a prioritized plan that adapts as dependencies are discovered. Which approach is most appropriate and why?

  1. Approach A, because fixed sequential pipelines are always more reliable and predictable in CI environments.
  2. Approach A, because the steps (scan, generate, run, report) are well-defined and can be executed in a deterministic order.
  3. Approach B, because this is an open-ended task where the structure, dependencies, and high-impact areas cannot be known upfront and must be discovered during execution.
  4. Approach B, because adaptive decomposition is always superior to fixed pipelines regardless of task type.
展開解析

Correct Answer: C

「為舊程式庫補完整測試」是典型的開放式任務：你事前不知道哪些模組最重要、哪些有複雜的相依性、哪些已有部分測試。正確的動態適應拆解方法是：先 map 結構（摸清整體）→ 找高影響區（哪裡最值得先測）→ 建立可調整的優先計畫，並隨著發現新相依性不斷更新計畫。這種方法能應對「邊查邊發現新資訊」的開放式任務本質。

A 錯在哪：固定流水線適合可預測的任務，但「為未知的舊程式庫補測試」步驟無法事先完全定義；用固定流水線可能在發現複雜相依性時卡住。B 錯在哪：雖然「scan → generate → run → report」看似有步驟，但這個框架太粗糙，無法處理「哪些地方先測」「如何應對發現的相依性」等關鍵決策；表面上有步驟不代表適合固定流水線。D 錯在哪：動態適應拆解並非萬用最優解——對可預測的多面向審查（如標準安全 checklist）用動態拆解反而會徒增複雜度和不確定性。

Q 3 Scenario 5 · Claude Code for Continuous Integration

A CI job uses Claude Code to review a pull request with 12 changed files. The per-file analysis is thorough, but the final report misses a breaking change where a function signature modified in utils.py is called with the old signature in three other files. Which change best addresses this gap?

  1. Increase the context window size so all 12 files can be analyzed together in a single pass.
  2. Run a separate cross-file integration pass after all per-file local analyses are complete, specifically to detect inter-file dependencies and interface consistency issues.
  3. Add a static analysis linter to the CI pipeline to catch signature mismatches before Claude Code runs.
  4. Ask Claude Code to re-analyze the files in reverse order to ensure it does not miss later-occurring changes.
展開解析

Correct Answer: B

這道題描述的問題正是「逐檔 local pass + 跨檔 integration pass」架構的設計初衷。逐檔分析能確保每個檔案被深入審查（已做到），但跨檔關係（函式簽名變更、介面一致性）需要一個獨立的 integration pass 專門處理。在所有 local pass 完成後，用各檔的摘要跑一次跨檔整合分析，能有效捕捉此類跨越多個檔案的介面問題。

A 錯在哪：加大 context window 讓所有檔案塞進同一個 context，會重新引入 attention dilution 問題——單一 pass 容量雖然更大，但注意力仍然被分散；兩階段架構（逐檔 + 跨檔）才是正確解法。C 錯在哪：靜態分析工具確實能捕捉簽名不符，但這個問題問的是 task decomposition 策略，且靜態工具無法替代語意層面的 code review；兩者互補但選項 B 更直接回答了如何在現有架構中解決跨檔問題。D 錯在哪：改變分析順序不能解決跨檔依賴問題——無論正序還是逆序，逐檔分析的設計就是每次只看一個檔，無法在同一個 pass 中偵測跨檔關係。
