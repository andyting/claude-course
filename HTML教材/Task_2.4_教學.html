Task Statement 2.4 — Integrate MCP servers into Claude Code and agent workflows

Knowledge of:

  • MCP server scoping: project-level (.mcp.json) for shared team tooling vs user-level (~/.claude.json) for personal/experimental servers
  • Environment variable expansion in .mcp.json (e.g., ${GITHUB_TOKEN}) for credential management without committing secrets
  • That tools from all configured MCP servers are discovered at connection time and available simultaneously to the agent
  • MCP resources as a mechanism for exposing content catalogs (e.g., issue summaries, documentation hierarchies, database schemas) to reduce exploratory tool calls

Skills in:

  • Configuring shared MCP servers in project-scoped .mcp.json with environment variable expansion for authentication tokens
  • Configuring personal/experimental MCP servers in user-scoped ~/.claude.json
  • Enhancing MCP tool descriptions to explain capabilities and outputs in detail, preventing the agent from preferring built-in tools (like Grep) over more capable MCP tools
  • Choosing existing community MCP servers over custom implementations for standard integrations (e.g., Jira), reserving custom servers for team-specific workflows
  • Exposing content catalogs as MCP resources to give agents visibility into available data without requiring exploratory tool calls
本題情境 · SCENARIO 2
Scenario 2 — Code Generation with Claude Code

團隊用 Claude Code 做產生程式、重構、除錯與文件。本 Task 要把外部系統(GitHub、Jira、資料庫)透過 MCP server 接進 Claude Code:用 .mcp.json 分享給全隊、用 ${GITHUB_TOKEN} 管金鑰、用 MCP resources 讓 agent 不必一直瞎探。

一句話抓住主軸:「設定放哪裡(scope)」與「金鑰怎麼不外洩」是這個 Task 的兩條主線。 共用工具放專案層、個人實驗放使用者層;金鑰永遠用環境變數展開,絕不寫死進會進版控的檔案。

Knowledge of · 知識點

知識 1  MCP server 的 scope：專案層 .mcp.json vs 使用者層 ~/.claude.json

遇到這個問題時用到你的團隊新加入了一個 GitHub MCP server，有人把設定寫在個人機器的使用者層設定檔，導致其他隊友 clone 後無法使用；你需要理解 MCP server 設定的 scope 機制，決定設定應該放哪裡。

同一個團隊要共用的 MCP server(例如連 GitHub、Jira),設定要寫進專案層的 .mcp.json——這個檔放在 repo 裡、會進版控,所以 clone 下來的每個隊友都自動拿到同一套工具。反過來,你個人在玩、還在實驗的 server,放使用者層的 ~/.claude.json——只對你生效,不會吵到隊友。

判斷準則很簡單：「這個工具該不該被全隊看到？」該 → 專案層（project-scoped）；只是自己用 → 使用者層（user-scoped）。

# 專案層 .mcp.json(放 repo 根目錄,會進版控 → 全隊共用)
# 例:Code Generation 團隊共用的 GitHub MCP server
{
  "mcpServers": {
    "github": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-github"]
    }
  }
}

# 使用者層 ~/.claude.json(只在你機器上 → 個人/實驗用)
{
  "mcpServers": {
    "my-scratch-tool": { "command": "python", "args": ["~/experiments/tool.py"] }
  }
}
考點重點:共用 → .mcp.json(專案層、進版控);個人實驗 → ~/.claude.json(使用者層、不分享)。

知識 2  環境變數展開（environment variable expansion）：用 ${GITHUB_TOKEN} 管金鑰，不把 secret 寫進版控

遇到這個問題時用到安全審查發現有人不小心把 GitHub personal access token 硬編碼進 .mcp.json 並 commit 到 repo，導致 token 外洩，你需要了解如何用環境變數展開機制避免 secret 進入版控。

.mcp.json 會進版控，所以絕對不能把真正的 token 字串直接寫進去——一旦 commit，全世界都看得到。正確做法是寫 ${GITHUB_TOKEN} 這種環境變數佔位符（environment variable placeholder），Claude Code 在連線時會去環境變數裡把真值展開填入。檔案裡只留變數名，真值留在每個人各自的環境裡。

# .mcp.json:用 ${VAR} 佔位,真 token 不入庫
{
  "mcpServers": {
    "github": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-github"],
      "env": {
        # ✅ 佔位符:連線時從環境變數展開
        "GITHUB_PERSONAL_ACCESS_TOKEN": "${GITHUB_TOKEN}"
      }
    }
  }
}

# 真值放各自環境(.env / shell),不進版控
# export GITHUB_TOKEN="ghp_xxxxxxxxxxxx"

# ❌ 千萬不要:把真 token 寫死進 .mcp.json → commit 即外洩
# "GITHUB_PERSONAL_ACCESS_TOKEN": "ghp_realsecret123"
一句話記住:檔案只放 ${VAR} 名字,真金鑰留在環境變數。

知識 3  所有 MCP server 的工具在「連線時」被一次發現，同時可用（tool discovery at connection time）

遇到這個問題時用到你的 agent 同時掛載了 GitHub 和 Jira MCP server，有人擔心 agent 在同一任務中無法同時存取兩邊的工具，你需要說明 MCP 的工具發現機制如何讓多個 server 的工具並存可用。

Claude Code 啟動連線時,會把所有已設定的 MCP server(專案層 + 使用者層)的工具一次全部探索出來,然後同時放進 agent 可用的工具清單。不是用到才連、也不是一次只能開一個——是連線當下全部就緒、同時可用。

實務含意:你掛了 GitHub server 又掛了 Jira server,agent 在同一個任務裡可以一邊查 issue、一邊開 PR,兩邊工具並存,不需要切換。

# 連線時:三個 server 的工具一次全被發現,同時進工具清單
{
  "mcpServers": {
    "github": { "command": "npx", "args": ["-y", "@modelcontextprotocol/server-github"] },
    "jira":   { "command": "npx", "args": ["-y", "@community/mcp-jira"] },
    "postgres":{ "command": "npx", "args": ["-y", "@modelcontextprotocol/server-postgres"] }
  }
}
# → agent 同時握有 github_*、jira_*、postgres_* 全部工具,
#   可在同一次寫程式任務裡查 issue、讀 schema、開 PR。
重點:連線時一次發現全部工具 → 多個 server 的工具「同時並存可用」。

知識 4  MCP resources：把「內容目錄」攤開，減少 exploratory tool calls（探索性工具呼叫）

遇到這個問題時用到你的 agent 在開始寫程式之前總是先發出一連串的 list_issues、get_issue 呼叫來了解有哪些工作，浪費大量 token 和時間，你需要了解如何用 MCP resources 讓 agent 直接看到可用資料的目錄，省掉這些探索性呼叫。

除了「工具(tools)」,MCP server 還能提供「資源(resources)」。Resources 就像把一份內容目錄(issue 摘要清單、文件層級結構、資料庫 schema)直接攤開給 agent 看。差別在哪?沒有 resources 時,agent 為了搞清楚「有哪些資料可用」,得先發一堆探索性工具呼叫(列 issue、列表格、翻目錄);有 resources,它一眼就看到全貌,省掉那些來回。

# ❌ 沒有 resources:agent 為了知道有哪些 issue,先瞎探
list_issues()        # 探索呼叫 1
get_issue(101); get_issue(102); get_issue(103)  # 一個個翻…

# ✅ 用 MCP resource 攤開內容目錄(例:issue 摘要清單)
# server 把目錄當 resource 暴露,agent 連線時就看得到:
{
  "resources": [
    { "uri": "jira://issues/summary",
      "name": "Open issues summary",
      "description": "所有未結 issue 的標題、狀態、負責人一覽" },
    { "uri": "db://schema/public",
      "name": "Database schema" }
  ]
}
# → agent 直接讀目錄,不必先發一串探索性呼叫
重點:resources = 攤開「有哪些資料」的目錄 → 少掉探索性工具呼叫。

Skills in · 技能點

技能 1  在專案層 .mcp.json 設定共用 server，並用環境變數展開做驗證

遇到這個問題時用到你的 Code Generation 團隊要把 GitHub MCP server 共享給所有開發者，同時確保每個人的 access token 不會洩漏到 git 歷史記錄，你需要正確設定專案層設定檔並使用環境變數展開來管理認證。

這是知識 1 + 2 的合體實作:共用的 GitHub MCP server 寫進 .mcp.json,認證 token 用 ${GITHUB_TOKEN} 展開。隊友 clone 下來,各自設好自己的 GITHUB_TOKEN 環境變數即可,設定檔本身不含任何 secret。

# .mcp.json — 共用 + 環境變數展開(Code Generation 團隊範例)
{
  "mcpServers": {
    "github": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-github"],
      "env": { "GITHUB_PERSONAL_ACCESS_TOKEN": "${GITHUB_TOKEN}" }
    }
  }
}
# 隊友只需:export GITHUB_TOKEN=... → 工具立即可用,設定零洩漏

技能 2  個人/實驗 server 設在使用者層 ~/.claude.json

遇到這個問題時用到你正在開發一個實驗性的自訂程式碼掃描 MCP server，需要在 Claude Code 中測試它但不想影響同事的工作環境，你需要知道應該把設定放在哪個層級。

你正在寫一個自製的程式碼掃描工具,還沒成熟、不想推給全隊。放使用者層的 ~/.claude.json,只在你機器上生效,既能立刻在 Claude Code 裡試,又不會污染專案設定。

# ~/.claude.json — 只屬於你的實驗性 server
{
  "mcpServers": {
    "my-lint-experiment": {
      "command": "python",
      "args": ["~/dev/experimental-linter/server.py"]
    }
  }
}
# 成熟後再「升級」到專案層 .mcp.json 分享給全隊
重點:實驗放使用者層,穩定後再搬到專案層分享。

技能 3  把 MCP tool description（工具描述）寫詳細，免得 agent 寧可用 Grep 也不用更強的工具

遇到這個問題時用到你安裝了一個能跨整個 GitHub 組織做語意搜尋的 MCP 工具，但 agent 仍然偏好使用只能搜尋本機檔案的內建 Grep，你需要了解為何工具描述不夠具體會讓 agent 退回使用熟悉的內建工具。

這條很反直覺、很常考。你裝了一個強大的 GitHub 程式碼搜尋 MCP 工具,結果 agent 卻一直用內建的 Grep——為什麼?因為你的工具描述太模糊,agent 看不出它比 Grep 強在哪,就退回用熟悉的內建工具。解法:把工具描述寫得具體——它能做什麼、回傳什麼、什麼時候該用它而不是 Grep。

# ❌ 描述太模糊 → agent 看不出價值,寧可退回用內建 Grep
{ "name": "code_search", "description": "Search code" }

# ✅ 描述具體:講清楚能力、輸出、何時優於 Grep
{
  "name": "code_search",
  "description": "跨整個 GitHub 組織做語意 + 符號搜尋,回傳檔案路徑、"
                 "行號、所屬函式與呼叫關係。當需要跨 repo 找某函式的"
                 "所有呼叫點時,優先用此工具而非僅限本機的 Grep。"
}
重點:工具描述要寫清楚「能做什麼、回傳什麼、何時勝過 Grep」,否則 agent 會偏好內建工具。

技能 4  標準整合用社群現成 server，自訂 server 留給團隊特有流程

遇到這個問題時用到你的團隊要把 Jira 整合進 Claude Code，有人建議從頭自製一個 MCP server，你需要評估何時應該使用社群現成的解決方案、何時才值得投入自製 server 的開發成本。

遇到像 Jira 這種標準整合,別自己從頭刻一個 MCP server——社群早就有現成、維護良好的版本,拿來用就好。自己寫 server 的成本(開發、維護、踩坑)只該花在團隊特有、社群沒有的工作流上。這是工程取捨,不是技術問題。

# ✅ 標準整合(Jira)→ 直接用社群現成 server
{
  "mcpServers": {
    "jira": { "command": "npx", "args": ["-y", "@community/mcp-jira"] }
  }
}

# ❌ 為了標準 Jira 整合自己刻一個 → 浪費維護成本
# ✅ 自訂 server 只留給「團隊特有」流程,例如:
{
  "mcpServers": {
    "internal-deploy": {   # 公司自家部署系統,社群沒有 → 才值得自製
      "command": "node", "args": ["./tools/deploy-mcp-server.js"]
    }
  }
}
重點:標準的用社群現成;自製只給團隊特有流程。

技能 5  把內容目錄做成 MCP resource，讓 agent 一眼看見可用資料

遇到這個問題時用到你的 agent 在開始寫 SQL 查詢之前總是先一張張列出資料表，耗費了大量 token，你需要把資料庫 schema 做成 MCP resource 讓 agent 連線時就直接看到完整的 schema 目錄，免去探索性呼叫。

技能版的知識 4。把 issue 摘要、文件層級、資料庫 schema 這類「目錄型」內容做成 resource 暴露出去。agent 連線當下就看到「有哪些東西可查」,直接挑要的,不必先發一連串探索性呼叫去摸清楚有什麼。

# 自訂 server 端:把 DB schema 當 resource 暴露
def list_resources():
    return [
        {
            "uri": "db://schema/public",
            "name": "Public schema catalog",
            "description": "所有資料表、欄位、型別與外鍵關係一覽",
        },
    ]

# → agent 寫查詢前直接讀 schema resource,不必先一張張表去試探
重點:目錄型內容 → 做成 resource → agent 少瞎探、直接用。

Q 1 Scenario 2 · Code Generation with Claude Code

A development team wants to share a GitHub MCP server configuration across all team members using version control. An engineer proposes writing the following directly into .mcp.json: "GITHUB_PERSONAL_ACCESS_TOKEN": "ghp_abc123secrettoken". What is the most critical problem with this approach?

  1. The .mcp.json file should be placed in the user's home directory, not the project root.
  2. Hardcoding the token in .mcp.json will commit the secret to version control, exposing it to anyone with repository access.
  3. GitHub tokens cannot be used with MCP servers; OAuth must be used instead.
  4. The token format is invalid and will cause the MCP server to fail to connect.
展開解析

Correct Answer: B

.mcp.json 放在 repo 根目錄會進版控，把真實 token 寫進去等於把 secret commit 出去，任何能存取 repo 的人（包括 CI 系統、fork 的外部人員）都能看到。正確做法是用 ${GITHUB_TOKEN} 環境變數佔位符，讓真值只存在各人的環境變數中而不進入 git 歷史。

A 錯在哪：.mcp.json 本就應該放在專案根目錄（project-scoped），這樣才能進版控被全隊共享；放在使用者層反而失去共享的目的。C 錯在哪：GitHub MCP server 支援 personal access token 認證，題目的問題不在認證方式而在 secret 管理。D 錯在哪：題目沒有顯示 token 格式無效，而且即使格式正確，把真實 token 寫進版控也是嚴重的安全問題。

Q 2 Scenario 2 · Code Generation with Claude Code

A team has configured three MCP servers (GitHub, Jira, PostgreSQL) in their project's .mcp.json. A developer claims that the agent can only use one MCP server at a time and must be explicitly switched between them. The architect needs to correct this misunderstanding. What is the accurate description of how MCP tool discovery works?

  1. MCP servers are connected lazily — tools from each server are only discovered when the agent first calls a tool from that server.
  2. All configured MCP servers are connected at startup, and their tools are discovered simultaneously and made available to the agent at the same time.
  3. The agent can only use tools from one MCP server per conversation turn; switching servers requires a new API call.
  4. MCP tools are discovered in the order the servers are listed in .mcp.json, and later tools may override earlier ones with the same name.
展開解析

Correct Answer: B

MCP 的工具發現機制是在連線時（connection time）一次性探索所有已設定的 server，並將全部工具同時加入 agent 的可用工具清單。這代表 agent 在同一個任務中可以同時使用來自 GitHub、Jira 和 PostgreSQL 的工具，不需要任何切換動作。

A 錯在哪：MCP server 不是 lazy loading，而是在連線時主動一次全部探索；「第一次呼叫時才發現」的描述是錯的。C 錯在哪：agent 在單一 conversation turn 中可以同時呼叫來自不同 server 的工具，不存在「每次只能用一個 server」的限制。D 錯在哪：MCP 沒有「後來的工具覆蓋先前的」機制；工具依其名稱和來源識別，不依序覆蓋。

Q 3 Scenario 2 · Code Generation with Claude Code

A Claude Code agent is configured with a powerful code_search MCP tool that performs semantic search across the entire GitHub organization. Despite this, the agent consistently uses the built-in Grep tool instead. The tool description for code_search currently reads: "Search code repositories." What is the most effective change to make the agent prefer the MCP tool?

  1. Add an instruction to the system prompt: "Always prefer code_search over Grep for code searches."
  2. Rename the tool to github_semantic_search so its name better differentiates it from Grep.
  3. Rewrite the tool description to specify its capabilities, outputs, and when to use it over Grep — for example: "Performs semantic and symbol search across the entire GitHub organization; returns file paths, line numbers, and call relationships. Use instead of Grep when cross-repo search or call graph analysis is needed."
  4. Remove Grep from the agent's available tools so it has no alternative.
展開解析

Correct Answer: C

Agent 偏好 Grep 是因為 code_search 的描述「Search code repositories」太模糊，看不出它和 Grep 有何差異或優勢。根據 Task 2.4 技能 3，解法是把工具描述寫具體：說明它能做什麼（語意搜尋、跨 repo）、回傳什麼（路徑、行號、呼叫關係）、何時優於 Grep（需要跨 repo 或呼叫圖分析時）。描述夠清楚，agent 自然知道什麼情況該用它。

A 錯在哪：system prompt 裡的 keyword instruction（"Always prefer code_search"）是 keyword-sensitive 做法，且這個問題的根本原因是工具描述不清，不是 system prompt 沒有指示。B 錯在哪：改名確實有助於區分，但名字本身傳達的資訊有限；真正決定 agent 選擇的是 description 的內容，光改名不夠。D 錯在哪：移除 Grep 是破壞性做法，可能讓 agent 在只需要本機搜尋的情況下也被迫使用較重的 MCP 工具，且沒有解決描述不清的根本問題。
