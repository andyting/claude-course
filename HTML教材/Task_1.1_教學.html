Task Statement 1.1 — Design and implement agentic loops for autonomous task execution

Knowledge of:

  • The agentic loop lifecycle: sending requests to Claude, inspecting stop_reason ("tool_use" vs "end_turn"), executing requested tools, and returning results for the next iteration
  • How tool results are appended to conversation history so the model can reason about the next action
  • The distinction between model-driven decision-making (Claude reasons about which tool to call next based on context) and pre-configured decision trees or tool sequences

Skills in:

  • Implementing agentic loop control flow that continues when stop_reason is "tool_use" and terminates when stop_reason is "end_turn"
  • Adding tool results to conversation context between iterations so the model can incorporate new information into its reasoning
  • Avoiding anti-patterns such as parsing natural language signals to determine loop termination, setting arbitrary iteration caps as the primary stopping mechanism, or checking for assistant text content as a completion indicator
本題情境 · SCENARIO 1
Scenario 1 — Customer Support Resolution Agent

你在用 Claude Agent SDK 打造客服解決 agent,透過 get_customer / lookup_order / process_refund / escalate_to_human 等 MCP 工具處理退貨與帳務爭議。本 Task 的 agentic loop 就是這個 agent 的核心控制流程。

一句話抓住主軸:agentic loop 就是「問 Claude → 看它要不要用工具 → 幫它跑工具 → 把結果餵回去 → 再問」這個圈圈,而停與不停,只看一個訊號:stop_reason。 這個 Task 的所有考點,都繞著「怎麼正確控制這個迴圈的開始、繼續、與結束」轉。

Knowledge of · 知識點

知識 1  agentic loop 的生命週期:送請求 → 看 stop_reason → 執行工具 → 回傳結果

遇到這個問題時用到你的 loop 不知道何時該繼續、何時該停，只能靠猜或硬設次數——正確的控制訊號是什麼？

agentic loop 是一個重複的圈。每一輪:你把目前的對話送給 Claude,Claude 回應後你檢查它的 stop_reason。如果是 "tool_use",代表「它想用工具」——你就去執行它要求的工具,把結果加回對話,再進下一輪。如果是 "end_turn",代表「它講完了、不需要工具了」——迴圈結束。

把它想成你跟助理共事:你交代任務,助理說「我需要查一下資料庫」(tool_use),你幫它查、把結果給它,它再繼續想;直到它說「好了,這是最終答案」(end_turn)。

# agentic loop 的骨架
messages = [{"role": "user", "content": "幫我查訂單 1234 的狀態並處理退款"}]

while True:
    response = client.messages.create(model=MODEL, messages=messages, tools=TOOLS)

    if response.stop_reason == "end_turn":   # ✅ Claude 說完了 → 結束
        break

    if response.stop_reason == "tool_use":   # Claude 要用工具
        messages.append({"role": "assistant", "content": response.content})
        tool_results = execute_tools(response.content)   # 幫它跑工具
        messages.append({"role": "user", "content": tool_results})  # 結果餵回去
考點重點:迴圈的方向盤是 stop_reason;"tool_use" 繼續、"end_turn" 結束。

知識 2  工具結果會被附加到 conversation history（對話歷史）,讓模型據此推理下一步

遇到這個問題時用到Claude 一直重複索取同一個工具，好像完全看不到上一輪的執行結果——問題出在哪裡？

每跑完一個工具,你要把結果加回 messages（即 conversation history，對話歷史）。下一輪 Claude 看到的是「包含這次工具結果」的完整對話,它才能根據新資訊決定接下來要做什麼。如果你跑了工具卻沒把結果加回去,Claude 下一輪等於什麼都沒看到——它會一直重複要求同一個工具,或亂猜。

關鍵:工具結果用 role: "user" 的訊息加回去,且每個結果要對應到當初的 tool_use_id,Claude 才知道「這是我剛剛要的那個工具的回覆」。

def execute_tools(content_blocks):
    results = []
    for block in content_blocks:
        if block.type == "tool_use":
            output = run_tool(block.name, block.input)
            results.append({
                "type": "tool_result",
                "tool_use_id": block.id,     # ↑ 對應回原本的呼叫
                "content": output,
            })
    return results
# 回傳後,呼叫端會把它 append 進 messages,進入下一輪推理
一句話記住:工具結果不回填進對話 = Claude 等於沒看到 = 迴圈空轉。

知識 3  model-driven（模型驅動）決策 vs. pre-configured decision tree（預先寫死的決策樹）

遇到這個問題時用到同事說「直接 if 退款 → 呼叫 A → B → C 把順序寫死就好」——這在生產環境遇到沒想到的情況時會有什麼問題？

agentic loop 的精神是讓 Claude 自己根據 context 決定下一步用哪個工具（即 model-driven，模型驅動）。你提供工具清單,但「先做什麼、再做什麼、要不要做」由 Claude 推理。這跟傳統「寫死的 if-else decision tree（決策樹）/ 固定工具順序（pre-configured tool sequence）」相反——後者每種情況你都得事先想到並寫程式。

差別:pre-configured 流程遇到沒設想過的情況就卡住;model-driven 能依現場彈性應變。代價是它較難預測,所以才需要 stop_reason 這種明確的控制訊號來收尾。

# ❌ 寫死的決策樹:每種情況都要自己 if-else,難以擴充
def handle(req):
    if "退款" in req:
        cust = get_customer()
        order = lookup_order()
        return process_refund(order)   # 順序與分支全靠人手排
    elif "查詢" in req:
        ...

# ✅ model-driven:給工具,讓 Claude 自己決定先後與是否需要
TOOLS = [get_customer, lookup_order, process_refund, escalate_to_human]
# 由 agentic loop 中的 Claude 依 context 推理該呼叫哪個、何時停
重點:agentic = 讓模型推理決策;不是把流程寫死成決策樹。

Skills in · 技能點

技能 1  用 stop_reason 控制迴圈:"tool_use" 繼續、"end_turn" 結束

遇到這個問題時用到你要實作 agentic loop 的 while 迴圈——break 的條件應該長什麼樣？繼續跑的條件又是什麼？

這是知識 1 的實作核心。控制流程只該看 stop_reason:等於 "tool_use" 就繼續跑工具進下一輪;等於 "end_turn" 就跳出迴圈。不要用別的東西當主要判斷依據。

# ✅ 正確:迴圈的繼續/終止,只看 stop_reason
def agent_loop(user_msg):
    messages = [{"role": "user", "content": user_msg}]
    while True:
        resp = client.messages.create(model=MODEL, messages=messages, tools=TOOLS)
        messages.append({"role": "assistant", "content": resp.content})

        if resp.stop_reason == "end_turn":
            return resp          # 結束:回傳最終回應

        if resp.stop_reason == "tool_use":
            results = execute_tools(resp.content)
            messages.append({"role": "user", "content": results})
            # 不 break,迴圈自然進下一輪

技能 2  每輪之間把工具結果加進 context,讓模型納入新資訊

遇到這個問題時用到工具執行完了，結果要怎麼「接回」messages 讓 Claude 下一輪能讀到？role 要設什麼、要帶哪個 id？

這是知識 2 的實作版。重點在於「每一輪之間」都要把工具結果回填,Claude 才能把新拿到的資訊納入推理。漏了任何一輪的回填,後續推理就建立在缺漏的資訊上。

# 多步驟範例:查客戶 → 查訂單 → 處理退款,逐步把結果回填
messages = [{"role": "user", "content": "訂單 1234 要退款"}]

while True:
    resp = client.messages.create(model=MODEL, messages=messages, tools=TOOLS)
    messages.append({"role": "assistant", "content": resp.content})
    if resp.stop_reason != "tool_use":
        break
    # ↓ 把這一輪的工具結果加回去,下一輪 Claude 才看得到
    messages.append({"role": "user", "content": execute_tools(resp.content)})
# 每輪累積:客戶資料 → 訂單資料 → 退款結果,全在 context 裡
重點:工具結果要逐輪累積進 context,推理才連貫。

技能 3  避開 anti-patterns（反模式）:別用自然語言、別把 iteration cap 當主要停止機制

遇到這個問題時用到你看到同事寫了 if "完成" in resp.text: break，或是 for i in range(5): 來控制 loop——這三種反模式分別錯在哪裡？

這條最常考。三個一定要避開的錯誤停止方式:

Anti-pattern 1（反模式一）:解析自然語言判斷該不該停。例如偵測 Claude 有沒有講「完成了」「done」這種字。模型措辭千變萬化,靠關鍵字判斷一定會誤判。
Anti-pattern 2（反模式二）:把固定 iteration cap（迭代次數上限）當作主要的停止機制。「最多跑 5 圈就停」可以當安全保險絲（safety fuse）,但不能當主要邏輯——任務還沒完就被硬切掉,或上限設太大空轉。
Anti-pattern 3（反模式三）:看 assistant 有沒有文字內容（text content）來判斷是否完成。Claude 在要求工具時也可能附帶文字說明,有文字不代表它做完了。

# ❌ 反模式一:靠關鍵字判斷結束 → 措辭一變就誤判
if "完成" in resp.text or "done" in resp.text:
    break

# ❌ 反模式二:把次數上限當主要停止邏輯
for i in range(5):       # 沒做完就被切掉,或空轉到 5
    ...

# ❌ 反模式三:有文字就當作做完了
if resp.text:
    break          # Claude 要用工具時也常附帶文字說明

# ✅ 正解:停止只看 stop_reason;次數上限只當安全保險絲
MAX = 25   # 防失控用,不是主要邏輯
for _ in range(MAX):
    resp = client.messages.create(...)
    if resp.stop_reason == "end_turn":
        break      # 真正的停止依據
重點:停止只信 stop_reason;關鍵字、文字內容、固定次數都不是可靠的終止依據(次數上限只當保險絲)。

整個 Task 1.1 的記憶骨架

agentic loop 是一個圈:送請求 → 看 stop_reason → 跑工具 → 回填結果 → 再送。方向盤只有一個——stop_reason:"tool_use" 繼續、"end_turn" 結束。每輪都要把工具結果回填進對話歷史,Claude 才能據此推理。決策由模型驅動(不是寫死的決策樹)。要避開三大反模式:靠關鍵字、靠文字內容、把次數上限當主停止機制——次數上限只能當安全保險絲。

考試情境題

以下三題模擬正式考試格式，每題一個生產情境，四個選項。先嘗試作答，再展開解析。

Q 1 Scenario 1 · Customer Support Resolution Agent

Production logs show that your customer support agent terminates the loop early when Claude's response contains phrases like "I'll process your refund now" or "Let me check your order." Approximately 12% of requests end before any tool is actually called. What is the most likely root cause?

  1. The process_refund tool returns inconsistent output formats, causing the loop termination logic to throw an exception.
  2. The loop checks natural language signals in Claude's text response to determine termination, rather than inspecting stop_reason.
  3. The system prompt is missing instructions requiring Claude to call tools before returning a final response.
  4. The agentic loop has no maximum iteration cap, so it falls back to early termination when context grows too large.
展開解析

Correct Answer: B

「Claude 說出特定措辭 → loop 提前停止」是靠自然語言訊號判斷終止的典型症狀。Claude 在呼叫工具時常附帶說明性文字，若以文字內容決定是否結束，就會在工具尚未執行時跳出。正確做法只看 stop_reason："tool_use" 繼續、"end_turn" 才結束。

A 錯在哪：工具回傳格式問題不會造成「特定措辭觸發」的規律性提前停止。C 錯在哪：system prompt 缺失影響的是工具呼叫頻率，不是 loop 在 tool_use 前就終止。D 錯在哪：描述的是 context 大小觸發的問題，與「措辭觸發」的模式完全不符。

Q 2 Scenario 1 · Customer Support Resolution Agent

Production logs show the agent calls get_customer repeatedly within the same session — sometimes 3–4 times — even after a prior call already returned the customer's data successfully. What is the most likely architectural cause?

  1. The get_customer tool description is too broad, causing the model to trigger a call whenever customer-related terms appear in the conversation.
  2. The agentic loop does not append tool results back to the conversation history (messages), so Claude cannot see results from prior iterations.
  3. The system prompt is missing instructions telling Claude to cache lookup results across tool calls.
  4. The maximum iteration cap is set too high, allowing Claude to keep calling tools even when it already has sufficient information.
展開解析

Correct Answer: B

重複索取同一工具是工具結果未回填進 messages 的典型症狀。Claude 下一輪收到的 messages 若不含上一輪的工具結果，它便無法得知資料已取得，因此再次請求。正確做法：每輪後以 role: "user"（帶 tool_use_id）把 tool result 附回 messages。

A 錯在哪：工具描述過廣是「呼叫錯工具」的問題，不會造成同一工具重複呼叫的規律。C 錯在哪：快取是應用層邏輯，agentic loop 的本質是讓模型從對話歷史推理，靠 prompt 指示快取是錯誤方向。D 錯在哪：迭代次數上限是安全保險絲，不會導致特定工具被反覆呼叫的模式。

Q 3 Scenario 1 · Customer Support Resolution Agent

Your team is debating two designs: Option 1 — hardcode tool order with if-else logic (refund request → get_customer → lookup_order → process_refund); Option 2 — provide Claude the full tool set and let the model reason about which tools to call. In production, customers sometimes submit combined refund and billing inquiries, and sometimes need only an order status check. What is the core advantage of the model-driven approach in this varied context?

  1. Option 1, because a fixed sequence guarantees deterministic tool calls and prevents unpredictable model behavior.
  2. Option 2, because the model can adapt its tool usage to unanticipated request combinations based on actual conversation context, without requiring code changes for each new case.
  3. Option 1, because if-else execution is faster than model reasoning, reducing agent response latency.
  4. Option 2, because the stop_reason mechanism automatically enforces the correct tool call order to ensure compliance.
展開解析

Correct Answer: B

model-driven 的核心優勢是「彈性應對未設想情況」——客戶提出混合需求或邊緣情況時，寫死的 if-else 決策樹會卡住或走錯分支，而模型能根據當前 context 推理出合適的工具序列，不需要人工枚舉所有情況。

A 錯在哪：deterministic 是方案一的優點，但「無法應對未設想情況」是嚴重的生產風險，且題目明確說情境多變。C 錯在哪：在實際 API 呼叫延遲面前，if-else 與模型推理的 CPU 差異微不足道；且方案一反而需要人工維護所有分支。D 錯在哪：stop_reason 控制的是 loop 的停止時機，與工具呼叫順序的強制執行無關。
