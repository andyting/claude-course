Task Statement 4.4 — Implement validation, retry, and feedback loops for extraction quality

Knowledge of:

  • Retry-with-error-feedback: appending specific validation errors to the prompt on retry to guide the model toward correction
  • The limits of retry: retries are ineffective when the required information is simply absent from the source document (vs format or structural errors)
  • Feedback loop design: tracking which code constructs trigger findings (detected_pattern field) to enable systematic analysis of dismissal patterns
  • The difference between semantic validation errors (values don't sum, wrong field placement) and schema syntax errors (eliminated by tool use)

Skills in:

  • Implementing follow-up requests that include the original document, the failed extraction, and specific validation errors for model self-correction
  • Identifying when retries will be ineffective (e.g., information exists only in an external document not provided) versus when they will succeed (format mismatches, structural output errors)
  • Adding detected_pattern fields to structured findings to enable analysis of false positive patterns when developers dismiss findings
  • Designing self-correction validation flows: extracting "calculated_total" alongside "stated_total" to flag discrepancies, adding "conflict_detected" booleans for inconsistent source data
本題情境 · SCENARIO 6
Scenario 6 — Structured Data Extraction

承接 4.3:tool_use + schema 已消滅語法錯誤,但語意錯誤(line items 不加總、值放錯欄)還在。本 Task 教你怎麼驗證抽取結果、把錯誤回饋給模型 retry 自我修正,以及判斷哪些情況 retry 根本沒用。範例全用具名工具 extract_invoice 與 calculated_total / stated_total / conflict_detected 欄位。

一句話抓住主軸:schema 保證格式對,但保證不了內容對。抽完要驗、驗錯要把「具體錯在哪」餵回去讓模型重抽——但也要認清:資訊根本不在文件裡時,retry 再多次都沒用。

Knowledge of · 知識點

知識 1  Retry-with-error-feedback:把「具體驗證錯誤」附回 prompt 引導修正

重試的正確姿勢不是「再跑一次,祈禱這次對」,而是把這次到底錯在哪寫清楚,連同原文一起餵回去。例如「line items 加總 1,180 但 stated_total 是 1,240,差 60」——模型拿到具體誤差,才知道往哪修。空泛地說「請再檢查」效果差很多。

考點重點:retry 時 append specific validation errors → 引導模型修正,而非盲目重跑。

知識 2  Retry 的極限:資訊「根本不在文件裡」時,重試無效

非常重要的判斷力。retry 能救的是格式錯、結構錯(模型有資訊只是排錯)。但如果某欄位的資訊壓根不在這份文件裡(例如要 PO 號,但 PO 在另一份沒給的文件),那無論重試幾次,模型只會一直瞎編或一直 null——retry 解決不了「資訊缺席」。

重點:retry 治 format/structural 錯;治不了「required 資訊不存在於來源」。

知識 3  回饋迴圈設計:用 detected_pattern 追蹤「哪種寫法觸發了 finding」

這條跨到 Scenario 5(CI review)的回饋設計。當 review 產生一個 finding,順便記下是哪種 code 構造觸發的(detected_pattern)。日後若開發者一直「駁回(dismiss)」某種 pattern 的 finding,你就能系統性地分析:這個 pattern 是不是高 false positive,該調整 prompt。

重點:detected_pattern 欄位 → 系統性分析 dismissal(駁回)模式、抓 false positive 來源。

知識 4  語意驗證錯誤 vs schema 語法錯誤

把 4.3 的警語講透:schema 語法錯誤(漏引號、型別錯)已被 tool use 消滅;但語意驗證錯誤(數字不加總、值放到錯欄)schema 抓不到,要靠你自己寫驗證邏輯。這兩類錯誤的處理方式不同——語法靠 tool use 預防,語意靠驗證+retry 補救。

重點:semantic errors(不加總/放錯欄)≠ syntax errors(tool use 已解決);前者需自寫驗證。

Skills in · 技能點

技能 1  Follow-up 請求:把原文 + 失敗的抽取 + 具體驗證錯誤一起餵回,讓模型自我修正

實作 retry-with-feedback。重試的那一輪,prompt 要包含三樣:原始文件、上次抽錯的結果、這次驗出的具體錯誤。三者齊備,模型才能對照修正。

def retry_with_feedback(document, failed_extraction, errors):
    # Scenario 6:把原文 + 失敗結果 + 具體錯誤一起餵回 extract_invoice
    correction_prompt = f"""上一次抽取有錯,請修正後重新呼叫 extract_invoice。

[原始發票文件]
{document}

[上次抽取結果(有誤)]
{json.dumps(failed_extraction, ensure_ascii=False)}

[驗證發現的具體錯誤]
{errors}
"""
    return client.messages.create(
        model="claude-sonnet-4-6", max_tokens=1024,
        tools=[extract_invoice],
        tool_choice={"type": "tool", "name": "extract_invoice"},
        messages=[{"role": "user", "content": correction_prompt}],
    )
重點:retry prompt = 原文 + 失敗抽取 + 具體錯誤,三者缺一不可。

技能 2  判斷 retry 會不會有效:資訊缺席 vs 格式/結構錯

retry 不是無腦重跑。先分類錯誤:格式/結構錯 → retry 有救;required 資訊不在來源 → retry 無用,該走別的路(標 needs_external_source、轉人工、或回報缺漏)。亂 retry 只是浪費 token 與時間。

def should_retry(error_type):
    # Scenario 6:格式/結構錯可救;資訊缺席不可救
    retryable = {"format_mismatch", "wrong_field", "not_summing"}
    unfixable = {"info_absent"}   # 例:PO 在另一份未提供的文件

    if error_type in retryable:
        return True           # 餵回錯誤、重抽會成功
    if error_type in unfixable:
        return False          # retry 無效 → 標記缺漏 / 轉人工
    return True
重點:先分類:format/structural → retry;info_absent → 別 retry,改走人工或標缺漏。

技能 3  在 findings 加 detected_pattern,分析開發者駁回的 false positive 模式

承接知識 3。每筆 finding 帶上 detected_pattern,記錄它是被哪種寫法觸發的。累積一陣子後,統計「哪些 pattern 最常被開發者 dismiss」——那多半就是 false positive 大戶,可據此回頭修 prompt(呼應 Task 4.1 暫時停用高誤報類別)。

# Scenario 5/6:finding 帶 detected_pattern,供 dismissal 分析
finding_schema = {
    "type": "object",
    "properties": {
        "location":         {"type": "string"},
        "issue":            {"type": "string"},
        "severity":         {"type": "string"},
        # ↓ 記錄是哪種寫法觸發的,日後統計被駁回率
        "detected_pattern": {"type": "string"},
    },
    "required": ["location", "issue", "detected_pattern"],
}

# 例:某 detected_pattern 被 dismiss 90% → 高 false positive,回頭修 prompt
重點:detected_pattern 讓你量化哪種 pattern 是 false positive 大戶。

技能 4  設計自我校驗流程:抽 calculated_total 對照 stated_total、加 conflict_detected

這是抓語意錯誤的關鍵技巧。與其只抽一個 total,不如同時抽文件上寫的 stated_total與由 line items 自己加總出的 calculated_total,兩者一比就能驗出「不加總」的問題;再加一個 conflict_detected 布林,標記來源資料本身互相矛盾的情況。讓驗證內建在 schema 裡。

# Scenario 6:抽兩個 total 互相對照,內建語意驗證
extract_invoice = {
    "name": "extract_invoice",
    "input_schema": {
        "type": "object",
        "properties": {
            "line_items":       {"type": "array"},
            "stated_total":     {"type": "number"},   # 文件上寫的
            "calculated_total": {"type": "number"},   # line_items 自行加總
            "conflict_detected":{"type": "boolean"},  # 來源自相矛盾時 true
        },
        "required": ["stated_total", "calculated_total", "conflict_detected"],
    },
}

def validate(data):
    # 兩個 total 不一致 → 語意錯誤,觸發 retry-with-feedback
    if abs(data["stated_total"] - data["calculated_total"]) > 0.01:
        return f"stated_total {data['stated_total']} 與加總 {data['calculated_total']} 不符"
    return None
重點:calculated_total vs stated_total 對照 + conflict_detected,把語意驗證做進 schema。

整個 Task 4.4 的記憶骨架

tool_use 消滅語法錯誤,但語意錯誤(不加總、放錯欄)要自己驗。驗到錯就走 retry-with-error-feedback:把原文 + 失敗抽取 + 具體錯誤一起餵回讓模型自我修正。但要先判斷——格式/結構錯 retry 有救,資訊根本不在文件裡時 retry 無用,該轉人工或標缺漏。回饋迴圈用 detected_pattern 追蹤駁回模式抓 false positive;語意驗證的招牌做法是同時抽 calculated_total 對照 stated_total,並加 conflict_detected 標記來源矛盾。
