官方考綱原文

Task Statement 4.3 — Enforce structured output using tool use and JSON schemas

Knowledge of:

  • Tool use (tool_use) with JSON schemas as the most reliable approach for guaranteed schema-compliant structured output, eliminating JSON syntax errors
  • The distinction between tool_choice: "auto" (model may return text instead of calling a tool), "any" (model must call a tool but can choose which), and forced tool selection (model must call a specific named tool)
  • That strict JSON schemas via tool use eliminate syntax errors but do not prevent semantic errors (e.g., line items that don't sum to total, values in wrong fields)
  • Schema design considerations: required vs optional fields, enum fields with "other" + detail string patterns for extensible categories

Skills in:

  • Defining extraction tools with JSON schemas as input parameters and extracting structured data from the tool_use response
  • Setting tool_choice: "any" to guarantee structured output when multiple extraction schemas exist and the document type is unknown
  • Forcing a specific tool with tool_choice: {"type": "tool", "name": "extract_metadata"} to ensure a particular extraction runs before enrichment steps
  • Designing schema fields as optional (nullable) when source documents may not contain the information, preventing the model from fabricating values to satisfy required fields
  • Adding enum values like "unclear" for ambiguous cases and "other" + detail fields for extensible categorization
  • Including format normalization rules in prompts alongside strict output schemas to handle inconsistent source formatting
本題情境 · SCENARIO 6
Scenario 6 — Structured Data Extraction

用 Claude 從非結構化文件抽資料,並以 JSON schema 驗證、接下游系統。本 Task 教你用 tool_use + JSON schema 保證輸出「一定」符合結構(消滅 JSON 語法錯誤),搭配 tool_choice 控制要不要/呼叫哪個 extract_* 工具。所有範例都用具名的 extract_invoice / extract_metadata 工具。

一句話抓住主軸:別再請模型「輸出 JSON」然後自己 parse 字串——把抽取設計成一個帶 JSON schema 的工具,讓模型「呼叫工具」,結構就被保證了。 語法錯誤從此消失,但語意錯誤要另外防。

Knowledge of · 知識點

知識 1  tool_use + JSON schema 是最可靠的 structured output（結構化輸出）方式

遇到這個問題時用到你的發票抽取管線每天有 3% 的請求因為模型回傳的 JSON 包含多餘的說明文字或漏掉引號而 parse 失敗，下游系統因此產生錯誤告警，你需要從根本消滅這類語法錯誤。

傳統做法:在 prompt 裡叫模型「請回我 JSON」,然後你 json.loads() 它的文字回覆——常常遇到漏引號、多逗號、夾雜說明文字而 parse 失敗（syntax error，語法錯誤）。改用 tool use:你定義一個工具,它的 input_schema 就是你要的 JSON 結構;模型「呼叫這個工具」時,參數會保證符合 schema,JSON 語法錯誤直接消滅。

考點重點:guaranteed schema-compliant output、eliminate JSON syntax errors = tool use + JSON schema。

知識 2  tool_choice 三種模式:auto / any / 強制特定工具

遇到這個問題時用到你有三個抽取工具（發票、收據、論文），但傳入的文件類型未知；同時某個流程要求一定要先跑 extract_metadata 才能進行後續 enrichment，你需要為不同情境選擇正確的 tool_choice 設定。

這是 4.3 最常考的辨析,務必記牢:

"auto":模型「可以」呼叫工具,也可以直接回文字(不保證結構化)。
"any":模型必須呼叫某個工具,但可自己選哪一個。
強制特定工具 {"type":"tool","name":"..."}:模型必須呼叫你指定的那一個。

一句話記住:auto=可不叫;any=一定叫但自選;forced=指定叫哪個。

知識 3  schema 消滅 syntax error（語法錯誤）,但不防 semantic error（語意錯誤）

遇到這個問題時用到你改用 tool use 後 JSON parse 失敗率降到零，但財務部門反映有些發票的 line items 加總不等於 total_amount，而這個問題通過了 schema validation，你需要了解為什麼以及如何補救。

很重要的一條警語。strict JSON schema 保證格式對(欄位齊、型別對、是合法 JSON),但它管不到內容對不對:line items 加起來不等於 total、值被放到錯的欄位——這些都是 schema 合法、但 semantic error（語意錯誤）仍然存在的情況。語意錯誤要靠 validation（驗證）流程(Task 4.4)另外抓。

重點:schema 治 syntax errors,治不了 semantic errors(不加總、放錯欄位)。

知識 4  schema 設計:required vs optional、enum 的 "other" + detail 可擴充模式

遇到這個問題時用到你發現模型為了滿足必填的 po_number 欄位而捏造 PO 號碼，同時新的文件類型（信用備忘單）不在 doc_type enum 裡，你需要重新設計 schema 來防幻覺並支援未來擴充。

設計 schema 時兩個關鍵決策:哪些欄位必填(required)、哪些該選填(optional/nullable);以及 enum(列舉)欄位要不要留一個 "other" 加一個 detail 字串欄,讓不在清單上的類別也能被表達——這樣未來新類型不用改 schema 就能容納(可擴充)。

重點:required/optional 要分清;enum 用 "other" + detail 留擴充空間。

Skills in · 技能點

技能 1  把抽取定義成「帶 JSON schema 的工具」,從 tool_use 回覆取結構化資料

遇到這個問題時用到你要把現有的「prompt 請模型輸出 JSON 字串再 parse」的流程，改成保證不會有 JSON 語法錯誤的架構，並且要能從 API 回應中正確取出結構化資料。

核心實作。定義 extract_invoice 工具,input_schema 就是發票該有的欄位;呼叫 API 後,從回覆裡 type == "tool_use" 的 block 取 .input,就是保證合規的結構化資料。

import anthropic
client = anthropic.Anthropic()

# Scenario 6:把「抽發票」定義成一個帶 JSON schema 的工具
extract_invoice = {
    "name": "extract_invoice",
    "description": "從發票文件抽出結構化欄位",
    "input_schema": {
        "type": "object",
        "properties": {
            "invoice_number": {"type": "string"},
            "total_amount":  {"type": "number"},
            "currency":      {"type": "string"},
        },
        "required": ["invoice_number", "total_amount"],
    },
}

resp = client.messages.create(
    model="claude-sonnet-4-6",
    max_tokens=1024,
    tools=[extract_invoice],
    tool_choice={"type": "tool", "name": "extract_invoice"},
    messages=[{"role": "user", "content": document}],
)

# 從 tool_use block 取出保證合規的結構化資料
for block in resp.content:
    if block.type == "tool_use":
        data = block.input   # 已符合 schema 的 dict
重點:工具的 input_schema = 目標結構;從 tool_use block 的 .input 取資料。

技能 2  文件類型未知時,用 tool_choice: "any" 保證有結構化輸出

遇到這個問題時用到你的批次處理管線每天收到數千份混合文件（發票、收據、論文），文件類型沒有事先標籤，你需要保證每一份都用正確的工具抽取，同時不能讓模型回傳純文字跳過結構化輸出。

當你準備了多個抽取 schema(發票、收據、論文),但進來的文件不知道是哪一種,設 tool_choice: "any":強制模型一定要呼叫工具(不准只回文字),但讓它自己選最合適的那個 extract 工具。

# Scenario 6:多個抽取 schema,文件類型不明 → 讓模型自選
tools = [extract_invoice, extract_receipt, extract_paper_metadata]

resp = client.messages.create(
    model="claude-sonnet-4-6",
    max_tokens=1024,
    tools=tools,
    tool_choice={"type": "any"},   # 一定要叫某個工具,但哪個由模型決定
    messages=[{"role": "user", "content": unknown_document}],
)
# 模型會挑出最符合文件型別的 extract_* 工具來呼叫
重點:多 schema + 類型不明 → tool_choice: "any"(一定叫、自選)。

技能 3  強制特定工具:確保某個抽取先跑(在 enrichment 之前)

遇到這個問題時用到你的 enrichment 流程需要先從文件抽出 metadata（類型、日期、供應商），再根據這些 metadata 去外部 API 查詢補充資料，但你發現模型有時跳過 extract_metadata 直接嘗試 enrichment 而失敗。

有時流程上必須先抽出 metadata,後續步驟才能 enrich(補資料)。這時用強制特定工具,確定模型一定先呼叫 extract_metadata,不會跳過或選別的。

# Scenario 6:強制先跑 extract_metadata,再做後續 enrichment
resp = client.messages.create(
    model="claude-sonnet-4-6",
    max_tokens=1024,
    tools=[extract_metadata, enrich_record],
    # 指定名字 → 模型必須先呼叫 extract_metadata
    tool_choice={"type": "tool", "name": "extract_metadata"},
    messages=[{"role": "user", "content": document}],
)
metadata = next(b.input for b in resp.content if b.type == "tool_use")
# 接著才用 metadata 進入 enrichment 步驟
重點:{"type":"tool","name":"extract_metadata"} → 保證指定工具先跑。

技能 4  來源可能沒有的資訊,欄位設為 optional(nullable),防止模型瞎編

遇到這個問題時用到你把 po_number 放進 required 後，稽核發現模型在沒有採購單的一般消費發票上捏造了 PO 號碼，這些假數字進入了 ERP 系統，你需要修正 schema 設計防止這種幻覺。

關鍵反幻覺技巧。如果某欄位放進 required,但文件其實沒有那個資訊,模型為了「滿足必填」就會編一個值。正確做法:把「不一定有」的欄位設成 nullable / optional,讓模型可以誠實回 null,而不是捏造。

# Scenario 6:po_number 不是每張發票都有 → 設 nullable
schema = {
    "type": "object",
    "properties": {
        "invoice_number": {"type": "string"},
        # ✅ 可為 null:文件沒有時就回 null,不會被逼著瞎編
        "po_number": {"type": ["string", "null"]},
    },
    # po_number 不放進 required → 允許缺漏
    "required": ["invoice_number"],
}
重點:來源可能沒有 → optional/nullable,防止為了滿足 required 而捏造。

技能 5  enum 加 "unclear"(模糊)與 "other" + detail(可擴充)

遇到這個問題時用到你的 doc_type enum 只有 invoice/receipt/paper，但客戶開始傳來信用備忘單和退款通知，模型強行把這些分到最近似的類別，產生錯誤的分類結果，你需要在不改 schema 的前提下容納新類型。

enum 限制了可選值,但現實會有判不準和清單外的情況。兩個慣用補丁:加一個 "unclear" 讓模型在不確定時誠實標註(而非硬猜);加 "other" 搭配一個 detail 字串欄,容納未列舉的新類別。

# Scenario 6:文件分類 enum,留 unclear 與 other
schema = {
    "type": "object",
    "properties": {
        "doc_type": {
            "type": "string",
            # unclear=判不準也不硬猜;other=清單外的新類型
            "enum": ["invoice", "receipt", "paper", "unclear", "other"],
        },
        "other_detail": {"type": ["string", "null"]},  # 當 other 時填說明
    },
    "required": ["doc_type"],
}
重點:enum 加 "unclear"(誠實)與 "other"+detail(可擴充)。

技能 6  在 prompt 裡併入「格式正規化規則」,搭配嚴格 schema

遇到這個問題時用到你的發票來自不同國家的供應商，日期格式有 2024/1/3、Jan 3 2024、03-01-24 等多種寫法，金額有 $1,240 和 1240.00 兩種格式，雖然 schema 保證了欄位存在，但欄位內的格式不統一讓下游系統無法直接使用。

schema 管結構,但來源格式很亂(日期 2024/1/3 vs Jan 3 2024、金額 $1,240 vs 1240.00)。光靠 schema 不會自動統一。做法:在 prompt 裡寫明正規化規則(日期一律 ISO、金額去逗號轉 number),讓輸出進到 schema 前先被統一。

# Scenario 6:嚴格 schema + prompt 內的正規化規則
prompt = """抽取發票欄位。正規化規則:
- 日期一律轉成 ISO 格式 YYYY-MM-DD
- 金額去除貨幣符號與千分位逗號,輸出純數字(number)
- 幣別轉成 ISO 4217 代碼(NT$ → TWD,$ → USD)
""" + document

resp = client.messages.create(
    model="claude-sonnet-4-6", max_tokens=1024,
    tools=[extract_invoice],
    tool_choice={"type": "tool", "name": "extract_invoice"},
    messages=[{"role": "user", "content": prompt}],
)
重點:schema 管結構、prompt 裡的 normalization rules 管「亂格式統一」,兩者並用。

整個 Task 4.3 的記憶骨架

要保證結構化輸出,別 parse 字串——把抽取設計成帶 JSON schema 的工具,從 tool_use 取 .input,JSON 語法錯誤消滅。tool_choice 三模式:auto(可不叫)、any(一定叫、自選,用於文件類型不明)、forced(指定工具先跑,如 extract_metadata)。schema 治語法不治語意(不加總、放錯欄位要靠 4.4)。設計上:來源可能沒有的欄位設 nullable 防瞎編;enum 加 "unclear" / "other"+detail;再把正規化規則寫進 prompt 統一亂格式。

考試情境題

Q 1 Scenario 6 · Structured Data Extraction

Your invoice extraction service processes 10,000 documents daily. Currently you ask Claude to "respond with a JSON object" and parse the text response with json.loads(). Your monitoring shows a 4% failure rate from JSON syntax errors — missing quotes, extra commas, or explanatory text mixed into the response. What is the most reliable architectural fix?

  1. Add "respond only with valid JSON, no extra text" to the system prompt and implement retry logic on parse failures.
  2. Define an extract_invoice tool with a JSON input_schema and use tool_choice to force the model to call it, then read the structured data from the tool_use block's .input field.
  3. Use few-shot examples showing valid JSON output to train the model to produce better-formatted responses.
  4. Post-process the model's text response with a regex to extract the JSON portion before parsing.
展開解析

Correct Answer: B

B 正確：tool use + JSON schema 是「消滅 JSON syntax error（語法錯誤）」的根本解法。模型呼叫工具時，API 層保證輸出符合 input_schema，不可能出現漏引號或夾雜說明文字的問題。從 tool_use block 的 .input 取值，得到的就是已保證合規的 dict，不需要 parse 字串。

A 錯在哪：再強調「只回 JSON」仍是依賴模型的文字輸出，4% 失敗率是模型行為特性，不是因為指令不夠明確；加 retry 只是緩解症狀，無法從根本消滅語法錯誤。C 錯在哪：few-shot 可以提升一致性，但不能「保證」不出現語法錯誤，遇到複雜或邊界文件仍可能出問題，達不到「消滅」的效果。D 錯在哪：regex post-processing 是脆弱的 workaround，維護成本高、遇到新的格式問題又會失效，不是可靠的架構選擇。

Q 2 Scenario 6 · Structured Data Extraction

You have three extraction tools: extract_invoice, extract_receipt, and extract_paper_metadata. An incoming document batch has no pre-labeling — document types are unknown. You need to guarantee that every document produces structured output (no plain text responses), but the model should choose the most appropriate tool for each document. Which tool_choice setting achieves this?

  1. tool_choice: "auto" — the model decides whether to call a tool or return text.
  2. tool_choice: {"type": "tool", "name": "extract_invoice"} — force all documents through the invoice tool.
  3. tool_choice: "any" — the model must call one of the tools but selects which one itself.
  4. No tool_choice setting needed; structured output is guaranteed once tools are defined.
展開解析

Correct Answer: C

C 正確："any" 設定強制模型一定要呼叫某個工具（不准只回文字），同時讓模型自己選最合適的那一個。這正好符合「必須有結構化輸出 + 讓模型選正確工具」的雙重需求。

A 錯在哪："auto" 表示模型「可以」呼叫工具，也可以直接回文字，不保證有結構化輸出。題目要求「guarantee structured output」，auto 不符合。B 錯在哪：強制 extract_invoice 會把論文和收據也用發票 schema 抽，產生嚴重的 semantic error（語意錯誤），因為不同類型的文件欄位定義完全不同。D 錯在哪：定義工具不等於保證模型會使用工具；不設 tool_choice 時預設行為等同 "auto"，模型可能回文字。

Q 3 Scenario 6 · Structured Data Extraction

Your invoice schema has po_number defined as a required string field. After processing 500 invoices from consumer vendors (who never issue PO numbers), your audit finds that po_number is populated with fabricated values like "PO-UNKNOWN" or random numbers in every record. What schema change best prevents this fabrication?

  1. Add an instruction to the prompt: "If po_number is not found in the document, output an empty string."
  2. Remove po_number from the schema entirely since not all vendors use it.
  3. Change po_number to allow null values (type: ["string", "null"]) and remove it from the required array.
  4. Add a validation step that checks if po_number matches a known PO format and rejects values that don't match.
展開解析

Correct Answer: C

C 正確：把欄位設為 nullable（type: ["string", "null"]）並從 required 移除，讓模型在文件沒有 PO 號時可以誠實回 null，而不是被迫捏造一個值來滿足 required 的要求。這是「optional/nullable 防幻覺」的標準設計模式。

A 錯在哪：文字指令「輸出空字串」的效果不穩定，模型可能不遵守，而且空字串和 null 在語意上不同，還是沒有解決 required 強迫模型填值的根本問題。B 錯在哪：完全移除欄位會讓有 PO 號的企業發票也抽不到這個值，過度砍需求；正確做法是保留欄位但允許 null。D 錯在哪：validation 是事後補救，無法防止幻覺進入資料庫；而且 PO 格式千變萬化，regex 難以涵蓋，並不是根本解法。
