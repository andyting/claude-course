Task Statement 5.4 — Manage context effectively in large codebase exploration

Knowledge of:

  • Context degradation in extended sessions: models start giving inconsistent answers and referencing "typical patterns" rather than specific classes discovered earlier
  • The role of scratchpad files for persisting key findings across context boundaries
  • Subagent delegation for isolating verbose exploration output while the main agent coordinates high-level understanding
  • Structured state persistence for crash recovery: each agent exports state to a known location, and the coordinator loads a manifest on resume

Skills in:

  • Spawning subagents to investigate specific questions (e.g., "find all test files," "trace refund flow dependencies") while the main agent preserves high-level coordination
  • Having agents maintain scratchpad files recording key findings, referencing them for subsequent questions to counteract context degradation
  • Summarizing key findings from one exploration phase before spawning sub-agents for the next phase, injecting summaries into initial context
  • Designing crash recovery using structured agent state exports (manifests) that the coordinator loads on resume and injects into agent prompts
  • Using /compact to reduce context usage during extended exploration sessions when context fills with verbose discovery output
本題情境 · SCENARIO 4
Scenario 4 — Developer Productivity with Claude（開發者生產力工具）

用 Claude Agent SDK 幫工程師探索陌生、龐大的 legacy codebase。探索一久,model 的 context 會塞滿 Read/Grep 的冗長輸出而開始退化。本 Task 教的就是用 scratchpad 檔、subagent 隔離、manifest 崩潰恢復與 /compact,讓 agent 在探索十萬行程式碼時仍記得稍早發現的具體類別。

一句話抓住主軸:探索大型程式庫時,context 會被 Read/Grep 的冗長輸出塞爆而退化——model 開始講「典型做法」而非你稍早查到的具體類別。對策:把關鍵發現寫進 scratchpad 檔、用 subagent 隔離冗長輸出、分階段先摘要再前進,並用 manifest 支援崩潰恢復。

Knowledge of · 知識點

知識 1  延長 session 的 context degradation（上下文降級）:開始給不一致答案、講「典型做法」而非具體類別

遇到這個問題時用到工程師用 Claude 探索一個 10 萬行的 legacy codebase 已進行 2 小時，model 開始說「退款通常由某個 service 處理」，而在 30 分鐘前它明確識別了 RefundProcessor.execute() 這個具體類別，前後答案矛盾且漸漸失去精確性。

探索一久,context 被大量 Read/Grep 輸出塞滿,model 會出現退化徵兆:答案前後不一致、開始引用「一般來說 service 層通常會…」這種典型模式,而不是它稍早真的查到的具體類別(例如 RefundProcessor)。這代表早期發現已經被擠出有效 context。

# 退化徵兆:從「具體」退回「泛泛」
# 早期(context 還健康):
#   "退款由 RefundProcessor.execute() 觸發,呼叫 LedgerClient"
# 延長 session 後(已退化):
#   "退款通常由某個 service 處理,一般會寫入帳本" ← 變泛泛,丟了具體類別

# ✅ 偵測到退化 → 該動用 scratchpad / subagent / compact(見下)
考點重點:退化的指標 = 答案不一致 + 引用「典型模式」取代「先前發現的具體類別」。

知識 2  scratchpad file（草稿檔）:把關鍵發現持久化,跨越 context 邊界

遇到這個問題時用到Agent 在探索第一階段識別了 AuthService、LedgerClient 等關鍵類別，但在 context 被壓縮後，這些具體發現消失，第二階段的回答開始用「一般的認證服務」等模糊描述，需要一個外部持久化機制來跨越 context 邊界。

對抗退化的核心工具:scratchpad 檔。把探索中的關鍵發現(哪個檔做什麼、關鍵類別、依賴關係)寫進外部檔案。它存在 context 之外,即使對話被 compact 或重啟,發現都還在——之後需要時再 Read 回來。

# ✅ 用內建工具把發現寫進 scratchpad,持久化到 context 之外
findings = """## 退款流程關鍵發現
- 入口: RefundProcessor.execute()  (src/payments/refund.py)
- 依賴: LedgerClient, NotificationQueue
- 測試: tests/payments/test_refund.py
"""
Write(path=".scratchpad/refund_flow.md", content=findings)

# 之後回答相關問題前,先 Read 回來,避免靠退化的記憶硬答
notes = Read(".scratchpad/refund_flow.md")
重點:scratchpad = 把關鍵發現存在 context 之外的外部檔,跨 context 邊界保命。

知識 3  subagent 委派:隔離冗長探索輸出,主 agent 只管高層理解

遇到這個問題時用到主 agent 直接執行 Grep("def test_", path=".") 搜尋整個 repo，數千行輸出進入主 context，導致 context 在後續問題前就已耗盡，無法繼續進行架構分析。

當某個調查會產生大量輸出(例如 Grep 整個 repo 找所有 test),不要讓主 agent 自己跑——那會把它的 context 灌爆。改成派一個 subagent 去跑,subagent 在自己隔離的 context 裡消化冗長輸出,只把精簡結論回給主 agent。主 agent 因此保持乾淨,專注於高層協調。

# ❌ 主 agent 自己 Grep 整個 repo → 冗長輸出灌爆主 context
all_tests = Grep("def test_", path=".")   # 數千行進主 context

# ✅ 派 subagent 去消化冗長輸出,只回精簡結論
summary = Task(
    agent="explorer",
    prompt="找出所有測試檔並摘要其覆蓋的模組,只回清單與重點。",
).result   # 主 agent 只收到精簡摘要,context 保持乾淨
重點:冗長調查交給 subagent 隔離消化,主 agent 只收結論、保高層協調。

知識 4  結構化狀態持久化:crash recovery（崩潰恢復）用 manifest

遇到這個問題時用到一個耗時 3 小時的大型 codebase 探索任務在中途因 API 逾時崩潰，所有已發現的架構資訊全部遺失，工程師必須從頭開始，若有 manifest 機制，只需從上次的斷點繼續。

長探索可能中途崩潰。對策:每個 agent 把自己的狀態匯出到已知位置,coordinator 在恢復時載入一份 manifest(清單),知道誰做到哪、發現了什麼,再把這些注入 agent 的 prompt 重新接續。這樣崩潰後不必從零重來。

# ✅ 每個 agent 匯出狀態到已知位置
Write(".state/explorer_01.json", agent_state)

# coordinator 恢復時載入 manifest,得知各 agent 進度
manifest = {
    "explorer_01": {"phase": "refund_flow", "status": "done"},
    "explorer_02": {"phase": "auth_module", "status": "in_progress"},
}
# 把已完成發現注入 prompt,從中斷處接續而非重來
重點:狀態匯出到已知位置 + coordinator 載入 manifest = 崩潰可恢復、不從零重來。

Skills in · 技能點

技能 1  派 subagent 調查特定問題,主 agent 保持高層協調

遇到這個問題時用到主 agent 需要同時了解測試覆蓋、依賴關係和 API 邊界，若每項都親自執行 Grep/Read，三項加起來的輸出會立即讓主 context 耗盡，無法完成高層架構的綜合分析。

知識 3 的實作。把具體、會產生大量輸出的調查問題(「找出所有測試檔」「追蹤 refund flow 的依賴」)各派一個 subagent 去查,主 agent 只彙整它們的結論。

def explore_codebase():
    tests   = Task(agent="explorer",
                   prompt="find all test files,回模組對應清單").result
    deps    = Task(agent="explorer",
                   prompt="trace refund flow dependencies,回依賴圖摘要").result
    # 主 agent 只收兩份精簡結論,保持高層視角
    return merge_high_level(tests, deps)
重點:具體調查問題 → 各派 subagent；主 agent 只收結論、不沾冗長輸出。

技能 2  維護 scratchpad file（草稿檔）記錄關鍵發現,後續問題先參照它以抗 context degradation（上下文降級）

遇到這個問題時用到工程師詢問「auth 模組怎麼運作？」時，agent 在 context 已部分退化的情況下給出了模糊的泛泛描述，若在探索階段就把 AuthService 的具體發現寫入 scratchpad，回答前先 Read 就能給出準確答案。

知識 2 的實作。每查到一塊就寫進 scratchpad;之後回答後續問題前,先 Read scratchpad 把具體發現拉回 context,而不是靠已退化的記憶硬答。

# 探索階段:邊查邊累積到 scratchpad
append_to_scratchpad(".scratchpad/findings.md",
    "- AuthService 在 src/auth/service.py,使用 JWT,15 分鐘過期")

# ✅ 回答「auth 怎麼運作?」前,先讀回具體發現
def answer_auth_question(q):
    notes = Read(".scratchpad/findings.md")   # 拉回具體類別
    return answer_with_context(q, notes)
重點:邊探索邊寫 scratchpad；回答前先 Read 回來,用具體發現取代退化記憶。

技能 3  進入下一階段前先摘要本階段發現,注入下一階段初始 context

遇到這個問題時用到第一階段的 subagent 完成了整體架構探索，但 spawn 第二階段 subagent 時直接給一個空白 context，第二階段浪費大量時間重新發現第一階段已知的架構事實。

探索分階段時,在 spawn 下一批 subagent 之前,先把本階段的關鍵發現摘要好,並把摘要注入下一階段的初始 context。這樣下一階段一開始就帶著前面的精華,不必重查,也避免把整段原始輸出拖進來。

def run_phases():
    # 階段一:理解整體架構
    phase1 = explore_architecture()
    summary1 = summarize(phase1)              # ✅ 先摘要

    # 階段二:把上一階段摘要注入初始 context 再 spawn
    phase2 = Task(agent="explorer",
        prompt=f"已知架構摘要:\n{summary1}\n\n請深入 refund 模組。")
    return phase2.result
重點:階段交棒 = 先摘要本階段、再把摘要注入下一階段初始 context。

技能 4  用結構化狀態匯出(manifest)設計 crash recovery（崩潰恢復）

遇到這個問題時用到兩個 explorer subagent 中，一個已完成 refund_flow 探索，另一個正在進行 auth_module 分析時系統崩潰。若有 manifest 機制，resume 時可以跳過已完成的部分，只繼續未完成的 auth_module 任務。

知識 4 的實作。把各 agent 狀態結構化匯出成 manifest;coordinator 在 resume 時載入 manifest 並注入各 agent 的 prompt,讓它們從上次中斷處接續。

def resume_exploration():
    manifest = load_json(".state/manifest.json")
    for agent_id, state in manifest.items():
        if state["status"] != "done":
            # ✅ 把既有狀態注入 prompt,從中斷處續跑
            Task(agent="explorer",
                 prompt=f"接續未完成探索,已知狀態:{state}")
重點:manifest 結構化匯出 + resume 時載入注入 prompt = 從中斷處接續。

技能 5  延長探索時用 /compact 壓低 context window（上下文視窗）用量

遇到這個問題時用到長時間的 codebase 探索 session 中，context 被累積的 Read/Grep 輸出塞至 80% 使用量，繼續探索風險截斷關鍵發現，需要在壓縮前先把重要發現落地到 scratchpad，再用 /compact 安全釋放空間。

當 context 被冗長探索輸出塞滿,可用 /compact 把對話壓縮,保留要點、丟掉囉嗦的中間過程,騰出空間繼續探索。它是延長 session 中對抗 context 爆滿的直接手段(常與 scratchpad 搭配:compact 前先把關鍵發現寫進 scratchpad,確保不會被壓掉)。

# 延長探索,context 快滿時:
# 1) 先把關鍵發現落地到 scratchpad(防止被壓掉)
Write(".scratchpad/phase3.md", key_findings)

# 2) 再用 /compact 壓縮對話,釋放 context 空間
#    /compact  ← 保留要點、丟掉冗長 Read/Grep 中間輸出

# ✅ compact 後 context 變乾淨,具體發現仍在 scratchpad,可隨時 Read 回來
重點:/compact 壓低 context 用量；搭配 scratchpad 先落地關鍵發現,壓縮才安全。

整個 Task 5.4 的記憶骨架

探索大型 codebase 時,Read/Grep 的冗長輸出會讓 context 退化(答案不一致、用「典型做法」取代先前查到的具體類別)。四大對策:把關鍵發現寫進 scratchpad 檔(存 context 之外,回答前先 Read 回來)、把冗長調查交給 subagent 隔離消化、階段交棒先摘要再注入下一階段、用 manifest 結構化匯出狀態以支援崩潰恢復。context 快滿時用 /compact,並先把發現落地到 scratchpad 再壓縮。

考試情境題

以下三題模擬正式考試格式，每題一個生產情境，四個選項。先嘗試作答，再展開解析。

Q 1 Scenario 4 · Developer Productivity with Claude

An engineer is using Claude to explore a 120,000-line legacy codebase. After 90 minutes of exploration, the agent was asked "Which class handles the refund processing?" In the first 30 minutes, the agent had clearly identified RefundProcessor.execute() in src/payments/refund.py. Now it responds: "Refund processing is typically handled by a service layer class that coordinates with the ledger system." Logs show the context is at 85% capacity. What is the most likely root cause?

  1. The model has been updated and lost the ability to analyze Python code
  2. Context degradation — the context is full of verbose Read/Grep output, pushing the specific class discovery from earlier turns out of effective context, causing the model to fall back on generic patterns
  3. The RefundProcessor class was renamed during the session
  4. The agent's system prompt does not include instructions for identifying payment classes
展開解析

Correct Answer: B

B 正確：這是 context degradation（上下文降級）的典型症狀——context 被大量 Read/Grep 的冗長輸出塞滿後，早期發現的具體類別名稱被擠出有效 context 範圍，model 開始用「典型模式」取代「先前發現的具體類別」。85% context 使用量正是退化的警訊。

A 錯在哪：模型本身的能力不會在 session 中途突然改變，這不是模型能力問題，而是 context 管理問題。C 錯在哪：codebase 在探索 session 中不會自行改變，RefundProcessor 仍然存在，只是已被擠出有效 context。D 錯在哪：system prompt 的設計問題在 session 開始就會顯現，不會在 90 分鐘後才突然發生，且問題描述明確顯示 30 分鐘前還能正確回答。

Q 2 Scenario 4 · Developer Productivity with Claude

An agent is exploring a large codebase to understand its architecture. The main agent directly runs Grep("def test_", path=".") across the entire repository to find all test files, receiving 4,200 lines of output that now fills a large portion of its context. The main agent can no longer fit its high-level architectural analysis work in the remaining context budget. What is the most effective change to address this?

  1. Increase the model's context window so it can hold more Grep output
  2. Have the main agent summarize the Grep output into prose before processing it to reduce token usage
  3. Spawn a subagent to run the Grep search and return only a concise module-to-test-file mapping, keeping the verbose discovery output isolated in the subagent's separate context
  4. Run the Grep search in batches of 500 lines to avoid overwhelming the context at once
展開解析

Correct Answer: C

C 正確：派 subagent 去執行會產生大量輸出的 Grep 任務，讓冗長輸出被隔離在 subagent 自己的 context 中消化，主 agent 只收到精簡的模組對應清單。這讓主 agent 的 context 保持乾淨，專注於高層架構協調工作。

A 錯在哪：更大的 context window 只是推遲問題——當 codebase 夠大時，冗長 Grep 輸出仍然會塞滿任何大小的 context，且不解決「主 agent 需要保持乾淨以進行高層協調」的核心需求。B 錯在哪：在主 agent 中把 4,200 行輸出摘要成散文，摘要過程本身就佔用大量 context，且主 agent 仍需先處理原始輸出才能摘要，問題並未得到根本解決。D 錯在哪：分批處理只是把相同的問題分散到多輪，總 token 使用量不變，最終仍然塞滿主 agent 的 context。

Q 3 Scenario 4 · Developer Productivity with Claude

A multi-agent codebase exploration task has been running for 2.5 hours. Two explorer subagents are active: explorer_01 completed the refund flow analysis, and explorer_02 is 60% through the authentication module analysis. The coordinator agent crashes due to an API error. When the engineer restarts the system, the coordinator has no record of which agents finished which tasks, so it restarts the entire exploration from scratch. What design change best addresses this issue?

  1. Increase the API timeout value to prevent the coordinator from crashing mid-task
  2. Save the entire conversation history to a database after each turn so the coordinator can replay all messages on resume
  3. Design each agent to export its state to a known file location after each phase, and have the coordinator load a manifest on resume to inject each agent's prior progress into their prompts
  4. Add a health-check endpoint that pings all subagents every 5 minutes and restarts any that have failed
展開解析

Correct Answer: C

C 正確：結構化 manifest 的 crash recovery（崩潰恢復）設計讓每個 agent 在完成每個階段後都將狀態匯出到已知位置。coordinator resume 時載入 manifest，得知 explorer_01 已完成（跳過）、explorer_02 進行到 60%（從中斷處接續），並把各 agent 的既有狀態注入其 prompt，避免重工。

A 錯在哪：調整 timeout 值可以減少某些類型的崩潰，但無法防止所有失敗情境（網路中斷、OOM 等），且完全沒有解決「崩潰後如何恢復」的問題。B 錯在哪：重播整個對話歷史不僅計算成本高，還可能因為 context window 限制而無法重播完整歷史，且重播過程中可能導致重複執行已完成的操作。D 錯在哪：健康檢查可以偵測失敗，但本身不提供任何恢復能力——當 subagent 失敗後，若沒有狀態持久化機制，重啟只會從零開始。
