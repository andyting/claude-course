Task Statement 3.2 — Create and configure custom slash commands and skills

Knowledge of:

  • Project-scoped commands in .claude/commands/ (shared via version control) vs user-scoped commands in ~/.claude/commands/ (personal)
  • Skills in .claude/skills/ with SKILL.md files that support frontmatter configuration including context: fork, allowed-tools, and argument-hint
  • The context: fork frontmatter option for running skills in an isolated sub-agent context, preventing skill outputs from polluting the main conversation
  • Personal skill customization: creating personal variants in ~/.claude/skills/ with different names to avoid affecting teammates

Skills in:

  • Creating project-scoped slash commands in .claude/commands/ for team-wide availability via version control
  • Using context: fork to isolate skills that produce verbose output (e.g., codebase analysis) or exploratory context (e.g., brainstorming alternatives) from the main session
  • Configuring allowed-tools in skill frontmatter to restrict tool access during skill execution (e.g., limiting to file write operations to prevent destructive actions)
  • Using argument-hint frontmatter to prompt developers for required parameters when they invoke the skill without arguments
  • Choosing between skills (on-demand invocation for task-specific workflows) and CLAUDE.md (always-loaded universal standards)
本題情境 · SCENARIO 2
Scenario 2 — Code Generation with Claude Code

團隊用 Claude Code 做產生程式、重構、除錯、文件,需要把它整進開發流程:自訂 slash command、CLAUDE.md 設定、判斷 plan mode 或直接執行。本 Task 教你怎麼幫團隊建可共享的 slash command 與 skill,並用 frontmatter 控制它們的行為。

一句話抓住主軸:slash command 與 skill 是你「打包工作流程」的兩種容器——差別在「放哪裡(誰看得到)」與「frontmatter 怎麼設(行為)」。考點全繞著 scope(project vs user)與三個 frontmatter 欄位(context: fork、allowed-tools、argument-hint)轉。

Knowledge of · 知識點

知識 1  Project-scoped vs user-scoped:slash command（斜線指令）放哪裡決定誰看得到

遇到這個問題時用到你建了一個 /review-pr 的 slash command（斜線指令），但隊友說他們的 Claude Code 裡找不到這個指令，你需要了解 command 存放位置與可見範圍的關係才能修正。

同樣是 slash command,放的位置決定它的「能見範圍」:

Project-scoped(.claude/commands/):放在專案目錄裡,會跟著 git 一起進版控,整個團隊都能用。適合團隊共用的工作流程,例如 /review-pr。
User-scoped(~/.claude/commands/):放在你個人家目錄,只有你自己看得到,不會影響別人。適合個人習慣的小工具。

# 團隊共享 → 進版控,大家都能用 /generate-tests
# 檔案位置:<repo>/.claude/commands/generate-tests.md

# 只有自己用 → 不進版控,不影響隊友
# 檔案位置:~/.claude/commands/my-scratch.md

# 兩者皆以 /<檔名> 觸發,例如 /generate-tests
考點重點:.claude/commands/ = 專案共享(進版控);~/.claude/commands/ = 個人。位置 = 能見範圍。

知識 2  Skill（技能）與 SKILL.md frontmatter 三大欄位

遇到這個問題時用到你的 /analyze-codebase skill（技能）每次跑完都把幾百行的分析原文倒進主對話，嚴重佔用 context window，你需要了解 frontmatter 的哪個欄位能解決這個問題。

Skill 放在 .claude/skills/,每個 skill 有一份 SKILL.md。檔案開頭的 frontmatter(用 --- 包起來的設定區)支援三個關鍵欄位:

context: fork — 讓 skill 在獨立子代理 context 跑,輸出不污染主對話。
allowed-tools — 限制 skill 執行時能用哪些工具。
argument-hint — 當使用者不帶參數就呼叫時,提示他要填什麼。

# .claude/skills/analyze-codebase/SKILL.md
# frontmatter:用 --- 包住的設定
---
name: analyze-codebase
description: 分析整個 codebase 並回傳摘要
context: fork              # 在隔離 context 跑,輸出不灌進主對話
allowed-tools: [Read, Grep, Glob]   # 只准讀,不准寫
argument-hint: "<要分析的目錄路徑>"   # 沒帶參數時提示
---

# 以下為 skill 的指示內容...
考點重點:三欄位各管一件事——fork 管「context 隔離」、allowed-tools 管「工具權限」、argument-hint 管「參數提示」。

知識 3  context: fork — 把吵雜輸出隔離在子代理

遇到這個問題時用到工程師執行 /brainstorm-refactors 之後，主對話被大量的探索輸出淹沒，後續的實作指令完全找不到焦點，你需要知道如何讓 skill 的雜訊保留在子代理而不污染主對話。

有些 skill 會吐出一大堆內容(例如分析整個 codebase),如果直接灌進主對話,會把寶貴的 context window 塞爆、把重點淹沒。context: fork 的作用是讓這個 skill 在一個隔離的子代理 context 裡執行,跑完只把精煉後的結果帶回主對話,中間那堆雜訊留在子代理裡。

用團隊情境想:工程師下 /analyze-codebase 想搞懂一個 legacy 模組,分析過程翻了上百個檔案——你不會想把這上百檔的原文都塞回主對話。

# ❌ 沒 fork:verbose 分析輸出全進主對話,context 被洗版
---
name: brainstorm-refactors
description: 腦力激盪多種重構方案
---

# ✅ 有 fork:探索/腦暴的雜訊留在子代理,只帶結論回來
---
name: brainstorm-refactors
description: 腦力激盪多種重構方案
context: fork
---
一句話記住:verbose 或 exploratory 的 skill → 加 context: fork,別污染主對話。

知識 4  個人化 skill（技能）:用不同名字放 ~/.claude/skills/,不影響隊友

遇到這個問題時用到你想修改團隊的 /generate-tests skill 讓它更符合自己的 TDD 習慣，但擔心改動後會影響所有隊友的工作流程，你需要知道如何在不影響他人的前提下建立個人變體。

團隊共用的 skill 你不該亂改——一改大家都受影響。要客製成自己順手的版本,做法是在個人目錄 ~/.claude/skills/ 建一個不同名字的變體。這樣你用你的,隊友用團隊原版,互不干擾。

# 團隊版(進版控,別人也在用):
#   <repo>/.claude/skills/generate-tests/SKILL.md

# ✅ 你的個人變體:換個名字放自己家目錄
#   ~/.claude/skills/generate-tests-mine/SKILL.md
# 改名 → 不覆蓋團隊版 → 隊友完全不受影響
重點:個人客製 = 放 ~/.claude/skills/ + 取不同名字,避免影響團隊。

Skills in · 技能點

技能 1  建 project-scoped slash command（斜線指令）給全隊用

遇到這個問題時用到你們團隊每個人 PR review 的流程和品質參差不齊，你想建一個標準化的 /review-pr 指令讓所有人只要一個指令就能跑統一的 review 流程。

知識 1 的實作。把 command 的 .md 放進 .claude/commands/ 並 commit,隊友 pull 之後就能直接打那個 slash command。

# 1) 在專案建立 command 檔
#   <repo>/.claude/commands/review-pr.md
#   內容:對 PR 做 code review 的指示

# 2) 進版控
git add .claude/commands/review-pr.md
git commit -m "add /review-pr command"

# 3) 隊友 pull 後即可 /review-pr,全隊一致

技能 2  用 context: fork 隔離 verbose / 探索型 skill（技能）

遇到這個問題時用到CI job 中的 /codebase-analysis skill 掃描完後把數千行的原始檔案內容倒進主對話，導致後續的 review 任務完全沒有可用的 context 空間，你需要用 context: fork 把探索過程隔離。

知識 3 的實作落點:把「會吐很多字」(codebase 分析)或「探索性質」(腦暴替代方案)的 skill,在 frontmatter 加 context: fork。

# .claude/skills/codebase-analysis/SKILL.md
---
name: codebase-analysis
description: 全庫掃描並回傳架構摘要
context: fork          # ✅ verbose → 隔離,只回摘要
allowed-tools: [Read, Grep, Glob]
---
請掃描整個 codebase,回傳:模組關係、進入點、可疑技術債。
只回精煉摘要,不要貼大量原始碼。

技能 3  用 allowed-tools 限制 skill（技能）能用的工具

遇到這個問題時用到你的 /scaffold-module skill 意外執行了刪除現有檔案的 Bash 指令，造成生產程式碼損失，你需要用 allowed-tools 把 skill 的工具權限收緊到只允許必要操作。

最小權限原則。在 frontmatter 用 allowed-tools 把工具縮到最小,避免 skill 做出破壞性動作。例如只給寫檔、不給執行 Bash 刪檔。

# ❌ 沒限制:skill 什麼都能做,含破壞性指令
---
name: scaffold-module
description: 產生新模組樣板
---

# ✅ 只准寫檔,擋掉危險操作
---
name: scaffold-module
description: 產生新模組樣板
allowed-tools: [Write]   # 僅檔案寫入,不給 Bash 等破壞性工具
---
重點:allowed-tools 收緊權限 → 防止 skill 執行破壞性動作。

技能 4  用 argument-hint 提示必填參數

遇到這個問題時用到開發者輸入 /generate-tests 但忘了帶目標檔案路徑，導致 skill 在整個 repo 亂跑產出大量無效測試，你需要 argument-hint 在缺少參數時立刻提示使用者補齊。

當使用者不帶參數就呼叫 skill,argument-hint 會提示他該填什麼,避免 skill 在缺資訊下亂跑。

# .claude/skills/generate-tests/SKILL.md
---
name: generate-tests
description: 為指定檔案產生單元測試
argument-hint: "<目標檔案路徑,例如 src/auth.py>"
---
# 開發者打 /generate-tests 卻沒給檔案時,
# 系統用 argument-hint 提示他補上路徑

技能 5  Skill（技能）vs CLAUDE.md file（CLAUDE.md 檔）:何時用哪個

遇到這個問題時用到你不確定新增的「TypeScript strict 模式」規範應該放進 CLAUDE.md 還是做成一個 skill，錯誤的選擇會讓規範只在特定場合生效或反而每次都被載入造成干擾。

兩者都是「給 Claude 的設定」,但觸發方式不同:

Skill = 按需呼叫,針對特定任務的工作流程(你叫它才跑)。
CLAUDE.md = 永遠載入的普世規範(每次都自動生效,例如全專案的命名規則、coding style)。

# ✅ 用 CLAUDE.md:每次都該套用的全域規範
# CLAUDE.md:本專案一律用 TypeScript strict、commit 訊息用祈使句

# ✅ 用 Skill:只在做某件事時才需要的流程
# /generate-tests:只有要寫測試時才呼叫
重點:普世且常駐 → CLAUDE.md;特定任務、按需才跑 → skill。

整個 Task 3.2 的記憶骨架

在 Scenario 2 的團隊裡:command/skill 放 .claude/(進版控、全隊共享)還是 ~/.claude/(個人、改名避免影響隊友),決定誰看得到。Skill 的 SKILL.md frontmatter 管三件事——context: fork(隔離 verbose/探索輸出)、allowed-tools(收緊工具權限防破壞)、argument-hint(提示必填參數)。最後一刀:永遠載入的普世規範用 CLAUDE.md,按需任務流程用 skill。

考試情境題

以下三題模擬正式考試格式，每題一個生產情境，四個選項。先嘗試作答，再展開解析。

Q 1 Scenario 2 · Code Generation with Claude Code

A developer on a team runs /codebase-analysis to understand a legacy authentication module. After the skill finishes, the main conversation context contains hundreds of raw file contents from the scan, leaving almost no room for the subsequent refactoring discussion. The SKILL.md frontmatter for that skill currently has no special configuration. What is the most effective single change to prevent this problem?

  1. Add allowed-tools: [Read, Grep] to the skill frontmatter to limit which files can be scanned.
  2. Add context: fork to the skill frontmatter so the verbose scan runs in an isolated sub-agent context and only the summary is returned to the main conversation.
  3. Move the skill file from .claude/skills/ to ~/.claude/skills/ so it does not share context with the project session.
  4. Add argument-hint: "<module path>" to the frontmatter so the developer scopes the scan to a single directory.
展開解析

Correct Answer: B

context: fork 讓 skill 在獨立子代理 context 裡執行，中間那堆 verbose 的掃描原文留在子代理，主對話只收到精煉摘要，context window 保持乾淨。這正是官方設計 context: fork 的核心用途。

A 錯在哪：allowed-tools 控制的是工具存取權限，不能控制輸出是否進入主對話。C 錯在哪：把 skill 移到個人目錄只影響可見範圍（誰能用），無法解決輸出污染主 context 的問題。D 錯在哪：argument-hint 可以縮小掃描範圍，但只要輸出還是直接進主對話，問題仍然存在，這不是根本解法。

Q 2 Scenario 2 · Code Generation with Claude Code

A team's /scaffold-module skill is designed only to generate boilerplate files. During an incident investigation, engineers discover that the skill occasionally executes Bash commands that delete existing files when the scaffolding logic encounters conflicts. The skill's SKILL.md has no allowed-tools restriction. Which change best addresses this security risk?

  1. Add context: fork to run the skill in an isolated context so any destructive actions do not affect the main workspace.
  2. Add allowed-tools: [Write] to the skill frontmatter to restrict tool access to file write operations only, blocking Bash and other destructive tools.
  3. Move the skill to ~/.claude/skills/ so it requires explicit user invocation and cannot be triggered accidentally.
  4. Add an argument-hint prompting the developer to confirm the target directory before execution.
展開解析

Correct Answer: B

allowed-tools: [Write] 直接套用最小權限原則：skill 只需要寫檔能力，把 Bash 等危險工具從允許清單（allowlist）中排除，就從根本上阻止了破壞性操作的發生。

A 錯在哪：context: fork 隔離的是輸出，讓雜訊不進主對話，但不限制 skill 能執行的工具種類，子代理裡的 Bash 仍可刪除檔案。C 錯在哪：把 skill 移到個人目錄改變的是可見範圍，無法限制執行時能用的工具。D 錯在哪：argument-hint 提示參數，但不能阻止 skill 在取得參數後仍執行危險操作。

Q 3 Scenario 2 · Code Generation with Claude Code

A team enforces a TypeScript strict mode rule across all their projects and also uses a /generate-tests workflow that developers invoke only when adding new features. An architect is deciding whether each of these should be configured as a CLAUDE.md rule or a skill. Which assignment is correct?

  1. Both should be skills: TypeScript strict mode as a skill triggered before every file edit, and test generation as a separate skill.
  2. TypeScript strict mode should be in CLAUDE.md (always-loaded universal standard), and test generation should be a skill (on-demand task-specific workflow).
  3. TypeScript strict mode should be a skill (invoked when needed), and test generation should be in CLAUDE.md (always-loaded so Claude always suggests tests).
  4. Both should be in CLAUDE.md to ensure they are always available without requiring explicit invocation.
展開解析

Correct Answer: B

CLAUDE.md 適合「每次工作都該套用的普世規範」——TypeScript strict 模式是編碼標準，應該每個檔案都生效；Skill 適合「只在做特定任務時才執行的工作流程」——/generate-tests 只在需要補測試時才呼叫，按需即可。

A 錯在哪：把 TypeScript strict 做成 skill 表示它只在主動呼叫時才生效，工程師可能忘記呼叫，規範就不一致了。C 錯在哪：把測試生成放進 CLAUDE.md 會讓 Claude 在每次互動都嘗試生成或建議測試，反而造成干擾。D 錯在哪：把 /generate-tests 這種任務型工作流程放進 CLAUDE.md 會讓每次 session 都永遠載入這段指令，浪費 context 且不必要。
