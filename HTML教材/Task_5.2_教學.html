官方考綱原文

Task Statement 5.2 — Design effective escalation and ambiguity resolution patterns

Knowledge of:

  • Appropriate escalation triggers: customer requests for a human, policy exceptions/gaps (not just complex cases), and inability to make meaningful progress
  • The distinction between escalating immediately when a customer explicitly demands it versus offering to resolve when the issue is straightforward
  • Why sentiment-based escalation and self-reported confidence scores are unreliable proxies for actual case complexity
  • How multiple customer matches require clarification (requesting additional identifiers) rather than heuristic selection

Skills in:

  • Adding explicit escalation criteria with few-shot examples to the system prompt demonstrating when to escalate versus resolve autonomously
  • Honoring explicit customer requests for human agents immediately without first attempting investigation
  • Acknowledging frustration while offering resolution when the issue is within the agent's capability, escalating only if the customer reiterates their preference
  • Escalating when policy is ambiguous or silent on the customer's specific request (e.g., competitor price matching when policy only addresses own-site adjustments)
  • Instructing the agent to ask for additional identifiers when tool results return multiple matches, rather than selecting based on heuristics
本題情境 · SCENARIO 1
Scenario 1 — Customer Support Resolution Agent（客服解決 agent）

客服 agent 目標是 80%+ 首次解決,但同樣關鍵的是「知道何時放手交給人」。本 Task 教 agent 何時呼叫 escalate_to_human、何時自己解決,以及當 get_customer 回傳多筆相符時該怎麼問清楚,而不是亂猜一個。

一句話抓住主軸:升級不是「客戶看起來生氣」就升,而是有明確觸發條件:客戶點名要真人、政策沒寫到、或真的卡住推不動。情緒與自評信心都不可靠。遇到多筆相符,要問更多識別資訊,不要憑啟發法選一個。

Knowledge of · 知識點

知識 1  合理的 escalation trigger（升級觸發）條件:點名要真人、政策例外/空白、推不動

遇到這個問題時用到客服 agent 在遇到「競品比價」請求時不知道該自行處理還是升級，因為政策文件只涵蓋本站調價，沒有明文規範競品情況，導致 agent 自行腦補規則給出錯誤承諾。

什麼時候該 escalate_to_human?官方列出三類觸發:(1) 客戶明確要求真人;(2) 遇到政策例外或政策根本沒寫到的情況(不只是「案件很複雜」);(3) agent 已經沒辦法有意義地推進。注意第二點:政策空白本身就是升級理由,不是非得很難才升。

def should_escalate(state):
    if state.customer_asked_for_human:
        return escalate_to_human(reason="customer_request")
    if state.policy_silent_or_exception:
        return escalate_to_human(reason="policy_gap")   # 政策沒寫到也要升
    if state.no_meaningful_progress:
        return escalate_to_human(reason="stuck")
    return resolve_autonomously(state)
考點重點:三觸發 = 要真人 / 政策空白或例外 / 推不動。政策空白≠案件複雜,但同樣要升。

知識 2  客戶明確要求 vs. 問題很單純:該立刻升 還是 提議先解決

遇到這個問題時用到客戶說「我要找你們主管！」時，agent 仍先嘗試自行查詢訂單並提出解決方案，等待了 3 輪後才升級，讓原本已不耐煩的客戶更加憤怒，CSAT 分數下滑。

關鍵的二分法:如果客戶明確要求真人,就立刻升,不要先自己查一輪;但如果問題其實很單純,agent 可以提議「我可以直接幫您處理」。差別在於「客戶是否明講要真人」。

# ✅ 客戶明講「我要找真人」→ 立刻升,不先調查
if message == "我要跟真人講話":
    escalate_to_human(reason="explicit_request")

# ✅ 問題單純(查退貨期)→ 提議直接解決
if issue == "還在退貨期嗎":
    return "我可以直接幫您確認並處理退貨喔!"
重點:明講要真人 → 立刻升;單純問題 → 提議自己解決。

知識 3  情緒升級與「自評 confidence calibration（信心校準）分數」都不可靠

遇到這個問題時用到系統將 sentiment == "angry" 設為升級觸發條件，結果一個單純詢問退貨期的生氣客戶被升級給真人客服，而一個語氣平和卻要求政策例外的複雜案件卻沒有被升級，造成資源錯置。

兩個常見的錯誤代理指標:(a) 用「客戶語氣」決定升級——語氣兇不代表案件複雜,語氣好也可能是棘手政策例外;(b) 用模型「自評的信心分數」當複雜度代理——模型常常該不確定時很有自信。真正該看的是案件本身的複雜度(政策有沒有寫、能不能推進),不是情緒或自評。

# ❌ 用情緒當升級依據:語氣兇就升、語氣好就硬解
if sentiment == "angry":
    escalate_to_human()           # 情緒 ≠ 複雜度

# ❌ 用模型自評信心當依據
if model_confidence < 0.6:
    escalate_to_human()           # 自評信心不可靠

# ✅ 看實際案件複雜度:政策是否涵蓋、能否推進
if not policy.covers(request) or state.stuck:
    escalate_to_human()
重點:情緒、自評信心 = 不可靠代理。判斷依據是案件實際複雜度。

知識 4  多筆相符要「問清楚」做 ambiguity resolution（模糊解析）,不要用啟發法亂選

遇到這個問題時用到呼叫 get_customer(name="陳怡君") 回傳三筆相符資料，agent 選取了第一筆（最近登入），結果處理到另一個客戶的帳號，造成資料外洩與退款流向錯誤的嚴重事故。

呼叫 get_customer 時若回傳多筆相符(同名、同 email 前綴…),不能憑「選最近一筆」「選訂單最多的」這種啟發法猜。正確做法是請客戶提供更多識別資訊(訂單號、後四碼…)來消歧義。猜錯客戶身分在客服場景是嚴重事故。

matches = get_customer(name="陳怡君")

# ❌ 啟發法亂選 → 可能處理到別人的帳號
if len(matches) > 1:
    customer = matches[0]           # 憑「第一筆」亂選

# ✅ 多筆相符 → 請客戶補識別資訊
if len(matches) > 1:
    return "我查到多筆符合的資料,方便提供訂單編號或手機後四碼嗎?"
重點:多筆相符 = 請求額外識別碼來消歧義,絕不用啟發法選。

Skills in · 技能點

技能 1  在 system prompt 用 few-shot 範例寫明確的 escalation trigger（升級觸發）準則

遇到這個問題時用到客服 agent 的 system prompt 只有一句「遇到複雜問題請升級」，導致 agent 對「複雜」的判斷標準不一致，有時升級單純問題、有時對複雜政策例外硬解，需要用 few-shot 範例讓判斷標準具體化。

把「何時升、何時自解」用具體 few-shot 例子寫進 system prompt,而不是只給一句抽象規則。例子能讓模型抓到判斷的「語感」,大幅降低該升不升、不該升亂升的情況。

SYSTEM_PROMPT = """你是客服解決 agent。升級準則如下:

範例 1 — 升級:
客戶:「我要直接找你們主管!」
→ 立刻 escalate_to_human(明確要求真人)

範例 2 — 自行解決:
客戶:「我這筆 $129.99 還能退嗎?」(在退貨期內)
→ 直接協助處理,不需升級

範例 3 — 升級:
客戶要求比對競品價,但政策只寫到本站調價
→ escalate_to_human(政策未涵蓋此情況)
"""
重點:升級準則 + few-shot 範例寫進 system prompt,讓判斷有依據。

技能 2  客戶明確要求真人時,立刻照辦,不先自己調查

遇到這個問題時用到客戶明確表示「我要跟真人講話」後，agent 仍先呼叫 lookup_order 試圖自行解決，讓等待升級的客戶又多等了兩輪回應，導致原本可以快速轉接的案件變成客訴。

知識 2 的實作。客戶說「我要真人」,就馬上 escalate_to_human——不要先跑 lookup_order、不要先試圖自己解決。硬要先調查,只會讓已經想找真人的客戶更不耐煩。

# ✅ 一偵測到明確要求,立刻升,跳過調查步驟
def handle(message, state):
    if is_explicit_human_request(message):
        return escalate_to_human(reason="explicit_request")
    # 否則才進入正常調查/解決流程
    return investigate_and_resolve(message, state)
重點:明確要求真人 = 立刻升,不先調查。

技能 3  能力範圍內:先安撫情緒並提議解決,客戶堅持才升

遇到這個問題時用到客戶抱怨「等很久了，你們的服務太差了！」但問題只是確認退貨期是否已過，agent 若直接升級是浪費人力，應先承認挫折感並提議立即協助，僅在客戶再次堅持時才升級。

客戶很挫折、但問題其實在 agent 能力範圍內時,正確做法是:先承認他的挫折,同時提議「我可以直接幫您處理」;只有當客戶再次堅持要真人,才升級。這跟技能 2 不同——技能 2 是客戶「明講要真人」,這裡是客戶「在抱怨但沒明講要真人」。

# ✅ 安撫 + 提議解決(問題在能力範圍內)
reply = "很抱歉讓您久等、造成困擾。這筆退款我可以現在直接幫您處理,要為您辦理嗎?"

# 若客戶再次堅持要真人 → 這時才升
if customer_reiterates_human:
    escalate_to_human(reason="customer_reiterated")
重點:挫折但可解 → 先安撫+提議解決;客戶再堅持才升。

技能 4  政策模糊或沒寫到客戶的情況時,升級

遇到這個問題時用到客戶要求比對競品價格，而公司政策文件只涵蓋「本站歷史最低價調整」，agent 在沒有授權的情況下自行決定拒絕或接受，任一做法都可能造成客戶流失或財務損失。

知識 1 第二觸發的實作。當客戶的請求落在政策沒明文規範的灰色地帶——例如政策只寫「本站調價」,客戶卻要求比對競品價——agent 不該自己腦補一個規則,而要升級讓有權限的人決定。

def handle_price_match(request, policy):
    if request.type == "competitor_price_match" and \
       not policy.addresses("competitor_pricing"):
        # 政策只談本站調價,沒寫到競品 → 升級
        return escalate_to_human(reason="policy_silent_competitor_match")
    return apply_own_site_adjustment(request)
重點:政策對該請求模糊/沉默 → 升級,不要自行腦補規則。

技能 5  工具回傳多筆相符時,指示 agent 請求額外識別資訊

遇到這個問題時用到客服系統的 get_customer API 在查詢常見姓名時頻繁回傳多筆相符，需要在 agent 指示中明確定義「多筆相符就請求識別碼」的行為，避免開發者或 agent 自行選擇啟發法。

知識 4 的實作。把「多筆相符就問清楚」寫成明確指示,讓 agent 在 get_customer / lookup_order 回多筆時,主動請客戶補識別碼,而不是靠啟發法挑一個。

def resolve_customer(name):
    matches = get_customer(name=name)
    if len(matches) == 0:
        return "查不到資料,方便提供訂單編號嗎?"
    if len(matches) > 1:
        # ✅ 多筆 → 請求額外識別資訊消歧義
        return "有多筆符合,請提供訂單編號或註冊 email 以便確認身分。"
    return matches[0]   # 唯一相符才直接用
重點:把「多筆→請求識別碼」寫成明確指示,杜絕啟發法選人。

整個 Task 5.2 的記憶骨架

客服 agent 的升級要靠明確觸發而非情緒:客戶明講要真人就立刻升、政策空白或例外要升、推不動要升;但問題單純時先提議自己解決,客戶挫折但可解就先安撫+提議、再堅持才升。情緒與自評信心都不可靠,判斷依據是案件實際複雜度。get_customer 回多筆相符時請求額外識別碼消歧義,不用啟發法亂選。所有準則用 few-shot 寫進 system prompt。

考試情境題

以下三題模擬正式考試格式，每題一個生產情境，四個選項。先嘗試作答，再展開解析。

Q 1 Scenario 1 · Customer Support Resolution Agent

A customer service agent receives this message: "This is the third time I'm contacting you about the same issue. I want to speak with a manager right now." The agent's current behavior is to first run lookup_order, analyze the case, and then offer to resolve before considering escalation. Logs show the customer must wait through 2–3 agent turns before being transferred. What is the most effective change to address this?

  1. Add sentiment analysis to detect anger scores above 0.8 and trigger escalation automatically
  2. Detect explicit human-agent requests at the start of message handling and call escalate_to_human immediately, before any investigation
  3. Increase the agent's self-reported confidence threshold so it escalates more readily when uncertain
  4. Add a cooldown timer so customers who request escalation are transferred after one additional resolution attempt
展開解析

Correct Answer: B

B 正確：當客戶明確要求真人時，應立刻升級，不需要先調查。在訊息處理流程的最前面偵測「明確要求真人」並立即呼叫 escalate_to_human，是最直接且尊重客戶意願的做法。

A 錯在哪：情緒分數是不可靠的代理指標——高情緒不代表案件複雜，也不代表客戶明確要求真人。這個做法在客戶生氣但問題簡單時會錯誤升級，而在客戶平靜但明確要求真人時可能不觸發。C 錯在哪：自評信心分數同樣不可靠，且完全沒有捕捉到「客戶明確要求真人」這個關鍵觸發條件。D 錯在哪：讓客戶再等一輪「解決嘗試」正是問題所在——客戶已明確表示要真人，任何額外的等待都會增加挫折感。

Q 2 Scenario 1 · Customer Support Resolution Agent

A customer contacts support saying: "I'm really frustrated — I've been waiting for my refund for two weeks." The agent's system prompt only says "escalate complex issues." The agent escalates immediately due to detected frustration. However, a review shows that 60% of escalated cases were straightforward refund status checks that the agent could have resolved. What is the most effective approach to reduce unnecessary escalations while still honoring genuine requests?

  1. Remove all escalation capability and require the agent to resolve every case autonomously
  2. Add few-shot examples to the system prompt showing that frustration alone does not trigger escalation — the agent should acknowledge frustration, offer resolution, and only escalate if the customer reiterates their preference for a human
  3. Replace the escalation trigger with a rule that only escalates cases open for more than 14 days
  4. Set the escalation confidence threshold to 0.9 so the model only escalates when very uncertain
展開解析

Correct Answer: B

B 正確：用 few-shot 範例在 system prompt 中明確示範「挫折但可解 → 先安撫 + 提議解決，客戶再堅持才升」的判斷邏輯。具體範例比抽象規則更能讓模型抓到判斷的語感，大幅降低因情緒誤觸升級的比率。

A 錯在哪：完全移除升級能力會在客戶明確要求真人、或政策空白時造成更大問題，這是矯枉過正。C 錯在哪：以案件開立時長作為升級條件完全偏離問題核心，且可能讓新開立的複雜政策例外案件無法即時升級。D 錯在哪：自評信心分數不可靠，且設定為 0.9 只會讓模型在所有案件上都假裝有信心，反而更不觸發必要的升級。

Q 3 Scenario 1 · Customer Support Resolution Agent

A customer named "Lin Wei" contacts support. The agent calls get_customer(name="Lin Wei") and receives three matching records. The agent selects the record with the most recent login, processes a return request, and the customer later reports that refund was applied to the wrong account. What change best prevents this type of error?

  1. Change the heuristic to select the record with the largest order history instead of most recent login
  2. Add a fallback that queries by email address if the name lookup returns more than one result
  3. Instruct the agent to request additional identifying information (order number or last 4 digits of phone) when get_customer returns multiple matches, rather than selecting based on any heuristic
  4. Limit get_customer to only return exact name matches to reduce the chance of multiple results
展開解析

Correct Answer: C

C 正確：多筆相符時，任何啟發法選擇都有處理到錯誤帳號的風險。正確做法是請客戶提供額外識別資訊（訂單號、手機後四碼）來進行 ambiguity resolution（模糊解析），確保唯一相符後才繼續處理。這是唯一能從根本消除猜測的方法。

A 錯在哪：換一個不同的啟發法（訂單量最多）同樣是在猜測，猜測的結果同樣可能出錯，沒有解決根本問題。B 錯在哪：用 email 備援查詢可能有幫助，但若客戶提供的 email 也有多筆相符，問題仍然存在；且這個方法並沒有消除在某些情況下仍需要額外識別資訊的需求。D 錯在哪：限制為精確姓名比對可能讓真正的客戶查不到（如略稱、空格差異），且即使是精確相符也可能有重名，無法根本解決問題。
