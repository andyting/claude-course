Task Statement 3.4 — Determine when to use plan mode vs direct execution

Knowledge of:

  • Plan mode is designed for complex tasks involving large-scale changes, multiple valid approaches, architectural decisions, and multi-file modifications
  • Direct execution is appropriate for simple, well-scoped changes (e.g., adding a single validation check to one function)
  • Plan mode enables safe codebase exploration and design before committing to changes, preventing costly rework
  • The Explore subagent for isolating verbose discovery output and returning summaries to preserve main conversation context

Skills in:

  • Selecting plan mode for tasks with architectural implications (e.g., microservice restructuring, library migrations affecting 45+ files, choosing between integration approaches with different infrastructure requirements)
  • Selecting direct execution for well-understood changes with clear scope (e.g., a single-file bug fix with a clear stack trace, adding a date validation conditional)
  • Using the Explore subagent for verbose discovery phases to prevent context window exhaustion during multi-phase tasks
  • Combining plan mode for investigation with direct execution for implementation (e.g., planning a library migration, then executing the planned approach)
本題情境 · SCENARIO 2
Scenario 2 — Code Generation with Claude Code

團隊用 Claude Code 做產生程式、重構、除錯。每接到一個任務,你都得先判斷:這是「先規劃再下手」的大工程(plan mode),還是「範圍清楚、直接改」的小事(direct execution)?本 Task 教你這個分流判斷,以及用 Explore subagent 探索而不爆 context。

一句話抓住主軸:任務複雜、牽連多檔、有架構抉擇 → 先 plan mode 規劃;範圍小又清楚 → 直接執行。核心是一道分流判斷,再加一個工具(Explore subagent)幫你在探索階段不爆 context。

Knowledge of · 知識點

知識 1  plan mode（計畫模式）適合:大規模、多種解法、架構決策、多檔修改

遇到這個問題時用到你需要把 monolith 的 payments 模組拆成獨立 microservice，這個改動牽涉 API 邊界重新設計、資料庫 schema 遷移、以及數十個呼叫端的修改，你需要知道是否應該先讓 Claude 規劃再動手。

plan mode 是為複雜任務設計的。判斷特徵:改動規模大、有多個都說得通的做法(需要先選)、牽涉架構決策、要動很多個檔案。這類任務一旦貿然下手,做錯方向就要大幅重來。

Scenario 2 的例子:把一個 monolith 拆成 microservice、或把某個 library 換掉(影響 45+ 個檔)——這些都該先 plan。

# ✅ 該用 plan mode 的徵兆(任一成立就考慮)
#   - 大規模改動(large-scale changes)
#   - 有多個都可行的做法,要先比較取捨
#   - 涉及架構決策(architectural decisions)
#   - 要修改多個檔案(multi-file)

# 例:library migration 影響 45+ 檔 → 先 plan mode
claude --permission-mode plan
# 先讓 Claude 探索、出方案,你確認後才動手
考點重點:大規模 / 多解法 / 架構抉擇 / 多檔 → plan mode。

知識 2  direct execution 適合:簡單、範圍清楚的小改動

遇到這個問題時用到oncall 工程師收到 stack trace 顯示 cart.py:42 有 KeyError，根因很明確是缺少 default value 處理，你需要判斷這個修正是否值得先跑 plan mode 還是直接執行。

反過來,如果任務簡單、範圍很清楚,規劃只是徒增延遲,直接做就好。官方例子:在某個 function 加一個驗證檢查。沒有方向之爭,沒有架構問題,單檔搞定。

# ✅ 該直接執行的徵兆
#   - 改動簡單、scope 清楚
#   - 單檔、無架構含意

# 例:在 validate_date() 加一個日期條件檢查
def validate_date(d):
    if d > today():           # 新增的一行驗證,範圍明確
        raise ValueError("date cannot be in the future")
    return d
# → 不需 plan,直接改
一句話記住:單檔、scope 清楚、無架構含意 → 直接執行,別過度規劃。

知識 3  plan mode（計畫模式）讓你先安全探索與設計,避免昂貴的重做

遇到這個問題時用到上次團隊讓 Claude 直接改了三個 service 的整合方式，做到一半才發現原本選的方案需要額外的基礎設施，整個重做花了兩天，你需要了解如何避免這種昂貴的 rework。

plan mode 的價值在於:在真的動手改之前,先安全地探索 codebase、把設計想清楚。它不會直接改檔,而是先產出計畫讓你檢視。這樣若方向錯了,你在「計畫」階段就能攔下,而不是等程式碼改了一半才發現要全部重來——那種重做(rework)成本很高。

重點:plan mode = 先想清楚再動手 → 把錯誤擋在計畫階段,省下昂貴 rework。

知識 4  Explore subagent:隔離吵雜的探索輸出,只回摘要保住主 context

遇到這個問題時用到你請 Claude 分析一個龐大的 legacy 認證系統，它翻了 80 個檔案並把所有原始內容倒進主對話，等到要開始重構時 context window 已幾乎耗盡，後續的實作階段沒有足夠空間，你需要一個方法隔離探索過程的雜訊。

複雜任務的「探索/發現」階段(discovery)常常很吵——翻一堆檔、grep 一堆結果。如果這些全進主對話,主 context window 很快被洗爆。Explore subagent 的作用:把這段 verbose 的探索放到子代理裡跑,主對話只收到精煉的摘要。

這跟 Task 3.2 的 context: fork、Task 1.3 的 subagent 觀念一脈相承——都是「把雜訊隔離、只帶結論回來」。

# ❌ 探索輸出全進主對話 → 翻 80 個檔的原文洗爆 context
# 主對話:讀 file1... file2... ... file80...(雜訊滿載)

# ✅ 用 Explore subagent:雜訊留子代理,主對話只收摘要
# Explore subagent → 回傳:「auth 流程集中在 3 個模組,
# 進入點是 login.py,session 由 redis 管理」
# → 主 context 乾淨,還有空間繼續做後續階段
重點:Explore subagent = 隔離 verbose discovery、只回摘要 → 保住主 context。

Skills in · 技能點

技能 1  為有架構含意的任務選 plan mode（計畫模式）

遇到這個問題時用到你接到任務要把現有系統從 REST API 整合換成 message queue 架構，這兩種方案有不同的基礎設施需求和 rollback 策略，你需要在動手前先讓 Claude 評估不同方向的取捨。

知識 1 的實戰落點。官方點名的情境:microservice 重構、library migration 影響 45+ 檔、在「不同基礎設施需求的整合方案」之間做選擇——這些都先 plan。

# ✅ 架構含意大 → plan mode 先出方案再確認
# 任務:把 payments 從 monolith 拆成獨立 service
claude --permission-mode plan \
  -p "規劃把 payments 模組拆成獨立 microservice:
列出受影響檔案、API 邊界、資料遷移步驟、回滾策略。"
# 先看計畫,確認方向對了才執行

技能 2  為範圍清楚的小改動選 direct execution

遇到這個問題時用到Sentry 告警顯示 validate_date() 函式沒有拒絕未來日期，你有明確的錯誤訊息與預期行為，你需要判斷這是否需要先規劃，還是直接讓 Claude 修。

知識 2 的落點。官方例子:有明確 stack trace 的單檔 bug fix、加一個日期驗證條件——直接做。

# ✅ 單檔、scope 明確 → 直接執行,不開 plan
# 任務:stack trace 指到 cart.py:42 的 KeyError,單檔修
claude -p "修正 cart.py:42 的 KeyError:
缺 key 時回傳預設值 0,並補一個測試。"
# 範圍清楚、無架構含意 → 規劃只是浪費時間
重點:有清楚 stack trace 的單檔修、加一個條件 → direct execution。

技能 3  在 verbose 探索階段用 Explore subagent 防 context 爆掉

遇到這個問題時用到你在做多階段重構任務，每次在第一個「探索 legacy 程式碼」階段就把 context 耗盡，導致後續的「實作重構」階段沒有足夠空間，你需要把探索過程隔離出去。

知識 4 的實作。多階段任務最怕在「發現階段」就把 context 用光,後面的實作階段沒空間。把探索丟給 Explore subagent。

# 多階段任務:探索 legacy 認證系統 → 之後要重構
# ✅ 探索階段交給 Explore subagent
#   Explore:掃 auth 相關檔,回傳精煉摘要
#   主對話只拿摘要 → context 不被 discovery 吃光
#   → 後續重構階段仍有充足 context 可用

技能 4  組合:plan mode（計畫模式）調查 + direct execution 實作

遇到這個問題時用到你要把所有 HTTP library 從 requests 換成 httpx，這影響 50 個檔案，但每個檔案的改法相對機械化，你需要先讓 Claude 規劃出完整的遷移步驟，確認沒有遺漏後再逐步執行。

兩者不是二選一,可以接力。官方例子:先用 plan mode 把 library migration 規劃好,確認方案後,再用 direct execution 照計畫執行。前段用規劃降風險,後段用直接執行求效率。

# 階段一:plan mode 調查 + 設計
claude --permission-mode plan \
  -p "規劃從 requests 遷移到 httpx,列出受影響檔與步驟。"

# 階段二:確認計畫後,direct execution 照表施工
claude -p "依先前計畫,把第 1~3 步的檔案改成 httpx 寫法。"
# ✅ 先規劃降風險,再直接執行求效率
重點:investigation 用 plan mode,implementation 用 direct execution,接力使用。

整個 Task 3.4 的記憶骨架

在 Scenario 2 接到任務先分流:大規模 / 多種解法 / 架構決策 / 多檔修改 → 用 plan mode 先安全探索與設計,把錯誤擋在計畫階段、省下昂貴 rework;簡單、範圍清楚的單檔小改(有 stack trace 的 bug fix、加一個驗證)→ direct execution,別過度規劃。探索階段吵雜時用 Explore subagent 隔離輸出、只回摘要,保住主 context。兩者可接力:plan mode 調查 → direct execution 實作。

Q 1 Scenario 2 · Code Generation with Claude Code

A team needs to migrate their HTTP client library from requests to httpx across 47 files in their codebase. Initial analysis shows at least three different integration patterns exist, each requiring a different migration approach, and the change also affects how the test suite mocks HTTP calls. The tech lead is deciding how to proceed with Claude Code. What is the most effective approach?

  1. Use direct execution immediately, since the migration is purely mechanical and does not require architectural decisions.
  2. Use plan mode first to explore the codebase, identify all three integration patterns, and produce a step-by-step migration plan before making any changes.
  3. Assign the task to the Explore subagent to scan all 47 files and generate the complete migration automatically without a planning phase.
  4. Use direct execution on the largest files first, then switch to plan mode if conflicts arise during the migration.
展開解析

Correct Answer: B

任務符合 plan mode 的所有判斷特徵：多個可行做法（三種整合 pattern）、影響 47 個檔案（multi-file）、牽涉測試策略變化（有架構含意）。先 plan 讓 Claude 探索並出方案，確認方向對了再執行，避免做到一半才發現某個 pattern 漏了。

A 錯在哪：「有三種不同整合 pattern 各需不同遷移方法」表示這不是純機械性任務，存在選擇點和架構含意，直接執行風險高。C 錯在哪：Explore subagent 的用途是隔離 verbose 的探索輸出保住主 context，它不是自動完成整個遷移任務的執行器。D 錯在哪：先動最大的檔案再回頭規劃會造成先做的那些與後來規劃出的方案不一致，增加 rework 成本。

Q 2 Scenario 2 · Code Generation with Claude Code

An on-call engineer receives a Sentry alert showing cart.py line 87: KeyError 'discount_code'. The stack trace clearly identifies the root cause: the code does not handle missing optional keys in the cart object. The fix requires adding a .get('discount_code', None) call in one function. What is the most appropriate execution strategy?

  1. Use plan mode to analyze all potential places in the codebase where similar KeyError patterns might exist before applying the fix.
  2. Use the Explore subagent to scan the entire codebase for related cart handling logic before making any changes.
  3. Use direct execution, as the fix is a well-scoped single-file change with a clear stack trace and no architectural implications.
  4. Use plan mode because the production incident requires a thorough root cause analysis across multiple files to prevent recurrence.
展開解析

Correct Answer: C

這是教材明確點名的 direct execution 場景：有明確 stack trace、單一檔案修改、無架構含意、範圍完全清楚。規劃只是增加不必要的延遲，直接執行是最有效率的做法。

A 錯在哪：掃描整個 codebase 找相似 pattern 超出了問題的 scope，目前的任務只是修一個已知的 bug，過度規劃浪費時間。B 錯在哪：Explore subagent 用於探索階段的 verbose 輸出隔離，在這個範圍清楚的單點修復場景中完全不需要。D 錯在哪：這個問題的根因已經非常清楚（缺少 .get 處理），用 plan mode 做「徹底根因分析」是過度工程化。

Q 3 Scenario 2 · Code Generation with Claude Code

A team is conducting a multi-phase refactoring of a legacy authentication system. During the first phase — exploring the existing codebase to understand the auth flow — Claude Code scans 80+ files and fills the main conversation context with raw file contents. By the time the exploration completes, there is insufficient context remaining for the second phase (implementing the refactored architecture). What should the team have done differently?

  1. Used plan mode for the exploration phase so Claude would generate a plan document instead of loading file contents into context.
  2. Used the Explore subagent for the verbose discovery phase, so that raw file contents stay in the subagent context and only a refined summary is returned to the main conversation.
  3. Broken the exploration into smaller chunks by exploring one directory at a time to avoid filling the context.
  4. Started with direct execution on the most critical auth files, then used the Explore subagent only for the remaining files.
展開解析

Correct Answer: B

Explore subagent 正是為這個情境設計的：把 verbose 的探索/發現階段放到隔離的子代理執行，中間大量的原始檔內容留在子代理，主對話只收到精煉的摘要。這讓後續的實作階段有充足的 context 空間可用。

A 錯在哪：plan mode 讓 Claude 在動手前先出規劃方案，但規劃本身也需要探索 codebase，如果不用 Explore subagent，探索時產生的 verbose 輸出仍會進入主 context，問題依然存在。C 錯在哪：分小批探索可以稍微緩解問題，但治標不治本，多次探索累積起來仍會消耗大量 context，而且每批之間可能遺漏跨目錄的關聯。D 錯在哪：先對重要檔案直接執行再探索其他的，在不了解整體架構前就開始修改，可能造成後來發現方向錯誤的 rework。
