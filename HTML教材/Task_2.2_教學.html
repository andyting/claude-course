官方考綱原文

Task Statement 2.2 — Implement structured error responses for MCP tools

Knowledge of:

  • The MCP isError flag pattern for communicating tool failures back to the agent
  • The distinction between transient errors (timeouts, service unavailability), validation errors (invalid input), business errors (policy violations), and permission errors
  • Why uniform error responses (generic "Operation failed") prevent the agent from making appropriate recovery decisions
  • The difference between retryable and non-retryable errors, and how returning structured metadata prevents wasted retry attempts

Skills in:

  • Returning structured error metadata including errorCategory (transient/validation/permission), isRetryable boolean, and human-readable descriptions
  • Including retriable: false flags and customer-friendly explanations for business rule violations so the agent can communicate appropriately
  • Implementing local error recovery within subagents for transient failures, propagating to the coordinator only errors that cannot be resolved locally along with partial results and what was attempted
  • Distinguishing between access failures (needing retry decisions) and valid empty results (representing successful queries with no matches)
本題情境 · SCENARIO 1
Scenario 1 — Customer Support Resolution Agent

延續客服解決 agent:當 lookup_order 查無訂單、process_refund 因金額超限被拒、後端暫時斷線時,MCP 工具要回傳結構化錯誤,讓 agent 知道能否重試或該不該 escalate_to_human。

一句話抓住主軸:工具出錯時,別只丟一句「失敗了」。 要回傳結構化的錯誤資訊——是哪一類錯、能不能重試、人看得懂的說明——這樣 agent 才能做出對的下一步(重試?換做法?還是直接跟使用者道歉)。

Knowledge of · 知識點

知識 1  MCP 的 isError 旗標:把「工具失敗」回報給 agent

MCP 工具回傳結果時,有一個 isError 旗標。它就是工具對 agent 說「這次我失敗了」的標準訊號。isError: true 代表這次呼叫沒成功,agent 看到就知道要走錯誤處理,而不是把錯誤內容當成正常結果。

# 客服 agent 呼叫 lookup_order 後,MCP 工具回應的基本形狀
success = {  # lookup_order 成功
    "isError": False,
    "content": [{"type": "text", "text": "訂單 A1023 狀態:已出貨"}],
}

failure = {  # process_refund 打後端時失敗
    "isError": True,          # ← 告訴 agent:這次失敗了
    "content": [{"type": "text", "text": "退款後端服務暫時無法連線"}],
}
考點重點:isError 是 MCP 標準的失敗回報旗標。

知識 2  四種錯誤類型要分清楚

不是所有錯誤都一樣。官方分四類,因為各類的處理方式完全不同:

transient(暫時性):逾時、服務暫時不可用 → 通常等一下重試就好。
validation(驗證):輸入不合法(如 order_id 格式錯) → 重試沒用,要修輸入。
business(業務規則):違反政策(如超過退款期限) → 不能重試,要照規則溝通。
permission(權限):沒有授權 → 重試也沒用,要走授權流程。

# 四類錯誤,各自對應不同處置
ERROR_HANDLING = {
    "transient":  "等待後重試(retry)",        # 逾時、服務暫時掛掉
    "validation": "修正輸入後再呼叫",         # 輸入不合法,重試無用
    "business":   "照政策向使用者說明",         # 違反規則,不可重試
    "permission": "走授權/升級流程",           # 無權限,重試無用
}
重點:transient / validation / business / permission，四類處置全不同。

知識 3  為什麼「統一的籠統錯誤」是壞事

如果每種錯誤都只回一句 "Operation failed",agent 就無從判斷該怎麼救。是該重試?還是修輸入?還是放棄?它看不出來,只能瞎猜——很可能做出錯誤的恢復決定(例如對一個不可重試的業務錯誤一直重試,白費功夫)。

# ❌ 籠統錯誤:agent 不知道該重試、修輸入、還是放棄
bad = {"isError": True, "content": [{"text": "Operation failed"}]}

# ✅ 結構化錯誤:agent 一看就知道下一步
good = {
    "isError": True,
    "errorCategory": "transient",
    "isRetryable": True,
    "content": [{"text": "付款服務逾時,稍後可重試"}],
}
重點:籠統錯誤剝奪了 agent 做正確恢復決策的能力。

知識 4  可重試 vs 不可重試:用 metadata 避免白費重試

關鍵分野:這個錯重試會不會有用?暫時性逾時 → 重試可能成功;輸入錯誤、違反業務規則、權限不足 → 重試一萬次也一樣失敗。回傳結構化的 isRetryable metadata,就能讓 agent不去做注定失敗的重試,省下時間與成本。

retryable     = {"errorCategory": "transient",  "isRetryable": True}
non_retryable = {"errorCategory": "validation", "isRetryable": False}

# agent 端的判斷
if err["isRetryable"]:
    retry_with_backoff()      # 值得再試
else:
    stop_and_handle(err)       # 別浪費重試
重點:isRetryable metadata 讓 agent 不浪費重試在注定失敗的錯誤上。

Skills in · 技能點

技能 1  回傳含 errorCategory、isRetryable、人類可讀說明的結構化錯誤

把知識落地成標準回應格式。三件套缺一不可:errorCategory(哪一類)、isRetryable(能不能重試)、人看得懂的 description(出了什麼事)。

def error_response(category, retryable, message):
    return {
        "isError": True,
        "errorCategory": category,        # transient / validation / business / permission
        "isRetryable": retryable,          # 布林
        "content": [{"type": "text", "text": message}],  # 人類可讀
    }

# 範例:後端逾時(可重試的暫時性錯誤)
return error_response("transient", True, "訂單服務逾時,請稍後重試。")

技能 2  業務規則違規:加 retriable:false + 對客戶友善的說明

業務錯誤(如超過退款期限)永遠不該重試。回應裡標明 retriable: false,並附上客戶能聽懂、不帶內部術語的說明,讓 agent 可以直接、得體地轉述給使用者。

# 業務規則違規:超過 30 天退款期限
return {
    "isError": True,
    "errorCategory": "business",
    "retriable": False,                  # 重試無意義
    "content": [{"type": "text",
        "text": "此訂單已超過 30 天退款期限,無法退款。"  # 客戶友善,可直接轉述
    }],
}
重點:business 錯誤要 retriable: false + 客戶友善說明,讓 agent 好溝通。

技能 3  agent 就地恢復暫時性錯誤,只把救不了的往上 escalate

好的分層處理:客服 agent 呼叫 lookup_order 遇到暫時性錯誤(後端逾時)時,自己先就地重試恢復(local recovery),不要一有閃失就丟給人工。只有本地解決不了的錯誤才 escalate_to_human,而且要連同已知資訊與「我試過什麼」一起交接,真人才能無縫接手。

def resolve_order_query(order_id, max_retry=3):
    for i in range(max_retry):
        r = lookup_order(order_id)
        if not r["isError"]:
            return r
        if r["errorCategory"] == "transient":
            sleep(2 ** i)             # 就地重試,不打擾真人
            continue
        break
    # 本地救不了 → escalate,並附已知資訊與嘗試紀錄
    return escalate_to_human(order_id=order_id,
            attempted=f"lookup_order 重試 {max_retry} 次仍逾時")
重點:暫時性錯誤 agent 就地恢復;救不了才 escalate_to_human,並附已知資訊與嘗試紀錄。

技能 4  分清「存取失敗」與「查無結果(空但成功)」

容易踩的坑:查詢成功但沒有符合的資料,這不是錯誤!空結果代表「查詢成功,只是沒命中」,應回正常成功 + 空集合。把它誤判成 access failure(存取失敗)去重試,就是浪費——存取失敗才需要重試決策。

# ✅ 查無結果:成功,只是空 → 不是錯誤,不該重試
empty_ok = {"isError": False, "content": [{"text": "找不到符合的訂單"}],
            "results": []}

# ❌ 存取失敗:真的沒查成 → 這才是 error,需要重試決策
access_fail = {"isError": True, "errorCategory": "transient",
               "isRetryable": True, "content": [{"text": "資料庫連線失敗"}]}
重點:空結果 = 成功(別重試);存取失敗 = 錯誤(才需要重試決策)。

整個 Task 2.2 的記憶骨架

工具失敗用 MCP 的 isError 旗標回報,但別只丟「失敗了」。要回結構化錯誤:標明 errorCategory(transient / validation / business / permission)、isRetryable、人類可讀說明。業務違規加 retriable: false + 客戶友善文字;subagent 就地恢復暫時性錯誤、救不了才連同部分結果上拋;最後別把空結果誤當存取失敗去重試。
