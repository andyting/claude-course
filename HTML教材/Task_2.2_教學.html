Implement structured error responses for MCP tools

官方考綱原文

Task Statement 2.2 — Implement structured error responses for MCP tools

Knowledge of:

  • The MCP isError flag pattern for communicating tool failures back to the agent
  • The distinction between transient errors (timeouts, service unavailability), validation errors (invalid input), business errors (policy violations), and permission errors
  • Why uniform error responses (generic "Operation failed") prevent the agent from making appropriate recovery decisions
  • The difference between retryable and non-retryable errors, and how returning structured metadata prevents wasted retry attempts

Skills in:

  • Returning structured error metadata including errorCategory (transient/validation/permission), isRetryable boolean, and human-readable descriptions
  • Including retriable: false flags and customer-friendly explanations for business rule violations so the agent can communicate appropriately
  • Implementing local error recovery within subagents for transient failures, propagating to the coordinator only errors that cannot be resolved locally along with partial results and what was attempted
  • Distinguishing between access failures (needing retry decisions) and valid empty results (representing successful queries with no matches)
本題情境 · SCENARIO 1
Scenario 1 — Customer Support Resolution Agent

延續客服解決 agent:當 lookup_order 查無訂單、process_refund 因金額超限被拒、後端暫時斷線時,MCP 工具要回傳結構化錯誤,讓 agent 知道能否重試或該不該 escalate_to_human。

一句話抓住主軸:工具出錯時,別只丟一句「失敗了」。 要回傳結構化的錯誤資訊——是哪一類錯、能不能重試、人看得懂的說明——這樣 agent 才能做出對的下一步(重試?換做法?還是直接跟使用者道歉)。

Knowledge of · 知識點

知識 1  MCP 的 isError 旗標：把「工具失敗」回報給 agent

遇到這個問題時用到你的客服 agent 在後端服務斷線時繼續把錯誤訊息當成正常回應處理，導致錯誤的退款狀態被呈現給使用者，你需要理解 MCP 如何用標準旗標區分「成功結果」與「工具失敗」。

MCP 工具回傳結果時,有一個 isError 旗標。它就是工具對 agent 說「這次我失敗了」的標準訊號。isError: true 代表這次呼叫沒成功,agent 看到就知道要走錯誤處理,而不是把錯誤內容當成正常結果。

# 客服 agent 呼叫 lookup_order 後,MCP 工具回應的基本形狀
success = {  # lookup_order 成功
    "isError": False,
    "content": [{"type": "text", "text": "訂單 A1023 狀態:已出貨"}],
}

failure = {  # process_refund 打後端時失敗
    "isError": True,          # ← 告訴 agent:這次失敗了
    "content": [{"type": "text", "text": "退款後端服務暫時無法連線"}],
}
考點重點:isError 是 MCP 標準的失敗回報旗標。

知識 2  四種 error category（錯誤類別）要分清楚

遇到這個問題時用到你的 agent 在遇到退款金額超限（業務規則違規）時反覆重試，浪費大量 API 呼叫且始終無法成功，你需要了解不同錯誤類型各自應該採取什麼處置，而不是對所有錯誤一律重試。

不是所有錯誤都一樣。官方分四類，因為各類的處理方式完全不同：

transient（暫時性錯誤）：逾時、服務暫時不可用 → 通常等一下重試就好。
validation（驗證錯誤）：輸入不合法（如 order_id 格式錯）→ 重試沒用，要修輸入。
business（商業邏輯錯誤）：違反政策（如超過退款期限）→ 不能重試，要照規則溝通。
permission（權限錯誤）：沒有授權 → 重試也沒用，要走授權流程。

# 四類錯誤,各自對應不同處置
ERROR_HANDLING = {
    "transient":  "等待後重試(retry)",        # 逾時、服務暫時掛掉
    "validation": "修正輸入後再呼叫",         # 輸入不合法,重試無用
    "business":   "照政策向使用者說明",         # 違反規則,不可重試
    "permission": "走授權/升級流程",           # 無權限,重試無用
}
重點:transient / validation / business / permission，四類處置全不同。

知識 3  為什麼「統一的籠統錯誤」是壞事

遇到這個問題時用到你的工具在各種失敗情況下都只回傳 "Operation failed"，導致 agent 無法判斷要重試、修正輸入還是直接向使用者道歉，你需要理解為何 uniform error response（統一錯誤回應）會癱瘓 agent 的自主恢復能力。

如果每種錯誤都只回一句 "Operation failed",agent 就無從判斷該怎麼救。是該重試?還是修輸入?還是放棄?它看不出來,只能瞎猜——很可能做出錯誤的恢復決定(例如對一個不可重試的業務錯誤一直重試,白費功夫)。

# ❌ 籠統錯誤:agent 不知道該重試、修輸入、還是放棄
bad = {"isError": True, "content": [{"text": "Operation failed"}]}

# ✅ 結構化錯誤:agent 一看就知道下一步
good = {
    "isError": True,
    "errorCategory": "transient",
    "isRetryable": True,
    "content": [{"text": "付款服務逾時,稍後可重試"}],
}
重點:籠統錯誤剝奪了 agent 做正確恢復決策的能力。

知識 4  retryable（可重試）vs 不可重試：用 metadata 避免白費重試

遇到這個問題時用到監控顯示你的 agent 對驗證錯誤（輸入格式不合法）執行了數十次重試，消耗了大量成本且最終仍然失敗，你需要了解如何透過結構化 metadata 讓 agent 在嘗試之前就知道這個錯誤是否值得重試。

關鍵分野：這個錯重試會不會有用？暫時性逾時 → 重試可能成功；輸入錯誤、違反業務規則、權限不足 → 重試一萬次也一樣失敗。回傳結構化的 isRetryable metadata，就能讓 agent 不去做注定失敗的重試，省下時間與成本。

retryable     = {"errorCategory": "transient",  "isRetryable": True}
non_retryable = {"errorCategory": "validation", "isRetryable": False}

# agent 端的判斷
if err["isRetryable"]:
    retry_with_backoff()      # 值得再試
else:
    stop_and_handle(err)       # 別浪費重試
重點:isRetryable metadata 讓 agent 不浪費重試在注定失敗的錯誤上。

Skills in · 技能點

技能 1  回傳含 errorCategory、isRetryable、人類可讀說明的 structured error（結構化錯誤）

遇到這個問題時用到你需要為 lookup_order 和 process_refund 工具設計標準錯誤回應格式，讓 agent 在遇到後端逾時、輸入格式錯誤或退款被拒時，能夠自動採取正確的下一步。

把知識落地成標準回應格式。三件套缺一不可:errorCategory(哪一類)、isRetryable(能不能重試)、人看得懂的 description(出了什麼事)。

def error_response(category, retryable, message):
    return {
        "isError": True,
        "errorCategory": category,        # transient / validation / business / permission
        "isRetryable": retryable,          # 布林
        "content": [{"type": "text", "text": message}],  # 人類可讀
    }

# 範例:後端逾時(可重試的暫時性錯誤)
return error_response("transient", True, "訂單服務逾時,請稍後重試。")

技能 2  business error（商業邏輯錯誤）違規：加 retriable: false + 對客戶友善的說明

遇到這個問題時用到客服 agent 在退款超過期限時回覆了含有系統內部術語的錯誤訊息（如「ERR_REFUND_POLICY_VIOLATION」），使用者看不懂且感到困惑，你需要設計讓 agent 能直接轉述的客戶友善錯誤格式。

業務錯誤(如超過退款期限)永遠不該重試。回應裡標明 retriable: false,並附上客戶能聽懂、不帶內部術語的說明,讓 agent 可以直接、得體地轉述給使用者。

# 業務規則違規:超過 30 天退款期限
return {
    "isError": True,
    "errorCategory": "business",
    "retriable": False,                  # 重試無意義
    "content": [{"type": "text",
        "text": "此訂單已超過 30 天退款期限,無法退款。"  # 客戶友善,可直接轉述
    }],
}
重點:business 錯誤要 retriable: false + 客戶友善說明,讓 agent 好溝通。

技能 3  agent 就地恢復 transient error（暫時性錯誤），只把救不了的往上 escalate

遇到這個問題時用到你的客服系統在後端暫時斷線時馬上升級給人工客服，造成人工客服被大量可自動恢復的暫時性故障淹沒，你需要設計 local recovery（就地恢復）邏輯，只在真正無法自動修復時才 escalate。

好的分層處理:客服 agent 呼叫 lookup_order 遇到暫時性錯誤(後端逾時)時,自己先就地重試恢復(local recovery),不要一有閃失就丟給人工。只有本地解決不了的錯誤才 escalate_to_human,而且要連同已知資訊與「我試過什麼」一起交接,真人才能無縫接手。

def resolve_order_query(order_id, max_retry=3):
    for i in range(max_retry):
        r = lookup_order(order_id)
        if not r["isError"]:
            return r
        if r["errorCategory"] == "transient":
            sleep(2 ** i)             # 就地重試,不打擾真人
            continue
        break
    # 本地救不了 → escalate,並附已知資訊與嘗試紀錄
    return escalate_to_human(order_id=order_id,
            attempted=f"lookup_order 重試 {max_retry} 次仍逾時")
重點:暫時性錯誤 agent 就地恢復;救不了才 escalate_to_human,並附已知資訊與嘗試紀錄。

技能 4  分清「存取失敗（access failure）」與「查無結果（空但成功）」

遇到這個問題時用到你的 agent 在查詢訂單回傳空陣列時觸發了重試邏輯，導致同一個不存在的訂單被查詢三次，你需要明確區分「查詢成功但無資料」與「查詢本身失敗」這兩種完全不同的情況。

容易踩的坑:查詢成功但沒有符合的資料,這不是錯誤!空結果代表「查詢成功,只是沒命中」,應回正常成功 + 空集合。把它誤判成 access failure(存取失敗)去重試,就是浪費——存取失敗才需要重試決策。

# ✅ 查無結果:成功,只是空 → 不是錯誤,不該重試
empty_ok = {"isError": False, "content": [{"text": "找不到符合的訂單"}],
            "results": []}

# ❌ 存取失敗:真的沒查成 → 這才是 error,需要重試決策
access_fail = {"isError": True, "errorCategory": "transient",
               "isRetryable": True, "content": [{"text": "資料庫連線失敗"}]}
重點:空結果 = 成功(別重試);存取失敗 = 錯誤(才需要重試決策)。

整個 Task 2.2 的記憶骨架

工具失敗用 MCP 的 isError 旗標回報,但別只丟「失敗了」。要回結構化錯誤:標明 errorCategory(transient / validation / business / permission)、isRetryable、人類可讀說明。業務違規加 retriable: false + 客戶友善文字;subagent 就地恢復暫時性錯誤、救不了才連同部分結果上拋;最後別把空結果誤當存取失敗去重試。

考試情境題

以下三題模擬正式考試格式，每題一個生產情境，四個選項。先嘗試作答，再展開解析。

Q 1 Scenario 1 · Customer Support Resolution Agent

A customer support agent calls process_refund. The tool returns {"isError": true, "content": [{"text": "Operation failed"}]}. The agent retries the call five more times, all failing, before giving up. Monitoring later reveals the failures were caused by a business rule violation — the order was outside the 30-day refund window. What is the most likely root cause of the unnecessary retries?

  1. The agent's retry logic was too aggressive and should have used exponential backoff.
  2. The error response lacked structured metadata (errorCategory and isRetryable), so the agent had no signal that this error was non-retryable.
  3. The isError flag was not set correctly in the MCP response.
  4. The agent should have called escalate_to_human after the first failure instead of retrying.
展開解析

Correct Answer: B

工具只回了 "Operation failed" 這句籠統訊息，沒有 errorCategory: "business" 和 isRetryable: false。Agent 看不到這些 metadata，只能假設這是暫時性問題並重試。結構化錯誤的核心價值就是讓 agent 在嘗試前就知道「這個錯誤重試有沒有用」。

A 錯在哪：exponential backoff 是處理 transient error 的好做法，但問題在 agent 根本不知道這是 non-retryable 的 business error，調整 backoff 策略無濟於事。C 錯在哪：題目說 isError: true 已正確設定，這不是根本問題；缺的是 category 和 retryable 欄位。D 錯在哪：一次失敗就 escalate_to_human 是過度設計，transient error 應該先就地恢復，只有無法本地解決的才 escalate。

Q 2 Scenario 1 · Customer Support Resolution Agent

A lookup_order MCP tool returns the following when a customer queries an order that doesn't exist: {"isError": true, "errorCategory": "transient", "isRetryable": true, "content": [{"text": "No order found"}]}. The agent retries three times and eventually fails. What is wrong with this error response design?

  1. The isError flag should be false for empty results — a successful query with no matches is not an error.
  2. The errorCategory should be "validation" because the order ID format may be invalid.
  3. The response is missing a human-readable description field for the customer.
  4. The tool should return an HTTP 404 status code instead of using the isError flag.
展開解析

Correct Answer: A

「查無訂單」是查詢成功但無資料的情況（empty result），不是存取失敗。應該回傳 isError: false 並附上空的 results 陣列，讓 agent 知道「查詢成功，只是沒有符合的結果」。把它標記為 isError: true, isRetryable: true 讓 agent 誤以為是暫時性存取失敗而浪費重試。

B 錯在哪：validation error 是「輸入不合法」，但「找不到訂單」並不代表輸入格式有問題，用戶可能查了一個合法但不存在的訂單號碼。C 錯在哪：加人類可讀說明是好習慣，但這不是這個錯誤設計的核心問題——根本問題是把「空結果」誤設為「錯誤」。D 錯在哪：MCP 工具不使用 HTTP 狀態碼，而是用 isError 旗標；這個選項混淆了 HTTP API 和 MCP 協議的概念。

Q 3 Scenario 1 · Customer Support Resolution Agent

A subagent handling order lookups encounters a transient database timeout. The agent is part of a multi-agent customer support system with a coordinator and a human escalation path. According to structured error handling best practices, what is the most effective approach?

  1. Immediately return isError: true to the coordinator with full error details so it can decide whether to retry.
  2. Attempt local recovery with retries (e.g., exponential backoff), and only propagate to the coordinator if all local retries fail — including what was attempted and any partial results.
  3. Escalate directly to a human agent with the error details since database timeouts require human intervention.
  4. Suppress the error and return an empty result set to avoid interrupting the coordinator's workflow.
展開解析

Correct Answer: B

Transient error（暫時性錯誤）的處理原則：subagent 先就地恢復（local recovery），用 exponential backoff 重試幾次。只有本地解決不了才往上 escalate 給 coordinator，而且要附上「已嘗試的動作」與「部分結果」，讓 coordinator 和後續接手者能夠無縫繼續，避免重複工作。

A 錯在哪：對於 transient error，立刻往上拋讓 coordinator 決定是不必要的負擔；subagent 有能力自己重試，應先嘗試本地恢復。C 錯在哪：database timeout 是 transient error，不需要人工介入；只有本地多次重試都失敗、且是 non-retryable error 才考慮 escalate_to_human。D 錯在哪：壓制錯誤並回傳空結果會讓 coordinator 以為查詢成功但無資料，做出錯誤的決策，是最危險的做法。
