Task Statement 5.1 — Manage conversation context to preserve critical information across long interactions

Knowledge of:

  • Progressive summarization risks: condensing numerical values, percentages, dates, and customer-stated expectations into vague summaries
  • The "lost in the middle" effect: models reliably process information at the beginning and end of long inputs but may omit findings from middle sections
  • How tool results accumulate in context and consume tokens disproportionately to their relevance (e.g., 40+ fields per order lookup when only 5 are relevant)
  • The importance of passing complete conversation history in subsequent API requests to maintain conversational coherence

Skills in:

  • Extracting transactional facts (amounts, dates, order numbers, statuses) into a persistent "case facts" block included in each prompt, outside summarized history
  • Extracting and persisting structured issue data (order IDs, amounts, statuses) into a separate context layer for multi-issue sessions
  • Trimming verbose tool outputs to only relevant fields before they accumulate in context (e.g., keeping only return-relevant fields from order lookups)
  • Placing key findings summaries at the beginning of aggregated inputs and organizing detailed results with explicit section headers to mitigate position effects
  • Requiring subagents to include metadata (dates, source locations, methodological context) in structured outputs to support accurate downstream synthesis
  • Modifying upstream agents to return structured data (key facts, citations, relevance scores) instead of verbose content and reasoning chains when downstream agents have limited context budgets
本題情境 · SCENARIO 1
Scenario 1 — Customer Support Resolution Agent（客服解決 agent）

客服 agent 處理退貨/帳務爭議,常常一通對話來回數十輪。客戶一開始講的退款金額、訂單編號、期望日期,若被「漸進式摘要」壓成模糊一句話,後面就會跟丟。本 Task 教的就是:把 lookup_order 這類工具回傳的一大包欄位裁乾淨,並把交易事實釘成不會被摘要吃掉的「case facts」。

一句話抓住主軸:長對話裡,「數字與事實」最容易在摘要與位置效應中流失。把它們抽出來、釘在每個 prompt 的固定位置,並把臃腫的工具輸出裁掉,才能在第 30 輪還記得客戶第 1 輪講的退款金額。

Knowledge of · 知識點

知識 1  漸進式摘要的風險:數字、百分比、日期、客戶期望被壓成模糊摘要

對話一長,常見做法是把舊歷史「摘要」成短文字以省 token。問題是:摘要會把精確的數值磨成模糊的形容詞。客戶說「我要退 $129.99,訂單 A-77214,希望本週五前到帳」,被摘成「客戶想退一筆款項」——金額、訂單、日期全沒了,後面 agent 只能瞎猜或重問。

# ❌ 漸進式摘要把可量化事實磨掉了
summary = "客戶對某筆訂單不滿,想要退款,態度有點急。"
# 金額?訂單號?期望日期?全部不見 → 下一輪只能重問,體驗變差

# ✅ 摘要可以做,但數字/日期/期望必須另外抽出來保留(見技能 1)
case_facts = {
    "refund_amount": "129.99",
    "order_id": "A-77214",
    "customer_expectation": "本週五前到帳",
}
考點重點:摘要可省 token,但絕不能把數字、百分比、日期、客戶明講的期望摘進去——這些要原值保留。

知識 2  「迷失在中間」(lost in the middle):模型對頭尾可靠、中段容易漏

把一大堆內容塞進一個長 prompt 時,模型對開頭和結尾的資訊處理得很穩,但中段的內容常被忽略。所以關鍵事實(case facts、最重要的工具結果)應該放在開頭或結尾,而不是埋在中間第 17 段。

# ❌ 把最關鍵的退款事實埋在長對話的正中央
prompt = long_history_part1 + "\n關鍵:退款 $129.99\n" + long_history_part2
# 中段的「退款 $129.99」很可能被模型略過

# ✅ 關鍵事實放最前面,細節歷史放後面
prompt = f"""[CASE FACTS]
退款金額: $129.99 | 訂單: A-77214 | 期望: 週五前

[對話歷史]
{full_history}
"""
重點:關鍵摘要放開頭、細節用明確 section header 組織,以對抗位置效應。

知識 3  工具結果會累積、且佔 token 與其相關性不成比例

每次呼叫 lookup_order 可能回傳 40+ 個欄位(運費試算、行銷標籤、倉庫代碼…),但對「處理退貨」真正有用的可能只有 5 個。這些臃腫輸出會一輪一輪累積在 context 裡,把 token 預算吃光,還稀釋了真正重要的資訊。

# lookup_order 原始回傳:40+ 欄位
raw = lookup_order("A-77214")
# raw 含:shipping_carrier、warehouse_zone、promo_tags、
#         loyalty_points、gift_wrap、... 大多與退貨無關

# ✅ 只留退貨相關欄位再進 context(見技能 3)
relevant = {k: raw[k] for k in
    ["order_id", "amount", "status", "purchase_date", "return_window"]}
重點:工具輸出進 context 前先裁;不裁,token 會被無關欄位耗光。

知識 4  後續 API 請求要帶「完整對話歷史」以維持連貫

Claude API 是無狀態的——它不會自己記得上一輪。每次發請求,你都要把完整對話歷史(messages 陣列)帶上,模型才能保持連貫。注意這跟知識 3 不衝突:「帶完整歷史」指的是訊息序列要完整,但每則訊息內的臃腫工具輸出仍應先裁乾淨。

# ✅ 每次請求帶上完整 messages,維持連貫
messages.append({"role": "user", "content": user_msg})
resp = client.messages.create(model="claude-...", messages=messages)

# ❌ 只送最後一句 → agent 忘了前面在處理哪筆退貨
resp = client.messages.create(model="claude-...",
    messages=[{"role": "user", "content": user_msg}])
重點:訊息序列要完整(API 無狀態);但訊息內的工具輸出要先瘦身。兩者並行不悖。

Skills in · 技能點

技能 1  把交易事實抽成持久的 "case facts" 區塊,放在摘要歷史之外

金額、日期、訂單號、狀態這類交易事實,抽出來做成一個獨立的 case facts 區塊,每個 prompt 都原樣帶上。它不參與摘要——歷史可以被壓縮,但 case facts 永遠是原值。

def build_case_facts(order):
    return {
        "order_id": order["order_id"],
        "amount": order["amount"],
        "purchase_date": order["purchase_date"],
        "status": order["status"],
    }

def build_prompt(case_facts, summarized_history, user_msg):
    # case facts 在摘要歷史之外,永遠原值帶上
    return f"""[CASE FACTS — 不可摘要]
{case_facts}

[對話摘要]
{summarized_history}

[客戶最新訊息]
{user_msg}
"""
重點:case facts = 交易事實的單一可信來源,獨立於可被摘要的歷史。

技能 2  多議題對話:把結構化 issue 資料抽到獨立的 context 層

同一通對話,客戶可能同時抱怨「兩筆訂單」。若混在一起,agent 很容易把 A 訂單的金額套到 B 訂單。做法:每個 issue 各自結構化(order ID / 金額 / 狀態),存到一個獨立的 context 層,彼此不混。

# ✅ 多議題:每個 issue 各一筆結構化資料
issues = [
    {"order_id": "A-77214", "amount": "129.99", "status": "退款處理中"},
    {"order_id": "A-80552", "amount": "45.00",  "status": "等待客戶確認"},
]
# agent 處理每個 issue 時,鎖定對應那一筆,不會張冠李戴
重點:多議題 → 每個 issue 獨立結構化 → 金額/狀態不會互相污染。

技能 3  在工具輸出累積進 context 前,先裁成只剩相關欄位

這是知識 3 的實作。lookup_order 回 40+ 欄位,但對退貨只需要少數幾個。在它進 context 之前就裁掉,而不是讓整包原始 JSON 一輪一輪堆積。

RETURN_FIELDS = ["order_id", "amount", "status",
                 "purchase_date", "return_window"]

def trim_order(raw_order):
    # 只保留退貨相關欄位,丟掉其餘 35+ 個無關欄位
    return {k: raw_order[k] for k in RETURN_FIELDS if k in raw_order}

raw = lookup_order("A-77214")
context.add_tool_result(trim_order(raw))   # ✅ 進 context 前已瘦身
重點:裁在「進 context 之前」,避免無關欄位一輪輪累積。

技能 4  關鍵摘要放開頭、用明確 section header 組織細節,以抗位置效應

這是知識 2 的實作。把多筆來源彙總成一個輸入時,關鍵發現的摘要放最前面,後面的細節用清楚的標題分段(=== 訂單 A-77214 ===),別讓重要結論埋在中段。

def assemble_input(key_findings, detail_blocks):
    out = "[關鍵發現]\n" + key_findings + "\n\n"   # ✅ 摘要在最前
    for title, body in detail_blocks:
        out += f"=== {title} ===\n{body}\n\n"          # 明確 header 分段
    return out
重點:摘要置頂 + 明確 section header = 對抗「lost in the middle」。

技能 5  要求 subagent 在結構化輸出中帶上 metadata,以支援下游正確綜合

當客服系統背後也用多 agent(例如一個 agent 查保固政策、一個查訂單),要求每個 subagent 的輸出都帶上 metadata(日期、來源出處、方法論脈絡)。下游做綜合時才能正確判讀,而不是把不同時間點的資料當成矛盾。

# ✅ subagent 輸出帶 metadata
policy_finding = {
    "content": "30 天內可全額退款",
    "metadata": {
        "source": "return_policy_v3",
        "effective_date": "2026-01-01",   # 下游可判讀時效
    },
}
重點:結構化輸出 + metadata(日期/來源)→ 下游綜合不誤判。

技能 6  讓上游 agent 回「結構化資料」而非冗長內容,以省下游 context 預算

當下游 agent 的 context 預算很緊時,改造上游:讓它回結構化的 key facts / 引用 / 相關性分數,而不是把整段推理鏈與冗長內文倒給下游。下游只需要「事實 + 出處 + 重要度」,不需要上游的思考過程。

# ❌ 上游回一大段推理 + 原文,吃光下游 context
upstream_out = "我先看了訂單,然後想到退款政策,再考慮... (數千字)"

# ✅ 上游回結構化精華:key facts + citation + relevance
upstream_out = {
    "key_facts": ["訂單 A-77214 在退貨期內", "金額 $129.99"],
    "citations": ["return_policy_v3 §2"],
    "relevance": 0.95,
}
重點:下游 context 緊 → 上游改回「結構化精華」,不傳冗長推理鏈。

整個 Task 5.1 的記憶骨架

客服長對話最怕數字與事實流失:漸進摘要會把金額/日期/期望磨糊,中段資訊會迷失在中間,而 lookup_order 的 40+ 欄位會把 token 吃光。對策三件套:把交易事實抽成case facts 釘在 prompt 開頭(不參與摘要)、工具輸出進 context 前先裁成相關欄位、彙總時摘要置頂 + 明確 header。多議題各自結構化、上下游用結構化 + metadata 傳遞;同時記得 API 無狀態,訊息序列要帶完整。
