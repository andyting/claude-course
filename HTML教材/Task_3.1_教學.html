Task Statement 3.1 — Configure CLAUDE.md files with appropriate hierarchy, scoping, and modular organization

Knowledge of:

  • The CLAUDE.md configuration hierarchy: user-level (~/.claude/CLAUDE.md), project-level (.claude/CLAUDE.md or root CLAUDE.md), and directory-level (subdirectory CLAUDE.md files)
  • That user-level settings apply only to that user—instructions in ~/.claude/CLAUDE.md are not shared with teammates via version control
  • The @import syntax for referencing external files to keep CLAUDE.md modular (e.g., importing specific standards files relevant to each package)
  • .claude/rules/ directory for organizing topic-specific rule files as an alternative to a monolithic CLAUDE.md

Skills in:

  • Diagnosing configuration hierarchy issues (e.g., a new team member not receiving instructions because they're in user-level rather than project-level configuration)
  • Using @import to selectively include relevant standards files in each package's CLAUDE.md based on maintainer domain knowledge
  • Splitting large CLAUDE.md files into focused topic-specific files in .claude/rules/ (e.g., testing.md, api-conventions.md, deployment.md)
  • Using the /memory command to verify which memory files are loaded and diagnose inconsistent behavior across sessions
本題情境 · SCENARIO 2
Scenario 2 — Code Generation with Claude Code

團隊用 Claude Code 做產生程式、重構、除錯與文件,並整合自訂 slash command 與 CLAUDE.md。本 Task 要把這些「給 Claude 的常駐指示」放對位置:全隊共用的規範進專案層、個人偏好進使用者層,並用 @import 與 .claude/rules/ 把龐大規範拆成模組,還會教你用 /memory 抓「新同事為何沒套到規範」這類 bug。

一句話抓住主軸:CLAUDE.md 是「給 Claude 的常駐說明書」,放錯層級,規範就傳不到該傳的人。 全隊要共享的規範放專案層(進版控)、只屬於你的偏好放使用者層(不分享);說明書太長就用 @import 和 .claude/rules/ 拆成模組。

Knowledge of · 知識點

知識 1  CLAUDE.md file（CLAUDE.md 檔）的三層階層:使用者層、專案層、目錄層

遇到這個問題時用到新團隊成員加入後發現 Claude Code 的行為與資深工程師機器上不一樣，你需要了解設定如何跨層級疊加，才能診斷規範究竟在哪一層生效。

Claude Code 會從三個層級讀 CLAUDE.md,範圍由大到小:
使用者層 ~/.claude/CLAUDE.md——你所有專案都生效的個人偏好。
專案層 .claude/CLAUDE.md 或 repo 根目錄的 CLAUDE.md——這個專案全隊共用。
目錄層 子資料夾裡的 CLAUDE.md——只在那個子目錄(例如某個 package)內生效。
三層會疊加,愈靠近你正在改的檔,規範愈具體。

# Scenario 2:一個用 Claude Code 開發的 monorepo,三層 CLAUDE.md
~/.claude/CLAUDE.md              # 使用者層:我個人偏好(所有專案)
my-monorepo/CLAUDE.md            # 專案層:全隊共用規範(進版控)
my-monorepo/packages/api/CLAUDE.md      # 目錄層:只管 api 這個 package
my-monorepo/packages/web/CLAUDE.md      # 目錄層:只管 web 這個 package
# 改 api 底下的檔時 → 使用者層 + 專案層 + api 目錄層 疊加生效
考點重點:三層 = 使用者(~/.claude)、專案(repo 根 / .claude)、目錄(子資料夾)。範圍由大到小、疊加生效。

知識 2  使用者層設定只對你生效,不會經版控分享給隊友

遇到這個問題時用到你的機器上 Claude 會套用某條編碼規範，但新同事 clone 同一個 repo 後卻完全沒有這條規範，你需要理解使用者層與專案層的根本差異才能找出根因。

關鍵差別:寫在 ~/.claude/CLAUDE.md 的東西只在你自己的機器上生效。它不在專案 repo 裡,所以不會被 commit、不會經版控傳給隊友。隊友 clone 專案,拿到的只有專案層的 CLAUDE.md,完全看不到你使用者層寫了什麼。這正是下面那個「新同事沒套到規範」bug 的根源。

# ~/.claude/CLAUDE.md(使用者層)— 只屬於你,不分享
# 例:你個人喜歡 Claude 回中文、commit 訊息用某格式
- 回覆一律用繁體中文
- 我偏好 commit message 加上 emoji 前綴

# ❌ 把「全隊都要遵守」的規範藏在這裡 → 隊友永遠收不到
# ✅ 團隊共用規範要放專案層(見知識 1),才會經版控分享
考點重點:使用者層 = 私人、不進版控、不分享;團隊規範必須放專案層。

知識 3  @import 語法:引用外部檔案,讓 CLAUDE.md 保持模組化

遇到這個問題時用到monorepo 中不同 package 各有不同技術棧，你的 CLAUDE.md 越來越龐雜，各 package 維護者抱怨載入了許多與自己無關的規範，你需要 @import 來讓每個 package 只引入相關標準。

當規範越長越雜,別把所有東西塞進一個巨大的 CLAUDE.md。用 @import 把外部標準檔引用進來——每個 package 的 CLAUDE.md 只 import 它真正相關的標準。這樣維護者可以依自己 package 的領域知識,挑要引哪些規範,而不是被迫吞下全部。

# packages/api/CLAUDE.md — 只引 api 相關的標準
# 這個 package 是後端服務,維護者知道該套哪些規範
@import ../../standards/typescript.md
@import ../../standards/rest-api-design.md
@import ../../standards/database-migrations.md

# packages/web/CLAUDE.md — 只引前端相關的
@import ../../standards/typescript.md
@import ../../standards/react-components.md
@import ../../standards/accessibility.md
# → 共用的 typescript.md 一處維護,各 package 各取所需
考點重點:@import = 把外部標準檔引進來,讓每個 package 各取所需、避免單檔肥大。

知識 4  .claude/rules/ 目錄:把規範拆成主題檔（rules file），取代單一巨檔

遇到這個問題時用到你的 CLAUDE.md 已超過 1500 行，測試規範、API 約定、部署流程全混在一起，每次要修改某塊都要全文搜尋，而且 PR review 時 reviewer 完全看不清楚改了什麼，你需要按主題拆檔來解決。

另一種模組化做法:不用一個塞爆的 CLAUDE.md,而是建 .claude/rules/ 目錄,把規範按主題拆成多個檔——testing.md、api-conventions.md、deployment.md 各管一塊。好處是好找、好維護、改一塊不會動到別塊,review 也清楚。

# Scenario 2:把龐大的 CLAUDE.md 拆進 .claude/rules/
.claude/
└── rules/
    ├── testing.md           # 測試規範
    ├── api-conventions.md    # API 命名與設計約定
    └── deployment.md         # 部署流程
# 每個主題一個檔 → 比一個 2000 行的 CLAUDE.md 好維護太多
考點重點:.claude/rules/ = 按主題拆檔(testing / api-conventions / deployment),取代單一巨檔。

Skills in · 技能點

技能 1  診斷階層問題:新同事沒收到規範,因為規範被放在使用者層

遇到這個問題時用到onboarding 後新工程師回報 Claude 產出的 API 回應格式不符合規範，但你和其他舊成員都沒問題，你需要診斷這是哪一層設定的問題並修正。

最經典的考題場景:某條重要規範「在你機器上有效,新同事卻完全沒套到」。直覺反應是「設定壞了」,但真正原因常是——這條規範被寫在使用者層 ~/.claude/CLAUDE.md,只對你生效,沒進版控,新同事 clone 專案根本拿不到。修法:把它搬到專案層,commit 進 repo,規範才會跟著程式碼一起傳給每個人。

# ❌ 病因:團隊規範誤放使用者層 → 只有你有,新同事沒有
~/.claude/CLAUDE.md:
    - 所有 API 回應一律用 snake_case

# ✅ 修法:搬到專案層並進版控 → 全隊(含新同事)都收到
# my-monorepo/CLAUDE.md(或 .claude/CLAUDE.md)
    - 所有 API 回應一律用 snake_case
# $ git add CLAUDE.md && git commit -m "share API casing rule"
重點:「只有我有、別人沒有」的規範 → 八成被放在使用者層,搬到專案層並 commit。

技能 2  用 @import 依維護者領域知識,選擇性引入各 package 的標準

遇到這個問題時用到金流 package 的維護者抱怨 Claude 產出的程式碼沒套用 PCI 安全規範，而前端 package 的人卻說塞了一堆不相關的後端規則，你需要用 @import 讓各 package 各取所需。

技能版的知識 3。每個 package 的維護者最清楚自己這塊該套哪些規範,就用 @import 只引那些。共用標準(如 security.md)集中一處維護,各 package 按需引入,不重複、不錯漏。

# packages/payments/CLAUDE.md — 金流 package,維護者知道要更嚴
@import ../../standards/security.md          # 金流必引安全規範
@import ../../standards/pci-compliance.md     # 這塊特有
@import ../../standards/typescript.md

# packages/docs/CLAUDE.md — 文件 package,不需金流那套
@import ../../standards/markdown-style.md
# → 各取所需:payments 引安全規範,docs 不必背這份

技能 3  把大 CLAUDE.md 拆成 .claude/rules/ 下的主題檔

遇到這個問題時用到在做 code review 時發現有人修改了測試規範卻順手動到部署規範，因為它們全在同一份 CLAUDE.md，你需要把規範按主題切開讓每個人只改自己負責的那一塊。

技能版的知識 4。當單一 CLAUDE.md 長到難維護,動手拆:依主題切成 testing.md、api-conventions.md、deployment.md 放進 .claude/rules/。每塊聚焦單一主題,要找測試規範就開 testing.md,清楚明確。

# ❌ 拆前:一個 1800 行的巨型 CLAUDE.md,什麼都塞
CLAUDE.md   # 測試、API、部署、風格…全混在一起,難找難改

# ✅ 拆後:按主題進 .claude/rules/
.claude/rules/testing.md          # 「怎麼寫測試」一律看這份
.claude/rules/api-conventions.md  # API 約定
.claude/rules/deployment.md       # 部署規範
# 改部署流程 → 只動 deployment.md,不影響其他主題
重點:巨檔難維護 → 按主題拆進 .claude/rules/,單檔聚焦、改動隔離。

技能 4  用 /memory 指令（slash command）確認「載入了哪些 memory 檔」,診斷跨 session 行為不一致

遇到這個問題時用到Claude Code 今天早上套用了 API 命名規範，但下午換了 session 之後產出的程式碼又不套了，你需要查清楚到底哪些 CLAUDE.md 檔在目前 session 裡被載入了。

有時 Claude Code 在不同 session「行為飄忽」——同一個專案,這次套到某規範、下次又沒套。要查為什麼,用 /memory 指令:它會列出目前實際載入了哪些 memory / CLAUDE.md 檔。對照清單就能看出是不是某層的檔沒被讀到、或某個 @import 路徑壞了,把「規範沒生效」這種隱形 bug 攤在眼前。

# Scenario 2:Claude Code 行為跨 session 不一致,先查載入了什麼
> /memory
# 輸出範例:列出目前生效的記憶檔
# ✅ Loaded:
#   ~/.claude/CLAUDE.md            (使用者層)
#   ./CLAUDE.md                    (專案層)
#   .claude/rules/testing.md       (@import 進來的)
# ❌ 若預期的 api-conventions.md 沒出現在清單 → 就是它沒被載入
#    (路徑錯了、或 @import 沒寫對) → 行為不一致的真兇
重點:行為跨 session 飄忽 → 用 /memory 看「實際載入了哪些檔」,對照預期找出沒讀到的那份。

整個 Task 3.1 的記憶骨架

CLAUDE.md 是給 Claude 的常駐說明書,分三層:使用者層(~/.claude,私人不分享)、專案層(repo 根 / .claude,進版控全隊共用)、目錄層(子資料夾,只管那塊)。最常考的 bug:團隊規範誤放使用者層 → 新同事收不到,修法是搬到專案層並 commit。說明書太長就模組化——用 @import 讓各 package 各取所需,或用 .claude/rules/ 按主題(testing / api-conventions / deployment)拆檔。行為跨 session 不一致時,用 /memory 查實際載入了哪些檔,揪出沒讀到的那份。

考試情境題

以下三題模擬正式考試格式，每題一個生產情境，四個選項。先嘗試作答，再展開解析。

Q 1 Scenario 2 · Code Generation with Claude Code

A senior engineer notices that Claude Code consistently applies the team's snake_case API naming rule on her machine, but a new hire who cloned the same repository two days ago reports that Claude never applies that rule. The new hire's Claude Code is the same version, and the project's root CLAUDE.md contains only general style notes. Where is the snake_case rule most likely stored, and what is the correct fix?

  1. The rule is in the project-level .claude/CLAUDE.md; fix by moving it to the root CLAUDE.md so both files are read.
  2. The rule is in the senior engineer's user-level ~/.claude/CLAUDE.md; fix by moving it to the project-level CLAUDE.md and committing it to version control.
  3. The rule is missing from the new hire's directory-level CLAUDE.md; fix by creating a subdirectory CLAUDE.md for each package the new hire works in.
  4. The rule is blocked by the new hire's local Git configuration; fix by resetting the new hire's .gitconfig to match the senior engineer's settings.
展開解析

Correct Answer: B

使用者層 ~/.claude/CLAUDE.md 只存在於個人機器，不進版控，新同事 clone repo 後完全拿不到這份設定。把規範移到專案層並 commit，才能讓所有人共享。

A 錯在哪：.claude/CLAUDE.md 屬於專案層，進版控後全隊都能讀到，若規範真的放這裡新同事也應有效，不符合題目症狀。C 錯在哪：目錄層 CLAUDE.md 只影響特定子資料夾，且要在每個資料夾各放一份，無法解釋「同一個 rule 只有資深工程師有」的現象。D 錯在哪：Git 設定與 Claude Code 的 CLAUDE.md 讀取完全無關。

Q 2 Scenario 2 · Code Generation with Claude Code

A team's monorepo has grown to 2,400 lines in a single root CLAUDE.md mixing testing, deployment, and API conventions. Engineers report that pull request reviews are painful because any CLAUDE.md change touches unrelated sections. The tech lead wants to reorganize so each concern can be changed independently. Which approach best addresses this?

  1. Split the CLAUDE.md into three separate files under .claude/rules/ named testing.md, deployment.md, and api-conventions.md.
  2. Create a separate CLAUDE.md in every subdirectory of the monorepo to distribute the content.
  3. Move all content to the user-level ~/.claude/CLAUDE.md so it does not appear in version control.
  4. Use @import to pull the entire monolithic CLAUDE.md into each package's local CLAUDE.md file.
展開解析

Correct Answer: A

.claude/rules/ 正是為了解決「巨型單檔難維護」而設計：按主題拆成獨立檔，每塊聚焦一個關注點，改部署規範只動 deployment.md，不會碰到測試或 API 那塊，PR review 一目了然。

B 錯在哪：在每個子目錄各放一份 CLAUDE.md 會造成大量重複內容，維護成本更高、更容易不一致。C 錯在哪：移到使用者層會讓設定離開版控，隊友完全看不到，是更嚴重的問題。D 錯在哪：把整份巨檔 import 進各 package 並沒有解決「內容混雜」的問題，只是複製了同樣的混亂。

Q 3 Scenario 2 · Code Generation with Claude Code

An engineer using Claude Code finds that on Monday the session applied the api-conventions.md rule correctly, but on Wednesday a new session silently ignored the same rule even though no files were deleted. The engineer wants to quickly verify which memory files are actually loaded in the current session. What is the most effective first diagnostic step?

  1. Run git log -- .claude/rules/api-conventions.md to check whether the file was accidentally deleted in a recent commit.
  2. Run the /memory command to list all memory and CLAUDE.md files currently loaded in the session.
  3. Restart the machine and re-open Claude Code to force a full reload of all configuration files.
  4. Add a duplicate copy of api-conventions.md to the project root to ensure it is always picked up.
展開解析

Correct Answer: B

/memory 指令會列出目前 session 實際載入的所有 memory / CLAUDE.md 檔，讓你立刻對照「預期應該在、但實際不在」的那份——通常就是路徑錯誤或 @import 寫錯導致的，是診斷跨 session 行為不一致最直接的方法。

A 錯在哪：git log 能查歷史是否有刪除，但題目說「沒刪檔」，這步不能告訴你目前 session 有沒有載入這份設定。C 錯在哪：重開機不能解決路徑設定錯誤，只是繞過診斷而非找到根因。D 錯在哪：複製一份到根目錄可能暫時解決問題，但沒有診斷為何原本那份沒被載入，問題仍會再次出現。
